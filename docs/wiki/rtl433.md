# rtl_433 sub-GHz devices (`--rtl433`, `rtl433_device`)

**Summary**: `--rtl433 SPEC` points sloth at the JSON event log that a
local, already-running `rtl_433` writes (`rtl_433 -F json`): one JSON
object per decode of an ISM-band device — car TPMS sensors, weather
stations, remotes, door and PIR contacts — on whatever frequency the
operator tuned the SDR to. sloth turns each line into a typed message
and keeps one row per `(model, id)` pair heard: first and last heard,
how many lines, the modulation, frequency, RSSI, SNR and noise the
decoder reported, and an allow-listed set of decoded readings. sloth is
**receive-only and file-only**: it never opens, tunes, hops or runs the
SDR — `rtl_433` owns it — and uses no network. It writes a change-only
`rtl433_device` record and an `rtl433_*` block in `sensor_health`. No
TUI view and no alert rule; slothweb shows the devices in its rtl_433
tab (`/api/rtl433`, below).

**Sources**: `src/rtl433.h`, `src/rtl433.c` (line parser, spec, device
table, bands and signature), `src/capture/rtl433_reader.h`,
`src/capture/rtl433_reader.c` (the tail), `include/sloth.h`
(`rtl433_msg_t`, `rtl433_device_t`, `rtl433_health_t`,
`rtl433_reject_t`, `SENSOR_RTL433`), `src/poll.c`
(`rtl433_health_poll()` in the health stage, `SENSOR_RTL433` in the
sensors stage), `src/sys_status.c` (the `rtl433` `source_status` row),
`src/jsonl.c` (`jsonl_emit_rtl433()`, the `rtl433_*` appends in
`jsonl_emit_sensor_health()`), `src/main.c` (`--rtl433`); tests
`tests/test_rtl433.c`; slothweb's side `web/src/web_rtl433.{c,h}`,
`web/ui/rtl433.js`, `web/tests/test_rtl433.c` and
`web/tests/test_fleet.c :: test_ingest_refuses_rtl433`. Format references, and the only two documents a
field here is claimed from: rtl_433's own
[`docs/DATA_FORMAT.md`](https://github.com/merbanan/rtl_433/blob/master/docs/DATA_FORMAT.md)
for the field semantics and bounds, and `src/r_api.c` (merbanan/rtl_433)
for the `-M protocol` and `-M level` metadata. The output shape is
`src/output_file.c` in the same tree.

## Where it sits against the seven questions

[[non-ip-sensors]] asks every family seven questions:

1. **Observable passively**: what `rtl_433` already decoded off the ISM
   band it is tuned to — a one-way, unauthenticated, unencrypted
   transmission from a battery sensor, which is what nearly every
   device in these bands sends. The lines in its event log.
2. **Hardware**: an SDR `rtl_433` drives (on beta-site a NESDR under
   `rtl433@<serial>.service`), which the operator runs. sloth needs only
   the file.
3. **State**: `rtl433_device_t` keyed `(model, id)` and
   `rtl433_health_t` (`include/sloth.h`).
4. **View**: slothweb's rtl_433 tab (below). No TUI view, no device
   drawer.
5. **JSONL / `--db`**: the change-only `rtl433_device` record,
   `rtl433_*` on `sensor_health`, a `sensor` record of kind `rtl433`,
   and a `source_status` row named `rtl433`. No sloth.db table yet.
6. **Out of scope**: opening, tuning, hopping or running the SDR;
   running `rtl_433` itself; transmitting anything at all (replaying a
   captured remote code would be transmitting, which `MISSION.md` §2
   rule 1 forbids absolutely); any detector over this data (TPMS
   following, replayed remote codes) until it has a cited source;
   the fleet export, which withholds this kind until it is classified
   (below).
7. **Testing**: hand-written JSON lines in `rtl_433`'s documented shape
   with invented models, ids and readings (`tests/test_rtl433.c`),
   temporary files for the reader (appends, a partial line,
   copytruncate, rename rotation, a file that appears later); no
   captured log and no fixture file.

## Passive, and why reading this file keeps it so

`rtl_433` is a receiver. It demodulates what is already in the air and
has no transmit path at all. sloth's relationship to it is narrower
still: sloth opens **one regular file read-only** and reads bytes past
an offset. It issues no SDR ioctl, sets no centre frequency, starts no
process and opens no socket. That is the same shape as `--aprs` (Dire
Wolf's packet log) and the file form of `--adsb` (readsb's
`aircraft.json`), and `MISSION.md` §2 is unaffected for the same
reason.

The temptation this page exists to refuse: these bands are full of
remotes whose codes are static, and a decoder that can read a code
could in principle send it. sloth cannot and will not. Replaying a
captured code is transmitting onto the segment under observation, which
§2 rule 1 forbids with no flag, build option or deployment mode that
turns it off.

## The source

`--rtl433 /var/lib/rtl_433/events.jsonl` or
`--rtl433 file:///var/lib/rtl_433/events.jsonl`. Only an absolute local
path: a relative path, a directory path, `file://HOST/` and any other
scheme exit 2, as does `--rtl433` with `--replay`. The file need not
exist when sloth starts.

`rtl_433` writes one JSON object per decode and flushes it per record
(`src/output_file.c`), either to a path it opened or through a shell
redirect; logrotate's `copytruncate` empties the same inode in place.
So every second (`RTL433_POLL_MS`) the reader
(`src/capture/rtl433_reader.c`, a worker started after the privilege
drop) opens the path read-only (`O_RDONLY | O_NONBLOCK | O_CLOEXEC`, a
regular file only), `fstat()`s it and keeps (device, inode, offset):

| what it finds | what it does |
|---|---|
| the first look, a file already there | starts at its **end**: what `rtl_433` wrote before this run is not replayed |
| a file where the last poll found none | reads it from the start (`rtl_433` just created it with its first decode) |
| a different inode | a rotation by rename: the new file from the start (`rtl433_rotations`) |
| a size below the offset | a truncation (`copytruncate`): from 0 (`rtl433_truncations`) |
| more bytes | the new bytes, at most 256 KiB a poll (`RTL433_POLL_BYTES`); a partial last line waits for the next poll |

One case the size test cannot see, stated for the same reason
[[aprs]] states it: a truncation followed, before the next poll, by
`rtl_433` writing past the old offset. The reader then reads on from
the old offset, the decodes between 0 and there are skipped, and the
next line read may start mid-record and is refused as bad. It is
accepted, not handled.

A line over 1024 bytes (`RTL433_MAX_LINE`) is one bad line, skipped to
its newline. Blank lines are skipped and are not bad. A missing file is
a state (`waiting`), not an error; an unreadable path or one that is not
a regular file is `error`, counted.

With `StandardOutput=append:` systemd opens the file once and rtl_433
keeps that descriptor, so a **rename** rotation leaves rtl_433 writing
on into `events.jsonl.1` while sloth tails the new, empty
`events.jsonl` (`live`, no decodes) until rtl_433 restarts. Rotate this
log with `copytruncate` (beta-site's logrotate does), or restart the
service in `postrotate`.

## The line, and what is kept

Every line is hostile. Anyone with a transmitter in these bands chooses
what a decoder writes about them, the model string and the id included,
and an id is unique only by convention — a sender may reuse another
device's. A row here is a hypothesis about a transmitter, never an
identification of a vehicle or a person; the rule [[mac-randomisation]]
states for 802.11 sequence numbers applies for the same reason, and
harder, because a TPMS id stays fixed to a wheel for years.

`rtl_433`'s JSON writer escapes `"`, `\`, CR, LF and TAB and **nothing
else**, so any other control byte reaches sloth raw and a quoted field
is not safe to print for having been quoted. Every string field is
cleaned to printable ASCII on the way in.

Kept, each with its document:

| key | from | kept as |
|---|---|---|
| `model` | DATA_FORMAT.md, required | the row key's first half; printable ASCII, at most 32 bytes ("less than 32 characters" there) |
| `id` | DATA_FORMAT.md, optional there | the row key's second half, as written; an integer id becomes its own decimal spelling, at most 16 bytes |
| `type`, `subtype` | DATA_FORMAT.md | printable ASCII, at most 16 bytes each (`dev_type` in the record, so it does not collide with the stream's own `type`) |
| `channel` | DATA_FORMAT.md | a secondary id, as written, like `id` |
| `mic` | DATA_FORMAT.md | only its three documented values: `CRC`, `CHECKSUM`, `PARITY` |
| `protocol` | r_api.c (`-M protocol`) | an integer 0..65535 |
| `mod` | r_api.c (`-M level`) | only its three written values: `ASK`, `FSK`, `LoRa` |
| `freq`, `freq1` | r_api.c (`-M level`) | one field, MHz: the ASK and LoRa branches write `freq`, the FSK branch `freq1`, and the chain is exclusive, so a line carries one of them |
| `freq2` | r_api.c (`-M level`) | MHz, the other FSK tone |
| `rssi`, `snr`, `noise` | r_api.c (`-M level`) | dB |
| `battery_ok` | DATA_FORMAT.md | 0 empty .. 1 full |
| `temperature_C`, `temperature_F` | DATA_FORMAT.md | the value **and its unit**, never converted |
| `humidity` | DATA_FORMAT.md | % relative |
| `pressure_kPa`, `pressure_hPa`, `pressure_psi`, `pressure_PSI` | DATA_FORMAT.md documents hPa and psi; the TPMS decoders write `pressure_kPa` (`src/devices/tpms_citroen.c`, `tpms_renault.c`) and `pressure_PSI` (`tpms_toyota.c`) | the value **and its unit**, never converted |

Units travel with the value because DATA_FORMAT.md's rule is
`<Type>_<Unit>` "in sensors native units insofar possible with no
conversion", and `rtl_433` converts only when asked (`-C si`).
Converting here would publish a figure the decoder never wrote, so the
record carries the reading back under the key it arrived under.

Recognised and deliberately **not** kept:

- The **per-model keys** — `state`, `code`, `flags`, `learn`, `moving`,
  `repeat`, `maybe_battery` and the rest. Each is one decoder's field
  rather than a documented one, and the name does not fix the JSON
  type: `flags` is `DATA_INT` in `src/devices/tpms_citroen.c` and
  `DATA_STRING` in `src/devices/tpms_renault.c`. Typing them from a
  single site's observation would be a guess dressed as a schema, so
  they are counted in `rtl433_other_keys` until a per-key survey of the
  decoders says what each one is. That counter is the measured size of
  the gap, and a rising value is not a fault — it is the field set of
  whatever is on the air.
- `time`. Its format follows `rtl_433`'s `-M time[:...]` options and, by
  default, the host's locale, and the file carries no statement of
  which were used, so a stamp read out of it would be a guess at a
  clock. It is recognised and skipped (not counted, since `-M time`
  puts it on every line), and a row's first and last heard are the
  **host's** clock at the read.
- `msg`, `codes`, `bits`, `description`, `tag` and the LoRa metadata
  `sf` / `bw` / `cr` / `sync`: counted, not stored.

### Refused, by reason

A line is refused whole only for its structure or its key, and each
refusal has its own counter so that "the decoder is writing garbage"
and "the decoder is writing objects sloth cannot key" are told apart:

| counter | what it counts |
|---|---|
| `rtl433_rej_oversize` | longer than `RTL433_MAX_LINE` (1024 bytes) |
| `rtl433_rej_not_object` | not one JSON object, or bytes after it |
| `rtl433_rej_malformed` | a JSON syntax error inside the object — a truncated last line after a crash, for one |
| `rtl433_rej_no_model` | no usable `model` |
| `rtl433_rej_no_id` | no usable `id` |

The sum of those five is `rtl433_bad_lines`, so no refusal escapes the
breakout.

`id` is **optional** in DATA_FORMAT.md and required here, which is the
one place this parser is stricter than its document. The table is keyed
`(model, id)`; a line with no id cannot be keyed, and keeping it under
an invented id would merge every such device into one row. A decoder
emitting model-only events therefore reads as `rtl433_rej_no_id`
climbing, which is the honest report of it. Keeping those events as
model-only rows is a follow-up, not a bug.

An **optional** value that is present but out of range is a different
case: its field is left **absent** and counted in `rtl433_bad_values`,
never clamped, and the line is still a message, because the key and the
signal metadata on it are a real observation. The bounds are wide
sanity bounds rather than spec limits — DATA_FORMAT.md states units,
not ranges, so the bound's job is to refuse a value that cannot be a
reading, not to second-guess a sensor.

## The device table

One row per `(model, id)`, at most 256 (`RTL433_MAX_DEVICES`). On full
the least recently heard row is overwritten and the loss is tallied
under `evict_rtl433` and in the source's own `rtl433_evicted`: the key
space belongs to whatever is transmitting, so a spray of invented
models churns the table and can never make sloth allocate or go deaf to
a new device for the rest of the run (the `STAB_OLDEST` policy,
`src/stab.h`).

The merge is sticky: a value is replaced only by a line that carries
one, so a TPMS line with no temperature does not erase the temperature
of the line before it. Nothing is retired by age — a device heard once
and never again is a real observation of the band — so the only thing
that removes a row is the table filling, and there is no `gone` record.

## JSONL

`rtl433_device`, change-only on the signature in `src/rtl433.h`: the key,
`first_seen` (an evicted row heard again is a new row), the discrete
facts, and every continuous value as a band — RSSI in 3 dB steps, the
frequency in whole MHz, temperature, pressure and humidity to one unit,
`battery_ok` to a tenth. `msgs`, `last_seen`, `snr`, `noise`, `freq2`
and `other_keys` are written and never signed: each moves with every
decode, and signing one would turn a change feed into a per-decode
firehose — one TPMS within earshot of a kerbside sensor writes a line
every few seconds for as long as the car is parked there. The frequency
is banded to a whole MHz because the band is what the number is for
(433.92 against 868 or 915) and `rtl_433`'s own estimator moves by tens
of kHz between decodes of one stationary transmitter.

Field-by-field shape: [[jsonl-schema]].

## slothweb: the rtl_433 tab and `/api/rtl433`

slothweb keeps the `rtl433_device` records it reads off the stream in
memory (`web/src/web_rtl433.c`), one row per `(model, id)`, at most 512
(twice sloth's 256, so rows sloth has just evicted can sit beside the
live ones until they age out); on full the least recently reported is
dropped and counted (`evictions`). sloth retires nothing by age and
writes every row it keeps at least once per 300 s heartbeat, so a row
with no record for 660 s is one sloth no longer has: slothweb drops it
and counts it (`aged`). A record whose `first_seen` differs from the
row's is sloth's new row for that key and replaces it. Each record is
sloth's whole row (its merge is sticky), so a field a record omits is
absent on slothweb's row too. slothweb never writes sloth.db.

Every string is re-checked against sloth's own rule (1 to its cap of
printable ASCII, no quote or backslash; `mic` and `mod` to their three
words) and every number against the bound sloth's parser applies, and
is absent outside it, never clamped. A record with no usable `model`,
`id` or `first_seen` is refused and counted (`rejected`). A temperature
or pressure is served with its unit (`temp_unit` `C`/`F`, `pres_unit`
`kPa`/`hPa`/`psi`) and never converted; a record carrying two units of
one reading is ambiguous and leaves that reading absent.

`GET /api/rtl433?limit=N` (1..512, default all): `now`, `src`, the
counters (`records`, `evictions`, `aged`, `rejected`), `sensor` (the
newest `sensor_health`'s `rtl433_*` block with the reject breakout as
`rej`, or `null` when sloth runs without `--rtl433`), `total`, then
`devices` most recently heard first, `shown` and `cut` (the list
stopped before a row that might not fit). An unknown parameter or a bad
`limit` is 400. The records are Monitor scope (`web_scope.c`): the
SDR is a passive receiver, as the ADS-B and APRS decoders' are, so
Monitor and Hybrid answer devices and Local answers `out_of_scope`
after checking the query. `/api/health` carries an `rtl433` member of
counts only.

The tab (after Spectrum) is one table — model, id, type and subtype,
channel, decodes, first and last heard, frequency, RSSI, temperature,
humidity, pressure and battery — with the decoder's state above it.
The figures are those of the last record sloth wrote, which is change
only on the bands above, not of the last decode. Every string came over
the air and reaches the page through `textContent` only.

Not built: a device drawer (each row already shows every field sloth
keeps; a drawer earns its place once there is history to draw, which
needs the sloth.db table below).

### Receivers tab: `USED BY` stays blank

The Host tab's receivers table ties a source to a receiver when the
source names the device it reads (`tie()` in `src/sys_status.c`, as the
GNSS row does for `nmea:/dev/ttyACM0`). This one cannot honestly: sloth
reads a file, and nothing in it says which SDR wrote it. rtl_433 is told
its SDR by serial (`-d :<serial>`) on its own command line, while the
receiver scan keys a USB SDR by its bus port; pairing the two would mean
sloth reading rtl_433's command line or unit file, or guessing from
"the only RTL-SDR present" — the first is outside the file-only
contract above, the second is wrong the day a second dongle is plugged
in (beta-site already runs one for ADS-B). The ADS-B and APRS rows are
blank for the same reason.

## Fleet sharing

Withheld. A sub-GHz decode is heard over the air, so ADR 0009's rule
("anything that is thru monitor mode is game") would admit it — but the
rule is **fail closed**, and a kind that has not been classified does
not travel. `web/src/web_fleetshare.c` does not know this kind, and
that is deliberate until the owner classifies it; the export has no
writer for it, and the importer refuses a peer answer carrying an
`rtl433_device` line whole (`test_ingest_refuses_rtl433`). See
[ADR 0009](adr/0009-fleet-monitor-only.md).

## Privacy

A TPMS id is fixed to a wheel for years, so a log of ids with times is a
log of which vehicles passed a fixed point and when — the same
sensitivity [[aprs]] and [[mac-randomisation]] describe, without the
mitigation that address rotation gives on 802.11. The records go to the
operator's own sinks only; sloth ships nothing anywhere. Tests and
documentation use invented models and ids, never a device heard on the
air.
