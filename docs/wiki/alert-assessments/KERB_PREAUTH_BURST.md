## What the rule checks

Input: `s->kerb_events`, the Kerberos aggregate table of `MAX_KERB_EVENTS` = 64 rows keyed by **client IP** - whichever endpoint of a port-88 flow is not the KDC (`include/sloth.h:512-526`; `src/kerb_snoop.c:96-100`). `kerb_snoop_observe()` identifies each message by its outer ASN.1 `[APPLICATION]` tag byte (AS-REQ 0x6A, AS-REP 0x6B, TGS-REQ 0x6C, TGS-REP 0x6D, KRB-ERROR 0x7E, per RFC 4120 §5.10 [5]) at offset 0, or offset 4 for the TCP 4-byte length prefix (`src/kerb_snoop.c:24-28`, `:67-90`). For a KRB-ERROR it walks the DER for the `[6]` error-code field (`A6 LEN 02 ilen <bytes>`, bounded to the first 96 bytes) (`:44-62`) and buckets the code: 25 → `preauth_required_count`, **24 → `preauth_failed_count`**, 6 → `principal_unknown_count`, else `error_other_count` (`:122-130`). The constants are `KDC_ERR_C_PRINCIPAL_UNKNOWN` 6, `KDC_ERR_PREAUTH_FAILED` 24, `KDC_ERR_PREAUTH_REQUIRED` 25 (`src/kerb_snoop.c:31-33`) - matching the Windows event-4771 failure-code table, where 0x18 = KDC_ERR_PREAUTH_FAILED, 0x19 = KDC_ERR_PREAUTH_REQUIRED, 0x6 = KDC_ERR_C_PRINCIPAL_UNKNOWN [4]. These counters are running aggregates; nothing decays them within a row's lifetime.

Per tick the rule fires for any row whose `preauth_failed_count` is at or above `KERB_PREAUTH_BURST_THRESHOLD` = `tune_val(TUNE_KERB_PREAUTH_BURST)` (`src/alerts/rules_wired.c:919`, `:924`), default **5** (`src/tune.c:55`: `kerb.preauth_burst`, min 2, max 1000, unit "pre-auth failures"). Key: `kerb-burst:<src_ip>` (`:927`). Detail: `"<src>: <n> Kerberos pre-auth failures (spray indicator; unknown-principal=<a>, preauth-required=<b>)"` (`:928-935`). CRIT, `match_ip` = the source, `match_port` 88 (`:936-937`; `docs/wiki/kerberos-snoop.md:63-76`). The incident resolves 300 s after the last tick that re-asserted it (`include/sloth.h:860`); the 64-row table evicts least-recently-seen (`evict_kerb_event`, `src/sensor_health.h:96`). Both IPv4 and IPv6 UDP/88 and TCP/88 feed it since #132 (`docs/wiki/kerberos-snoop.md:17-20`).

Note the threshold is on `preauth_failed_count` alone; the `principal_unknown_count` and `preauth_required_count` are reported in the detail but do not gate, so the rule does not itself distinguish spraying (many principals) from one account failing repeatedly.

## The mechanism

Kerberos is the authentication protocol of every Active Directory environment; clients talk to the KDC on TCP/UDP 88. In the standard flow a client's first AS-REQ without pre-authentication draws a KRB-ERROR 25 (KDC_ERR_PREAUTH_REQUIRED), after which it resends with an encrypted timestamp; a wrong password yields KRB-ERROR 24 (KDC_ERR_PREAUTH_FAILED) [4], [5]. Password spraying (ATT&CK T1110.003) tries one password across many accounts to stay under per-account lockout, the opposite of guessing many passwords against one account (T1110.001); MITRE notes adversaries favour LDAP and Kerberos precisely because those attempts are less likely to raise the high-visibility logon-failure events SMB produces [2]. The repo corpus makes the same point: counting failures without regard to how many principals they span would conflate spraying and guessing and miss the one that evades lockout [1]. The commodity tool is kerbrute, whose passwordspray mode tests one password across a user list over single UDP frames, relying on the 24 vs "principal unknown" distinction, and which notes that pre-auth failures raise event 4771 but not the 4625 that defenders usually watch [3]. Microsoft's own 4771 guidance recommends alerting when failure code 0x18 appears N times in N minutes as a brute-force indicator [4]. sloth sees only failures, never success - a spray that lands on its first try produces nothing [1].

## Evidence that proves it

What sloth records:

- `alert` / `alert.*` JSONL under `kerb-burst:<src>` with the three counters in the detail;
- `kerb_event` state records keyed on `src_ip` (`docs/wiki/jsonl-schema.md:724`): `as_req_count`, `as_rep_count`, `tgs_req_count`, `tgs_rep_count`, `preauth_required_count` (25), `preauth_failed_count` (24), `principal_unknown_count` (6), `error_other_count`, `first_seen`, `last_seen`;
- a per-alert pcap if `--pcap-dir` is set (CRIT passes default `pcap.min_severity` 2); the filter is `match_ip` = source and port 88 either side (`src/alert_pcap.c:102-111`), so the file holds that source's KDC traffic from the ring.

What makes it a spray rather than a broken job: the source's failures span **many distinct principals** - sloth does not extract usernames (deliberately out of scope, `docs/wiki/kerberos-snoop.md:108-114`), so the proxy in the record is a high `principal_unknown_count` alongside the `preauth_failed_count` (a username sweep probing which accounts exist [4]), or correlation with the domain controller's 4771 events for many `TargetUserName`s from this `Client Address` [4]. A high `tgs_req_count` with little AS-REQ from the same workstation is the separate kerberoasting shape the record exposes but the rule does not alert on (`docs/wiki/kerberos-snoop.md:103-106`).

What refutes it (benign): the failures are all one principal (one service account, one workstation) with the count climbing steadily and indefinitely - a stale credential, not a spray [1], [2]; or a burst at a service restart that is not sustained [1]. The domain controller logs resolve both: sloth sees failures, so success and the principal spread must be read there [1], `docs/wiki/kerberos-snoop.md`.

## Benign causes

- **Stale service-account password.** A backup job, scheduled task or app pool with an out-of-date password re-authenticates and fails forever, producing exactly this signature from one source and one principal [1], [2] - the single most common benign trigger.
- **Service restart burst.** A service coming up and re-authenticating can briefly exceed 5, then stop; the engine resolves it after the quiet period [1].
- **Clock skew / expired password.** Error code 0x25 (clock skew) and 0x17 (password expired) are distinct codes bucketed as `error_other_count`, so they do not drive this alert [4]; only genuine wrong-password 0x18 does.

## Assessment

CRIT is appropriate for the thing it names - automated iteration against the KDC - because a sustained run of KDC_ERR_PREAUTH_FAILED from one source is well outside a human mistyping a password two or three times, which is the threshold's rationale (`docs/wiki/kerberos-snoop.md:78-82`). The honest caveat is that the rule gates on `preauth_failed_count` only, so it cannot by itself separate a spray (many principals, the dangerous case) from one stale credential (one principal, benign but noisy). The detail carries `unknown-principal` and `preauth-required`, which lets a responder judge, but the alert fires the same either way. Two refinements worth considering: gate additionally on principal spread once username extraction lands (named as the Tier 2 follow-up, `docs/wiki/kerberos-snoop.md:108-129`), and window the counter so a stale job does not sit as a permanent CRIT (today the aggregate never decays within a row's life).

Prevalence: password spraying is a first-class ATT&CK sub-technique with commodity Kerberos tooling [2], [3]; no fetched source quantifies a field rate, so none is claimed. The technique is chosen specifically to evade lockout, which is why a network-side failure-rate detector is useful alongside DC logs [1], [4].

Reference host: not seen (null) - consistent with no KDC traffic observed (no AD on the monitored segment). The behavioural note for an operator: because the failure counter does not decay, a single misconfigured job would, over time, present as one steady CRIT under its source IP - so a persistent `kerb-burst` on one key is more likely a stale credential than an active spray, and a spray more often shows as several sources or a climbing `principal_unknown_count`.

Sufficient to act on alone? No - it is a strong lead. A responder should (1) read whether the failures span many principals (DC 4771 events for this `Client Address`, or a high `principal_unknown_count` here) [4]; (2) rule out a stale-password job - one principal failing indefinitely; (3) check the DC logs for whether any account authenticated from the source, since sloth sees only failures [1]. If spraying, block the source and reset any account that authenticated from it; if a stale credential, fix the job (`docs/wiki/alert-remediation.md:303-320`). Tune `kerb.preauth_burst` up on a segment with a known-noisy automation only after fixing the automation, not instead.
