## What the rule checks

Inputs: the beacon snapshot `s->beacon_aps[]` (up to MAX_BEACON_APS = 256 rows, include/sloth.h:1295), one row per BSSID carrying `ssid`, `enc` ("WPA3"/"WPA2"/"WPA"/"WEP"/"OPEN", derived at beacon_snoop.c:765-774), `mfp` (0 off / 1 capable / 2 required, from the RSNE MFPC/MFPR bits at beacon_snoop.c:595), `pairwise` (first pairwise cipher name) and `akm` (label containing "802.1X" for enterprise AKMs).

Condition (rules_twin.c:1648-1665): for every row `weak` with a non-empty SSID, find the same-SSID, different-BSSID row `strong` giving the highest `rsn_downgrade_score(strong, weak)`, and fire when that score is at least `ssid.confusion_thresh` (default 3). The scorer (rules_twin.c:1613-1644):

- returns 0 unless the weak side is itself a protected WPA network (`wpa_gen_rank(weak->enc) >= 2`), leaving OPEN/WEP twins to `rule_evil_twin`;
- +3 if the generation drops (WPA3->WPA2, WPA2->WPA);
- +2 MFP required->capable, +4 required->disabled, +2 capable->disabled;
- +1 GCMP->CCMP/TKIP, +1 CCMP->TKIP;
- +3 if `strong->akm` contains "802.1X" and `weak->akm` is set and does not (enterprise cloned as PSK — the #31 rogue-RADIUS sub-signal).

So at the default threshold a single generational drop, or MFP required->off, or an enterprise->PSK AKM swap each fires alone; a cipher drop alone (+1) never does.

Key (rules_twin.c:1673-1679): `ssidconf:<ssid, first 32 bytes kept, non-keepable bytes mapped to _>:<16 hex digits, FNV-64 of the full SSID>:<weak bssid>` via `akey_begin/akey_remote/akey_mac` (src/alert_key.c:92-104), because the SSID is attacker-chosen (#112). One incident per (SSID, weak BSSID); several weak BSSIDs under one name are several incidents.

Detail (rules_twin.c:1680-1683): `'<ssid>' downgraded on <weak bssid> [<enc>/mfp<n>] vs <strong bssid> [<enc>/mfp<n>] - SSID confusion`, with the SSID cut to its first 16 bytes (`%.16s`) and each `enc` label to 6. It carries both BSSIDs, both generation labels and both MFP levels; it does not carry the score, the AKM strings, the cipher, the channel or either RSSI.

Severity is always CRIT (rules_twin.c:1684-1685) with no escalation path and no confidence term (plain `fire()`). The incident resolves when no tick re-asserts the key for ALERT_RESOLVE_AFTER_S = 300 s (include/sloth.h:860) — 300 s after either BSSID ages out or the posture gap closes. No `match_ip`, so no pcap is written and no evidence-ring frame IDs are cited.

Baseline note from the code (rules_twin.c:1595-1599): the published approach gates on a multi-hour per-SSID posture baseline and on BSSID age; sloth has neither and scores against the strongest posture in the current snapshot only.

## The attack

When a client joins a protected Wi-Fi network it authenticates the network's credentials (the password-derived key, or the RADIUS server) but not the network's name. The SSID is not mixed into the pairwise master key for most authentication methods, and the 4-way handshake carries no protected copy of it [1][3]. A client can therefore be driven to associate with a network whose name differs from the one its UI shows, provided the two networks share a credential. Gollier and Vanhoef named this SSID Confusion and it was assigned CVE-2023-52424 [1][3].

The paper's canonical setup is a single operator who uses the same credential on two SSIDs, one per band — e.g. a better-secured 5 GHz name and a weaker 2.4 GHz name. An attacker in a machine-in-the-middle position (feasible against all existing Wi-Fi via a multi-channel MC-MitM, per the paper §3.3) makes a victim intending the stronger name connect to the weaker one; the client still shows the trusted name. The paper shows this can also auto-disable a VPN that trusts an SSID, and downgrade a client onto a band with weaker protections [3]. By Table 1 of the paper the vulnerable methods are Home WPA3 with SAE-loop, Enterprise 802.1X/EAP, Mesh AMPE, FILS and Home WEP; WPA1/WPA2-PSK are protected because they fold the SSID into the PMK (§3.4.2), WPA3 with SAE-const likewise derives the PMK from the SSID and is not vulnerable (§3.4.3), and Fast BSS Transition resists it because PMK-R0 hashes the SSID (§3.7.1) [3]. The CVE record's "Home WPA3 SAE-loop" wording matches [4].

sloth cannot see which network a client *believes* it is on — that belief lives in the supplicant. What it detects is one on-air shape the attack can take: the same SSID advertised by a second BSSID with weaker RSN protection than the strongest the sniffer has seen for that name. In the paper's stage 1 the rogue clone sits on a different channel, reuses WrongAP's MAC address, and rewrites WrongNet to TrustedNet in the beacons it relays (§3.3) — so the sniffer sees TrustedNet advertised with WrongNet's posture. Two limits follow from the code. The rule fires only if a genuine, stronger BSSID for TrustedNet is also in the beacon snapshot; the paper notes the victim is fooled "even when [TrustedNet] is not" nearby, and that case is invisible to this rule. And because the clone shares WrongAP's BSSID, a sensor that hears both channels sees one BSSID alternating between two SSIDs. The beacon table keeps one row per BSSID and overwrites its `ssid` with whichever beacon arrived last (beacon_snoop.c:1130-1131), so the rule compares that BSSID as TrustedNet or as WrongNet depending on the most recent frame; the row's SSID history records both names, but two is below `rule_karma`'s default `karma.ssid_thresh` of 3 (src/tune.c:40). That is also the on-air shape of a classic evil twin that advertises a trusted name with downgraded crypto to make association easier. Tooling that stands up such an AP includes the Wi-Fi Pineapple [5], wifiphisher (Evil Twin / Known Beacons) [7] and eaphammer for the enterprise case [6]; mdk4 beacon flooding (mode b) can seed the duplicate name [4].

## Evidence that proves it

What sloth records for this type: the detail line's two BSSIDs, the two `enc` generation labels and the two `mfp` levels. No pcap (no `match_ip`) and no cited frames. The durable record is the JSONL `alert`/`alert.*` stream (sev 2, `ty` = SSID_CONFUSION's enum, technique T1557.004) and the SQLite `alerts` row keyed on `ssidconf:...`. The browsable corroboration is the `[b] Beacons` and `[x] Twins` views, which show both BSSIDs' full RSN/AKM inventory, channel, vendor OUI and RSSI — the fields the alert detail omits.

To call it real, read both BSSIDs in `[b] Beacons` and check:

- the weak BSSID's OUI is from a different vendor than the operator's APs, or is unknown — a same-vendor controller rarely downgrades one VAP's posture;
- the weak BSSID is recent (appeared mid-session) while the strong one is long-standing — an attacker's AP is new, a transition-mode ESS is not;
- the weak BSSID's RSSI swings or is markedly stronger/closer than the operator's AP (cross-check `EVIL_TWIN_PROXIMITY`);
- a `DEAUTH_FLOOD` against the strong BSSID in the same window (the attack-chain correlate, rule_evil_twin_attack_chain) — clients being driven off the real AP toward the weak one.

What refutes it (the benign fingerprint): both BSSIDs share the operator's vendor OUI and have been present together since capture start; the "downgrade" is a documented WPA2/WPA3 transition-mode ESS where the 2.4 GHz radio is simply older (the paper itself notes 2.4 GHz APs commonly lack MFP/beacon protection, §3.2.1) [3]; the weaker label is an artifact of an SAE-EXT-KEY-only RSNE (the #128 class that `enc` labelling was corrected for). If the two BSSIDs are the operator's own transition estate, this is a posture finding, not an intrusion — closer to `WPA_DOWNGRADE`.

## Benign causes

- **WPA2/WPA3 transition-mode ESS.** The single largest false positive: a mixed estate where one radio offers SAE (WPA3) and another offers PSK (WPA2) under one name scores +3 and fires. Tell apart by same-vendor OUI and long co-presence.
- **Per-band SSID with shared credentials.** The very configuration the paper calls the common case: legitimate until an attacker exploits it. sloth reporting it is arguably correct — it is a real exposure — but it is the operator's own network, so it is a hardening item, not an attack.
- **Cross-vendor range extender / mesh node** repeating the SSID with a thinner RSNE. This is issue #51's historical false positive for the coarser `EVIL_TWIN` rule; it can trip this one too when the extender drops MFP.
- **Enterprise + guest PSK sharing a name** — rare but possible, and it hits the +3 AKM path.

## Assessment

Severity rationale: a genuine SSID-confusion / enterprise evil twin against the operator's own SSID is a credential-interception and traffic-interception event, which earns CRIT. But the rule fires CRIT on any same-name posture gap in range, including a neighbour's transition ESS, so the floor is too low for the ceiling it claims. The honest grading is WARN for an uncorroborated posture gap and CRIT only when the SSID is designated (`--my-ssid`) or an age/proximity/deauth corroborator is present — the same confidence doctrine already applied to the evil-twin family (#89/#94).

Real-world prevalence: the flaw is universal across clients [3], but SSID Confusion as a named technique has essentially no public incident reporting; the broader evil-twin family is documented in APT use (APT28 / Wi-Fi Pineapple) [5]. So a firing here is far more often a mixed-posture estate than an intrusion.

Reference-host noise verdict: 3,206,014 fires on 12 keys. The rule counts per poll tick (≈4/s), so this is ~267k ticks ≈ 18.6 hours of standing condition per pair, not 3.2M distinct events — twelve persistent same-name posture gaps that each sat in range for most of a day. That pattern is a deployment, not an attacker. The noise is in the *counter*, not the key: 12 keys is quite readable, but the `count` field makes each look like a millions-strong flood. Recommend surfacing `observations` (which only moves when the detail changes) instead of `count`, and gating CRIT on designation or an age/deauth corroborator.

Is the evidence sufficient to act? Not on its own. The detail line proves a posture gap exists; it does not prove an adversary. A responder should first open `[b] Beacons` for both BSSIDs and decide ownership: if both are the operator's, raise the weak radio's posture (enable SAE/MFP, stop reusing one credential across SSIDs per the paper's mitigation [3]); if the weak BSSID is foreign and on controlled premises, locate and remove it; if foreign and off-premises, report it and do not join or probe it (remediation: docs/wiki/alert-remediation.md "SSID_CONFUSION").
