## What the rule checks

Input is `s->ssdp_devices[0..ssdp_count]` (capped at MAX_SSDP_DEVICES 64) — SSDP/UPnP rows sloth observed passively (no M-SEARCH is sent). The qualifying predicate is `ssdp_cam_row()` → `cam_ssdp_row()` (src/camera_vendor.c:712-725), which accepts a row only when `nts != "search"` (an M-SEARCH's ST is what the *asker* wants, so a control point searching for cameras is not one) and either:

- `type == urn:schemas-upnp-org:device:DigitalSecurityCamera:1` (UPnP_DSC1) — the UPnP Forum's standardized camera device type (dsc = 1, a strong self-claim); or
- `type == urn:schemas-upnp-org:device:Basic:1` (UPnP_BASIC1) **and** the SERVER header's product token names a camera vendor (`cam_vendor_server()`, src/camera_vendor.c:581-605, matching Hikvision/EZVIZ/Dahua/Amcrest/Axis/Reolink/Mobotix/Lorex/Arlo case-insensitively on a token boundary). Basic:1 is the type for products with no standard type, so alone it says nothing; it counts only with the vendor SERVER token (#145 ruling).

The device identity is the USN's UUID (`usn_device()` strips at "::", UDA 1.0 §1.1.4 "uuid:device-UUID::type", lines 92-98), so one camera's several NOTIFYs are one device. The rule computes a deterministic total order over a device's rows (`ssdp_row_before()`, DSC row first, then by IP/SERVER/USN/NTS, lines 120-129) and fires only from the lead row (`lead` stays 1, lines 150-165), folding the rest into one detail with a "; N more row(s) for this device" tail — this is the fix for per-row detail churn that otherwise climbed alert.update every tick (comment lines 131-138). Key: `camssdp:usn:<first 48 chars of the USN's device part, e.g. uuid_..., with ':' and other non-key-safe bytes as '_'>:<FNV-64 of the whole device part>` (`akey_remote(devs[i], 48)`, src/alert_key.c:88-104), or, with no UUID, `camssdp:ip:<ip>` (`akey_ip`, IPv6 bracketed) (lines 167-177). WARN, confidence 0. Two detail variants (lines 189-201): DSC devices ("UPnP DigitalSecurityCamera:1 device at <ip> announced itself over SSDP ..."), optionally noting a Basic:1 SERVER vendor also seen under the same UUID; Basic:1 devices ("UPnP Basic:1 device at <ip> names camera vendor <v> in its SERVER header ... the device's own claim, not a registry check"). `fire(...)` passes `d->ip` as match_ip, port 0 (lines 202-203). Technique deliberately empty (self-announcement, not T1046); pinned by `tests/test_research_corpus.c :: test_uncitable_kinds_with_a_real_basis_are_still_cited`.

## The attack

No attack — an exposure/identity signal from the device's own UPnP advertisement. SSDP is UPnP's discovery layer: a device multicasts NOTIFY ssdp:alive messages carrying NT (the device/service type), NTS ("ssdp:alive"/"ssdp:byebye"), USN (unique service name) and SERVER [8]. The UPnP Forum's **DigitalSecurityCamera:1 Device Template v1.01** (2005-03-24, authored at Axis Communications) defines `urn:schemas-upnp-org:device:DigitalSecurityCamera:1` for a device providing "live snapshot still images" and "live motion images (video)" — so a NOTIFY with that NT is the device naming itself a camera in the one field that exists for that [3]. **Basic:1.0** (2002-12-12) "provides a mechanism for products that wish to use UPnP, but for which there is not yet an appropriate standard base device type" — so Basic:1 says nothing about device class on its own, hence the vendor-SERVER requirement [4]. The SERVER header is, per UDA 1.0 §1.1.2, a "Concatenation of OS name, OS version, UPnP/1.0, product name, and product version. Specified by UPnP vendor" [8] — the product-name token is the vendor's own claim about its maker. Operationally this matters for the same reason as CAM_MDNS_SERVICE: cameras are high-value, often-insecure attack surface (Mirai; camera-stack CVEs) [5][6].

## Evidence that proves it

The detail (above) names the announcer IP, the device type (DSC or Basic:1), the SERVER header, the vendor token (for Basic:1), the NTS, and a count of folded rows. With `--pcap-dir`, `alert_pcap` writes ring packets matching the announcer IP (src/alert_pcap.c:105-113), capturing the SSDP NOTIFY datagrams (and the device's other traffic) around fire time. The `src/ssdp_snoop.c` row retains the last SERVER across a byebye (src/ssdp_snoop.c:142 only overwrites `server` when the header is present; UDA §1.1.3 byebye carries no SERVER, per the code comment - not re-quoted here). JSONL `alert.*` records carry `key`, `detail`, `sev`, `match_ip`, `pcap_path` when written; no `technique`. The `sensor_health` counter `evict_ssdp_device` moves if the SSDP table overflows.

To call it a real camera: for a DSC row, a NOTIFY whose NT is exactly `urn:schemas-upnp-org:device:DigitalSecurityCamera:1` from the host (the standard type is a strong claim). For a Basic:1 row, a NOTIFY with a SERVER header whose product token is one of the camera vendors on a token boundary — stronger if corroborated by the same host's OUI or an mDNS/RTSP signal. What refutes "camera": a MediaRenderer or other non-camera UPnP type (the rule already rejects these - only DigitalSecurityCamera:1 and Basic:1 can match; docs/views/alerts.md:151: "a MediaRenderer is not a camera type whatever its SERVER says"), an M-SEARCH (rejected — the asker's want), or a Basic:1 whose SERVER names a camera brand that also makes routers/NVRs (the detail's "device's own claim, not a registry check" caveat applies; device class is not observed).

## Benign causes

Not false positives (the device really did advertise), but non-camera or authorised triggers: a Basic:1 device from a vendor that sells cameras *and* other gear, where this particular box is an NVR, router or bridge (the SERVER names the brand, not the product line) — the detail flags this. And authorised cameras: a correctly-inventoried camera advertising DigitalSecurityCamera:1 trips this on first sighting exactly as an unknown one does, since the rule makes no ownership distinction. The discriminator is reconciliation against inventory plus corroborating signals (OUI, mDNS, RTSP). A DSC self-claim is high-specificity for "a camera"; a Basic:1 vendor-SERVER match is softer and the detail says so.

## Assessment

WARN is correctly calibrated: a surveillance/exposure finding from the device's own UPnP claim, not an adversary action — the empty ATT&CK technique is right. The DSC path is high-confidence (the device uses the standard camera type); the Basic:1 path is advisory and honestly labelled. Underlying prevalence and stakes are high (cameras, Mirai, camera CVEs) [5][6], so surfacing a camera's presence is useful even though the finding is benign. On the reference host it did not fire (host data null) and is structurally quiet, with the per-device folding making it quieter than a per-row design would be. No dedupe or threshold tuning is warranted. The evidence (self-advertisement plus a pcap of the SSDP NOTIFYs and the host's traffic) identifies and locates the device but does not assert compromise. A responder reconciles against inventory; an unexpected camera should be located, its credentials and firmware checked, and removed or segmented if it does not belong [remediation: docs/wiki/alert-remediation.md].
