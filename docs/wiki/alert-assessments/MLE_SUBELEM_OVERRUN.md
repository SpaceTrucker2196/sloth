## What the rule checks

**Input.** `s->mlds[]`, the snapshot of the Multi-Link Device roster that `src/mle.c :: mle_observe()` keeps from every Basic Multi-Link Element sloth decodes out of a Beacon or Probe Response (`src/beacon_snoop.c:407-408` records the element body and its own length byte `tln` as `mle_body`/`mle_len`; `src/capture/probe.c:552` hands them to `mle_parse()`) and, since #129, out of (Re)Association Requests (`src/assoc_track.c`).

**Condition.** `rule_mle_subelem_overrun()` (rules_mle.c:85-105) loops the roster and fires for every entry with `malformed_subelem_len_total != 0`. No threshold: one frame is enough. The classification is in `mle_parse()` (src/mle.c:252-272): the Link Info subelement chain is walked with the shared TLV iterator; if it stops with `TLV_OVERRUN`, `malformed_subelem_len = 1` and one of two shapes is recorded:

- `at + 2 > len` - a trailing fragment too short to hold the 2-byte ID/Length header; `subelem_overrun_bytes = at + 2 - len` (mle.c:258-262).
- otherwise a subelement whose declared body reaches past the element: `bad_subelem_len = ie_body[at+1]`, `subelem_overrun_bytes = at + 2 + bad - len` (mle.c:268-270).

The walk stops at the first fault; the MLD MAC (read at a fixed offset before any attacker-controlled length is trusted, mle.c:116-121) and any affiliated link addresses already decoded are kept. A zero-length subelement and a chain ending exactly on the last byte are legal and never fire. `mle_observe()` then accumulates `malformed_subelem_len_total++` plus the latest `bad_subelem_len`, `subelem_overrun_bytes`, `malformed_subelem_len_last_seen` (mle.c:433-437).

**Not evaluated downstream.** A frame with `malformed_subelem_len` set is excluded from the cross-link cipher comparison (mle.c:308) - posture read from a chain whose lengths do not add up is not trusted.

**Key.** `"mle_subelem_overrun:<mld_mac>"` (rules_mle.c:93), one incident per MLD identity.

**Detail.** `"MLD <mac> sent a Multi-Link Element whose Link Info subelement chain overruns the element by <subelem_overrun_bytes> byte(s) (declared subelement length=<bad_subelem_len>; <total> such frame(s) seen) - CVE-2026-58374 class"` (rules_mle.c:95-101).

**Severity.** CRIT, unconditionally (rules_mle.c:102). No ownership gate, no confidence (plain `fire()` → `fire_conf(…, 0, …)`, engine.c:671-677 → confidence 0 → omitted from JSONL).

**Escalation / resolution.** None. The count in the detail changes with each new bad frame, which flips the detail signature and emits an `alert.update` at most once per `ALERT_UPDATE_MIN_S` = 60 s (include/sloth.h:867; engine.c:527-538). The alert never resolves on its own while the MLD stays in the roster; it can only disappear if the MLD entry is LRU-evicted from the 64-slot table (mle.c:369-377) and the key then goes quiet for `ALERT_RESOLVE_AFTER_S` = 300 s (include/sloth.h:860).

**Sensor health.** Each faulting element increments `parse_fault_mle_malformed` (`SH_PF_MLE_MALFORMED`, sensor_health.h:224; noted at mle.c:357-358).

## The attack

Wi-Fi 7 (IEEE 802.11be-2024 [6]) lets one device - a Multi-Link Device, MLD - run several radios under one identity, and the Multi-Link Element is how an AP or client describes those radios to the other side: a Common Info part (the MLD MAC and optional fields) followed by Link Info, a chain of Per-STA Profile subelements, one per affiliated link [6][2]. Each subelement is ID(1)+Length(1)+body, with no padding between them, so the chain is required to fill the space the element declared exactly [2].

A receiver that trusts those declared lengths without bounding them against the element reads past the end of the element. That is the defect family the w1.fi 2026-1 advisory reports in hostapd and wpa_supplicant 2.11 and pre-2.12 snapshots built with `CONFIG_IEEE80211BE`: it states the issues "can result in process termination due to buffer read overflow checks and memory corruption," reachable by "invalid Management frames without needing authentication or user action" [3]. CVE-2026-58374 is the member with its own number - a missing bounds check in AP-mode association processing where a Per-STA Profile `link_id` of 15 exceeds hostapd's `links[]` storage, CVSS 3.1 6.5 (AV:A/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H), fixed in hostapd 2.12 [4][5]. The advisory's eight mitigation commits are six link-ID validation fixes and two Common Info length fixes; it adds that "code review of similar areas showed other potential areas that did not have complete validation of the received messages" [3]. The subelement-chain overrun this rule reports is that read-overflow class, but no listed commit is specific to it [1][3].

Consequence: a pre-authentication denial of service against the AP (hostapd exits) or against a client (wpa_supplicant) from radio range, no credentials needed [3][4]. MITRE maps the vector under T1669 Wi-Fi Networks (Initial Access) - gaining access via the wireless network - and the technique page does not name this CVE [7].

Tooling: no public tool implementing this specific frame shape was located in this pass; the oss-security disclosure describes the crafted Per-STA Profile in prose only [5]. The element travels in an ordinary management frame, so the general injection primitive is available to any 802.11 frame crafter.

## Evidence that proves it

**What sloth records.** The `alert` / `alert.create` JSONL record with `title=MLE_SUBELEM_OVERRUN`, `sev=2`, `technique=T1669`, `key=mle_subelem_overrun:<mld_mac>` and the detail string above; `count` = evaluations (ticks), **not** frames (jsonl-schema.md:297, 390). The per-frame figure is only inside `detail`. The `wifi_mld` record for the same `mld_mac` carries whatever link addresses were decoded before the fault (jsonl-schema.md:711). `sensor_health.parse_fault_mle_malformed` rises by one per faulting element.

**No pcap and no evidence IDs.** The rule calls `fire()` with `match_ip = NULL` (rules_mle.c:102-103), so `--pcap-dir` cannot export for it, and it passes no evidence-ring IDs, so `evidence_count` is absent and `--collect-handshakes` writes nothing for it. `research/cve/2026-58374.md` states the raw frame is not held for this rule yet [1]. **This is the gap a responder feels first**: the alert gives the MLD MAC, the declared length and the overshoot, and nothing else about the frame.

**What makes it real.** In an independent capture of the same channel (the detail does not name the channel - another gap), a Beacon / Probe Response / (Re)Association Request from `mld_mac` whose Basic Multi-Link Element (Element ID 255, Extension 107 [2]) carries a Per-STA Profile (subelement ID 0) with a Length equal to the detail's `bad_subelem_len`, positioned so that start+2+Length exceeds the element's own Length by `subelem_overrun_bytes`. A `bad_subelem_len` of 0 with a non-zero overshoot is the 1-byte-tail shape. The same MLD MAC with a steadily rising "such frame(s) seen" count over seconds is a sender repeating the frame - a fuzzer or a DoS loop, not a one-off glitch. `sensor_health.parse_fault_mle_malformed` climbing at the same time corroborates.

**What refutes it.** A `wifi_mld` record for the same MAC with normal link addresses and `links_truncated=0` across hundreds of frames, with "such frame(s) seen" stuck at 1, is more consistent with a single corrupt frame (e.g. one that slipped past FCS filtering) than with an attack. A radiotap bad-FCS flag on the frame, if the capture retains it, settles it.

## Benign causes

- **A 1-byte trailing tail.** hostapd's own per-STA-profile loops stop when fewer than two bytes remain rather than flagging it [1]; sloth reports it. A vendor that padded Link Info with one octet would fire this rule for the association's life. No such vendor behaviour was found documented; the standard defines no padding [2]. `bad_subelem_len=0`, `subelem_overrun_bytes=1` from a known-good AP is the shape to suspect, and it is an AP conformance bug, not an attack.
- **Fragmented elements.** A Multi-Link Element longer than 255 octets is carried with Fragment elements (ID 242); sloth does not reassemble them (named as a false *negative* for the cipher rule in `research/ieee/802.11be-9.4.2.312-mld-identity.md` [2]). A profile cut at a fragment boundary could in principle read as an overrun. Not observed; worth a test case.
- **Corrupted frames reaching the parser.** Bit errors that passed FCS filtering can corrupt a Length byte. Fingerprint: count 1, never repeats, MLD otherwise healthy.

## Assessment

**Severity.** CRIT is justified by the shape rather than by impact: the frame as transmitted already exceeds its own declared bounds, which no conformant implementation produces [2][3], and the known consequence of trusting it is an unauthenticated AP crash [3][4]. The impact ceiling is DoS, not compromise (CVSS A:H, C:N, I:N [4]); an argument for WARN on impact alone exists, and the sibling rules that report merely *shaped* lengths are WARN. CRIT is defensible here because the certainty of malice-or-defect is near total and a repeating sender is actively probing the segment's APs.

**Prevalence.** Wi-Fi 7 hardware is mainstream (233 M devices forecast 2024 [8]); hostapd is the user-space AP daemon for Linux mac80211 and FreeBSD net80211 drivers [9] (the "ships in OpenWrt / most Linux APs" framing an earlier draft used could not be sourced from the OpenWrt page it cited and is dropped); the vulnerable builds are 802.11be-enabled before 2.12 [3][4]. Attack prevalence is unknown: disclosure was June 2026 [4][5] and no exploitation report was found in this pass. Treat as low-frequency, high-certainty.

**Reference host.** `host:null` - never fired, the right baseline for a site with no hostile Wi-Fi 7 frames. If it does fire there, one key per MLD accrues ~4 evaluations/s forever (lifetime counter, no recency bound), so a `count` in the millions after days means only "it happened once and the MLD is still in the roster." **Recommendation:** bound re-firing on `malformed_subelem_len_last_seen` the way `rule_queue_evict` bounds on `last_release_ts`, and/or resolve the key after `ALERT_RESOLVE_AFTER_S` clean. The detail already carries the frame count, so nothing is lost.

**Is the evidence sufficient to act on?** Partly. The detail gives the MLD MAC, the offending length and the overshoot - enough to recognise the frame in a capture - but sloth keeps no copy of the frame, no channel, no RSSI, and no evidence IDs for this rule. For a CRIT that is thin; wiring the evidence ring (`fire_ev()` as `rule_mle_reconfig_no_mlo` does at rules_mle.c:236-239) would let `--collect-handshakes` write the bytes.

**Responder's first steps.** (1) Patch: hostapd/wpa_supplicant ≥ 2.12 or distro backports of the w1.fi 2026-1 commits on every 802.11be-enabled AP and client you own [3][4]. (2) Read "such frame(s) seen": 1 = investigate as a possible glitch, rising = a transmitter is sending it now. (3) Locate: the MLD MAC's `wifi_mld` / `beacon` records give the link addresses; if the sender is an AP you own, check its firmware; if not, locate it by signal and do not probe or join it (MISSION §2). (4) Check your own AP processes for a restart at the alert's `first_seen`.
