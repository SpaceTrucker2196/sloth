## What the rule checks

Inputs: the beacon table `s->beacon_aps[]`, filled only from Beacon frames (management subtype 8, `src/beacon_snoop.c:808`; probe responses never enter it), the BTM steer table `s->btm_steers[]`, the deauth victim table, the attacker-OUI tables in `src/wifi_oui_attacker.c`, and the approved inventory when `--inventory` is loaded. Hidden SSIDs are skipped (`rules_twin.c:1337`).

**Branch 1 - weak/strong clone (`rules_twin.c:1342-1427`).** For each AP whose `enc` is `OPEN`/`WEP` (`enc_is_weak`, :1326), find a same-SSID BSSID whose `enc` is `WPA`/`WPA2`/`WPA3` (`enc_is_strong`, :1329). One fire per weak BSSID (`break`, :1426). Confidence `clamp(TWIN_W_WEAK_CLONE 85 + positive - context)` (:1387; weights `alerts.h:139-150`). CRIT, verdict `suspected impersonation`; demoted to WARN `inventory-approved pair, weak/strong split` when both halves are approved (:1401-1405). Key `alert_pair_key("twin",...)` (:1377) → `twin:<bssid_lo>:<bssid_hi>:<site>:<enc_lo>/<enc_hi>` (:200-218, :223-227); `site` is from `--site`/the inventory file, never RF.

**Branch 2 - same-security pair with positive evidence (`rules_twin.c:1461-1575`).** Skips `OPEN`/empty `enc` (:1461). For a same-SSID, same-`enc`, different-BSSID sibling, `twin_evidence_score()` (:235-300; called :1469) must return non-zero, which happens only when at least one positive signal is present and the pair is not both-approved:

| signal | weight | hard? | source |
|---|---|---|---|
| `diff_oui` first 3 bytes differ | +20 | no | :242 |
| `hashes_differ` both vendor-IE hashes present and unequal | +35 | no | :249-251 |
| `attacker_oui` Hak5 00:13:37, Alfa 00:c0:ca (Hak5-bundled) or any listed Espressif block on either side | +40 | yes | :252-253, wifi_oui_attacker.c:8-11, :17-29 |
| `steered` BTM Request w/ Disassoc-Imminent named either BSSID within twin.steer_window_s | +25 | yes | :255-256, :92-105 |
| `inv_mismatch` a half not approved for a declared SSID | +50 | yes | :264-266, :282 |
| `nbr_claim` 802.11k neighbour claim | -30 (context) | - | :258, :284 |
| `same_oui` | -15 (context) | - | :285 |

`confidence = clamp(positive - context, 5, 95)` (:287). Severity ladder (:1475-1529): WARN `vendor OUI differs`/`same vendor OUI`; CRIT `vendor-IE fingerprint differs` on `hashes_differ`; CRIT `attacker-tool OUI present`; CRIT `BSSID not in the approved inventory`; a BTM steer appends `+btm-steered by <AP>` and lifts WARN→CRIT (:1510-1521); an 802.11k claim demotes to WARN only when no hard signal backs the row (:1528-1529). Key `twin-fp:<lo>:<hi>:<site>:<profile>` (:1543). Detail: `'<ssid>' on <A> AND <B> [<enc>] - suspected impersonation, conf N% - <reason><notes><steer><class>` (:1554-1557); `<class>` is ` [class=<ap_class> wired=<w>]` (:341-344) where `ap_class` is impostor/neighbor/declared/? and `w` is `wired_attach_label()`, which is `?` for every row until a wire-side correlator registers (`wired_attach.c:37-43`). One fire per `a` per tick (`break`, :1574).

**Branch 3 - attack chain (`rules_twin.c:1736-1798`).** Hidden-SSID and `OPEN`/empty-`enc` APs are skipped (:1739-1740). When a BSSID is the victim of a `DEAUTH_FLOOD` whose threshold was last met (`flood_last`) within `deauth.twin_window_s` (5 s; :1743-1749) and a same-SSID, same-`enc`, different-BSSID, different-OUI sibling exists (:1757-1761), the sibling is tainted (`taint_mark`, :1763; TTL EVIL_TWIN_TAINT_TTL_SECS 300 s, `alerts.h:50`) and `EVIL_TWIN` fires CRIT (:1794) under key `twin-chain:<ssid sanitised, ≤32 bytes>:<16-hex FNV-1a of the SSID>` (`akey_remote`, :1773-1775; `alert_key.h:21`) with detail `'<ssid>' attack-in-progress: real=<A> twin=<B> [<enc>]` (:1776-1778). One fire per flooded `a` per tick (`break`, :1796). Table order (`rules_table.c:44-46`) runs this after `rule_evil_twin` so the taint is read on the next tick.

Evidence IDs: branches 1-2 cite both halves' newest 4 beacons (`twin_pair_evidence`, :52-62; BEACON_EVIDENCE_IDS 4) - branch 1 puts the weak clone first (:1420-1421); branch 2 puts the accused half first only when `twin_choose_sides()` can pick one, otherwise canonical lo/hi order so the list does not flip between ticks (:1559-1569). Branch 3 cites the twin's beacons then the newest deauth-flood frames against the real AP (:1783-1793). No `match_ip` is passed, so `--pcap-dir` writes nothing for this type (`alert_pcap.c:105`); the beacons are reachable only via the 802.11 evidence ring (`--collect-handshakes`, `docs/wiki/pcap-export.md:155`). A key silent for ALERT_RESOLVE_AFTER_S (300 s) resolves; a severity move emits `alert.escalate`/`alert.update` at once (`engine.c:519-526`).

### One device is not a pair (#188, 2026-11-11)

This subsection supersedes the branch 2 description above wherever the two differ; the line anchors above predate it and were not re-pinned (only `rule_file` was). Constants and reasoning are in `src/alerts.h` beside the weight table; the code is `twin_pair_is_sibling()`, `twin_ap_band()`, `bssid_is_laa()` and `btm_steered_to()` in `src/alerts/rules_twin.c`, all read by `twin_evidence_score()`, so the rule and the `[x]` Twins view change together.

Field data behind it (issue #188, one sensor, 2026-11-04 to 2026-11-10): 38 pairs reached CRIT, 33 of them one device's 2.4 GHz and 5 GHz radios, at 10-20 % confidence; 26 of the 38 had a locally administered BSSID.

| check | what it does | constant |
|---|---|---|
| sibling pair | BSSIDs differing in at most 2 bytes, on two different known bands, first heard within 10 s of each other: one device, not a candidate. `twin_evidence_score()` returns 0 and clears every observed flag. `inv_mismatch` is exempt and is scored as before | `TWIN_SIBLING_MAX_DIFF_BYTES` 2, `TWIN_SIBLING_WINDOW_S` 10 |
| OUI comparison | made only when both BSSIDs are globally administered. With bit 0x02 of the first octet set on either, neither `diff_oui` (+20) nor `same_oui` (-15) is set | - |
| `hashes_differ` | compared only when both radios are on the same known band; an unknown band (channel 0) is not "same" | - |
| self-steer | a BTM steer whose steering BSSID is within 2 bytes of the candidate it names sets `self_steer` and nothing else: no weight, not hard, no `+btm-steered by` note | `TWIN_SIBLING_MAX_DIFF_BYTES` |
| confidence gate | branch 2 demotes CRIT to WARN when no hard signal backs the row and confidence is under 50 | `TWIN_CRIT_MIN_CONF` 50 |
| late arrival (ruling 3b) | `late_arrival`, +20, soft: the later-heard half was first heard at least 120 s after the earlier one; the earlier one has been heard again since; the later one was first heard at least 120 s after the sensor was last known to be moving, and its SSID is new on its BSSID this session (`beacon_ap_t.arrival`: an AP the beacon table dropped and heard again is a return, not an arrival); the pair already has positive evidence; and a half is locally administered. Detail marker `+late-arrival`, Twins flag `>`, `twin_episode.late_arrival` | `TWIN_W_LATE_ARRIVAL` 20, `twin.late_arrival_s` 120 (30..86400) |

The window comes from the issue's observation that sibling radios first appear 1-3 s apart on a parked sensor (each beacons about every 100 ms, so the gap is the hopper reaching the other band); 10 s is three times the worst observed. The 6 GHz band is recognised only from the HE 6 GHz Operation Information source, the same rule `ap_band_label()` uses.

Consequences for the severity ladder in branch 2: `vendor-IE fingerprint differs` is CRIT only together with a cross-device signal (35 + 20 = 55): `diff_oui` between two globally administered addresses, or `late_arrival` where a half is locally administered. The two never add, since a late arrival is not counted on a pair of globally administered addresses. Without one it is WARN on a same-OUI pair (20 %) and on a pair with a locally administered half (35 %). An 802.11k claim on the 55 % row brings it to 25 % and WARN, as before. Hard-signal rows are not gated, so an attacker-tool OUI or an inventory mismatch can still be CRIT at a low confidence; that is deliberate, for the reason a neighbour claim cannot demote them.

**Late arrival (owner ruling 3b).** Masking the U/L bit left a rogue on a locally administered address at WARN 35 % with nothing to add; before #188 it could reach CRIT on three bytes that were never an OUI. The issue names the signal that needs none: "spoofing an existing SSID implies the twin's `first_seen` comes well after the original's". It is set under six conditions (the first four in `twin_pair_late_arrival()`, the last two in `twin_evidence_score()`), each of which exists because the gap is otherwise not about the transmitters:

- *The gap.* 120 s by default (`twin.late_arrival_s`). The issue's own radios appear 1-3 s apart and the sibling window is 10 s; a sensor start is one pass of the hop list (the default 11 channels at 100-2000 ms each, 22 s at worst), so 120 s is five worst passes. Sensor start needs no clock of its own: the beacon table is empty at start, so a gap of N is also N seconds of listening. The knob's floor is 30 s.
- *Both on the air.* The earlier half's `last_seen` must be at or after the later half's `first_seen`. The table keeps an AP for `BEACON_AGE_SECS` (300 s) after it was last heard, so a sensor driven past two APs of one carrier SSID holds both with a gap of minutes and the first was never heard again.
- *A sensor at rest.* The later half must have been first heard at least the same wait after the sensor was last known to be moving (a GNSS fix at 1 m/s or more, `twin_sensor_moving()` from #189). On a moving sensor arrival order is the route. This is remembered (`g_twin_moved_at`), not read off the current fix: the fix history is 64 fixes deep and a gap driven through stands for as long as the pair does. No GNSS is "not known to be moving" and suppresses nothing. `alerts_clear()` forgets it.
- *A name new to the session.* `first_seen` belongs to the table entry, and the table rebuilds an entry it dropped: an AP silent for `BEACON_AGE_SECS` (300 s), or one that lost its slot in a full table (`MAX_BEACON_APS`, 256), comes back under a new `first_seen`. So the table remembers what it drops (`src/beacon_snoop.c`, "BSSIDs the table has forgotten") and stamps each entry's `arrival` when it is created and whenever it takes another SSID: `NEW`, `RETURN`, or `UNSURE`. Only `NEW` on the later half counts. Owner ruling on the review finding that a router at the edge of range, and the issue's carrier-offload pair, reached CRIT 55 % when one half came back.
  - *Keyed on BSSID and SSID.* The question is whether this name has been heard from this address before. A BSSID-only memory would let a transmitter make itself known by beaconing any name once, five minutes ahead; with the name in the key it has to have sent the name it copies, and that earlier moment was scored as the arrival it was. An entry dropped while still hidden is not remembered.
  - *Bounded.* A ring of 4096 (sixteen tables' worth, 24 bytes each, static; nothing is allocated on the frame path, and it is scanned only when an entry is dropped, created or renamed). No age-out: for the session, as ruled. When full the oldest memory is overwritten, after which "not found" no longer means "never heard"; an entry the memory does not know is then `UNSURE` and not counted, until the memory again reaches back a day (`BEACON_RECALL_TRUST_S` 86400), past which a returning AP counts as new. That is the quiet failure. Its cost: a site that drops more than 4096 distinct BSSID/SSID pairs a day, or a beacon flood of random addresses, turns the signal off (the flood is `BEACON_FLOOD`'s row). Since JSONL 1.2.0 it is no longer silent: `sys_status`'s `beacon_recall_overflowed` / `beacon_recall_quiet` (written at once when either goes to 1) and slothweb's Sensor health line say when the signal is off and until when.
  - *`first_seen` is not rewritten.* Restoring the original would tell `COUNTRY_ABSENT`, `TPC_ABSENT`, `WPA_DOWNGRADE` and the DFS-masking CSA test, which read it as "this entry has been watched since", a longer story than a rebuilt entry has. One byte in existing padding; `sloth_state_t` does not grow.
  - *It replaces the full-table guard added in review* (`evict_age_s1`, which refused every insert within the wait after an eviction). An entry dropped for room is remembered like one dropped for age, so its re-insert is known exactly and a BSSID never heard before that arrives at a full table is still an arrival.
  - The operator clearing the beacon table clears the memory with it.
- *Corroboration only.* The weight is added only to a pair that already has positive evidence, and the flag is never set without the weight. A late arrival alone raises no row: otherwise every same-SSID pair first heard two minutes apart (a mesh node at the edge of earshot, a guest SSID enabled later) becomes a WARN, a Twins episode and an `EVIL_TWIN_PROXIMITY` candidate.
- *A locally administered half.* Owner ruling on review: the weight and the flag apply only to a pair in which at least one BSSID is locally administered, the case the signal was asked for. Two globally administered addresses are scored on their OUIs as before: a same-vendor mesh pair whose nodes differ in vendor IEs, or a two-vendor pair with nothing but its OUIs, stays at 20 % however far apart the halves were first heard (inside slothweb's 20 % mute), and a two-vendor pair with a vendor-IE mismatch stays at 55 rather than 75. The flag is never set without the weight, so `>` in the Twins view and `late_arrival` in `twin_episode` follow the same restriction.

20 is what `diff_oui` is worth, because it stands in for it. The floor is pinned by test: under 15 the locally administered rogue stays below the gate. There is no ceiling to pin since the restriction: on a pair with a locally administered half nothing deducts but a neighbour claim, which demotes a soft CRIT whatever the sum.

What it does not cover, stated so the noise verdict above is not read as closed:

- "New to the session" is new to this sensor. An AP that was out of earshot until now and one switched on now look the same. An AP that drops out and returns is no longer a late arrival (above); one never heard before in the session still is, whatever its history elsewhere.
- A transmitter that knows the rule can announce itself: one beacon carrying the SSID it means to copy, sent when the gap does not count (inside the 120 s after the original was first heard, while the sensor is moving) or sent without the evidence a late arrival corroborates (the original's own vendor IEs, or another band), then silence for 300 s. When it starts in earnest it is a return. Not guarded: a minimum presence before a BSSID is remembered would cost the edge-of-range AP heard once, which is the case the memory exists for, and would only lengthen the announcement.
- When the memory has overflowed (above) a real late arrival is not counted, and a locally administered rogue stays at WARN 35 %.
- The gap is a difference of wall-clock stamps. A host clock stepped forward between the two first sightings (a box with no RTC that NTP or GNSS corrects after sloth has started) is read as a gap, for as long as both entries stay in the table. Not guarded: the beacon table keeps no monotonic `first_seen`, and adding one would also serve the sibling window.
- A moving sensor with no GNSS is not known to be moving. The "both on the air" condition covers two APs it passed one after the other; it does not cover two APs that were both in earshot at some point on the route.
- A rogue on a locally administered address that shows no same-band vendor-IE mismatch (another band, or no vendor IEs) has no positive evidence for a late arrival to corroborate and raises no row, as since #188.

- The sibling window is measured from when the *sensor* first heard each radio. At sensor start everything in range is first heard together, so the address and band conditions carry the test alone; on a moving sensor the 5 GHz radio can be heard minutes after the 2.4 GHz one and the pair is not a sibling. In that second case the other three checks still leave a same-vendor or locally administered pair with no positive evidence, so it is silent, but a third-party steer at it would count.
- A copy placed within 2 bytes of its victim's address loses the BTM-steer signal for steers the victim's own BSSID appears to send. It is still scored on OUI, vendor IEs, inventory and attacker OUI.
- The other benign CRIT pairs in the same data were not addressed by this change: a three-node same-OUI mesh on one channel whose vendor IEs differ is still reported, at WARN and 20 % rather than CRIT. The carrier offload pair and the faint ISP pair are handled since 2026-11-12 (next subsection). The offload pair in the issue has a locally administered half, which held it at WARN and 35 % unless the second router counted as a late arrival, which needs it never to have been heard under that name before in the session (first heard 120 s or more after the first, on a parked sensor, with the first still being heard), when it is CRIT at 55 %; a router that was there, dropped out and came back does not; two such routers with different globally administered OUIs and differing vendor IEs on one band would be CRIT at 55 %, and nothing short of an inventory tells that from an impersonation.

### Two devices that are meant to be there (#188, 2026-11-12)

The sibling test answers "one device or two". Of the issue's five non-sibling CRIT pairs, three were a same-OUI mesh (WARN 20 % since the change above) and two were two devices that were benign anyway. Both are handled in `twin_evidence_score()` and the branch 2 gate; constants and reasoning beside the weight table in `src/alerts.h`.

| check | what it does | constant |
|---|---|---|
| carrier SSID | `carrier_ssid`: the SSID is, case folded and exactly, one a carrier broadcasts from every subscriber's gateway: `Spectrum Mobile` (the issue's pair), and the carrier rows of `OPEN_SETUP_AP`'s hotspot guardrail (`SpectrumWiFi`, `xfinitywifi`, `XFINITY`, `CableWiFi`, `CoxWiFi`, `Cox Mobile`, `optimumwifi`, `attwifi`). Context, subtracted from confidence; the pair stays a candidate and the row stays. Detail marker `+carrier SSID` | `TWIN_C_CARRIER_SSID` 35 |
| faint half | `faint`: either half's strongest reading in the 60 s window (its newest when the window has aged out) is at or under -92 dBm, or the table has heard it on fewer than `twin.crit_min_beacons` beacons. No weight; a soft-signal row with it set is WARN. 0 in a reading or in `frame_count` is "unseen" and is not faint. Detail marker `+faint` | `TWIN_PROX_FLOOR_DBM` -92, `twin.crit_min_beacons` 5 (1..1000) |

Why the carrier SSID is context and not a skip: a second vendor, a second firmware and a late arrival are exactly what the next customer's router looks like under a carrier name, so the soft signals cannot tell it from a copy, but a hard signal can. 35 takes the strongest soft sums (55) to 20, inside slothweb's mute, and no further; an attacker-tool OUI, a BTM steer from another device or an inventory mismatch still carries the row to CRIT. Exact names, because a per-site suffix (`XFINITY-Den`) is somebody's own network. Venue hotspots and guest networks are deliberately not on the list: one operator runs each, which is what a twin of one copies.

Why faint gates severity and not confidence: the issue's ISP pair was two vendors at -100 dBm on one or two beacons each. Two vendors and two firmwares are still what was observed (55 %), but a copy sloth can barely hear is no threat to the clients around sloth, and a fingerprint read off one or two frames at the decode margin has not been read twice. -92 dBm is `EVIL_TWIN_PROXIMITY`'s floor (#189) and its reasoning: receiver floor about -95 dBm, and at -92 or below which beacons decode is fading. Five beacons is five passes of the hop list for an AP in steady earshot, under two minutes at the default list's worst; a copy that has stood that long has given far more. Hard signals are exempt, as from the confidence gate.

How the issue's pairs now classify (`tests/test_alerts.c :: test_twin_issue_188_field_pairs_classify`, one row each): residential routers A and B, both GM hotspot shapes, the VW hotspot and the self-steering T-Mobile gateway raise no row; the ASUS mesh pair is WARN 20 %; the Spectrum Mobile pair WARN 20 % (35 + 20 - 35); the -100 dBm ISP pair WARN 55 % `+faint`. Real: two vendors on one band with different vendor IEs CRIT 55 %; a locally administered copy that arrived late CRIT 55 %; an attacker-tool OUI CRIT, barely heard or under a carrier name; the deauth-then-twin chain CRIT on its own key.

What it costs: an evil twin of a carrier SSID that shows only soft signals is WARN at 20 % or less, which slothweb mutes; and a copy heard only at the edge of earshot, or in its first few beacons, is WARN until it is heard properly. The chain (branch 3) does not read either flag: a deauth flood against one carrier router still names the other the rogue.

Tests: `tests/test_alerts.c :: test_twin_issue_188_field_pairs_classify`, `:: test_twin_carrier_ssid_is_context`, `:: test_twin_faint_bounds`, each naming its mutations. `:: test_twin_an_ap_that_returns_is_not_a_late_arrival` used the issue's carrier SSID and now uses a name of no carrier's, and records the copy on five beacons.

**Branch 3 asks the same question (owner ruling 4a).** Until this change `rule_evil_twin_attack_chain` compared the first three bytes of any two addresses and had no sibling test, so a deauth flood against one radio of a dual-band device named the device's other radio the rogue at CRIT and tainted it: a GM hotspot's `02:24:a5` / `02:49:a5`, or any AP whose two radios sit in neighbouring OUI blocks. This supersedes the "different-OUI sibling" wording of the branch 3 paragraph above. The second BSSID is now "the other half" only when:

- it has the flooded AP's SSID and `enc` (not `OPEN`), as before;
- the two are not globally administered addresses sharing an OUI. That skip is kept from before and is the chain's own: the scorer reports a same-vendor mesh whose nodes differ in vendor IEs at WARN, and under a flood one node would otherwise be named the rogue;
- `twin_evidence_score()` calls the pair a candidate. That is the sibling test, the U/L bit, the same-band rule and the inventory in one call, and it is the pair `rule_evil_twin`, the `[x]` Twins view and `EVIL_TWIN_PROXIMITY` use.

What that changes, beyond the dual-band case: a pair with a locally administered half is admitted on evidence (a same-band vendor-IE mismatch, an attacker-tool OUI, a BTM steer, an inventory mismatch) and never on its first three bytes, whether they differ (the vehicle hotspot, which was named) or match (two locally administered addresses derived from one base address, which were skipped). Two radios the inventory approves both of are no longer named each other's rogue. The detail string is unchanged and never carried OUI text.

What it costs: a copy on a locally administered address that shows no evidence of its own (another band, no vendor IEs) is not named under a flood. `DEAUTH_FLOOD` still reports the flood; the `attack-in-progress` row, the taint and the `.22000` provenance line are what is lost. Before the change it was named whenever its first three bytes differed from the victim's, as a random address's almost always do.

## The attack

Wi-Fi clients pick a network by name. The SSID is a free-text element any transmitter can put in a beacon, and the 802.11 4-way handshake authenticates the shared credential, not the name [6]. So two access points can legitimately or maliciously advertise one SSID, and a client cannot tell from the name alone which radio it is talking to. An evil twin is a rogue AP that broadcasts a trusted network's SSID to make victims associate to it instead of the real one; ATT&CK calls it Adversary-in-the-Middle: Evil Twin: "Adversaries may provide a stronger signal strength or block access to Wi-Fi access points to coerce or entice victim devices", and "Locations with high concentrations of public Wi-Fi access, such as airports, coffee shops, or libraries, may be targets" [5]. Once a client associates, the operator sits in the middle: "a user may be directed to a fake login page or captive portal webpage to capture the victim's credentials" and "Custom certificates may be used in an attempt to intercept HTTPS traffic" [5]; the WPA handshake can also be captured for offline cracking.

The classic escalation is to pair the twin with a deauthentication flood (branch 3): knock clients off the real AP so they re-associate, and the stronger or only remaining same-name radio is the rogue [1][5]. Tooling is turnkey - the WiFi Pineapple advertises a pool of SSIDs and "will answer for all SSIDs which are permitted by the filter configuration" [8]; wifiphisher "creates a fake wireless network that looks similar to a legitimate network" and simultaneously deauthenticates clients to drive them over [7]; an ESP32 Marauder's "Beacon Spam AP spams beacon frames that copy a known access point scanned by scanap" [9]. Vanhoef and Piessens showed a continuous jammer plus a same-SSID AP on a second channel can force a channel-based man-in-the-middle with commodity dongles [11]. The 2024 AFP case is the attack in the wild: a man ran portable free-Wi-Fi access points on domestic flights and at Perth, Melbourne and Adelaide airports, with a fake captive portal asking users to "log in using their email or social media accounts"; the investigation began from "reports from airline employees in April 2024" [10].

## Evidence that proves it

sloth records, in the detail: the SSID, both BSSIDs, the shared `enc`, the separate `confidence` percentage, the `reason` (which positive signal fired), the `ap_class`, the literal `wired=?`, and, when present, the steering AP (`+btm-steered by <AP>`) and `+not in inventory`. The cited evidence-ring IDs point to both halves' newest beacons, the accused half first (`docs/wiki/pcap-export.md:155`); with `--collect-handshakes --eapol-dir` those beacons can be exported and opened in Wireshark. The twin's own beacons are the proof of what was on the air under that name.

To call a same-security row real, a reader should see at least one hard signal: the twin's BSSID OUI on the Hak5/Espressif list, a vendor-IE fingerprint that genuinely differs from the real AP's stock firmware (stock emits IEs in a stable order; a rogue copying only SSID+cipher produces a different `vendor_ies_hash`), a BTM Request that named the rogue as a roam destination while carrying Disassociation Imminent, or an inventory mismatch. Branch 3's `attack-in-progress` is the strongest standalone case: a deauth flood against one half within 5 s of a different-OUI same-name twin appearing - jam, re-associate, capture.

What refutes it: a cross-vendor OUI with nothing else is the fingerprint of a benign mixed-vendor mesh or a range extender (sloth's own documented #51 false positive). A matching `vendor_ies_hash` across the pair, an 802.11k neighbour relationship, both BSSIDs in the approved inventory, or the weak half being the operator's own guest SSID all point benign. RSSI is explicitly not used to name the impostor (`rules_twin.c` / Twins view: the operator's own AP is usually the closest radio, so RSSI gets it backwards).

## Benign causes

- **Multi-vendor mesh / range extenders.** Same SSID, different OUI, same cipher - branch 2 WARN at 20% confidence. The documented #51 false positive. Tell apart by OUI ownership and by `vendor_ies_hash` agreement; declare both BSSIDs in `--inventory` to silence.
- **Operator's own open guest network** sharing a name stem with the protected one - branch 1. The weak/strong split is real (an OPEN BSS beside a protected one under one name is a downgrade lane), so the rule demotes rather than drops it when both are approved.
- **WLAN controller multi-VAP / band-steering.** A controller may legitimately send BTM steers; the chain only escalates when the steer named *this* BSSID with Disassociation Imminent, which load-balancing steers do not set.
- **A rebooting legitimate AP** re-appearing under its own name. No OUI/hash/inventory signal, so it stays low-confidence.

## Assessment

Severity is right: the design correctly separates "how bad if true" (sev) from "how likely true" (confidence), and reserves CRIT for signals an attacker cannot cheaply forge. The real-world prevalence is high and the consequence - credential and handshake capture - is serious [5][10]. The evidence is sufficient to act on when a hard signal or the attack chain is present; a bare `vendor OUI differs` WARN is a lead to verify, not a finding.

The reference-host noise is the problem, and it is a presentation problem, not a rule problem: 2.07e6 fires per pair means `count` is measuring how long each pair sat in the air, so the alert page must show `observations`/timestamps/`confidence`, never `count`. A responder should first read `confidence` and `ap_class`, then the cited beacons; load `--inventory` to collapse the benign majority; and treat an `attack-in-progress` (chain) row or an `attacker-tool OUI present` row as the ones worth walking down with a directional antenna. Do not join or probe the suspected rogue (`alert-remediation.md:439`).
