## What the rule checks

Inputs: the per-BSSID 802.1X posture table `s->rogue_radius[]` (MAX_ROGUE_RADIUS = 32 rows, include/sloth.h:1781), filled by `eap_track_observe()` from EAP frames decoded off the air (src/eap_track.c), snapshotted each poll by `eap_track_snapshot()`. Per BSSID the tracker records:

- `weak_method` (eap_track.c:138) — a latch set to 1 the first time any EAP frame for that BSSID, in either direction (a Request from the AP or a Response from the client — the tracker does not check the code field), carries method type MD5 (4) or GTC (6), per `eap_type_is_weak()` (eap_parse.c:116-118).
- `identity_leaks` (eap_track.c:143-147) — incremented for each EAP Response/Identity frame (code = Response, type = Identity) whose identity string is *not* an anonymous outer identity. The anonymity test (eap_track.c:144) treats a string starting with "anonymous" or with "@" (bare `@realm`) as anonymous; anything else is a real username leak, and the most recent is kept in `last_identity`.
- `eap_types_seen` — a bitmap of every method type observed, for the `[z]` view.

Condition (rules_enterprise.c:413-435): for each BSSID row, skip unless `weak_method` is set or `identity_leaks > 0`. Fire CRIT if `weak_method`, else WARN.

Key (rules_enterprise.c:422): `rogueradius:<bssid>` via plain snprintf — the BSSID is the transmitter's own, not remote-chosen. One incident per BSSID.

Detail (rules_enterprise.c:423-430): if weak, `BSSID <bssid> offered weak EAP (MD5/GTC), <n> identity leak(s) - rogue-RADIUS lure`; else `BSSID <bssid> leaked <n> real EAP identity(ies) - check outer identity`. It carries the BSSID and the leak count; it does not carry which method (MD5 vs GTC), the leaked username (that lives in the `[z]` view / `last_identity`), the client MAC, or a timestamp.

Severity (rules_enterprise.c:431-433): CRIT iff `weak_method`, else WARN. Plain `fire()` — no confidence term, no evidence frames, no `match_ip`, so no pcap. Resolves 300 s after the last re-assertion. There is no time-based ageing of the posture table: `eap_track.c:15-19` declares it `STAB_OLDEST`, so a row leaves only when all 32 slots are taken and it is the least recently seen (counted as SH_EVICT_ROGUE_RADIUS). With fewer than 32 enterprise BSSIDs in range a latched `weak_method` row, and its CRIT, stands for the life of the process.

Sibling rule: `rule_peap_no_server_cert` (rules_enterprise.c, ALERT_TYPE_PEAP_NO_SERVER_CERT, T1557) reads the same table's `nocert_sessions` and is the client-side half (CVE-2023-52160). ROGUE_RADIUS is the AP-side half. They are deliberately separate (research/cve/2023-52160.md; docs/wiki/enterprise-rogue.md).

## The attack

WPA-Enterprise (802.1X) moves authentication off the AP to a RADIUS server, reached over an EAP conversation the client and server run through the access point (RFC 3748) [9]. Two things in that conversation are visible to a monitor-mode radio and are the attack's fingerprint.

First, the **inner method**. A sound enterprise deployment negotiates a TLS-protected method (PEAP, EAP-TTLS, EAP-TLS) and runs MSCHAPv2 or similar inside the tunnel. An attacker standing up a rogue AP that advertises the corporate SSID wants the client to use a *weak* method instead: EAP-MD5 (type 4), whose challenge/response is offline-crackable and provides no mutual authentication (RFC 3748 §5.4) [9], or EAP-GTC (type 6), which RFC 3748 §5.6 says MUST NOT carry a cleartext password outside a protected tunnel — exactly the protection a rogue removes [9]. eaphammer automates a "GTC downgrade attack against connected clients in [an] attempt to capture plaintext credentials" [5]; hostapd-wpe impersonates PEAP/MSCHAPv2, EAP-TTLS variants and more, returns EAP-Success so the client believes it connected, and logs the captured credentials for cracking with asleap or John the Ripper [6].

Second, the **outer identity**. The EAP Response/Identity frame crosses before any TLS tunnel exists, so it is readable by anyone in range (RFC 3748 §5.1: identity exchanges are sent in cleartext and can be snooped) [9]. A correctly configured supplicant sends an anonymous outer identity (`anonymous@realm` or bare `@realm`, per RFC 7542 §2.4 on username privacy) [10] and reveals the real username only inside the tunnel. A client that sends its real username in the outer identity leaks it to a passive listener whether or not any rogue is present — which is why the identity-leak case is WARN, not CRIT.

The reason the AP-side rule matters even against a *correct-looking* rogue is CVE-2023-52160: when wpa_supplicant (through 2.10) is configured not to verify the server's TLS certificate in Phase 1 — a common misconfiguration — an `eap_peap_decrypt` flaw lets the rogue send an EAP-TLV Success instead of starting Phase 2, so the client joins the impersonated network without the attacker knowing any credential [7][8]. Even without that flaw, a client that skips certificate validation will run its inner method against any server, which is what makes the identity-and-challenge harvest above work. This belongs to MITRE's Evil Twin sub-technique T1557.004 [3][4].

## Evidence that proves it

What sloth records: the detail line's BSSID and leak count, and — in the `[z] Rogue RADIUS` view — the full per-BSSID posture: every EAP method type seen (`eap_types_seen` bitmap), the `weak` flag, the leak count, and `last_identity` with seconds since last heard. No pcap (no `match_ip`) and no cited frames. The JSONL `alert` stream carries sev (2 for weak, 1 for leak-only) and technique T1557.004.

To call a CRIT real: open `[z]` and read which methods the BSSID offered. MD5/GTC on a BSSID advertising the operator's corporate SSID from an unknown vendor OUI, especially a new BSSID that appeared mid-day, is an active harvest — cross-check `[x] Twins` and `[b] Beacons` for the same BSSID (an enterprise evil twin trips the twin detector too). Leaks climbing on one BSSID while other APs of the same ESS show none means clients are being answered by that radio. If `PEAP_NO_SERVER_CERT` also fires for a client on that BSSID, the harvest is not hypothetical — a device accepted an uncertified server.

What refutes it: a weak method offered by a BSSID that is unambiguously the operator's own enterprise AP (same vendor OUI, long-standing, matches the controller inventory) is a misconfiguration to fix, not a rogue — the fix is to stop offering MD5/GTC. An identity leak with no weak method is clients missing anonymous outer identities: a hygiene finding, benign in cause, and the "fix" is client supplicant configuration. The anonymity test is simple (prefix "anonymous" or leading "@"); an unusual-but-legitimate anonymous scheme that does not match those forms would be miscounted as a leak — check `last_identity` in `[z]` to see the actual string.

## Benign causes

- **Legitimately misconfigured enterprise AP** still offering EAP-MD5 or EAP-GTC. Real on older or sloppy deployments; distinguished from a rogue only by ownership (vendor OUI, inventory, longevity).
- **Clients without anonymous outer identities.** Produces the WARN identity-leak case honestly; the cause is client config, not an attacker (docs/views/rogue-radius.md "What's normal").
- **Stock FreeRADIUS method negotiation.** FreeRADIUS 3.x ships `default_eap_type = md5` in `mods-available/eap` [11], so an unmodified server proposes EAP-MD5 first and a PEAP/TTLS client NAKs it. The rule latches on that one Request. Tell apart in `[z]`: `eap_types_seen` also shows a NAK (type 3) alongside a TLS method (PEAP/TTLS/TLS). sloth does not record which method a conversation completed with, so this is an inference from the bitmap, not proof.
- **A non-standard but intentional anonymous identity** that does not start with "anonymous" or "@" — miscounted as a leak. Inspect the string.

## Assessment

Severity rationale: the CRIT/WARN split tracks the real difference between "attacker infrastructure is present" (a weak method offered) and "a client here is leaking a username" (an exposure with common benign causes). Both are correct to report, and the detail is honest about which it is. The one gap is that the detail does not say *which* weak method (MD5 vs GTC) or carry the leaked username — both are in `[z]`, but an alert-page reader has to pivot there.

Real-world prevalence: this is a mature, automated attack class. eaphammer and hostapd-wpe are off-the-shelf [5][6], and CVE-2023-52160 made the client side trivially exploitable across what the disclosure counts as ~2.3 billion Android users plus Linux/ChromeOS [7][8]. Targeted use against named enterprises (eduroam is the canonical example in the disclosure) is documented; broad opportunistic use is less reported but entirely feasible.

Reference-host noise verdict: not seen — the batch gives host:null, so there is no firing data to arithmetic over. Structurally the rule cannot flood: the key space is the number of enterprise BSSIDs in range (`weak_method` latches once per BSSID; `identity_leaks` moves only on a real Identity frame). Any large `count` would be the per-tick evaluation counter, not distinct events; the fix if it ever looks loud is to show `observations`. Because 802.1X appears only around WPA-Enterprise, on a home/PSK segment this rule is simply silent.

Is the evidence sufficient to act? For a CRIT, close to it once the stock-FreeRADIUS MD5-first negotiation is ruled out in `[z]` (`eap_types_seen` showing NAK and a TLS method alongside MD5): a weak method actually used is almost never benign on a modern enterprise network, so the first action is to determine ownership. If the BSSID is the operator's, raise its EAP config (drop MD5/GTC). If it is not and it is on controlled premises, locate and remove it; otherwise report it and do not join or probe it. Treat any client that associated as having exposed its outer identity, and set `ca_cert` + `domain_suffix_match` on every 802.1X client so it only completes against the operator's server — the defence for both this and CVE-2023-52160 (docs/wiki/alert-remediation.md "ROGUE_RADIUS"; docs/wiki/enterprise-rogue.md).
