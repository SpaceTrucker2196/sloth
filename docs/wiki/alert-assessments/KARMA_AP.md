## What the rule checks

Inputs: the beacon table `s->beacon_aps[]` (each AP carries a distinct-SSID history `ssid_history[]`/`ssid_history_n`, appended per Beacon when a new SSID is seen, capped at 8 - `beacon_snoop.c:1134-1152`). The history is fed **only from Beacon frames** (subtype 8, `beacon_snoop.c:808`); the probe-response path (`beacon_note_probe_resp_ies`, :1465) merges WPS fields only and never adds an SSID. So this rule sees the *beaconing* lure variants (PineAP SSID pool, MANA loud, wifiphisher Known Beacons, mdk4 b) and is blind to a classic KARMA radio that only answers unicast probes without beaconing. Other inputs: the client PNL table `s->pnl_clients[]`, the deauth victim table, the EAPOL events (for PMKID), and the tool-signature table `src/tool_fingerprint.c`.

`rule_karma_ap()` (`rules_twin.c:970-1096`) fires once per BSSID whose `ssid_history_n >= KARMA_SSID_THRESH` (default 3, `--tune karma.ssid_thresh`). That bare crossing is a *candidate* (WARN). Severity escalates to CRIT (:1015-1016) only when one of three candidate-specific corroborators holds:

- `pnl_corrob`: one single station's PNL asks for at least `KARMA_PNL_CORROB_MIN` = 2 of this BSSID's advertised SSIDs (`karma_pnl_client_hits`, declared `karma_detect.h:83`; the constant is `:64`) - the actual PineAP Beacon-Response shape. The *union* over all clients is reported (`, N in client PNLs`) but no longer escalates or scores (#90).
- `deauth`: a shared-victim deauth-then-lure chain (`karma_deauth_lure_victim`) - a station deauthed off a *different* BSSID within KARMA_DEAUTH_WIN_SECS = 60 s whose PNL asks for one of this candidate's SSIDs, or that has since associated with it.
- `tool_verified`: a capture-backed tool-signature match. Every shipped row is UNVERIFIED (`tool_fingerprint.c`), so this is unreachable today; an UNVERIFIED match is informational and does not escalate.

Confidence (`rules_twin.c:1017-1033`) starts at `KARMA_W_SSID_THRESH` = 20 and adds `KARMA_W_PNL_OVERLAP` 25 (pnl_corrob), `KARMA_W_DEAUTH_VICTIM` 30 (deauth), `KARMA_W_IE_COLLAPSE` 10 (#187: the advertised SSIDs collapsed onto one IE fingerprint - confidence only, never severity), tool weight 10/30, `KARMA_W_PMKID` 10, clamped 5..95 (`alerts.h:279-322`). A harvested PMKID from this BSSID adds `+PMKID` but never escalates alone (legit 802.11r/PMK-caching also produces one). Key is `karma_alert_key(bssid)` (:1077; one place, shared with the dashboard badge, `karma_detect.h:40`). Detail: `KARMA BSSID <mac>: <N> SSIDs<ie note><pnl note><chain><pmkid><tool><hw>, conf N%[ - candidate, uncorroborated]`, where `<hw>` (#151, `hw_karma_context()` in `src/attack_hw.c`) is ` +setup-AP Pineapple_XXXX@<bssid>` when a different live BSSID beacons Hak5's documented setup SSID, then ` hw:suspected-<device>` from the verdict layer; the same verdict rides the JSONL record as `hw_verdict`/`hw_signals`. Context only: neither moves severity or confidence, and `corroborated-` needs a capture-backed input, which nothing shipped is (`docs/wiki/attack-hardware-fingerprints.md`) (:1078-1082). Evidence IDs: one frame per distinct SSID, the newest carrying it (`ssid_history_ev`, up to 8; :1086-1090). No `match_ip`, so no `--pcap-dir` file; beacons reachable only via the evidence ring.

## The attack

A client keeps a Preferred Network List of networks it has joined and, historically, probed for them by name when disconnected. KARMA, by Dino Dai Zovi and Shane Macaulay in 2005, patched a driver "to allow the creation of an 802.11 Access Point that responds to any probed SSID" [5] - the AP answers a client's probe for `HomeNet` by claiming to *be* `HomeNet`, for `CorpWiFi` by being `CorpWiFi`, and so on. The client, finding its remembered network apparently present, auto-associates, and the attacker is the man in the middle (ATT&CK maps this to AiTM / T1557; the evil-twin sub-technique says adversaries "can respond with the same SSID to imitate the trusted, known network" to "probe requests for known or previously connected networks" [4][9]). The fingerprint from a passive sensor is one BSSID (one radio) carrying many unrelated SSIDs; sloth reads that from beacons only (above), so the probe-response-only form is out of its sight.

Modern phones randomise probe-request MACs and mostly stopped broadcasting their full PNL, which blunted the original KARMA. The revival is the MANA / beacon-response variant: SensePost's hostapd-mana offers "KARMA/MANA Mode - respond to any device looking for an SSID as that network (probe response)" and "MANA Loud - re-broadcast probe responses for SSIDs learned from other devices" [6]; the WiFi Pineapple's PineAP maintains an SSID pool and "will answer for all SSIDs which are permitted by the filter configuration" with a single or pseudo-random BSSID per SSID [7]; wifiphisher's Known Beacons attack "broadcasts a dictionary of common ESSIDs" the surrounding stations have likely joined before [8]. mdk4 mode b "Sends beacon frames to show fake APs at clients" [10]. The gain is identical to an evil twin's: association, then credential capture, handshake capture, or traffic interception.

## Evidence that proves it

sloth records the BSSID, the count of distinct SSIDs, the PNL note (and, when a single station corroborates, that station's MAC - `, 3 in client PNLs (2 on <mac>)`), the chain marker, `+PMKID`, any tool attribution, and the confidence. The cited evidence-ring frames are one beacon per distinct SSID - the set *is* the finding, so those frames are the proof that one radio carried all those names.

To call it a real lure, a reader should see a CRIT: either a single station's PNL asking for >=2 of the SSIDs (the beacon-response shape, and the named station can be inspected in the KARMA `[y]` and client views), or the deauth-then-lure chain naming a shared victim (deauth off a different AP, then that victim's PNL or association ties it to this radio). A high Jaccard overlap (J% in the `[y]` view) between the advertised set and a client's PNL, trending toward 100%, is the sharpest PineAP tell (`docs/views/karma.md`). A collapse of every SSID onto one IE fingerprint adds a little weight (#187) - but only a little, and the reason is worth reading before leaning on it: the multi-VAP contrast that phrase implies is not one sloth can draw, because a VAP has its own BSSID and so never becomes a candidate, and the Multiple BSSID set's nontransmitted profiles are not decoded. A renamed BSS collapses identically. `research/papers/mbssid-per-bss-ie-variation.md`.

What refutes it: the union-only PNL hit (one common name like a carrier hotspot landing in one passer-by's list) is a fact about the neighbourhood, not this radio - the #90 false positive, which is why union no longer escalates. A multi-VAP enterprise AP legitimately carries several SSIDs on one BSSID; a mesh/repeater rebroadcasts the networks behind it; captive-portal gear cycles SSIDs. The SSID-count ranges overlap the threshold by design (benign 1-4 vs threshold 3), so the bare count is a candidate, never a verdict.

## Benign causes

- **Multi-VAP / enterprise AP** carrying 3-4 SSIDs on one radio - crosses the count, no corroborator. Tell apart: IE uniformity plus no single-station PNL overlap; the SSIDs are the site's own, not a grab-bag.
- **Repeater / mesh node** rebroadcasting the networks behind it (`docs/views/karma.md`).
- **Captive-portal / hotspot gear** that cycles SSIDs over a session.
- **An AP renamed a few times** over a long session accrues the same distinct-SSID count as a lure.
- **A legitimate PMKID** from 802.11r fast-roaming or PMK caching - informational only, never a standalone escalation.

## Assessment

Severity is right and the rule is unusually well-disciplined: the #90 pass removed exactly the coincidence escalators (union PNL, unrelated floods) that would make it a false-positive machine, and leaves CRIT meaning *corroborated* - which, per the owner ruling, is not the same as *confirmed* for a passive sensor. Prevalence of the technique is high in tooling but the corroborated form is rare in the wild given modern client behaviour [5][6][7].

The reference host shows this working as designed: 60 candidates, all WARN (max_sev 1), none corroborated - i.e. 60 benign-looking multi-SSID radios, not 60 lures. The 415.7e6 count is pure time-in-table and must not be shown as "415 million KARMA events". A responder should read the WARN/CRIT split first, ignore uncorroborated WARNs unless the SSID set is itself suspicious (a grab-bag of unrelated names from one radio), and treat a CRIT - a named single-station PNL match or a deauth-then-lure chain - as an active lure: locate the radio if on controlled premises, and check which of the operator's clients associated and what they sent (`alert-remediation.md:487`). Do not join it. Operationally, raise `karma.ssid_thresh` in a multi-VAP-dense site to cut candidate volume.
