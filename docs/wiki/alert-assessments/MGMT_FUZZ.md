## What the rule checks

*This section describes the rule as assessed, before #173. What #173 changed (the detail, and how often the rule fires) is in the **Since #173** paragraph at the end of Assessment; file:line references below are to the assessed tree except `rule_file`.*

Inputs: the beacon snapshot `s->beacon_aps[]`, specifically three saturating uint16 per-BSSID counters (include/sloth.h:1609-1611; set on the BSSID's first record at beacon_snoop.c:1368-1370, accumulated on every later frame at :1230-1235):

- `fuzz_ie_overruns` — the TLV walk over the beacon's information elements ended in TLV_OVERRUN with at least two trailing bytes, i.e. an element announced a length that ran off the end of the frame (beacon_snoop.c:720-730; a one-octet tail is deliberately not counted here, only in the sensor-wide `SH_PF_IE_OVERRUN` tally). The code comment calls this the "mdk4 mode m / crafted injection" shape; see The attack for why mode m is a doubtful attribution.
- `fuzz_oversize_ssid` — the SSID element (tag 0) had length > 32, which is invalid per IEEE 802.11 §9.4.2.2 (beacon_snoop.c:277-281).
- `fuzz_truncated_rsn` — an RSN element (tag 48) was present but either shorter than the 8 bytes needed to hold Version + Group Data Cipher selector (beacon_snoop.c:236) or, at 8+ bytes, cut off inside a later field by `rsn_ie_parse` (`r.truncated`, beacon_snoop.c:558-560 — the #128 class, which also raises `SH_PF_RSN_MALFORMED`).

Each is counted per frame during parse and added into the per-BSSID total, guarded against wrap at 0xffff. (Strictly the guard is `if (counter < 0xffff) counter += n` — a check before the add, not a true saturate — so a frame carrying several faults that lands when the counter is within `n` of 0xffff can still wrap; irrelevant at thresholds of 3 and 5, but "saturating" is the code comment's word, not quite the code's behaviour.) A well-formed AP leaves all three at 0.

Condition (rules_wifi_mgmt.c:1267-1288): `score = ie_overruns + oversize_ssid + truncated_rsn`; skip if `score < mgmt.fuzz_warn` (3). Fire CRIT if `score >= mgmt.fuzz_crit` (5), else WARN. Each sub-term is bounded only by its own uint16 saturation; the rule applies no per-term cap, so a single pathological counter can carry the whole score. (The header comment at rules_wifi_mgmt.c:1262-1263 says "each capped so a single pathological BSSID can't dominate"; the code does not do that — the comment is stale.)

Key (rules_wifi_mgmt.c:1279): `mgmtfuzz:<bssid>` via plain snprintf — the BSSID is the transmitter's own address, not remote-chosen text, so the typed builder is not needed. One incident per BSSID.

Detail (rules_wifi_mgmt.c:1280-1284): `BSSID <bssid> malformed IEs: <n> overrun / <n> oversize-SSID / <n> truncated-RSN - 802.11 mgmt fuzzing`. It carries the three counts and the BSSID; it does not carry a rate, a timestamp, the channel or the RSSI. Severity is chosen at :1285-1287.

Escalation is real and tested: the same BSSID moving from score 3 to score 5 emits one `alert.escalate` WARN->CRIT on the same incident (tests/test_alerts.c:9485-9511, test_lifecycle_escalation_emits_an_escalate_event). No `match_ip`, so no pcap; it does cite no evidence frames (plain `fire()`). Resolves 300 s after the last tick that re-asserted the key (ALERT_RESOLVE_AFTER_S), which in practice means 300 s after the row leaves the beacon table, since the counters never fall below threshold while it is there.

## The attack

802.11 management frames (beacons, probe responses, association frames) carry a chain of information elements, each a type/length/value triple. A receiver has to parse attacker-controlled lengths and contents before it has authenticated anything, which makes the parser an attack surface reachable by any radio in range — the endpoint-exhaustion target MITRE calls T1499 [3]. The attacker's goal is not bandwidth but a specific machine's parser or state machine: a crash, a hang, or memory corruption.

Three shapes sloth can see from the bytes:

- **IE length overrun** — an element claims a length that runs past the frame end. A naive parser walks off the buffer. mdk4's packet fuzzer (mode f, "a simple packet fuzzer with multiple packet sources and a nice set of modifiers") is the off-the-shelf generator of such frames [4]. sloth's code comments (rules_wifi_mgmt.c:1255, beacon_snoop.c:720) also name mode m, but the mdk4 README describes mode m as sending "random packets or re-injects duplicates on another QoS queue to provoke Michael Countermeasures on TKIP APs" — a TKIP MIC-failure DoS that shuts the AP down for a minute, not a malformed-IE beacon generator — so the source does not support mode m as a producer of this shape [4].
- **Oversize SSID** — an SSID field longer than the 32-byte maximum. Kismet flags the same thing (its LONGSSID alert: "Over-sized SSIDs are indicative of packet corruption ... or of an attack attempting a buffer overflow on the access point or client drivers") [9].
- **Truncated RSN** — an RSN element too short to be valid, which a parser that trusts the tag may index past.

The severe end of this class is remote code execution: Broadpwn (CVE-2017-9417, Nitay Artenstein, Exodus Intelligence, July 2017) was a heap overflow in Broadcom Wi-Fi chipsets' handling of a WMM vendor-specific IE in an association response, triggered with no user interaction by impersonating an AP the device was probing for, before any authentication ("sniff the victim's probe requests over the air, impersonate an AP that the STA is looking for, then trigger the bug without going through any authentication"), affecting most Samsung Galaxy, Nexus and iPhone models [5][6]. Butti and Tinnes documented a family of 802.11 driver crashes from malformed frames a decade earlier [7]. sloth cannot see whether any receiver actually crashed — it reports only that the malformed frames were transmitted (the standing caveat in research/mitre/T1499.md) [3].

## Evidence that proves it

What sloth records: the three per-BSSID counts in the detail line, and — because this is a wireless L2 finding with no IP flow — nothing in `--pcap-dir`. The JSONL `beacon` snapshot carries the same three fields when any is non-zero (`fuzz_ie_overruns`/`fuzz_oversize_ssid`/`fuzz_truncated_rsn`, jsonl.c:1008-1011), so a consumer can watch them move over time, which the alert `count` cannot distinguish from standing. `sensor_health` moves `SH_PF_IE_OVERRUN` (the sensor-wide parse-fault tally, sensor_health.h:222) and `SH_PF_RSN_MALFORMED` when these shapes are seen, so a rising sensor-wide fault tally alongside one BSSID's alert helps tell "one AP is malformed" from "my radio/driver is mangling frames".

To call it real: a true fuzzing attack is a *rate* — many malformed frames per second from one BSSID, counts climbing while you watch, ideally alongside a strong/nearby RSSI and perhaps a spoofed or rotating transmitter. Cross-check `[b] Beacons` for the BSSID's vendor OUI and whether it otherwise looks like a real AP. A matching `MGMT_FUZZ` on several distinct BSSIDs at once (a sweep) is a stronger attack read than one BSSID stuck above threshold.

What refutes it (benign fingerprint) depends on the shape of the count, and there are two cases. A **flat** count - a non-zero counter that stops climbing after the first few beacons, on a BSSID with an ordinary vendor OUI and a stable SSID - means only a few frames were faulty (a corrupted capture, a one-off malformed frame); it is weak evidence of anything. A count that **keeps climbing** at about the beacon rate means a fault in every beacon, and that has two readings: a driver or parser artefact, or an attacker. The classic in-tree instance of the artefact is #122/#123: drivers that deliver the FCS trailer (radiotap FLAGS 0x10 — ath9k, rt2800 in monitor mode) had their last four octets walked as an extra element, raising `fuzz_ie_overruns` by one per frame on healthy air until it saturated; both parse entry points now strip the trailer first (docs/views/beacons.md:273-278). A residual driver quirk produces the same steady per-beacon climb, so a climbing count on one ordinary-looking BSSID, with the sensor-wide parse-fault tally also rising, points at the radio/driver; many shapes, many BSSIDs, or a rate above the beacon interval points at an attacker.

## Benign causes

- **Buggy firmware / drivers.** research/mitre/T1499.md names a misbehaving driver as the common benign cause [3]; the FCS-trailer case (#122/#123) is the documented in-repo example.
- **Radio/monitor artifacts on the sensor side.** A corrupt capture (bad FCS frames passed up, radiotap misparse) can manufacture overruns. The sensor-wide `SH_PF_*` tallies are the cross-check: if the whole sensor's fault rate is high, suspect the capture, not 403 attackers.
- **Non-conformant IoT beacons.** Cheap APs and ESP-based devices sometimes emit short or odd RSNEs that trip `truncated_rsn` without malice.

## Assessment

Severity rationale: WARN/CRIT keyed on an accumulating malformed-frame score is sound, because a conformant AP sits at exactly 0 and the rule never over-claims effect (it says "malformed IEs seen", not "parser crashed"). The CRIT threshold of 5 vs WARN of 3 is a reasonable "one bad shape vs several" line. The weakness is not the thresholds but the lack of a rate: a saturating lifetime counter cannot distinguish a fuzzer sending thousands of malformed frames a second from a driver that emits one malformed IE per beacon for an hour — both eventually exceed 5.

Real-world prevalence: the tooling is real and shipping (mdk4 modes f and m) [4] and the worst case is RCE (Broadpwn) [5][6], but opportunistic fuzzing of a specific nearby AP is uncommon in practice; most field hits are firmware bugs.

Reference-host noise verdict: 501,455,737 fires on 403 keys. Because the rule counts per tick, this is not half a billion attacks — it is 403 BSSIDs that each crossed threshold and were re-counted every ~250 ms for the duration they stayed above it, summed over the capture (~1.24M ticks ≈ 86 h per key; residency is unbounded while an AP keeps beaconing, so this can be a single long-lived AP per key rather than many recurrences). The honest population is 403 BSSIDs with malformed IEs — a large number that, for one sensor, points at a driver/parse artifact affecting many APs (or the sensor's own radio) rather than 403 independent fuzzing campaigns. Recommendations: surface `observations` not `count` on the alert page (it only moves when the counts change); add a frames-per-second rate to the detail so a true high-volume fuzzer separates from a stuck-high driver; consider decaying or windowing the counters so a one-off malformed beacon does not park a BSSID above threshold for its whole residency.

Is the evidence sufficient to act? For triage, yes — it correctly flags that something in range is sending non-conformant management frames. For attribution, no: a responder should first check whether the counts are climbing (rate) and whether the sensor-wide `SH_PF_*` tallies implicate the capture, then look at `[b] Beacons` for the BSSID. If frames persist and climb from a plausible real AP, locate the transmitter; the source names no fix for the receiving parser (docs/wiki/alert-remediation.md "MGMT_FUZZ").

**Since #173.** The detail is `BSSID <b> malformed IEs (<kinds>): <band> per 100 frames heard`, the rate recommended above in per-frame form (score x 100 / `frame_count`). A driver putting one bad IE in every frame reads `50 or more`; three stray frames in ten thousand read `under 1`. The band edges sit away from 100 and 200, the figures a constant fault produces. Decaying or windowing the lifetime counters is not done. The counters still saturate at 0xffff while `frame_count` keeps climbing, so past saturation the quotient would fall with every frame (a fault in every beacon at 10/s reads `10-49` after ~18 h and `under 1` after a week); once any counter is saturated the detail reads `counters saturated, rate no longer measured` instead of a band, one change and then still. Test: `tests/test_alert_tick_rate.c`.
