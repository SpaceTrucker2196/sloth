## What the rule checks

Input is the same per-(BSSID, STA) WPS session table from `src/wps_track.c`, snapshotted under one lock (`wps_track_snapshot`, src/alerts/rules_enterprise.c:349). The window is read from the tune registry (`tune_val(TUNE_WPS_PIXIE_SUCCESS_WINDOW_S)`, default 86400 s = 24 h, line 351).

The rule is a correlation over two runs at one BSSID (src/alerts/rules_enterprise.c:353-366):
1. Outer loop: any session whose `cred_ts` is set — a run that reached **M7, M8 or Done** (M7 carries the credentials; `cred_ts` is stamped when the newest attempt first reaches that, src/wps_track.h:125-137, src/wps_track.c:125).
2. Inner loop: at the *same* BSSID, any session (any STA — "any station counts as the completer, because the rerun need not use the MAC that probed", comment lines 332-334) that `wps_track_m3_abandon()` reports as M3-abandoned, whose M3 time `m3 < cred_ts` (the abandon preceded the completion) and `cred_ts - m3 <= window`. When several qualify, the newest abandoned M3 is named (lines 363-364).

Unlike the PROBE, the silence window does **not** gate this rule (comment lines 330-331): a rerun with the cracked PIN can start at once, so waiting for a quiet minute would miss it. Severity CRIT, confidence 0. Key: `wpspixieok:<bssid>:<completing sta>` (lines 375-379). Title is `WPS_PIXIE_SUCCESS`, a deliberate short form because the kind name (24 chars) exceeds ALERT_TITLE_LEN (20), comment lines 344-345.

Two detail variants (lines 380-397): if the probing session also sent refused online guesses (`guess_n > 0`, i.e. closed attempts that reached M4 without credentials, src/wps_track.h:119-124), the detail says it "may be an online PIN brute force, not Pixie-Dust"; otherwise it attributes the sequence to Pixie-Dust. Both name both stations, the BSSID, the gap in seconds, and end "treat the PSK as exposed."

## The attack

This is the last line of Bongard's step list — "Do the full WPS protocol to get the credentials" [3]. After the offline crack (see WPS_PIXIE_PROBE) yields the PIN, the attacker reruns the WPS exchange with that PIN; the enrollee accepts both PIN halves and sends the network credentials in M7 ("E -> R M7 ... Ekwk(E-S2 || Credentials)") [3]. The product is the WPA/WPA2 passphrase — `reaver`'s stated end goal: it is "a robust and practical attack against Wi-Fi Protected Setup (WPS) registrar PINs in order to recover WPA/WPA2 passphrases" [5], and after a Pixie crack "User will have to execute reaver with the cracked PIN (option -p) to get the WPA pass-phrase" [5]. MITRE T1110.002 Password Cracking covers recovering usable credentials from captured material offline [6].

Crucially, the rule reads the *deferred* shape, not reaver's common success path. Checked against reaver's source by the repo corpus (read at commit f9b5e15) [1], a successful `reaver -K` runs pixiewps while processing M3 and, on success, swaps the cracked PIN into the *same* exchange and continues to M4..M8 — one continuous M1..M8 run with no M3 abandon, which neither Pixie rule can distinguish from an ordinary enrolment [1]. What this rule sees is the two-run case the failure paths leave: pixiewps failing or outlasting reaver's receive timeout (NACK, exit, "Send pin with -p" - a string in reaver's source, per the corpus read, not in either README [1]), or an offline crack of saved M1/M3 run separately, followed later by a run that uses `-p PIN` [1][5]. `bully` and OneShot were not checked by the corpus and are not claimed either way [1]; OneShot runs Pixie Dust through wpa_supplicant without monitor mode and has a `-w, --write` option that writes AP credentials to a file on success [9].

## Evidence that proves it

Detail fields (above) name both stations (probing and completing), the BSSID, the time gap, and — when `guess_n > 0` — the misattribution caveat. No per-alert pcap: `fire(...)` is called with `match_ip = NULL`, `match_port = 0` (line 398), as the evidence is L2 EAP-WSC. The substrate is the two `src/wps_track.c` sessions; their opcode timelines (`ev[]`, WPS_EVT_RING 16) and `cred_ts` / `abandon_m3_ts` / `guess_n` fields are the proof and are visible in the `[b]` beacon detail screen. JSONL `alert.*` records carry the T1110.002 technique, the key, and the observations/evaluations split (src/jsonl.c:574-575, 589-617).

To call it a real Pixie success, the reader wants, at one BSSID within 24 h: an earlier run that reached M3 and stopped with no M4 (the abandoned run), then a later run reaching M7/M8/Done, with `guess_n == 0` on the probing session (no refused online guesses). If `guess_n > 0`, read it as a likely *online* brute force that succeeded — still a PSK compromise, different attack. What refutes a *malicious* reading: the completing run is the operator's own known device enrolling legitimately, and the "abandoned" earlier run was a receiver gap (e.g. a --hop dwell elsewhere) in that same legitimate enrolment.

## Benign causes

Two, both named in the repo corpus [1] (Bongard's slides cover the attack, not the sensor's failure modes). First, a legitimate enrolment that completes within the window after a channel-hopping or weak-signal receiver missed the M4..M8 of an *earlier* legitimate run at the same AP, so that run read as M3-abandoned. Second, an online PIN brute force (CERT VU#723755) that succeeded after the sensor missed a single M4: that refused guess records as an M3 abandon, and the later success fires this rule — the CRIT is correct because the PSK is gone, but the attack is an online brute force, not Pixie-Dust, which is why the `guess_n > 0` detail variant exists. Telling them apart: whether the completing device is a known, authorised enrollee, and whether the probing station shows a machine-rate burst of refused guesses (points to online brute force) versus a single clean M3 abandon (points to Pixie or a receiver gap).

## Assessment

CRIT is justified by consequence: a correct firing means the passphrase is recoverable and must be changed — the detail says "treat the PSK as exposed." The rule is unusually careful about its own limits: it corroborates a sequence, does not confirm a PRNG weakness [1][3], and explicitly flags the online-brute-force misattribution. Real-world exposure tracks WPS deployment, which was near-universal by default historically [7]; the vulnerable fraction today is unquantified in sources found. On the reference host it did not fire (host data null) and is the quietest of the WPS family — it needs both a completed registration and a correlated prior abandon within 24 h, so it cannot be noisy without real WPS activity. No dedupe needed; `--tune wps.pixie_success_window_s` only sets how far back the correlation looks (floor 1 h, ceiling 1 week; the LRU session table, not this knob, bounds memory, src/tune.c:228-235). The evidence is sufficient to act: a responder should, if it is the operator's AP, immediately change the Wi-Fi passphrase, disable WPS PIN, and review devices that joined after the event [remediation: docs/wiki/alert-remediation.md]; if it is not the operator's AP, notify its owner and do not join it.
