## What the rule checks

**Input.** `s->onvif_devices[]`, the snapshot of the table `src/onvif_discovery.c` keeps from UDP/3702 SOAP-over-UDP messages the capture thread overhears (Hello, Bye, ProbeMatches, ResolveMatches; a bare client Probe carries no `Types`/`XAddrs` of its own and is not recorded as a device [1]). sloth sends nothing: there is no M-SEARCH or Probe path (MISSION §2) [1][13].

**Parsing (onvif_discovery.c:33-148).** A tag-name scan, not an XML parser: `EndpointReference/Address` (the `urn:uuid:` identity), `Types`, `Scopes`, `XAddrs` are extracted by local element name with any namespace prefix. The camera decision is `is_camera = strstr(types, "NetworkVideoTransmitter") != NULL` (onvif_discovery.c:146). Rows are keyed by UUID when present, else by source IP, and a UUID-less message never attaches to a row that has a UUID (onvif_discovery.c:15-24). `is_camera` is **sticky**: a later Bye (which carries no `Types`) cannot un-camera a row (onvif_discovery.c:179-182). The row records `kind` (the message type), `xaddrs`, IPv4/IPv6 last-seen, and is LRU-evicted by `last_seen` with the eviction counted as `evict_onvif_device` (sensor_health.h:120).

**Rule (rules_wired.c:546-567).** For every row with `is_camera`, fire. No threshold, no state check (a fully configured camera's boot-time Hello fires the same as anything else [1]).

**Key.** `"cam-wsd:<uuid>"`, falling back to `"cam-wsd:<ip>"` when the device gave no UUID (rules_wired.c:556-557). The UUID survives a DHCP lease change [1][6].

**Detail.** `"ONVIF camera at <ip> announced itself over WS-Discovery (<kind>)[, service <xaddrs>]"` (rules_wired.c:558-563). `kind` is the last message type seen; the stored strings are `Hello`, `Bye`, `ProbeMatch`, `ResolveMatch` - singular (onvif_discovery.c:131-134), even though the wrapper elements matched are the plural `ProbeMatches` / `ResolveMatches`.

**Severity.** WARN, unconditionally (rules_wired.c:564). Technique is empty by design (`include/sloth_alerts.def:170-181`, the comment block above the X line): T1046 would claim an enumeration sloth did not perform; the kind is on the named list in `tests/test_research_corpus.c :: test_uncitable_kinds_with_a_real_basis_are_still_cited` [1][3].

**pcap.** `match_ip = d->ip`, `match_port = 0` (rules_wired.c:565): with `--pcap-dir` and `pcap.min_severity <= 1`, packets to/from the camera's address export. The engine sets `match_ip` only when the incident is created (engine.c:400-401, 579-580). `d->ip` is overwritten with the source of every message (onvif_discovery.c:172), so the export filter is whichever address the camera used for the message current at the first fire. That can be its IPv6 link-local address, in which case its IPv4 traffic is not exported.

**Escalation / resolution.** None. Detail changes when `kind` or `xaddrs` change (e.g. Hello → Bye) → `alert.update` at most once per 60 s. Resolves only if the row is evicted and the key is quiet for 300 s. A **Bye does not end the incident**: the row and its sticky `is_camera` stay, so a camera that announced it left the network keeps firing every tick with the detail "...announced itself over WS-Discovery (Bye)".

## The background (this is an exposure, not an attack)

There is no attacker in this finding. WS-Discovery (OASIS, 2009) lets a Target Service make itself locatable without a directory: it multicasts a **Hello** when it joins the network, a **Bye** when it leaves, and answers any **Probe** / **Resolve** it hears with a unicast **ProbeMatches** / **ResolveMatches** describing itself [5]. The transport is SOAP over UDP to 239.255.255.250 (IPv4) / FF02::C (IPv6), port 3702 (§3.1.1) [5]. The specification "does not require that endpoints participating in the discovery process be secure" (§8.1); compact signatures are a SHOULD, not a MUST, so an unsigned Hello is conformant [5].

ONVIF, the IP-camera interoperability profile family, makes this mandatory: a compliant device "shall implement the Target Service role as specified in [WS-Discovery]" (Core Spec §7.1), the default mode "shall be the discoverable mode", a discoverable device "sends multicast Hello messages once connected to the network" and "always listens for Probe and Resolve messages", and - the spec's own threat note - "in order to thwart denial-of-service attacks, it shall be possible to set a device into non-discoverable mode" (§7.2) [6]. The Hello must carry `XAddrs` with the device-service URL (§7.3.2.3) and `Scopes` such as `onvif://www.onvif.org/hardware/…`, `/name/…`, `/location/…` (§7.3.2.2) [6]. So a conformant camera tells the whole segment its address, model, name, and the URL of its management API, unauthenticated, on every boot.

What that gives someone already on the segment: a complete camera inventory with service URLs, no packets sent (or one multicast Probe), as the step before credential attacks on the ONVIF/RTSP/HTTP services the `XAddrs` point at. IP cameras are a mass-exploitation class - Hikvision's CVE-2021-36260 (unauthenticated command injection, CVSS 9.8) was exploited at scale [9] - and the discovery protocol itself is a DDoS reflector: Shadowserver scans found 17,621 Internet-reachable WS-Discovery responders on IPv4 (2023-03-14), average amplification 293, median 305, abused since 2019 [8]. On the client side ONVIF Device Manager, python-onvif, nmap's `wsdd-discover`, and EdgeX's device-onvif-camera service all speak the Probe side; none is needed to receive a Hello.

## Evidence that proves it

**What sloth records.** `alert` / `alert.create` with `title=CAM_WS_DISCOVERY`, `sev=1`, no `technique` field (dropped when empty, jsonl-schema.md:298), key and detail above; `count` = ticks (jsonl-schema.md:297). The `device` record for the camera's IP (or MAC, if a MAC-keyed record holds the IP within `camera.join_fresh_secs`) carries `device_class="camera"`, `cam_signals` bit 1 (WS-Discovery), `camera_model` from the `name`/`hardware` scopes, and `sources` bit 64 `DEV_SRC_CAMERA` (jsonl-schema.md:699) [10]. `sensor_health.evict_onvif_device` says whether the 32-row table is churning (a UUID spray would do that, onvif_discovery.c:26-27).

**pcap.** With `--pcap-dir` and `--tune pcap.min_severity=1` (or 0), a per-alert pcap filtered to the camera's IP; the Hello itself is UDP 3702 from the camera to 239.255.255.250 and is in the capture if it recurs within the window. The `packet` record for the message carries `info` = `"WSD <kind> cam"` (onvif_discovery.c:197-199).

**What makes it a real camera.** `Types` containing `NetworkVideoTransmitter` alongside `tds:Device` - Hikvision announces `dn:NetworkVideoTransmitter tds:Device`, TP-Link Tapo `tdn:NetworkVideoTransmitter` [7] - with `Scopes` of the `onvif://www.onvif.org/...` form and an `XAddrs` such as `http://<ip>/onvif/device_service` [6][7]. A `hardware`/`name` scope naming a camera model, a `Profile/Streaming` scope [6], and an mDNS/SSDP/RTSP sighting joined on the same IP (`cam_signals` bits 4/8/32) corroborate [10].

**What refutes the "camera" label.** `NetworkVideoTransmitter` is the ONVIF type for any device that *transmits* video - a standalone encoder or an NVR re-exporting streams also uses it. The current ONVIF Core Specification (v26.06 §7.3.2.1) requires only `tds:Device` in `Types`; `NetworkVideoTransmitter` is a field convention, and the text of both v17.12 and v26.06 does not contain that QName [6][11]. So a `hardware` scope naming an encoder/NVR refutes "camera" (but not "ONVIF video device"), and - the reverse gap - a device announcing only `tds:Device` is a false *negative* for this rule.

## Benign causes

- **Every legitimate ONVIF camera, on every boot, forever.** Not a false positive in the rule's own terms, but the dominant benign case: the Hello is mandated behaviour [6] and the rule has no inventory check. The remediation page's guidance is "check it against the operator's own inventory" [4].
- **Encoders, NVRs, video servers** announcing `NetworkVideoTransmitter` [7] - real ONVIF transmitters that are not cameras.
- **A ProbeMatches answering someone else's Probe.** The operator's own VMS or ONVIF Device Manager probing the segment makes every camera answer; `kind=ProbeMatch` means *something* probed (possibly the operator, possibly not), not that an attacker did [1].
- **IPv6 link-local duplicates.** A camera announcing on both `239.255.255.250` and `ff02::c` is one row (UUID-keyed) with both addresses recorded (onvif_discovery.c:184-190); the detail shows only `d->ip`.
- **Table churn.** A sender spraying invented UUIDs evicts real rows (`evict_onvif_device` rises); the real camera then re-appears as a *new* incident after its next Hello (`reopen_count` on the alert).

## Assessment

**Severity.** The repo argues WARN because "a camera that is supposed to be there still produces this same signal: the operator's job is to recognise their own inventory" [1]. That is honest, and it is also the definition of a finding that gets muted. **Too high for the inventory-matched case.** A better ladder: LOW when the camera's MAC/IP is in `--known-macs` or the inventory, WARN when it is not, CRIT never (nothing here is an attack). The hooks exist (`--known-macs` roster, `ownership`); the rule does not read them.

**Prevalence.** Of the exposure: near-universal among ONVIF cameras (default discoverable [6]). Of attackers using it: discovery is the first step of every camera-hunting playbook, and the exploitation it precedes is well documented (CVE-2021-36260 [9]; WS-Discovery reflection since 2019 [8]). On a LAN sloth monitors, the relevant risk is the one the ONVIF spec itself names - DoS via the discovery listener - plus the inventory it hands anyone on the segment.

**Reference host.** `host:null`. Never fired. Given the mandated Hello, this means the monitored segment carries no ONVIF discoverable device, or the capture interface is not a multicast-group member / does not see link-local multicast (a mirror port that strips multicast, or a monitor-only deployment). Not a noise problem. If cameras are expected, verify `packet` records with `dst_port=3702` exist at all before concluding the segment is camera-free.

**Is the evidence sufficient to act on?** Yes for what it claims: the camera's IP, UUID, kind and service URL are exactly what an operator needs to find it in inventory or on the wall. It does not and cannot claim the camera is unconfigured, rogue or vulnerable [1]; those are `CAM_SETUP_SSID`, `CAM_MDNS_SERVICE` / RTSP, and the device-record join's job [10].

**Responder's first steps.** (1) Match UUID/IP/`camera_model` against the camera inventory and the `device` record (`cam_evidence`, `cam_vetoes`) [10]. (2) Known camera: accept, consider LOW; if it should not be discoverable, set it non-discoverable via its ONVIF `SetDiscoveryMode` (Core Spec §7.2 / §8.3.19) [6] and block 3702/udp at segment boundaries [8]. (3) Unknown camera: locate by `XAddrs` IP → switch port / DHCP lease, and remove it. Do not connect to its `XAddrs` from sloth's host; sloth only listens (MISSION §2) [13]. (4) Any camera: check firmware against the vendor's advisories; Hikvision CVE-2021-36260 is the canonical reason why [9].

## Benign vs real summary

A `Types` string with `NetworkVideoTransmitter`, `onvif://` scopes naming a camera model, and a matching `device` record with `cam_signals` corroboration is a real camera; whether it is *wanted* is the operator's inventory question, not sloth's. Only `tds:Device`, or a `hardware` scope naming an encoder/NVR, is a non-camera ONVIF device.
