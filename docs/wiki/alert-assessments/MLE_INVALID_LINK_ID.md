## What the rule checks

Input is the MLD table `s->mlds[]` (`sloth_mld_t`, keyed by MLD MAC; include/sloth.h:3516), populated by `mle_observe()` from `mle_parse()` of Multi-Link elements. `mle_parse()` is called on Beacons/Probe Responses (`src/capture/probe.c:552`) and on (Re)Association Requests (`src/assoc_track.c:202`) - the latter path, added in #129, is the one `hostapd_process_ml_assoc_req()` actually takes. The rule sits at line 63 of rules_table.c, 37th in run order.

The parser check (src/mle.c:160-186): only the Basic Multi-Link variant is decoded (`type == MLE_TYPE_BASIC`, mle.c:87). Walking the Link Info subelement chain, each Per-STA Profile (`MLE_SUBELEM_PER_STA`, slen >= 3) carries a 2-byte STA Control field whose bits 0-3 are the Link ID (`sc & 0x000f`, mle.c:171). The condition (mle.c:181): `link_id >= 15 || (seen_link_ids & (1u << link_id))` sets `malformed_link_id = 1` and records `bad_link_id`; otherwise the link_id's bit is set in `seen_link_ids`. Checked unconditionally, independent of whether an affiliated MAC follows, because the vulnerable field is the Link ID itself (mle.c:176-184). `sh_parse_fault_note(SH_PF_MLE_MALFORMED)` is called once per element at the end of the parse when `malformed_link_id` (or `malformed_subelem_len`) is set (mle.c:352-358) - so the `parse_fault_mle_malformed` counter does move with this finding, one count per offending element, not per Per-STA Profile.

`mle_observe()` (src/mle.c:420-427) adds the per-frame finding onto the MLD's persisted entry: `malformed_link_id_total++`, stores `bad_link_id`, stamps `malformed_link_id_last_seen`. This is a lifetime signal "never cleared by a later clean frame" (mle.c:419-422) - the sticky behaviour.

The rule (rules_mle.c:21-39) walks the MLD table and fires when `m->malformed_link_id_total` is non-zero. Key `mle_link_id:<mld_mac>` (plain `snprintf`, rules_mle.c:29). `ALERT_SEV_WARN`, `match_ip` NULL - no pcap, no evidence-ring citation (plain `fire()`). Detail: `MLD <mac> sent a Multi-Link Element Per-STA Profile with link_id=<bad_link_id> (valid range is 0-14; <total> such frame(s) seen) - CVE-2026-58374`. Technique `T1669` (include/sloth_alerts.def:161). No threshold - one offending frame fires; no knob.

## The attack

Wi-Fi 7 (IEEE 802.11be-2024 [14]) introduces Multi-Link Operation (MLO): one logical device, the MLD (Multi-Link Device), runs several radios ("links") under one stable MLD MAC address. In an association request, a client describes its links with Per-STA Profile subelements inside a Multi-Link Element, each tagged with a 4-bit Link ID.

CVE-2026-58374 / w1.fi advisory 2026-1 is a missing bounds check in hostapd's `hostapd_process_ml_assoc_req()` (src/ap/ieee802_11_eht.c) [5][6][7]. The Link ID field is 4 bits wide (0-15), but hostapd's `links[]` array has valid storage only for 0-14 (`MAX_NUM_MLD_LINKS` = 15, so indices 0..14) [7]. A crafted association request claiming `link_id = 15` writes out of bounds - "before the 4-way handshake and with no credential needed" [6]. The advisory's impact class is "process termination due to buffer read overflow checks and memory corruption", reachable "by sending invalid Management frames without needing authentication" [6]; the CVE record confirms the attack "does not require network credentials, prior authentication, or user interaction" and a DoS impact [5]. CVSS 3.1 base 6.5 (AV:A/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H) per the CVE record [5]. The repo's research doc gives 7.1 [1]; neither the w1.fi advisory [6] nor the oss-security post [7] carries any CVSS score, and no external source for 7.1 was found, so 6.5 is the figure to quote. Fixed in hostapd 2.12 (affected: 2.11 and newer snapshots before 2.12 with CONFIG_IEEE80211BE) [5][6]. The oss-security post names the researcher (Abhinav Agarwal), gives the fix commit, and mentions no PoC; it predates the CVE number (it records a CVE request) and is linked from the CVE record's references [5][7].

sloth has no AP process to crash and never will (MISSION §2); it detects the **frame shape that causes the crash** - a Per-STA Profile link_id of 15, or a link_id repeated inside one MLE - observed on the air before it reaches a vulnerable AP [1]. Mapped to T1669 (Wi-Fi Networks, Initial Access [11]): an unauthenticated, management-frame-driven association is the access vector.

## Evidence that proves it

What sloth records:

- `alert` / `alert.create` JSONL: `title MLE_INVALID_LINK_ID`, `key mle_link_id:<mld_mac>`, `sev 1`, `technique T1669`, `count` = evaluations. The offending `link_id` value and the lifetime count of such frames are in `detail`.
- The `wifi_mld` JSONL record for the MLD MAC: `mld_mac` (the stable identity captured even from a malformed frame, because the Basic MLE's MLD MAC sits at a fixed offset read before any attacker-controlled length, src/mle.c:118-122), `link_N_mac`, `links_truncated` (docs/wiki/jsonl-schema.md:711).
- sensor_health `parse_fault_mle_malformed` - "a Multi-Link element (beacon or association request) whose declared lengths or link IDs are the CVE-2026-58374 shapes the MLE_* alerts report per MLD" (docs/wiki/jsonl-schema.md:1262-1266). This counter moving in step with the alert is corroboration that the parser, not a higher layer, saw the bad value. Note it rides the heartbeat and is not in the change-only signature.
- No pcap and no evidence-ring citation: the rule uses plain `fire()`, not `fire_ev()`. (The sibling `MLE_SUBELEM_OVERRUN` and the reconfiguration rules cite evidence-ring frames; this one does not - the raw bytes are not retained for it.)

To call it real, a reader should see a `wifi_mld` record for the same MLD MAC and a `parse_fault_mle_malformed` increment at the alert time, with the detail naming `link_id=15` (or a repeated id). Because the MLD MAC is captured even on a malformed frame, the transmitter's asserted identity is always present - useful for locating the source, though the MAC is attacker-chosen and may rotate.

What would refute it: nothing benign produces `link_id >= 15` - the research is explicit that "there is no benign reason a conformant MLD would ever send it" [1]. A repeated link_id within one MLE is likewise never legal. So unlike the rate rules, there is no benign-fingerprint column here; the frame is malformed by definition.

## Benign causes

There are none that produce a *correct* reading. The only non-adversarial explanations are instrument error, not AP misbehaviour:

- **A buggy or experimental Wi-Fi 7 implementation** emitting a non-conformant MLE. This is still worth surfacing - it is a malformed management frame regardless of intent - but it is not an attack. No such implementation is documented in the fetched sources.
- **A sloth parse error** mis-reading a legal field as link_id 15. The parser reads the 4-bit field directly (`sc & 0x000f`, mle.c:171) and the repo's `tests/test_mle.c` builds the adversarial inputs per the IEEE clause by hand, so this is low-likelihood, but a single hit on hardware known to be conformant warrants checking the capture.

A patched hostapd (2.12+) is still worth alerting on: 2.12 fixes the OOB write but does not make `link_id = 15` legal, so the frame remains malformed and an operator with any unpatched Wi-Fi 7 AP on the segment needs to know regardless of which firmware the sender was probing for [1].

## Assessment

**Severity.** WARN is the rule's choice and is defensible on the stated ground - sloth detects the frame, not a confirmed crash, and cannot see the target's process state or patch level [1]. But the underlying input is an unauthenticated pre-association memory-corruption trigger with no benign reading, so a responder should treat a single hit as actionable rather than informational. One could argue for CRIT (the sibling `MLE_SUBELEM_OVERRUN` is CRIT, on the ground that it reports an overrun that has *already* happened rather than a value *shaped* to cause one - rules_mle.c:74-98); the WARN/CRIT line the repo draws is "value shaped to crash" vs "chain already overrun", and this rule is the former.

**Prevalence.** New and rare. The CVE published 2026-06-30 [5]; no public PoC or in-the-wild use is mentioned in [7] or was found in the fetched sources. Wi-Fi 7 deployment is early (802.11be-2024 published 2025-07-22 [14]), so both the vulnerable surface and any tooling are nascent. An operator seeing this today is more likely looking at a research/fuzzing tool or a buggy early implementation than a mature attack campaign - but the input is genuinely dangerous and cheap to craft.

**Noise on the reference host.** Not seen (null). Sticky per MLD MAC: one key, re-firing the same incident with a rising detail tally, not new incidents. The per-frame concern in the task prompt is handled by the stickiness - `malformed_link_id_total` counts frames in the detail, but `count` (evaluations) rises per tick while the sticky flag holds. Because the MLD table never ages an entry out, "while the flag holds" means for the life of the process unless 64 newer MLDs push the entry out by LRU: a single frame yields one row that never resolves, with count ~345,600 after a day. That is one quiet row, not noise, but an operator should not wait for it to clear. Rotating MLD MACs do fan out - one key per MAC, up to 64 live at once (`SLOTH_MLD_MAX`, mle.c:369-379), with evicted ones resolving after 300 s and new ones opening - so the bound is the table size, not one row. The eviction itself is not counted in sensor_health; only `parse_fault_mle_malformed` moves, once per offending element. A 64-row ceiling is tolerable against `MAX_ALERTS` 128; no dedupe or knob added here.

**Is the evidence sufficient to act on?** To know a crash-shaped frame was transmitted, yes. To know a specific AP crashed, no - sloth is a passive receiver sharing the channel, not the target's process table [1]. First response (docs/wiki/alert-remediation.md:1327-1343): note the MLD MAC; check whether any Wi-Fi 7 AP on the segment runs hostapd older than 2.12; update to 2.12+; locate the transmitter. Vendor fix is hostapd 2.12 (CVE-2026-58374, w1.fi 2026-1).

**Gaps.** No evidence-ring wiring (no retained bytes), so the finding rests on the detail plus `wifi_mld`/`parse_fault_mle_malformed` rather than on the frame itself. Two parse-time drops happen before the link_id check is reached and are false-negative paths: an element shorter than 10 octets is refused outright (mle.c:78), and an MLE whose MLD MAC is all-zero or group-addressed is refused at mle.c:121-122 (`mac_is_usable()`, mle.c:18-22). The hostapd bug does not depend on the MLD MAC value, so a crafted frame with a zero MLD MAC reaches a vulnerable AP and is invisible to this rule. No alert resolution while the MLD entry stays in the table (no age-out), so a cleared incident means eviction or restart, not that the sender stopped. The CVSS figure differs between the CVE record (6.5) [5] and the repo's research doc (7.1) [1]; no external source for 7.1 was found.
