## What the rule checks

Input: `s->bgp_sessions`, the BGP session table of `MAX_BGP_SESSIONS` = 32 rows keyed by the **canonicalised peer pair** - the two IPs sorted lexically so either direction lands on one row (`include/sloth.h:329-347`; `src/bgp_snoop.c:79-84`). `bgp_snoop_observe()` takes any TCP payload with 179 on either side (`:44`; dispatched from `src/capture/capture.c:713-718`) and walks it as back-to-back BGP messages: 16 bytes of `0xFF` marker, a 2-byte length in 19..4096, a 1-byte type (`:24-38`, `:53-75`), per the RFC 4271 §4.1 header whose marker "MUST be set to all ones", whose length "MUST always be at least 19 and no greater than 4096", and whose types are 1 OPEN, 2 UPDATE, 3 NOTIFICATION, 4 KEEPALIVE [3]. It stops at the first bad marker, bad length, truncated tail or unknown type (`:59-63`, `:71`). The per-segment tallies are added to the row's `open_count`, `update_count`, `notification_count` and `keepalive_count` (`:97-100`). The observer keeps no per-segment state, so a TCP retransmission of a segment carrying a NOTIFICATION is counted again. Nothing inside a message is parsed - no error code, no ASN, no NLRI (`docs/wiki/bgp-snoop.md:109-123`).

Per tick the rule fires for any row whose `notification_count` is at or above `BGP_NOTIFICATION_BURST_THRESHOLD` = `tune_val(TUNE_BGP_NOTIFICATION_BURST)` (`src/alerts/rules_wired.c:983`, `:988`), default **3** (`src/tune.c:57`: `bgp.notification_burst`, min 2, max 1000, unit "NOTIFICATIONs"). Key: `bgp-notif:<peer_a><><peer_b>` (`:990-992`). Detail: `"<a> <-> <b>: <n> BGP NOTIFICATION messages (session-instability or hijack-precursor; opens=<o> updates=<u> keepalives=<k>)"` (`:993-999`). CRIT, `match_ip` = `peer_a` - the lexically smaller address, not necessarily the peer that sent the NOTIFICATIONs - and `match_port` 179 (`:1000-1002`; `docs/wiki/bgp-snoop.md:68-74`). The incident resolves 300 s after the last tick that re-asserted it (`include/sloth.h:860`). The 32-row table evicts the least-recently-seen pair when full (`STAB_OLDEST`, `src/bgp_snoop.c:21-22`; `src/stab.h:27`; tallied as `evict_bgp_session`, `src/sensor_health.h:94`) and never expires rows by age.

The gate is `notification_count` alone; the other three counters are reported for context but do not affect the decision. A session protected by TCP MD5 under RFC 2385 still carries the all-ones marker under RFC 4271, so the "MD5 sessions are skipped" note in `docs/wiki/bgp-snoop.md:128-132` describes the pre-4271 marker semantics; what the parser actually requires is the RFC 4271 marker [3].

## The mechanism

BGP-4 "listens on TCP port 179" [3]. "A NOTIFICATION message is sent when an error condition is detected. The BGP connection is closed immediately after it is sent" (RFC 4271 §4.5), and §6 says that when any error condition it lists is detected "a NOTIFICATION message, with the indicated Error Code" is sent; the Cease code (§6.7) is the one a peer "MAY choose, at any given time" to send absent a fatal error [3]. So each NOTIFICATION is a session teardown, and a session that keeps tearing down keeps both routers withdrawing and relearning routes - the resource exhaustion the corpus maps to T1499: "Each NOTIFICATION tears the session down and forces a full re-convergence, and a peer that keeps sending them keeps a router doing expensive work" [1]. MITRE's T1499 is "Endpoint Denial of Service (DoS) attacks to degrade or block the availability of services", performed "by exhausting the system resources those services are hosted on" and, unlike a network DoS, "without saturating the network" [2].

The adversarial reading comes from RFC 4272, the BGP security vulnerabilities analysis: BGP "was originally designed with little consideration for protection of the information it carries"; of a spoofed NOTIFICATION it says "the ability of an outsider to spoof this message can lead to a severe disruption of routing over a wide area" (§3.1.4), and of a spoofed RST "the BGP speaker would bring down the connection" (§3.2.1.4); deleting routes after a session drop "can cause a cascading effect in which routing changes propagate through other peers" (§3.1.2); TCP MD5 (RFC 2385) "can counter this attack" (§3.2.1.1) [4]. The rule's comment adds a hijack-precursor framing - an on-path actor tearing down the legitimate session before announcing competing prefixes (`src/alerts/rules_wired.c:972-982`) - which is an inference about intent, not something the counter observes. The mitigations the operations BCP recommends are the ones that also make spoofing impossible: an ACL "that would discard all packets directed to TCP port 179 on the local device" from anyone but configured peers (RFC 7454 §4), TCP-AO ("SHOULD be preferred when implemented") or MD5 on the session (§5.1), and GTSM, which "effectively prevents all spoofing attacks" on directly connected peerings (§5.2) [5].

The corpus is explicit about the benign reading: "A flapping BGP peer with a real link problem produces BGP_NOTIFICATION_BURST honestly ... These are the benign triggers, and they are common" [1].

## Evidence that proves it

What sloth records:

- `alert` / `alert.*` JSONL under `bgp-notif:<a><><b>` with all four message counters in the detail;
- `bgp_session` state records keyed on `(peer_a, peer_b)` (`docs/wiki/jsonl-schema.md:728`): `open_count`, `update_count`, `notification_count`, `keepalive_count`, `first_seen`, `last_seen`;
- a per-alert pcap if `--pcap-dir` is set (CRIT passes the default `pcap.min_severity` 2, `src/tune.c:121`); the filter is `match_ip` = `peer_a` and port 179 either side (`src/alert_pcap.c:104-114`), so the file holds that peer's BGP from the ring - including the NOTIFICATION bodies, whose Error Code and Subcode (RFC 4271 §4.5, §6 [3]) the rule does not parse but a responder can read in Wireshark.

What distinguishes an attack from a flap: NOTIFICATIONs in the pcap arriving from an address or TTL that is not the configured peer (a spoof; GTSM exists to reject these [5]); an error code the real peer's logs do not show it sending; `open_count` climbing in step with `notification_count` (re-establishment after each teardown, `docs/wiki/bgp-snoop.md:100-102`) followed by UPDATEs carrying prefixes the operator does not expect from that neighbour (`:103-107`). The routers' own logs are the deciding source: they record which side sent each NOTIFICATION and why [1], `docs/wiki/alert-remediation.md:345-361`.

What refutes it: the error codes are Hold Timer Expired or a Cease the operator's own change window explains; the link shows errors or congestion in its own counters; the pcap shows the NOTIFICATIONs coming from the genuine peer address with the expected TTL. A single maintenance evening can produce three honest NOTIFICATIONs that then stand for the life of the row.

## Benign causes

- **Flapping peer.** A link with a real problem - congestion, MTU mismatch, a mis-tuned hold timer - resets the session repeatedly and produces this alert honestly; the corpus names it as common [1], and the wiki lists the same causes (`docs/wiki/bgp-snoop.md:76-84`).
- **Operator resets and config pushes.** Cease is the NOTIFICATION a peer "MAY choose, at any given time" to send [3]; three administrative resets over the life of a row (a config change, a capability mismatch fixed by a push, a planned failover) reach the threshold because the counter is a lifetime total (`src/bgp_snoop.c:99`; no `stab_expire`).
- **TCP retransmission.** The walker keeps no per-segment state (`src/bgp_snoop.c:46-75`), so a retransmitted segment that carries a NOTIFICATION increments the count again; on a lossy link, one logical NOTIFICATION can count two or three times.
- **Route flap dampening is a different thing.** The BCP's dampening (RFC 7454 §7) penalises oscillating *routes* [5]; this rule counts session teardowns, so a dampened prefix storm does not fire it, and the alert says nothing about prefix stability (`docs/wiki/bgp-snoop.md:121-123`).

## Assessment

Surfacing three session teardowns on one peering is sound: a healthy session carries only KEEPALIVEs every minute or so (`docs/wiki/bgp-snoop.md:86-95`), and each teardown is a real availability event for the routes that session carried [1], [3]. The caution is about the label. The detail offers "session-instability or hijack-precursor" as alternatives, and the second is an inference the rule has no evidence for, since it does not parse error codes, sender identity beyond the pair, or what the post-re-establishment UPDATEs announced. An operator who reads "hijack" from a firing whose actual cause is a flapping link has been misled by the wording, not informed by it. Two refinements worth considering: window `notification_count` so "burst" means what it says (the comment already talks of an "active aggregation window" that the code does not implement), and parse the NOTIFICATION Error Code into the detail, which costs two bytes of decode and turns "3 NOTIFICATIONs" into "3 x Hold Timer Expired" or "3 x Cease", the fact a responder reaches for first.

Prevalence: the spoofed-teardown case is documented in the protocol's own security analysis [4] and its mitigations are standard operations practice [5], but the corpus and the wiki both put the honest flapping peer first [1]; no fetched source quantifies a field rate, so none is claimed.

Reference host: not seen (null) - consistent with no BGP on the monitored segment; a LAN sensor will only ever see this on a peering link, a data-centre fabric, or a lab. The behavioural note for an operator who deploys it there: the counter never decays, so after one unstable night the pair stands as an incident until 32 newer pairs evict it, which on a fabric with a fixed set of peers may be never; a persistent `bgp-notif` key is more likely history than an ongoing problem, and `last_seen` on the `bgp_session` record is the field that says which.

Sufficient to act on alone? No - it says which peering to look at. A responder should (1) identify the two peers and read the routers' logs for which side sent each NOTIFICATION and its error code [1], `docs/wiki/alert-remediation.md:345-361`; (2) open the per-alert pcap and check the NOTIFICATION source address and TTL against the configured peer - a spoof from off-path is the attack, the real peer resetting is the flap [4], [5]; (3) if a flap, repair the link or configuration; if a third party, filter port 179 to configured peers and enable TCP-AO or MD5 and GTSM [5]. Tuning: raise `bgp.notification_burst` on a fabric with a known-unstable link only after the link is understood; lowering to 2 is reasonable on a peering that should never reset.
