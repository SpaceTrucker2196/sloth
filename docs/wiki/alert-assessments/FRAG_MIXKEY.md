## What the rule checks

Two inputs, both on the monitor thread.

1. **Fragment sessions.** For every fragmented data frame (`fragmented = fn > 0 || more`, `src/fragattack.c:488`; fed from `src/capture/probe.c:535` on every data frame, Protected or not), `frag_track()` (`:320`) keys a session on `(BSSID, SA, DA, TID)` (`sess_key_t`, `:108-111`). Fragment number 0 opens or replaces the session (`:324-327`; `sess_open`, `:289-309`), recording `start_protected` (`:303`) and `start_generation = eapol_key_generation(bssid, sa)` (`:325`, `:304`). A continuation with no session on file is dropped (`:333-334`).
2. **PTK generation.** `eapol_log.c` keeps a per-`(BSSID, STA)` counter (`pending_t.generation`, `src/eapol_log.c:95-103`) that increments when an **M3 carries an ANonce different from the one last installed** (`:798-816`), not merely when an M3 arrives, because an AP retries M3 verbatim when M4 is lost. `eapol_key_generation()` (`:1288-1294`) returns 0 when no pairing row exists.

Condition (`src/fragattack.c:358-372`): on a continuation fragment, all of

- the continuation is Protected and the session's fragment 0 was Protected (`:366`) - a mismatch is `FRAG_MIXED`'s finding;
- `start_generation > 0` (`:366`) - sloth witnessed an install for `(BSSID, SA)` before the session opened; 0 means no evidence, not generation zero;
- `eapol_key_generation(bssid, sa) > start_generation` (`:367`) - a new-ANonce M3 for this pair arrived after fragment 0.

Then `mixed_key++` and `last_sa/last_da/last_hit` (`:368-371`). The increment is per continuation regardless of `more`; the session closes only on `!more` (`:404`). Three things the condition does **not** check, from the code: the **sequence number** (`seq_ctrl` is stored at `:307` and read only by the PN-gap branch at `:390`); **age** (a session lives until replaced by a new fragment 0, closed by `!more`, or evicted from the 128-row STAB_OLDEST table, `:122-123`); and **direction** - the generation lookup is keyed on SA, which on a downlink (FromDS) frame is Address 3, the AP or a wired host, for which no handshake row exists, so `start_generation` is 0 and the branch is silent for AP-to-station reassemblies.

`rule_fragattack()` fires `ALERT_TYPE_FRAG_MIXKEY` at CRIT when `mixed_key > 0` (`src/alerts/rules_twin.c:713-725`). Key `fragmixkey:<BSSID>` (`:714`). Detail `"%u reassembly%s on %.17s spanned a completed key rotation - last %.17s -> %.17s (CVE-2020-24587)"` (`:715-719`). `match_ip` NULL, `match_port` 0 (`:723-724`): no per-alert pcap (`src/alert_pcap.c:105`). Resolution is 300 s after the last re-assert (`include/sloth.h:860`), which only happens on BSS-row eviction (`src/fragattack.c:47-48`) or restart. `last_sa`/`last_da` are shared by every FragAttacks branch on the row.

## The mechanism

"The 802.11 standard does not require that each fragment was decrypted using the same key. Therefore, an attacker can forge frames by mixing fragments of frames that were encrypted under different keys, i.e., by mixing fragments belonging to different security contexts" [2, Section 4.1]; CVE record: "doesn't require that all fragments of a frame are encrypted under the same key. An adversary can abuse this to decrypt selected fragments when another device sends fragmented frames and the WEP, CCMP, or GCMP encryption key is periodically renewed" [3]. The attack (Figure 4) is a multi-channel MitM: in stage 1 the adversary induces the client to send a two-fragment packet toward the adversary's server and forwards only its first fragment, `Enc^n_k{Frag0(s)}`, to the AP; "Before stage 2 starts, the client and AP must update, i.e., rekey, the pairwise session key from k to l using the 4-way handshake" - rekeys are predictable because they are periodic and "can be detected because they cause the packet numbers of the data-confidentiality protocol to restart from zero"; in stage 2 the adversary takes a fragment of the client's sensitive packet, encrypted under `l` with packet number n+1, relabels it with sequence number s (unauthenticated) and forwards it; the AP reassembles the two, and "the resulting frame ... exfiltrat[es]" cookies, POST data or basic-auth credentials sent over plaintext HTTP [2, Sections 4.3-4.4]. The fragments "must have consecutive packet numbers since the receiver will otherwise discard the fragments" [2, Section 4.3], so this is the attack that works even against a standard-compliant receiver.

The passively observable footprint: on the AP's channel, the adversary's forwarded frames carry the client's MAC as transmitter, so sloth sees fragment 0 of `(BSSID, client, DA, TID)`, then the 4-way handshake's M3 with a new ANonce for `(BSSID, client)`, then a Protected continuation on the same tuple - exactly the condition above. The corpus document is explicit that this needed state the tool did not have before slice 4 [1]. What sloth cannot know is whether the AP accepted the reassembly; a patched receiver drops it (Linux: "Prevent mixed key and fragment cache attacks" - a fragment whose key colour differs from the cache entry's is dropped [10]).

Tooling: `ping I,F,BE,AE` ("Inject two fragments encrypted under a different key"), `--pn-per-qos` for targets that enforce consecutive PNs, `ping I,F,BE,E` when the new key installs late [5].

## Evidence that proves it

What sloth records: `alert`/`alert.create` JSONL under `fragmixkey:<BSSID>` with the detail; the sloth.db `alerts` row for the key; the `[c]` view row with `mixed_key`, the pair, age and gate count (`docs/views/fragattack.md`). Independently, `eapol_log` records the handshakes it saw (the `eapol` JSONL records and, with `--collect-handshakes`, the handshake pcaps), so the M3 that moved the generation is itself on file. No per-alert pcap for this rule.

What makes it real: for the named `(BSSID, SA)`, (a) a Protected fragment 0 with sequence number s; (b) a 4-way handshake for that pair, M3 carrying a **new** ANonce, strictly between; (c) a Protected continuation fragment with the **same sequence number s** and fragment number > 0. In the attack the continuation's packet number is the first key's n+1 under the new key, and its payload is the client's own traffic re-addressed to the adversary's server [2, Section 4.3]. Whether the two share a sequence number is the signal sloth's session key does not enforce, so it is the first thing to confirm from an external capture.

What refutes it: the continuation's sequence number differs from the opening fragment's (a stale session matched by the sequence-blind key); or the generation moved because the client **reconnected** (deauth, roam, power-save loss) rather than rekeyed, and both fragments are that client's own resumed traffic. Because sloth does not decrypt or reassemble, the payload cannot be shown from the alert.

## Benign causes

- **Reconnect between a stale fragment 0 and an unrelated continuation.** On a hopping radio sloth misses last fragments, so sessions stay open (no age bound, `src/fragattack.c:122-123`); the client reassociates and runs a fresh 4-way handshake (new ANonce, generation+1, `src/eapol_log.c:812`); sloth then hears a continuation of a new MSDU on the same `(BSSID, SA, DA, TID)` whose fragment 0 it also missed. The sequence-blind match (`:333`) counts it. Fingerprint: `FRAG_CACHE` fires on the same BSS in the same minute (the reassociation also satisfies its condition, `:340-342`), `--hop` in the run flags, `frag_session` evictions in `sensor_health`, and sequence numbers that do not line up on an external capture.
- **Periodic PTK rekey mid-burst on a non-conforming transmitter.** A transmitter that fragments one MSDU across a key change is itself the receiver's problem, and the paper notes most APs do not rekey the pairwise key by default [2, Section 4.7], so this is rare; when it happens it is a stack bug worth knowing about, not a false signal.
- **A retransmitted continuation.** Counted again (`:366-372` runs per continuation frame), inflating the detail integer, not creating a hit.

## Assessment

CRIT fits the thing named: a reassembly whose halves were encrypted under two keys is the CVE's own failure mode and has no conforming transmitter cause. The confidence sloth actually has is lower than the name suggests, because what it can prove passively is "a fragment 0, then a new-ANonce M3 for the sender, then a continuation on the same address tuple", and the tuple omits the sequence number that would bind the two fragments to one MSDU. Two refinements would make the alert match its evidence: require `(sc & 0xfff0) == s->seq_ctrl` on this branch as the PN-gap branch already does (`src/fragattack.c:390`), and age sessions out (the paper's Linux reference point is two seconds [2, Section 4.6]). A WARN when the sequence numbers differ, CRIT when they match, would be truer still. The downlink blind spot (generation keyed on SA, so AP-originated reassemblies never qualify) is worth stating in the detector's docs: the paper's main attack targets the AP's reassembly of client traffic, which is the covered direction, but its client-side variant (Section 4.4) is not.

Prevalence: a design flaw present since 1997 and in every unpatched fragmentation-capable stack, but the default attack needs periodic pairwise rekeying, which the author found most APs do not do, and which is why the project site calls it theoretical [2, Sections 4.6-4.7][4]; the paper's own workaround is the non-consecutive-PN bug (`FRAG_PN_GAP`), not this one. CVSS reflects that: NVD 2.6, Cisco 4.8 [3][6]. No in-the-wild use reported [4][7].

Reference host: not seen (null). Read against the count semantics, a single hit would present as one permanent CRIT on one key advancing at least 4 evaluations a second until the BSS row is evicted, with the real fragment count in the detail; the siblings on this host measured the family's steady rate at an order of magnitude above the floor.

Sufficient to act on alone? No - a lead. A responder should (1) open the `[c]` view for the pair and check whether `FRAG_CACHE` fired on the same BSS at the same time (reconnect artefact, likely); (2) pull the handshake record for `(BSSID, SA)` from the `eapol` JSONL / handshake pcap to see whether the generation moved on a reassociation or on a rekey with no reassociation (a rekey is the attack's precondition); (3) capture the channel externally and confirm the two fragments share a sequence number; (4) if they do, treat the AP as the vulnerable receiver and patch it against the vendor advisory [9], per `docs/wiki/alert-remediation.md:1156-1169`. There is no tuning knob; on a `--hop` deployment expect the reconnect artefact and weigh the alert accordingly.
