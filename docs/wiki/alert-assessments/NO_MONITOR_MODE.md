## What the rule checks

Input: `s->ifaces` and `s->iface_count` (`include/sloth.h:3358`), an array of `iface_stat_t` whose `mode` is an `iface_mode_t`: `UNKNOWN`, `ETHER` (ARPHRD_ETHER, loopback, virtuals), `WIFI` (ARPHRD_IEEE80211, managed/station) or `MONITOR` (ARPHRD_IEEE80211_RADIOTAP / PRISM) (`include/sloth.h:42-54`). The platform fills it every poll through the vtable (`src/poll.c:77`). The Linux backend reads `/sys/class/net/<if>/type`, the ARPHRD value, and classes 803 or 804 as `MONITOR`, 801 as `WIFI`, anything else as `ETHER` (`src/platform/linux.c:74-89`); the comment at `:74-79` calls 804 "ARPHRD_IEEE80211_PRISM (older monitor mode)". The kernel header disagrees: `ARPHRD_IEEE80211_PRISM` is 802 and 804 is `ARPHRD_IEEE802154`, with `ARPHRD_IEEE802154_MONITOR` at 805 [7]. The capture side is stricter and consistent with the header: the probe interface auto-discovery accepts type 803 only (`src/capture/probe.c:171`). So an 802.15.4 interface would satisfy this rule without being a radio sloth could capture on, and a Prism-header monitor interface would raise it while being one.

Per tick `rule_no_monitor_mode()` (`src/alerts/rules_wifi_mgmt.c:759-768`) returns with no fire while the snapshot is empty, so the alert does not fire in the boot window before the first interface read (`:760`; `tests/test_alerts.c:3330-3337`), returns on the first interface whose `mode` is `MONITOR` (`:761-763`), and otherwise fires WARN with title `NO_MONITOR_MODE`, a fixed detail saying that no WiFi radio is in monitor mode and the WiFi SIGINT views will be empty, the key `nomon:global`, and no `match_ip` or `match_port` (`:764-767`). With no `match_ip` the per-alert pcap matcher returns 0 before anything else (`src/alert_pcap.c:104`), so no pcap is ever written for it, which is right: there is no flow to show. The rule runs right after `rule_weak_tls` and before `rule_bt_own_transmit`, the other own-state rule (`src/alerts/rules_table.c:98-100`). The engine increments `evaluations` (the `count` alias) on every tick's `fire()` under the open key (`src/alerts/engine.c:475-481`); the comment above the rule (`:753-758`) says the key "prevents re-firing every poll", which is true of incidents and false of the counter, and that once an operator flips a radio into monitor mode "the alert row stays but stops counting up", which is exactly right, after which the incident resolves 300 s later (`include/sloth.h:860`; `src/alerts/engine.c:927-935`). The engine's expiry test is `last_evaluated`, not `last_observed`, and the comment names this rule as the reason: a standing condition "renders the same detail forever" and must not resolve and re-create every five minutes (`src/alerts/engine.c:920-926`; `docs/views/alerts.md:43-48`). The technique is the empty string (`include/sloth_alerts.def:55-56`), pinned by `tests/test_research_corpus.c:339-357` (`test_own_state_kinds_are_named`) and `tests/test_alerts.c:3374-3378`. Tests of the rule itself: `tests/test_alerts.c:3308-3337`.

## The mechanism

There is no adversary here, so the mechanism is what monitor mode is and what sloth loses without it.

An 802.11 adapter in its normal mode filters by network and by address before anything reaches the host. The Wireshark capture guide puts it in two sentences: "Even in promiscuous mode, an 802.11 adapter will only supply to the host packets of the SSID the adapter has joined", and management and control frames "are discarded by most drivers, and hence they do not reach the packet capture mechanism"; whereas "In monitor mode the SSID filter mentioned above is disabled" and "all packets of all SSID's from the currently selected channel are captured" [4]. tcpdump's `-I` states the cost: monitor mode "is supported only on IEEE 802.11 Wi-Fi interfaces", and "in monitor mode the adapter might disassociate from the network with which it's associated" [5]. On Linux the mode is set through nl80211; `iw` is "a new nl80211 based CLI configuration utility for wireless devices" and creates a monitor interface with `iw phy phy0 interface add moni0 type monitor` [6]. Once the kernel has done that it reports the interface's link type as `ARPHRD_IEEE80211_RADIOTAP` (803), "IEEE 802.11 + radiotap header", against 801 for a plain 802.11 station interface [7] - and that number in `/sys/class/net/<if>/type` is the whole of what sloth reads (`src/platform/linux.c:80-87`). Frames from such an interface arrive with a radiotap header, "a de facto standard for 802.11 frame injection and reception" that supplies "additional information about frames, from the driver to userspace applications" behind `it_version`, `it_len` and `it_present` [8]; libpcap names the link type `LINKTYPE_IEEE802_11_RADIOTAP` (127), "Radiotap link-layer information followed by an 802.11 header" [10]. sloth applies the radiotap Flags octet before parsing - `0x10` "frame includes FCS", `0x20` "frame has padding between 802.11 header and payload (to 32-bit boundary)", `0x40` "frame failed FCS check" [9] - as `docs/wiki/monitor-mode.md:136-148` describes.

What that buys, and so what the alert says is missing, is the management-frame class: every AP in range with its SSID, BSSID, channel and RSN posture from beacons; every client in range and its PNL from probe requests; who is on which AP from association frames; the WPA2 4-way handshake and PMKID; the sequence-number trail that survives MAC randomisation; attack frames on the air (deauth and disassoc floods, forged action frames, fragmentation attacks, evil-twin beacons, KARMA responses); and a per-frame dBm reading (`docs/wiki/monitor-mode.md:46-66`). "A managed-mode NIC sees none of the above. This is why the NO_MONITOR_MODE alert exists: if sloth sees interfaces but none in monitor mode, it says so, because every WiFi SIGINT view will be empty" (`:67-69`). The capture-scope table lists the same set as the Monitor scope: beacons, probes, PNLs, associations, EAPOL, deauths, the channel mix "and every 802.11 detector" (`docs/wiki/capture-scope.md:36`). sloth never sets the mode itself; that is done with `iw` or `airmon-ng` before sloth starts (`docs/wiki/monitor-mode.md:13-14`, `:71-80`; `docs/wiki/what-sloth-does.md:101`), and under the shipped unit by `sloth-monitor-up` as `ExecStartPre` (`docs/wiki/deployment.md:149`; `packaging/bin/sloth-monitor-up:22-24` is `ip link set down`, `iw dev set type monitor`, `ip link set up`).

Why the corpus names it without citing a source: `docs/wiki/research-corpus.md:361-370` calls it "the kind that will never be cited" - "It is sloth's own operational state, not a claim about an adversary, and there is no CVE, advisory, technique or clause to cite for it", which is why `alert_technique()` returns `""` and `research/coverage.c` reads that rather than a second list [3]. Two corpus documents then use it as the reference case when a later kind needed an empty technique for a different reason: `research/papers/ws-discovery-onvif.md:81-83` says `OPEN_SETUP_AP` "and `ALERT_TYPE_NO_MONITOR_MODE` settled the same shape of question before this: a cited basis with no ATT&CK ID is still a real basis" [1], and `research/papers/nist-sp1800-36-onboarding.md:56-59` draws the line: "that one reports sloth's own rig, this one reports an observed third-party device" [2]. `docs/wiki/alerts.md:430-435` and `:713-714` state the same two-form rule.

## Evidence that proves it

What sloth records:

- `alert` / `alert.create` ... `alert.resolve` under `nomon:global`; `count` is the number of ticks the condition held (`docs/wiki/jsonl-schema.md:391`), so a count of 1 is one tick and a count in the millions is a wired-only deployment;
- the `--db` `alerts` row, one for the whole process life unless the condition clears and returns;
- `iface` state records naming each interface with its counters (`docs/wiki/jsonl-schema.md:695`) - they do not carry the mode, which is shown in the TUI interfaces view as `MON` / `[monitor]` (`src/views/iface.c:39`, `:629`);
- no per-alert pcap (no `match_ip`, `src/alert_pcap.c:104`).

What confirms it on the host: `iw dev` lists no interface of `type monitor`, and `cat /sys/class/net/<if>/type` reads 801 (or 1) for every interface rather than 803 [6], [7]. What refutes it: an interface whose type reads 802 (a Prism-header monitor interface) - the alert is then a false fire by the 803/804 check, and the capture auto-discovery would miss that interface too (`src/capture/probe.c:171`). What explains a one-tick fire: the interface read happened while the radio was between modes or before it enumerated; `ip link set down`, `iw ... set type monitor`, `ip link set up` is three kernel operations (`packaging/bin/sloth-monitor-up:22-24`), and a radio that re-enumerates is handled by `BindsTo=` and a restart rather than a reopen (`docs/wiki/monitor-mode.md:118-122`).

## Benign causes

- **Startup ordering.** The first non-empty interface snapshot arrives before the radio reports type 803; the rule reads sysfs each poll (`src/platform/linux.c:80-87`), so the next tick clears it and the incident resolves 300 s later. The shipped unit runs `sloth-monitor-up` before `ExecStart` (`docs/wiki/deployment.md:149`) precisely to avoid this, so a fire under it is a re-enumeration or a slow mode switch, not a missing step.
- **A wired-only deployment.** An operator running sloth as an IP monitor with no Wi-Fi radio sees this alert permanently, counting up every tick. It is correct - the 802.11 views and detectors are empty - and there is no knob to silence it; the opposite stance, `--monitor-only`, fails closed when no monitor interface exists (`docs/wiki/monitor-mode.md:86-88`).
- **An adapter or driver without monitor support.** Not every chipset supports it (`docs/wiki/monitor-mode.md:90-92`); the `iw` command then fails and the interface stays at 801.
- **Not benign, a defect:** an IEEE 802.15.4 interface (type 804) on the host suppresses the alert while providing no 802.11 capture, because `src/platform/linux.c:84` accepts 804 under a comment that mislabels it as Prism [7].

## Assessment

WARN is right, and so is the empty technique. The alert is the sensor telling the operator that the entire 802.11 half of the tool is dark - "every WiFi SIGINT view will be empty" (`docs/wiki/monitor-mode.md:67-69`), and with it every detector the capture-scope page lists under Monitor (`docs/wiki/capture-scope.md:36`) - which is a louder statement than most WARNs make, but it is a statement about the rig, not the network. Making it CRIT would put a configuration note in the band consumers page on, and the two-form exemption the corpus documents exists to keep own-state findings out of the adversary vocabulary [1], [2], [3]. The one correction the code needs is the ARPHRD set: 803 is radiotap, 802 is Prism, 804 is 802.15.4 [7]; `src/platform/linux.c:78` and `:84` should say 802 where they say 804, or drop the second value, and `src/capture/probe.c:171` already accepts 803 alone. The rule's comment should also stop saying "fires once"; it fires every tick and dedups to one incident, which the count semantics above make explicit.

Prevalence: this is not a technique and has no rate in the field. It fires on every start of sloth on a host whose Wi-Fi interfaces are all managed-mode, which is the kernel's state for every interface until an nl80211 tool changes its type [4], [6], and for the life of a wired-only run.

Reference host: 1 fire, 1 key, WARN, 0 reopens, on 2026-11-01. Because the rule fires on every tick the condition stands, a count of 1 means it stood for exactly one tick: one interface snapshot listed interfaces and no monitor radio, and the following snapshot - at most 250 ms later, and sooner if the loop woke early - had one. On the shipped unit the radio is flipped before sloth starts (`docs/wiki/deployment.md:149`), so the most plausible readings are a radio re-enumerating under the running process, or the type file read once before the mode change had settled. Either way the sensor started, or restarted, without a monitor interface for one tick, the condition cleared on its own, and the incident resolved 300 s later with nothing reopened. Nothing to tune. The single key means this alert cannot flood: it is one incident per process life per outage, and the count is a duration.

Sufficient to act on alone? Yes - it is an instruction. A responder should (1) check `iw dev` for an interface of `type monitor` and `/sys/class/net/<if>/type` for 803 (`docs/wiki/alert-remediation.md:622-627`); (2) if none, confirm the adapter and driver support monitor mode and put it in that mode with `ip link set <if> down; iw dev <if> set type monitor; ip link set <if> up` (`docs/wiki/monitor-mode.md:77-80`) [6], then restart sloth, or under the shipped unit confirm `sloth-monitor-up` ran and `SLOTH_IFACE` names the right radio (`docs/wiki/deployment.md:149`); (3) if the count is 1 and the alert has resolved, nothing - the sensor recovered by itself, and the `alert.resolve` record is the proof.
