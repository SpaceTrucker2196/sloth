## What the rule checks

Input is the DNS log `s->dns_log[]` (a 256-entry ring, `dns_log.c:17`, MAX_DNS_LOG 256), populated from parsed DNS on the capture path. `rule_dns_tunnel()` (`src/alerts/rules_wired.c:407-456`) builds up to 16 buckets (:414; a 17th parent in the window is silently dropped, :429) keyed on the 2-label parent domain (`parent_domain()`, :389-399, takes everything after the second-to-last dot, so `x.example.co.uk` buckets under `co.uk`). For each query (not response - `is_resp` rows are skipped, :421) within the last `ALERT_NXDOMAIN_WINDOW_S` = 60 s (:422; `include/sloth.h:843`), it increments the parent's `qcount` and, if the leftmost label length is `>= DNS_TUNNEL_LABEL_THRESH` (default 30, `--tune dns.tunnel_label_thresh`), its `long_hits` (:438-440). A bucket's `src` is the source IP of the *first* query seen for that parent in the walk (:432-433); later queriers to the same parent are not recorded.

A parent fires `ALERT_TYPE_DNS_TUNNEL` at `ALERT_SEV_CRIT` (:453) when `qcount >= DNS_TUNNEL_TOTAL_THRESH` (default 15) AND `long_hits >= DNS_TUNNEL_LONG_HITS` (default 8) (:444-445). Key `dns_tunnel:<parent, 40 chars>` (:448). Detail: `<qcount> queries to <parent, 20 chars>, <long_hits> with subdomain >= <thresh> chars` (:449-452). `match_ip` is the bucket's `src` (the first querier, above) and `match_port` is 53 (:454), so `--pcap-dir` will carve the matching UDP/53 packets for the querying host. Thresholds come from the tune registry (`tune.c:41-43`), defaulting to the values they had as #defines.

One fire per qualifying parent per tick; the incident resolves 300 s (ALERT_RESOLVE_AFTER_S) after the parent last met both thresholds. Because only the last 256 logged queries are in scope and the window is 60 s, a slow tunnel that paces itself under 15 queries/60 s per parent, or keeps labels under 30 bytes, stays under the bar - the rule's acknowledged blind spot.

## The attack

DNS is usually permitted outbound even where everything else is blocked, and ATT&CK notes "DNS traffic may also be allowed even before network authentication is completed", which is why adversaries use it for command and control and exfiltration [4]. The query name is an attacker-controlled field that reaches a server the attacker owns (the authoritative server for the parent zone), and the response carries data back. To move bytes out, a tunnel encodes payload into the leftmost labels of queries to its parent zone; to move bytes in, it reads the answer records.

iodine is the canonical tunnel: "upstream data is sent gzipped encoded with Base32; or Base64 ... or Base128" inside the query hostname, and downstream uses "NULL and PRIVATE ... TXT, SRV, MX, CNAME, A" records, bounded by DNS limits - "one query can be max 256 chars. Each domain name part can be max 63 chars" [7], which are RFC 1035 §2.3.4's 63-octet label / 255-octet name ceilings [10]. dnscat2 is "designed to create an encrypted command-and-control (C&C) channel over the DNS protocol"; its examples show hex-encoded labels under the tunnel domain and its default record-type list is `TXT,CNAME,MX` [8]. DNSExfiltrator base64url-encodes a file and packs "the longest supported label size of 63 chars" per request [9]. Cobalt Strike's DNS Beacon checks in over A/AAAA/TXT records with a randomly assigned per-host URI, only calling home when a task is queued [11]. Named malware families - DNSMessenger, OilRig's BONDUPDATER, DNS_TXT_Pwnage - use the same channel [5]. The Paxson et al. study scanned 230 billion lookups from production networks and confirmed 59 tunnels, "conventional tunnels that embed the payload in the query names" being the primary class [6].

What an attacker gains: a covert bidirectional channel that survives most egress filtering and is invisible to anyone watching only HTTP/HTTPS. The cost is bandwidth - DNS is slow and chatty - which is exactly what makes the burst of long subdomains to one zone detectable.

## Evidence that proves it

sloth records the parent domain, the querying source IP, the total query count and the long-subdomain count over the 60 s window; and with `--pcap-dir` it carves the actual UDP/53 packets for that source (match_ip + port 53, `rules_wired.c:454`, `alert_pcap.c:103-114`). The pcap is the primary evidence: open it and the queries should show long, high-entropy leftmost labels (base32/base64-looking, 30+ chars) to a single parent, often with TXT/NULL/CNAME answers coming back carrying data rather than addresses.

To call it a tunnel, a reader should see: sustained volume to one parent (a tunnel must keep moving bytes), labels that decode to binary rather than being human-readable hostnames, and answer records (TXT/NULL/large CNAME chains) that carry payload rather than resolving to a normal address. Entropy plus volume plus a single parent zone is the signature.

What refutes it: the parent is a known CDN, anti-abuse, or telemetry service that legitimately encodes data in subdomains (the T1071.004 corpus is explicit: "Long, high-entropy DNS names are also how several content-delivery and anti-abuse systems work normally ... it will report it repeatedly"). The remediation step 1 says the same - check whether the parent is a known service before isolating [2] (repo `alert-remediation.md:509`). A benign service will also show the answers resolving to real addresses or returning normal service data, not opaque payload.

## Benign causes

- **CDN / anti-abuse / reputation services** that encode request context into subdomains to one parent zone. The single most common false positive; identify by the parent's ownership.
- **Endpoint security / antivirus** products that do reputation lookups via long encoded DNS names.
- **Telemetry and some mail-security gateways** that hash or encode into subdomains.
- **Misconfigured clients** generating long auto-generated names to one domain.

Tell them apart by resolving who owns the parent and whether the answers carry payload or resolve normally; a benign service is a stable, attributable domain, a tunnel is an attacker-registered zone whose answers carry data.

## Assessment

Severity CRIT is defensible: a single source sending a sustained burst of long high-entropy subdomains to one zone is a high-signal pattern, and sloth is careful to call it a shape, not an intent. The detector reads thresholds from the tune registry so an operator on a network that runs such a service can raise them rather than suppress the type. The evidence (the carved UDP/53 pcap) is sufficient to begin an investigation but not to conclude one - the analyst must attribute the parent domain.

No reference-host data was provided for this type, so the noise verdict is inferred from the mechanics: the key dedupes per parent and only 16 parents are tracked per tick, so even an active tunnel counts up as one key per tick, not per query - quiet-to-moderate by construction. If a benign CDN/AV parent trips it repeatedly, the first move is to raise `dns.tunnel_total_thresh` or `dns.tunnel_label_thresh`, or allowlist that parent at the resolver; the rule itself should not be disabled. A responder should first identify the parent and the querying host, read `DGA_DOMAIN`, `NXDOMAIN_BURST` and `BEACONING` on the same host for a fuller picture, and if the domain is not a known service, isolate the host and block the parent at the resolver (`alert-remediation.md:509`).
