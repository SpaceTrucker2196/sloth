## What the rule checks

*This section describes the rule as assessed, before #173. What #173 changed (the detail, and how often the rule fires) is in the **Since #173** paragraph at the end of Assessment; file:line references below are to the assessed tree except `rule_file`.*

Inputs. The per-BSS FragAttacks counter table in src/fragattack.c, read through `frag_bss_count()` / `frag_bss_copy()` (a locked copy per row, #111, so the eight snprintf fields below cannot read a BSSID from one row and an SA from the row that replaced it). The counters are maintained by the frame observer (fragattack.c, fed from probe.c `on_probe_frame`). The field this branch reads is `plaintext_unicast` (include/sloth.h:1425).

The key-install gate. The counter is bumped only when a very specific condition holds (fragattack.c:550-595):

- The frame is Protected=0 (unencrypted) data, individually addressed, not a group address, not an A-MSDU.
- Four-address (WDS/mesh) frames are skipped entirely (`has_addr4`, fragattack.c:481).
- A prior **Protected** frame from this exact (BSSID, SA) pair has already been witnessed - `sta_known(bssid, sa)` is true, set by `sta_mark_protected()` when any encrypted frame from that station was seen (fragattack.c:231-245, 550-556). Without that, an unprotected frame is an open network or a client mid-association - the common case - and is ignored (fragattack.c:564). The gate is **per-SA and ordered**: protection must have been witnessed *before* the plaintext frame. SA is the frame's source address, not its transmitter: on a FromDS frame that is addr3, often a wired host behind the AP rather than the AP, so the "station" whose key install was witnessed can be any source the AP relays. Since #180 the AP's own two identities are one station to the gate: an SA equal to the BSSID or to the AP MLD MAC that BSSID's beacon advertised is filed under the BSSID, so an 802.11be AP MLD's encryption witnessed under one address gates its plaintext under the other. The mld-sibling heuristic FRAG_EAPOL_RELAY uses is not applied here - a guess may withhold a CRIT, never create one.
- The frame's EtherType is readable on the first fragment and is **not** EAPOL (fragattack.c:593-594): EAPOL is legitimately unprotected even after key install (that is how rekeying works), so it is excluded; a frame whose EtherType cannot be read (a continuation fragment) is also excluded, because "calling it an attack because we cannot see what it is would be a guess dressed as a detection."

Only when all three hold does `plaintext_unicast++` (fragattack.c:595). An evasion that hid this detector via the HT Control / Order bit skew was fixed 2026-10-14 (reading the LLC header four bytes late on a non-QoS data frame), covered by `test_order_bit_does_not_hide_a_plaintext_frame` (docs/wiki/fragattacks.md).

Condition. `rule_fragattack()` (rules_twin.c:581-608) copies each live frag_bss row; when `plaintext_unicast > 0` it fires `ALERT_TYPE_FRAG_PLAINTEXT` at CRIT, key `fragplain:<bssid>` (rules_twin.c:595-607) - per BSS, not per station: the gate is per (BSSID, SA) but the counter and the key are per BSSID, so a second offending station on the same BSS joins the open incident rather than opening one. "CRIT on the first one. This is not a threshold detector: a station whose encrypted traffic we have already seen has no legitimate reason to send one plaintext non-EAPOL frame, so the count is evidence volume, not confidence." The detail names the count, the BSSID, and the last SA->DA, with the CVE pair. Caveat: `last_sa`/`last_da` are one pair per BSS row shared by every FragAttacks branch (plaintext, broadcast fragment, A-MSDU EAPOL, EAPOL relay and the reassembly-session checks all write them - seven sites, fragattack.c:343, 353, 369, 395, 506, 536, 598, including the cache-poison, mixed-protect, mixed-key and PN-gap paths), so the SA->DA shown may belong to a later hit of a different kind, not to the plaintext frame. Lifetime: `plaintext_unicast` is cumulative and never decays, and the BSS row's `last_seen` is refreshed by every data frame on that BSS (`bss_get()` at fragattack.c:493 runs before any filter), and the table has no time expiry (`STAB_OLDEST`, fragattack.c:47-48; only `g_mpdu` is expired, :443), so one plaintext frame keeps this CRIT re-asserting until the row is LRU-evicted by 64 other BSSes (`FRAG_MAX_BSS`) - the incident outlives the BSS: it keeps firing after the AP has left range, and on a quiet RF neighbourhood it never resolves on its own. No evidence IDs, no match_ip, no pcap.

## The attack

FragAttacks (Vanhoef, "Fragment and Forge," USENIX Security 2021) is a family of twelve CVEs against 802.11's frame aggregation and fragmentation [3][4]. Three are design flaws present since 1997; the other nine are implementation bugs found across essentially every vendor tested. Their shared outcome: an adversary in radio range can get frames of their choosing accepted into an encrypted WPA/WPA2/WPA3 session **without holding the key**.

`FRAG_PLAINTEXT` covers two of the implementation bugs whose on-air artefact a passive monitor can see:

- **CVE-2020-26140** - a receiver accepts plaintext (unencrypted) data frames in a protected Wi-Fi network [5].
- **CVE-2020-26143** - a receiver accepts *fragmented* plaintext data frames in a protected network; "An adversary can abuse this to inject arbitrary data frames independent of the network configuration" [6].

Both are "accepting plaintext after key install" bugs: on a network where traffic should be encrypted, a vulnerable stack nonetheless processes a frame with the Protected bit clear. The attacker injects such a frame to inject data into the session - the paper demonstrates using the aggregation/plaintext flaws to intercept credentials, control an IoT device, and pivot to take over an outdated Windows 7 machine, all from within radio range [4]. The paper found "every single device we tested was vulnerable to at least one of our attacks," though plaintext acceptance specifically varied: in its results (§6, Tables 1-3) "11 devices even accept plaintext frames (CVE-2020-26140), and another 9 accept fragmented but not unfragmented plaintext frames (CVE-2020-26143)".

Crucially, sloth sees the *attempt*, never the *effect*: whether the victim's driver actually accepted the plaintext frame is a decision inside another machine, and nine of the twelve CVEs exist precisely because that decision varies by vendor. The alert says "this was transmitted," not "this worked." The author states he is not aware of in-the-wild exploitation, attributing the long non-discovery to the subtlety of the design flaws [4].

## Evidence that proves it

What sloth records. The alert detail carries the count of unprotected frames (`plaintext_unicast`), the BSSID, the last source->destination pair, and the CVE identifiers. The `[c]` FragAttacks view (docs/views/fragattack.md) mirrors the per-BSS counters, showing the seven-CVE breakdown for the selected BSSID plus "N protected frame(s) witnessed on this BSSID (key-install gate)". There is no per-event evidence blob and this rule writes no pcap - `src/alert_pcap.c` already serves that role for the rules that cite frame IDs, but FRAG_PLAINTEXT is a counter detector and passes none.

What makes it real. The gate is the proof: a frame with the Protected bit clear, carrying something other than EAPOL, from a station whose *encrypted* traffic sloth has already seen on that BSS. That ordering is what distinguishes an attack artifact from the mundane: a station past key install, on a protected network, has no legitimate reason to emit a plaintext non-EAPOL data frame. A responder should see, in the evidence, that the same (BSSID, SA) pair was witnessed sending encrypted frames *before* the plaintext one.

What refutes it. The benign reading is a driver bug - a non-conforming stack emitting plaintext when it should encrypt - which is itself worth knowing and is what nine of the twelve FragAttacks CVEs describe. The open-network case (no encryption to begin with) and the still-associating case (key not yet installed) are both excluded by the gate, so a finding is never simply "an open network" or "a client connecting." A single EAPOL frame is excluded (legitimate rekeying). If the detail shows a plaintext count against a station with no prior protected frame, that is a bug in the gate, not a finding - but the code makes that impossible by construction.

## Benign causes

- **Driver / firmware bugs.** The documented benign trigger (docs/views/alerts.md): a non-conforming stack that emits a plaintext frame after key install. Nine of the twelve FragAttacks CVEs are exactly such implementation defects, so a finding may be a vulnerable/buggy device rather than an active attacker - either way the device needs firmware attention.
- **Essentially nothing else.** The gate removes the open-network and mid-association cases, and EAPOL is exempt, so there is no large class of legitimate plaintext-after-key-install traffic. This is why the rule is CRIT on the first hit rather than threshold-based.

## Assessment

Severity rationale. CRIT-on-first-hit is justified by the gate, not by volume. The confidence lives in the ordered per-(BSSID, STA) key-install condition: once sloth has witnessed encryption from a station, one plaintext non-EAPOL frame from it on that protected BSS has no benign reading beyond a driver bug (itself CRIT-worthy as a vulnerability). Treating the count as evidence volume rather than confidence is the correct framing - more plaintext frames do not make it more of an attack, they make it a larger body of evidence.

Real-world prevalence. FragAttacks' design flaws reach every protected Wi-Fi network and every device the paper tested had at least one of the flaws [3][4], and -26140/-26143 are among the few members passively observable, but the author reports no known in-the-wild exploitation, the available tooling is a test suite rather than a weaponized flooder, and a real attack additionally needs a receiver that accepts the plaintext (which many patched stacks no longer do). So the base rate of a genuine malicious hit is low; a finding more often flags a vulnerable/buggy device.

Reference-host noise. 20,510,606 fires on **1 key**, max_sev CRIT. This is the per-tick count at its most misleading: one per-BSS incident that stayed open and re-qualified produces 20.5 M evaluations, which is poll ticks - **not** 20.5 M plaintext frames and not 20.5 M alerts. At exactly 4 ticks/s that is ~59 days, so the tick rate on this host was evidently well above the floor. Cadence caveat: the tick arithmetic assumes the default 250 ms poll with an idle keyboard. `poll_tick()` runs once per main-loop iteration (`poll_data()` at src/main.c:1628 calls it at :205) and the wait before it is cut short by any keypress or by `event_wake_signal()` on a new or escalated alert (src/alerts/engine.c:526, 608), so real ticks/s is >= 4 and every duration derived here is an upper bound; `--refresh-ms` changes the base. The honest finding count is **1**; the real frame volume is `plaintext_unicast` in the detail. The per-BSS key already dedupes. Recommendation: surface the incident count with first_seen/last_seen and the detail's `plaintext_unicast` instead of `evaluations`/`count` on the alert page. `observations` does not collapse it: the detail changes whenever `plaintext_unicast` or the shared `last_sa`/`last_da` move (any FragAttacks branch writes those), and after each change `observations` rises every tick until the next 60 s update refreshes the stored `detail_sig` (engine.c:487, 534). No dedupe or threshold change is warranted; this is a presentation issue identical to the other counter-based wireless rules in this batch.

Is the evidence enough to act on? Yes, to the extent of "this BSS/station needs attention": the ordered gate makes the finding trustworthy as "an unprotected frame was transmitted on a protected session after key install." It does not prove the frame was *accepted* (that is inside the receiver) - the alert honestly says "transmitted," not "worked." First response: note the BSSID and the (SA, DA) pair; recognize these as the on-air artefact of CVE-2020-26140/-26143; update the firmware of the AP and the clients on that BSS to versions carrying the FragAttacks fixes (the per-vendor advisories indexed from the paper) - whether the receiver accepted them is a per-vendor driver decision (docs/wiki/alert-remediation.md).

**Since #173.** The detail is `<n> unprotected data frame(s) on <bssid> after key install (CVE-2020-26140/-26143)`, with `n` exact below ten and by decade above; the SA->DA pair, which belonged to the row and not to this kind, stays on the `[c]` FragAttacks view. A per-kind offender pair (a `fragattack.c` change) is the follow-up if the alert should name the station again. Residency is still the table's LRU, as this assessment recommends leaving it. Test: `tests/test_alert_tick_rate.c`.
