## What the rule checks

Input: `s->ssh_flows`, the SSH flow table of `MAX_SSH_FLOWS` = 64 rows keyed by **(client IP, server IP)** (`include/sloth.h:349-373`; `src/ssh_snoop.c:16-22`). `ssh_snoop_observe()` takes any TCP payload with 22 on either side (`:62`; dispatched from `src/capture/capture.c:749-754`) and tests whether it starts with the literal `SSH-` and has a second `-` within the first 12 bytes (`:32-40`) - the RFC 4253 §4.2 identification string `SSH-protoversion-softwareversion SP comments CR LF`, which "both sides MUST send" once the connection is established, and after which "Key exchange will begin immediately" [3]. Only the **server's** string is counted: a payload from source port 22 increments `banner_count` on the (client = dst, server = src) row and overwrites `server_banner`; the client's string is seen and discarded, because counting both would double every connection (`:65-82`, `:95-96`). Each TCP connection produces exactly one server banner, so `banner_count` is the number of connections that reached the SSH handshake. Nothing after the banner is visible - authentication happens inside the encrypted transport - so the count includes connections that authenticated successfully just as it includes ones that failed (`docs/wiki/ssh-snoop.md:111-116`). The observer keeps no per-connection state, so a retransmitted banner segment counts again. SSH on a port other than 22 is not observed (`:62`). The counter is a lifetime total for the row; nothing decays it.

Per tick the rule fires for any row whose `banner_count` is at or above `SSH_BRUTE_FORCE_THRESHOLD` = `tune_val(TUNE_SSH_BRUTE_FORCE)` (`src/alerts/rules_wired.c:1018`, `:1023`), default **10** (`src/tune.c:58`: `ssh.brute_force`, min 2, max 1000, unit "attempts"). Key: `ssh-brute:<client>-><server>` (`:1025-1027`). Detail: `"<client>-><server>: <n> SSH banners (brute-force; <server_banner, 30>)"` (`:1028-1032`). CRIT, `match_ip` = the client, `match_port` 22 (`:1033-1035`; `docs/wiki/ssh-snoop.md:59-65`). The incident resolves 300 s after the last tick that re-asserted it (`include/sloth.h:860`). The 64-row table evicts the least-recently-seen pair when full (`STAB_OLDEST`, `src/ssh_snoop.c:21-22`; `src/stab.h:27`; tallied as `evict_ssh_flow`, `src/sensor_health.h:98`) and never expires rows by age; a process restart empties it (`ssh_snoop_clear`, `:109-113`).

The rule's comment speaks of "ten distinct banner exchanges to the same server inside the active window" and compares the threshold with fail2ban's 5 "with a wider window" (`src/alerts/rules_wired.c:1006-1017`). There is no window: the comparison is between fail2ban's 5 failures in 10 minutes [6] and sloth's 10 connections ever.

## The mechanism

SSH servers "normally listen for connections on port 22" [3]. MITRE T1110.001: "Adversaries with no prior knowledge of legitimate credentials within the system or environment may guess passwords", and the list of commonly targeted services begins "SSH (22/TCP)" [2]; the parent T1110 adds that "an adversary may systematically guess the password using a repetitive or iterative mechanism" and lists Chaos, which "conducts brute force attacks against SSH services to gain initial access", and Kinsing, which "has attempted to brute force hosts over SSH" [7]. The attack tool the rule names is hydra, which attacks "SSH (v1 and v2)" and is built around "parallelized connects" that the user tunes with `-t` ("The higher - the faster") [4]. The defensive tool it compares itself with is fail2ban, which "scans log files like /var/log/auth.log and bans IP addresses conducting too many failed login attempts" [5], by default when a host "has generated maxretry during the last findtime seconds" with `maxretry = 5` and `findtime = 10m` [6].

What the network sees of a guessing attempt is the connection cadence: each try is a fresh TCP connection that completes the cleartext banner exchange before the encrypted authentication fails and the server drops it (`docs/wiki/ssh-snoop.md:18-23`; `include/sloth.h:357-363`). The corpus states the limits plainly: the thresholds "cannot separate a hostile automation from a broken one", the rule is "a rate over a window, and the window matters as much as the count", and an attempt that succeeds on its first try produces nothing [1]. Two of the corpus's own descriptions do not match the code and are flagged here: `research/mitre/T1110.md` describes the SSH failure shape as "connection closed without reaching the session stage", and `docs/wiki/alert-remediation.md:367-369` calls the rule "a rate of failed sessions"; the rule counts banners, which every session produces whether it fails or succeeds (`src/ssh_snoop.c:65-71`), and it has no rate. The wiki's own page says so (`docs/wiki/ssh-snoop.md:111-116`).

## Evidence that proves it

What sloth records:

- `alert` / `alert.*` JSONL under `ssh-brute:<client>-><server>` with the count and the server's software string;
- `ssh_flow` state records keyed on `(src_ip, dst_ip)` (`docs/wiki/jsonl-schema.md:729`): `banner_count`, `server_banner`, `first_seen`, `last_seen`;
- a per-alert pcap if `--pcap-dir` is set (CRIT passes the default `pcap.min_severity` 2, `src/tune.c:121`); the filter is `match_ip` = the client and port 22 either side (`src/alert_pcap.c:104-114`), so the file holds that client's SSH connections from the ring: SYNs, both banners, the KEXINIT, and the connection's lifetime.

What points to an attack: `banner_count` climbing by tens or hundreds within seconds of `first_seen` (hydra at its default parallelism opens many connections a second [4]); connections in the pcap each torn down within a second or two of the banner, with no sustained data phase; a **client** address that is unknown or external; the same client appearing on many `ssh_flow` rows against different servers (a sweep, `docs/wiki/ssh-snoop.md:87-90`); and, decisively, the server's authentication log showing many failed attempts for many usernames from that address, which is what fail2ban reads [5], [6]. Whether any attempt succeeded is only in that log; sloth cannot see it [1], `docs/wiki/alert-remediation.md:363-381`.

What refutes it: `banner_count` that grew slowly - a few per hour or per day - over a `first_seen`/`last_seen` span of days; connections in the pcap that stay open for minutes and move data (an interactive session, an rsync); a client that is the operator's own automation host; a server log with no failures. On the reference host, the fact that the same four keys reopened after resolving (which needs the count to re-cross 10 from an empty table) fits a routine job better than four incidents.

## Benign causes

- **Scripted short sessions.** Every tool that runs one command per SSH connection - a cron rsync or scp, a CI runner, Ansible, a git remote over SSH, an IDE's remote file browser - produces one server banner per command. Ten commands over the row's life cross the threshold; the counter never decays (`src/ssh_snoop.c:95`; no `stab_expire`), so this is not a question of if but of when.
- **Successful sessions count.** Authentication is encrypted, so a connection that logged in counts exactly like one that failed (`:65-71`; `docs/wiki/ssh-snoop.md:111-116`). The corpus's "stale credential" benign case [1] applies, but so does the far larger population of credentials that are not stale.
- **Reconnects.** The rule's own rationale allows "a handful" of reconnects after network blips (`src/alerts/rules_wired.c:1012-1013`); a laptop that sleeps and wakes, a VPN that drops, or a multiplexed client that reopens its control connection reaches ten over days, not minutes.
- **NAT aggregation.** The key is the client IP, so a NAT or jump host in front of several users is one row, and their combined sessions sum.
- **TCP retransmission.** A retransmitted banner segment is counted again (`src/ssh_snoop.c:58-101` keeps no per-connection state), inflating the count on a lossy link.

## Assessment

CRIT is the right severity for an SSH password-guessing attack, which is why the rule exists and why the mapping to T1110.001 is honest [1], [2]. The disagreement is with what the rule actually tests. Credential guessing is a rate - fail2ban's definition is five failures inside ten minutes [6] - and the rule's own comment describes a window (`src/alerts/rules_wired.c:1006-1017`); but the code tests a lifetime connection count that includes successful logins and lives as long as the row does. On a quiet segment the row lives for the life of the process. So the rule, as built, fires CRIT on "these two hosts have had ten SSH sessions, ever", which on most networks describes the backup server, the CI runner and the administrator's workstation. The refinement is simple and worth doing: keep a timestamped ring of recent banners per row (or a count plus a window start) and gate on N inside M seconds; the `ssh_flow` record already carries `first_seen` and `last_seen`, so the display can approximate a rate today. Until then, WARN would describe the confidence the evidence supports.

Prevalence: first-class, with SSH named first among targeted services [2] and botnet families that target SSH for initial access on the procedure list [7]; the existence and defaults of fail2ban are themselves evidence of how routine the problem is against any exposed port 22 [5], [6]. No fetched source quantifies a field rate, so none is claimed.

Reference host: 64,873,479 fires on 4 keys, max CRIT, 5 reopens, first seen 2026-10-15, last seen 2026-11-01. Keys are per (client, server), so four pairs ever qualified. The ~16.2M evaluations per key cannot be 16.2M connections: they are ticks on which the row stood above threshold. At the 4 ticks/s floor that would be ~47 days per key, which exceeds the 18-day span between first and last seen, so the loop averaged roughly 10 ticks/s - which is what early wake on alert activity predicts on a host that also carries standing `CLEARTEXT_CRED`, `WEAK_TLS` and `SMB1_USE` incidents, and what those siblings' arithmetic shows too. The 5 reopens on 4 keys mean a key resolved (no tick re-asserted it for 300 s, `include/sloth.h:860`) and later fired again; since the counter cannot fall while the row exists, that requires the row to have been evicted or the process restarted and the same pair to have re-crossed 10 afterwards. A routine job doing that after each restart is the likely reading; four separate incidents that each resumed after a sensor restart is not. The operator should check the four `ssh_flow` records: if `banner_count` grew over days and the clients are their own hosts, these are findings about automation, not intrusions.

Sufficient to act on alone? No - as built it is a prompt to look at the pair, not evidence of an attack. A responder should (1) read the `ssh_flow` record's `banner_count` against `first_seen`/`last_seen` to get a rate; (2) identify the client - the operator's own automation host or an unknown address - and open the per-alert pcap to see whether sessions are short-lived (guessing) or long and data-carrying (work); (3) read the server's authentication log for failed attempts, usernames tried and any success, since sloth sees neither [1], `docs/wiki/alert-remediation.md:363-381`; (4) if an attack, block the source and reset any account that logged in from it; if a stale credential, fix the job; if routine automation, record the pair. Tuning: raising `ssh.brute_force` buys time, not discrimination, because the count still only rises; the sensor_health example in the wiki shows an operator already running `ssh.brute_force=25` (`docs/wiki/jsonl-schema.md:1069`), which is the same compromise. The fix is the window, not the number.
