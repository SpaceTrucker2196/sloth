## What the rule checks

Input: the per-BSSID Multi-Link table in `src/mle.c` (`sloth_mle_bss_t[]`, SLOTH_MLE_BSS_MAX=64), fed by `mle_bss_observe_frame()` from Beacon (subtype 8) and Probe Response (subtype 5) frames. Run order: `src/alerts/rules_table.c:69` (0-based table index 42), right after MLE_RECONFIG_NO_MLO.

Detector (mle.c:617-653): when a frame's own Basic MLE is present (`sc.own`): if it is a Beacon, the row records the BSS's identity from it - `beacon_mld_mac`, `beacon_link_id` (when Link ID Info Present), the timestamp and the frame's event id (617-623). If it is a Probe Response and a Beacon identity is already on file (624), the two are compared, but only when within `MLE_PR_BEACON_WIN_SECS` = 30 s (sloth.h:2285) using a both-directions age test so a replayed/reordered capture cannot compare against a future Beacon (634-637). The comparison (638-640): `mac_diff = memcmp(sc.mld_mac, beacon_mld_mac) != 0`, and `lid_diff = sc.has_link_id && beacon_has_link_id && sc.link_id != beacon_link_id`. On either difference it records `pr_beacon_diff_total++`, which fields differed, both identities, the last-seen time, and both event ids (641-652).

Deliberately NOT compared (mle.c:625-633 and research doc): Per-STA Profiles (a Beacon has none, an ML Probe Response has Complete ones); a Basic MLE carrying an AP MLD ID (hostapd puts the requested MLD's element first in a multi-link Probe Response, so the BSS's own identity is the first Basic MLE *without* an AP MLD ID); the BSS Parameters Change Count (moves on every critical update); the capability subfields; and Link ID unless both frames set Link ID Info Present. The newest Beacon is the baseline, so a reconfigured AP MLD is compared against its current claim.

Rule (rules_mle.c:259-301): for each row with `pr_beacon_diff_total > 0`, key `mle_pr_beacon_diff:<bssid>` via `akey_*` (270-272). Detail (273-293) names both sides - `MLD <b> link_id <n> in its Beacon but MLD <p> link_id <m>` (or just the MLD MACs, or just the Link IDs, depending on which differed) - then `... in a Probe Response within <30>s (<N> such frame(s) seen) - corroborates a second transmitter for this BSSID, not which one is genuine - IEEE 802.11be-2024 9.4.2.322`. Fires `ALERT_SEV_WARN` via `fire_ev()` citing both the Beacon and the Probe Response (294-299; each id only when non-zero); `match_ip = NULL`.

## The attack

A Beacon and a Probe Response from one BSSID are the same BSS describing its own AP MLD membership. In both, that BSS's own Basic Multi-Link element carries the MLD MAC Address (unconditional in the Basic variant) and, in what hostapd builds, the BSS's own Link ID [1]. Neither can differ between the two frames while the AP MLD is unchanged. Two answers for one BSSID inside the freshness window is the shape of a second transmitter answering probes under that BSSID with another MLD identity - an impersonator that beacons as the real AP but hands out its own MLD MAC in directed Probe Responses. sloth tags it T1669 (Wi-Fi Networks), the same technique as the sibling MLE rule; the assignment is the repo's (include/sloth_alerts.def), not a MITRE mapping of this specific impersonation - T1669 as MITRE describes it is gaining access by connecting to a wireless network [7].

The layout facts are grounded in three public implementations that agree (the standard text is paywalled and was not read): hostapd's `hostapd_eid_eht_basic_ml_common()` writes the own MLD MAC and own Link ID in every Basic MLE; `hostapd_probe_resp_fill_elems()` emits the requested MLD's Basic MLE (with an AP MLD ID) first and then this BSS's own (without one); Wireshark's dissector shows the MLD MAC unconditional and Link ID Info conditional; mac80211 reads the same fields [1]. The rule's restraint - comparing only fields both frames must carry - is what keeps a conformant multi-link Probe Response quiet (`tests/test_mle_bss.c :: test_conformant_ml_probe_response_does_not_fire`). It also creates two known, named false negatives, each the direct price of a false-positive guard: a forged Probe Response whose only Basic MLE carries an AP MLD ID (or that sends no Basic MLE without one) offers no identity and is never compared, and one that clears Link ID Info Present is checked on MLD MAC alone. A forger who simply copies the real MLD MAC and Link ID is invisible here by construction.

## Evidence that proves it

The detail names both identities (the Beacon's and the Probe Response's MLD MAC and/or Link ID) and does not pick a genuine one. The alert cites both frames by evidence-ring event ID, so with `--collect-handshakes` the Beacon and the disagreeing Probe Response both reach disk (docs/wiki/pcap-export.md §4). JSONL carries `evidence_count`/`evidence_id_0..1` and `technique` T1669.

What a reader should confirm in the two cited frames: both are from the same BSSID; the Beacon's own Basic MLE and the Probe Response's own Basic MLE (the first without an AP MLD ID) name different MLD MAC Addresses, or different own Link IDs when both carry Link ID Info; and the two are within 30 s. What refutes it: the difference is in a field the rule should not have compared (an AP-MLD-ID-bearing Basic MLE, a Change Count, a Per-STA Profile) - but the detector already excludes those, so a surviving finding is a genuine identity mismatch. A legitimately reconfigured AP MLD is not refuting evidence: the baseline is the newest Beacon, so the rule compares against the current claim, and a Probe Response matching that newest Beacon does not fire.

## Benign causes

- **A conformant multi-link Probe Response.** The main thing the rule is built not to fire on: its first Basic MLE carries an AP MLD ID (the requested MLD), so the identity comparison uses the BSS's own Basic MLE without one, which matches the Beacon (test_conformant_ml_probe_response_does_not_fire).
- **A legitimately reconfigured AP MLD.** Handled by the newest-Beacon baseline and the 30 s freshness window - the AP is compared against what it says now, not against a stale Beacon.
- **A reordered or replayed capture.** The both-directions age test prevents comparing against a Beacon "from the future."

## Assessment

WARN is correct and the detail is scrupulous: it names both identities and refuses to say which is real, because a passive receiver hears two frames, not which radio sent each. False-positive risk is low because the comparison is confined to fields both frames must carry and is anchored to the newest Beacon within a tight freshness window - the design choices that keep conformant Wi-Fi 7 APs silent. The cost is the named false negatives (AP-MLD-ID-only identity, cleared Link ID Info, copied MLD MAC), which the research doc states plainly as the price of the guards rather than hiding. On the reference host it is not seen, consistent with the null data and the early state of MLO on air. Prevalence is unmeasured - this is forward-looking coverage of a 2024-25 standard. A responder should note the BSSID and, if it is their own AP and a second transmitter is using it, locate that transmitter and remove it if on premises they control, otherwise report it (docs/wiki/alert-remediation.md §MLE_PR_BEACON_DIFF). The evidence (two cited frames with conflicting own-MLD identity) is enough to investigate a second transmitter, not to attribute which frame is the impostor.
