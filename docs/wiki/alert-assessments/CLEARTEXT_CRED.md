## What the rule checks

Input: `s->cleartext_creds`, the exposure ring of `MAX_CLEARTEXT_CREDS` = 64 rows (`include/sloth.h:1196`, `:3513`), each a `cleartext_cred_t` with `src` (client), `dst` (server), `dst_port`, `protocol[16]`, `username[64]`, `password_observed` and `ts` (`include/sloth.h:1198-1206`). There is no password field; the header above it says the record holds "the *fact* of exposure and the username, never the password or its hash" (`:1191-1195`), and `src/cleartext_creds.h:6-16` makes that structural: `cleartext_creds_record_user()` has no password parameter, and `cleartext_creds_mark_password()` takes only the flow tuple.

Five snoops feed the ring, each from the TCP dispatch on its cleartext port (`src/capture/capture.c:795-800`): HTTP Basic on 80/8080/8000, where `http_snoop_scan_creds()` (`src/http_log.c:634`, called at `src/capture/capture.c:633`) base64-decodes the `Authorization: Basic` value, splits on the first colon, records the part before it and marks a password if anything followed (`src/http_log.c:672-700`); FTP on 21, `USER` then `PASS` (`src/ftp_snoop.c:40-57`); POP3 on 110, the same pair (`src/pop3_snoop.c:40-56`); IMAP on 143, the tagged `LOGIN` verb (`src/imap_snoop.c:114-129`); SMTP on 25/587, `AUTH PLAIN` decoded inline and `AUTH LOGIN` (`src/smtp_snoop.c:211`, `:235`, `:256-278`). There is no Telnet snoop in `src/` (only `src/services.c` names the port), although `research/mitre/T1040.md:17-18` and `docs/wiki/jsonl-schema.md:573` list Telnet among the protocols; that is a documentation overclaim, noted here.

The recorder (`src/cleartext_creds.c`) sanitises the username to printable ASCII (`:77-79`), coalesces on the full tuple so a repeat bumps `ts` instead of adding a row (`:40-53`, `:83-88`), and when the ring is full evicts the row with the oldest `ts` (`:55-62`, `:90`); it emits the `cleartext_cred` JSONL record at record time, before the alert engine sees it (`:101-104`). `mark_password` sets the flag on the most recently touched row of the same (src, dst, port, protocol) and is a silent no-op when none exists (`:109-133`). `cleartext_creds_snapshot()` (`:135-141`) copies the ring into the state each poll (`src/poll.c:177`).

Per tick `rule_cleartext_cred()` (`src/alerts/rules_wired.c:186-213`) fires once per row. The key is built with the typed builder: `cred` + src + dst + port + protocol + the username as a remote component kept to 32 bytes plus a hash (`:192-200`), and an overflowed key skips the row (`:201`); the shape is `cred` + `:<src>:<dst>:<port>:<proto>:<user, 32 kept>:<hash>` (`docs/wiki/alerts.md:128`), and `ALERT_KEY_LEN` 192 is sized to this rule's worst case (`include/sloth.h:841-842`). Detail: `"<proto> user <user,24> in the clear on <proto,20>[ (password observed)] -> <dst,24>:<port>"` (`:202-209`). WARN, `match_ip` = the client, `match_port` = the server port (`:210-211`). The rule runs late in the table, after the BLE rules (`src/alerts/rules_table.c:104`). The engine increments `evaluations` (the `count` alias) per `fire()` under an open key (`src/alerts/engine.c:475-481`), resolves after 300 s without one (`include/sloth.h:860`; `src/alerts/engine.c:927-935`), and opens a new incident with `reopen_count` carried over on the next fire (`:543-547`, `:594-598`); the `--db` row folds later incidents into `reopens` (`src/db_schema.c:534-545`). Tests: `tests/test_cleartext_creds.c:171-174`, `tests/test_alerts.c:5391` and `:9181-9182`.

## The mechanism

T1040, Network Sniffing: "Adversaries may passively sniff network traffic to capture information about an environment, including authentication material passed over the network", using "the network interface on a system to monitor or capture information sent over a wired or wireless connection", for instance by placing "a network interface into promiscuous mode"; the take "may include user credentials, especially those sent over an insecure, unencrypted protocol" [2]. The protocols the snoops read say so themselves. HTTP Basic forms the credential by "concatenating the user-id, a single colon (':') character, and the password" and Base64-encoding it; "The Basic authentication scheme is not a secure method of user authentication", its most serious flaw being "the cleartext transmission of the user's password over the physical network", so it "SHOULD NOT be used" without HTTPS [3]. FTP's `PASS` argument "is a Telnet string specifying the user's password" that "must be immediately preceded by the user name command" [4]. POP3: "Use of the PASS command sends passwords in the clear over the network" [5]. SASL PLAIN is "a simple clear-text user/password" mechanism whose message is `[authzid] UTF8NUL authcid UTF8NUL passwd`, and implementations "SHOULD NOT advertise and SHOULD NOT make use of the PLAIN mechanism unless adequate data security services are in place" [6]. IMAP's "LOGIN command identifies the client to the server and carries the plaintext password authenticating this user"; "clients MUST NOT use LOGIN on unsecure networks", a server must be able to advertise `LOGINDISABLED`, and a client "MUST NOT send a LOGIN command if the LOGINDISABLED capability is advertised" [7].

The corpus names the symmetry: "sloth is demonstrating the technique in order to report it. A passive monitor that can see a password is proof that anything else on that segment can too, which is precisely the finding" [1]. That is also why the record keeps what it keeps - the fact, the protocol, the endpoints, the username - and why "a forensic record that leaks what it is reporting on has made the problem worse" [1]. The T1040 mapping is the mapping of what sloth did, not of an adversary it saw.

## Evidence that proves it

What sloth records:

- `cleartext_cred` JSONL records, one per new tuple, with `src`, `dst`, `dst_port`, `protocol`, `username`, `pw_observed` (`docs/wiki/jsonl-schema.md:562-575`), emitted at record time (`src/cleartext_creds.c:101-104`), with the cadence note that repeats coalesce on the ring (`docs/wiki/jsonl-schema.md:584-588`);
- the `--db` `cleartext_creds` table (`src/db_schema.c:570`), upserted so that `pw_observed` once set stays set and `last_seen` advances (`src/db.c:638-644`);
- `alert` / `alert.*` under the `cred`-prefixed key; `count` is evaluations (`docs/wiki/jsonl-schema.md:391`), and each incident after the first is a `reopen`;
- no per-alert pcap at the default `pcap.min_severity` 2 (`src/tune.c:121`). That default is worth keeping for this type: the filter is client IP plus server port (`src/alert_pcap.c:103-113`), and a pcap of that flow would contain the password bytes the record was built not to hold (`src/cleartext_creds.h:7-12`).

What makes it actionable: `pw_observed` = 1 on a real account against a real service - the credential is readable by anything on the segment and should be treated as compromised (`docs/wiki/alert-remediation.md:644-647`). Many distinct `username` rows from one `src` to one `dst` in a short time is a guessing pattern worth reading alongside the brute-force alerts, though this rule does not rate anything. What makes it benign-but-still-a-finding: a printer or switch speaking a legacy protocol to a management host [1]. What refutes it as a secret: the username is `anonymous`, or the account is a documented throwaway on a LAN appliance. Absence is not assurance: "Credentials inside TLS are invisible, correctly", a `LOGIN` after `STARTTLS` is encrypted and not parsed, a Basic header on a port other than 80/8080/8000 is not scanned (`src/capture/capture.c:795-796`), and Telnet is not read at all.

## Benign causes

- **Legacy protocol on a management VLAN.** "A switch or printer speaking Telnet to a jump host is the ordinary cause, and it is still a real finding - just one whose answer is a migration plan rather than an incident response" [1]. (Telnet is the corpus's example; the snoops read FTP, POP3, IMAP, SMTP and HTTP Basic.)
- **Anonymous or throwaway accounts.** FTP records any `USER` token (`src/ftp_snoop.c:40-50`), so an anonymous login fires with `username` = `anonymous` and, if the client sent the conventional e-mail address, `pw_observed` = 1; the protocol did carry the pair, the pair just is not a secret.
- **HTTP Basic to a LAN appliance.** Cameras, printers and embedded web UIs use Basic over plain HTTP; RFC 7617 says it "SHOULD NOT be used" without HTTPS [3], so the finding is correct and the fix is the device's.
- **A mail client that did not upgrade.** `LOGIN` on 143 or `AUTH PLAIN` on 25/587 means the session was not protected first; the specifications require the client not to do that on an unsecure network [6], [7], so this is a misconfiguration on the client, not a false fire.

## Assessment

WARN is right and the record design is the reason the alert is safe to keep on. The corpus is clear that this "is a *posture* finding first and an incident finding only if someone was listening" [1]; the protocols concerned say in their own security sections that the password is on the wire [3], [4], [5], [6], [7]; and the exposure is true independent of any adversary. CRIT would be wrong for the common legacy-device case. The thing to protect is the record: the username is on the TUI detail and in JSONL and the DB, the password nowhere, and slothweb withholds this type's detail (`docs/wiki/alert-remediation.md:646-647`). Two documentation fixes follow from the code: Telnet is listed as a source in the corpus and the schema but no Telnet snoop exists, and the schema's `protocol` enumeration should match the five literals the snoops emit.

Prevalence: sniffing needs only position, which "on a shared wireless segment or behind a rogue AP is the easy part" [1], [2]. No fetched source quantifies how often cleartext credentials cross a given segment, so no rate is claimed; the corpus's qualitative claim is that legacy protocols on management networks are the usual source [1].

Reference host: 135,252,457 fires on 8 keys, max WARN, 14 reopens, first 2026-10-14, last 2026-11-03. Keys are per (client, server, port, protocol, username), so eight distinct credential exposures were ever observed - quiet by findings. The count is what makes this type the loudest on the host, and the arithmetic explains why: 16.9M evaluations per key at the 4 ticks/s floor would be 49 days, more than twice the 20-day span, so the floor is not the rate; the loop averaged about 10 ticks/s (it wakes early on alert fires, and the shipped unit runs with `--db-interval-secs 1`), and every one of the eight rows stood from first sight to the end of the span, because a row in a 64-slot ring on a segment that produced eight tuples in twenty days is never evicted. The 14 reopens on 8 keys are the only way a key can lapse: the process restarted (the ring is process memory) or a row was evicted, and the same credential was seen again, each later incident folded into the row's `reopens`. The number is the behaviour of a standing condition, not 135 million logins. The alert page should present the `cleartext_cred` row's `first_seen`/`last_seen` and `pw_observed`, label the engine `count` as evaluations, and never render the username where the page is shared.

Sufficient to act on alone? Yes. The record names the protocol, the client, the server and the account. A responder should (1) treat the credential as compromised and change it (`docs/wiki/alert-remediation.md:642-651`); (2) identify why the client used the cleartext protocol - an old device, a client not configured for STARTTLS or Implicit TLS, a web UI without HTTPS - and fix the client or the service [3], [6], [7]; (3) plan the migration off the protocol, since there is no vendor fix for a protocol that carries the credential by design (`:653-656`). Nothing to tune; the protocol set is the capture dispatch, and the default pcap severity floor should stay where it is.
