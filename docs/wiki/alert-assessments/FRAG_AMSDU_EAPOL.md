## What the rule checks

Input: the per-BSS counter table in `src/fragattack.c`, fed by `frag_observe_frame()` from the monitor thread on every data frame (`src/capture/probe.c:535`), read on main by `rule_fragattack()` through a locked row copy (`src/alerts/rules_twin.c:583-586`; `frag_bss_copy`, `src/fragattack.c:638-646`). The field this branch reads is `amsdu_eapol_spoof` (`src/fragattack.h:201-207`; mirrored for the `[c]` view in `include/sloth.h:1461`).

The counter is incremented in `observe_locked()` (`src/fragattack.c:470`) only when every one of these holds, in this order:

- data frame, not Null/QoS-Null, not four-address (`:472`, `:477`, `:481`);
- **Protected = 0** - a protected frame takes the other branch, bumping `protected_frames` and marking `(BSSID, SA)` as having installed a key (`:550-557`);
- the **key-install gate**: `sta_known(bssid, sa)` is true (`:564`), i.e. a Protected frame with this exact source address on this BSSID was seen earlier (`sta_mark_protected`, `:236-246`; 128-row `g_sta` table, `:69-70`). SA is Address 3 on a downlink frame, so for AP-originated traffic the "station" whose install was witnessed is the AP or a wired host behind it;
- unicast DA (`:566`) and the QoS Control **A-MSDU Present bit set** (`amsdu == 1`, `:574`; `dot11_frame_amsdu`, `src/dot11_frame.c:218-221`, which is -1 on a non-QoS frame, so a non-QoS plaintext frame can never reach this branch);
- `first_amsdu_subframe_ethertype(f) == 0x888E` (`:582-583`). That reader (`:191-202`) requires fragment number 0, skips the MAC header, then **14 more bytes** (subframe DA(6) SA(6) Length(2)) and expects `AA AA 03` + EtherType there - the first subframe's own LLC/SNAP (`:197-201`). Only the first subframe is read, deliberately, because walking further means trusting the subframe Length field (`:186-190`).

Then `amsdu_eapol_spoof++` and `last_sa/last_da/last_hit` are written (`:584`, `:598-600`). A plaintext A-MSDU claiming any *other* EtherType returns silently (`:583`) and is counted by no branch at all, because `first_frag_ethertype()` declines A-MSDUs (`:166`) so FRAG_PLAINTEXT never sees it either.

`rule_fragattack()` fires `ALERT_TYPE_FRAG_AMSDU_EAPOL` at CRIT when `amsdu_eapol_spoof > 0` (`src/alerts/rules_twin.c:666-680`). Key `fragamsdueapol:<BSSID>` (`:667`) - per BSS, so a second offending source on the same BSS joins the open incident. Detail `"%u plaintext A-MSDU frame%s on %.17s whose first subframe claims to carry EAPOL - last %.17s -> %.17s (CVE-2020-26144)"` (`:668-673`). `match_ip` NULL, `match_port` 0 (`:678-679`), so no per-alert pcap (`src/alert_pcap.c:105`). No escalation. The incident resolves 300 s after the last tick that re-asserted it (`include/sloth.h:860`), which in practice means only when the 64-row BSS table evicts the row (`src/fragattack.c:47-48`, STAB_OLDEST on `last_seen`, which `bss_get()` refreshes on every data frame on that BSS, `:220-228`) or the process restarts. `last_sa`/`last_da` are one pair per BSS row written by every FragAttacks branch, so the pair in the detail may belong to a later hit of a different kind.

**The offset the rule reads is not the offset the CVE describes.** The CVE record says devices "accept plaintext A-MSDU frames as long as the first 8 bytes correspond to a valid RFC1042 (i.e., LLC/SNAP) header for EAPOL" [3]; the paper's Figure 8 shows those 8 bytes (`AA AA 03 00 00 00 88 8E`) occupying the first subframe's Destination field and the first two bytes of its Source field, with the subframe Length and the first subframe's body free for the attacker ("green ones can have any value") and the injected packet in subframe 2 [2, Section 6.5]. sloth reads the LLC/SNAP at body offset 14, the first subframe's *payload*. Nothing in the attack puts an EAPOL EtherType there, so the paper's frame does not trip this rule; the frame that does - a plaintext A-MSDU whose first subframe really carries an EAPOL MSDU - is one the paper does not describe. The repo's test builds the frame the code's way (`build_amsdu`, `tests/test_fragattack.c:1224-1248`, LLC at `sub_hdr + 14`, `:1242`), so it proves the code against its own model, not against Figure 8.

## The mechanism

A receiver in a protected network must accept plaintext EAPOL data frames while a client is connecting, because the 4-way handshake runs before the pairwise key exists; the receiver tells them apart from other plaintext by the LLC/SNAP header carrying EtherType 0x888E [2, Section 6.5]. CVE-2020-26144 is what happens when that check is applied to a frame whose A-MSDU Present bit is also set: "an adversary can construct a plaintext A-MSDU whose first 8 bytes can also be interpreted as a valid EAPOL LLC/SNAP header ... Although this causes the destination and source address of the first subframe to be invalid, meaning the receiver drops this subframe, other subframes are still processed. Hence, an attacker can inject arbitrary packets against devices that accept plaintext A-MSDUs whose first 8 bytes equal an EAPOL LLC/SNAP header" [2, Section 6.5]. The project site's one-line description is "Accepting plaintext A-MSDU frames that start with an RFC1042 header with EtherType EAPOL (in an encrypted network)" [4]. It is the plaintext half of the same unauthenticated-aggregation-flag design flaw whose encrypted half is `FRAG_AMSDU` (CVE-2020-24588), and the paper's Section 6.6 chains it with the EAPOL-forwarding bug (`FRAG_EAPOL_RELAY`) so the aggregation attack needs only a multi-channel MitM position [2, Section 6.6]. The repo corpus states the detector's premise: real EAPOL "is always its own MPDU, never a subframe of an aggregated one" [1]; the Linux transmitter bears that out - `ieee80211_xmit_fast()` refuses the A-MSDU path for the control-port (EAPOL) EtherType before anything else is considered [10].

What sloth sees is the injected frame on the air; whether the victim parsed it as an A-MSDU and processed subframe 2 is a decision inside the receiver, which the paper found varies by device and, for some, by whether a handshake was in progress [2, Section 6.5]. The alert says "transmitted", not "accepted".

Tooling: the author's test suite has `eapol-amsdu I,P` ("Send a plaintext A-MSDU containing a ping request cloacked as an EAPOL frame"), `eapol-amsdu BP` (sent during the handshake), and the `eapol-amsdu-bad` malformed variants [5].

## Evidence that proves it

What sloth records: the `alert`/`alert.create` JSONL under key `fragamsdueapol:<BSSID>` with the detail (frame count, BSSID, `last SA -> DA`); the `alerts` row in sloth.db for the same key with `first_seen`, `last_seen`, `count` (= evaluations) and `reopens`; the `[c]` FragAttacks view row for that BSSID showing `amsdu_eapol_spoof`, the pair, age and the `protected_frames` gate count (`docs/views/fragattack.md`). No pcap, no evidence-frame IDs.

What makes it real: on the named BSSID, a QoS Data frame with Protected = 0, the A-MSDU Present bit set, fragment number 0, whose first subframe payload begins `AA AA 03 00 00 00 88 8E` - and a Protected frame from the same SA on the same BSSID earlier in the capture. The paper's attack frame has that byte string at A-MSDU body offset 0 instead, and its first subframe Length is small with the injected IP/ARP packet in subframe 2 [2, Section 6.5]; an external capture should be read at both offsets.

What refutes it: the frame is not an A-MSDU (the bit mis-decoded) and offset 14 of a plain body merely happens to read as an EAPOL SNAP; or the "witnessed install" for SA is an unrelated earlier session on a 128-row station table that never ages (`src/fragattack.c:69-70`), i.e. an open-network frame from a MAC that once sent protected traffic on the same BSSID.

## Benign causes

- **Essentially none for the matched shape.** No stack aggregates EAPOL: the repo corpus [1] and the detector comment (`src/fragattack.c:575-581`) state it, and the Linux transmitter enforces it (`ieee80211_xmit_fast()`, "control port protocol needs a lot of special handling", returns false before A-MSDU building [10]).
- **A-MSDU bit mis-decode plus coincidental bytes.** A plaintext non-A-MSDU frame whose body bytes 14-21 read `AA AA 03 .. 88 8E` would need both the QoS A-MSDU bit misread by the capture path and an 8-byte coincidence. Stated from the frame format (`src/fragattack.c:191-202`), not independently sourced; treat as negligible.
- **Stale gate.** `g_sta` rows are evicted only by pressure (128 rows, `src/fragattack.c:69-70`), so a station that sent protected traffic days ago primes the gate for any later plaintext frame with that SA on that BSSID. For this branch that still needs a plaintext A-MSDU claiming EAPOL, so the stale gate widens the window rather than creating a false signal.

## Assessment

CRIT is right for the frame the rule matches: on a BSS where this source already encrypted, a plaintext aggregated frame whose first subframe claims to be an authenticator message has no conforming reading and is the "cloaked" shape in spirit. The honest caveat is about *which bytes*: the rule reads the first subframe's payload LLC/SNAP (body offset 14), while the CVE and Figure 8 describe the EAPOL LLC/SNAP in the first 8 bytes of the A-MSDU body [2, Section 6.5][3]. As implemented the rule would miss the paper's frame and the test suite's `eapol-amsdu` cases [5], and fire on a frame nobody has described. The fix is cheap and the evidence is in the clear either way: compare body bytes 0-7 against `AA AA 03 00 00 00 88 8E` (the CVE's shape) as well as the existing offset-14 read, and say in the detail which matched. Until then, a firing is a real plaintext-A-MSDU anomaly on a protected BSS, but not necessarily CVE-2020-26144's frame.

Prevalence: an implementation flaw found across several client stacks and FreeBSD in 2021, some only during the handshake [2, Section 6.5]; CVSS 3.1 6.5 from both NVD and Cisco [3][6]; patched across vendors (62 advisory links in the author's index [9]); no in-the-wild use reported by the author or the Wi-Fi Alliance [4][7]. An attacker needs radio range and a multi-channel MitM or an injection-capable card; sightings should be rare.

Reference host: not seen (null). The behavioural note stands from the count semantics: the counter never decays and the row is refreshed by every data frame on the BSS, so one frame would present as one permanent CRIT advancing at least 4 evaluations a second (the measured family rate on this host is far above the floor; see the FRAG_* siblings) - the detail's leading integer is the frame count, `count` is not.

Sufficient to act on alone? It is a strong lead that something on that BSS transmitted a plaintext aggregated frame it should not have. A responder should (1) read the `[c]` view for the pair and the gate count; (2) capture the channel externally and inspect the A-MSDU body at offset 0 and offset 14, and subframe 2, to decide whether it is the CVE's cloak, a genuinely aggregated EAPOL (vendor bug) or a mis-decode; (3) patch the receivers on that BSS against the vendor advisory [9] regardless, since the paper's cloak is only dangerous to unpatched stacks; (4) follow `docs/wiki/alert-remediation.md:1140-1154`. No tuning knob exists; `--hop` only lowers true-positive sensitivity by un-priming the gate.
