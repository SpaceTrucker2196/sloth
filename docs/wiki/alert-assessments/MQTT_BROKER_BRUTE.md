## What the rule checks

Input: `s->mqtt_flows`, the MQTT flow table of `MAX_MQTT_FLOWS` = 32 rows keyed by **(client IP, broker IP)**, with the client taken as whichever side is not on port 1883 (`include/sloth.h:443-475`; `src/mqtt_snoop.c:16-22`, `:188-195`). `mqtt_snoop_observe()` takes any TCP payload with 1883 on either side (`:167`; dispatched from `src/capture/capture.c:733-738`), reads the fixed-header type nibble and the 1-4 byte Remaining Length varint (`:169-182`), and handles CONNECT, CONNACK, SUBSCRIBE and PUBLISH (`:171-172`). For a CONNECT it walks the variable header and payload to pull the protocol level and, if the Username Flag is set, the username, copied only if every byte is printable ASCII (`:78-161`, `:203-204`, `:231-237`). For a CONNACK it reads byte 1 of the body as the return/reason code and tests it with `connack_is_failure()`: for protocol level <= 4 (v3.1.1 and earlier) the failures are codes 1..5; for v5 anything >= 0x80 (`:36-44`, `:205-216`, `:238-240`). Crucially the CONNACK handler has no stored protocol level to consult and hardcodes `pl = 4` (`:211-214`), so every CONNACK is scored by v3.1.1 rules; on a v5 flow a reason code in 1..5 would be misread as a failure and a code >= 0x80 correctly caught, but the two schemes are conflated. CONNECT increments `connect_count`; a failing CONNACK increments `connack_fail_count` (`:231-240`). Both are lifetime totals; nothing decays them, and a retransmitted segment is counted again. MQTT on 8883 (TLS) or over WebSockets is not seen here (`docs/wiki/mqtt-snoop.md:129-132`).

Per tick the rule fires for any row where `connect_count >= MQTT_BROKER_BRUTE_CONNECTS` OR `connack_fail_count >= MQTT_BROKER_BRUTE_FAILS` (`src/alerts/rules_wired.c:1118-1119`, `:1124-1126`), defaults **10** and **5** (`src/tune.c:61-62`: `mqtt.brute_connects` and `mqtt.brute_fails`, each min 2, max 1000). Key: `mqtt-brute:<client>-><broker>` (`:1128-1130`). Detail: `"<client>-><broker>: <c> CONNECTs / <f> fails (user=<last_username, 16>)"` with `?` when no username was seen (`:1131-1136`). CRIT, `match_ip` = the client, `match_port` 1883 (`:1137-1139`; `docs/wiki/mqtt-snoop.md:77-83`). The incident resolves 300 s after the last tick that re-asserted it (`include/sloth.h:860`). The 32-row table evicts the least-recently-seen pair when full (`STAB_OLDEST`, `src/mqtt_snoop.c:21-22`; `src/stab.h:27`; tallied as `evict_mqtt_flow`, `src/sensor_health.h:101`) and never expires rows by age; a process restart empties it (`:259-263`).

## The mechanism

MQTT is the dominant IoT publish/subscribe protocol; "TCP ports 8883 and 1883 are registered with IANA for MQTT TLS and non TLS communication respectively", and the 1883 path is cleartext [3]. The OASIS v3.1.1 spec requires that "After a Network Connection is established by a Client to a Server, the first Packet sent from the Client to the Server MUST be a CONNECT Packet", whose Protocol Name is "MQTT" and whose Protocol Level for v3.1.1 "is 4 (0x04)" [3]. The broker answers with a CONNACK whose return code is 0 "Connection Accepted" or, among others, 4 "Connection Refused, bad user name or password" and 5 "Connection Refused, not authorized" [3] - the two codes that mean a credential was rejected, which is what `connack_fail_count` counts.

Guessing those credentials is T1110.001 Password Guessing, "guess passwords ... using a repetitive or iterative mechanism" against a service that checks them [2]. The corpus gives MQTT its own rule under T1110 and describes the on-wire failure as "CONNACK with a non-zero return code" [1]. The attack surface is the IoT one: the wiki notes every botnet that carries SSH credentials also carries MQTT ones and that Mirai descendants "routinely sweep 1883 with the same admin/admin wordlists", and that many brokers shipped `allow_anonymous true` (`docs/wiki/mqtt-snoop.md:14-19`). The Mirai study documents the family it descends from: BASHLITE and Mirai "infected Linux devices by brute forcing default credentials", Mirai using "a dictionary of 62 username/password pairs" against devices reached on Telnet [4] - MQTT brokers are the same class of weakly-defaulted IoT target. Mosquitto's own 2.0 migration made `allow_anonymous` default to false and bound the broker to loopback by default, "to help encourage end users to take an informed choice about security, rather than just relying on the previously very forgiving defaults" [5], which is both the fix and the admission that the old default was the problem. The OASIS security chapter does not define a lockout; it notes only that "Deployments might use network level controls (where available) to implement rate limiting" (§5.4.8) [3], so a passive detector like this one is filling a gap the protocol leaves open.

## Evidence that proves it

What sloth records:

- `alert` / `alert.*` JSONL under `mqtt-brute:<client>-><broker>` with both counters and the last username;
- `mqtt_flow` state records keyed on `(src_ip, dst_ip)` (`docs/wiki/jsonl-schema.md:732`): `connect_count`, `connack_fail_count`, `subscribe_count`, `publish_count`, `proto_level`, `last_username`, `first_seen`, `last_seen`;
- a per-alert pcap if `--pcap-dir` is set (CRIT passes the default `pcap.min_severity` 2, `src/tune.c:121`); the filter is `match_ip` = the client and port 1883 either side (`src/alert_pcap.c:104-114`), so the file holds that client's MQTT from the ring: CONNECTs with their usernames and protocol levels, and CONNACKs with their reason codes, all cleartext.

What points to an attack: `connack_fail_count` rising (the broker explicitly refusing, codes 4 or 5 [3]) - the stronger signal, and the reason the fail threshold is lower; a `connect_count` that climbs with `publish_count == 0` and `subscribe_count == 0`, the shape of a client that never gets past authentication (`docs/wiki/mqtt-snoop.md:116-118`); `last_username` that is or rotates through watchlist values like `admin`, `root`, `mqtt`, `test` across the record stream (`:118-121`); and an external or unknown client. The pcap settles which path tripped and whether any CONNECT was accepted.

What refutes it: a `connect_count` that is high but paced like reconnects (a flaky device re-establishing on backoff, `docs/wiki/mqtt-snoop.md:98-101`) with `connack_fail_count == 0` and healthy `publish_count`/`subscribe_count`; a stable `last_username` that is the device's own account; `proto_level` consistent across the flow. A single misconfigured device with a stale credential produces `connack_fail_count` climbing indefinitely from one source, which the corpus names as the common benign trigger [1], `docs/wiki/alert-remediation.md:421-437`.

## Benign causes

- **Reconnecting devices (connect-count path).** MQTT clients reconnect on disconnect; a flaky link, an aggressive keepalive, or a boot loop produces many CONNECTs over the row's life, and the lifetime counter never decays (`src/mqtt_snoop.c:232`; no `stab_expire`), so a chatty device crosses 10 on its own (`docs/wiki/mqtt-snoop.md:98-101`).
- **Stale credential (fail path).** A device whose stored username or password is wrong re-tries forever and accumulates CONNACK failures from one source - the single most common benign trigger for the family [1]; it is a real finding (fix the device) but not an attack.
- **Provisioning.** A new device "might generate one or two" CONNACK failures during initial provisioning (`docs/wiki/mqtt-snoop.md:102-103`); several devices onboarded together can approach the fail threshold.
- **v5 reason-code conflation.** The CONNACK decoder hardcodes v3.1.1 semantics (`src/mqtt_snoop.c:211-214`), so a v5 broker that returns a reason code in 1..5 for a non-auth reason would be miscounted as a failure; the risk is bounded because the fail path still needs five such codes.
- **NAT and shared gateways.** Several devices behind one address are one row; their CONNECTs and failures sum.

## Assessment

The dual-threshold design is the right instinct and the two paths deserve different confidence. The CONNACK-fail path is specific: the broker has told sloth, in cleartext, that it refused the credential five times (codes 4 or 5 [3]), which no healthy client produces, so CRIT is justified there. The connect-count path shares the structural flaw of the SSH and RDP rules - a lifetime connection total with no window - and on an IoT segment, where devices reconnect constantly, it will fire on the chattiest benign device as readily as on a sweep; for that path alone WARN would describe the evidence. Two refinements worth considering: window `connect_count`, and record the protocol level from the CONNECT so the CONNACK decoder stops assuming v3.1.1 for every flow (the `mqtt_flow` row already carries `proto_level`, set from the last CONNECT at `src/mqtt_snoop.c:233`, so the decoder could consult it). The alert page should also say which threshold tripped, since "10 CONNECTs" and "5 auth refusals" are not the same finding.

Prevalence: MQTT has its own corpus rule under T1110.001 [1]; the explicit auth-failure codes are defined by the spec [3]; the IoT-sweep framing is the wiki's, grounded in the Mirai family's documented default-credential brute-forcing [4]; and Mosquitto's 2.0 default change is evidence the exposure was real and widespread [5]. No fetched source quantifies an MQTT field rate, so none is claimed.

Reference host: not seen (null) - consistent with no cleartext MQTT on the monitored segment (no broker on 1883, or a TLS-only broker on 8883, which sloth cannot read past the handshake). The behavioural note for an operator who deploys on an IoT segment: the connect-count path will produce one standing incident per chatty device, so expect those and read `connack_fail_count` and `publish_count`/`subscribe_count` to separate a reconnecting device (fails 0, publishes present) from a sweep (fails rising, publishes 0).

Sufficient to act on alone? For the fail path, close - five explicit auth refusals from one source is a real finding; for the connect-count path, no, it is a prompt. A responder should (1) read which threshold tripped and the `mqtt_flow` counters - `connack_fail_count` high is an auth attack, `connect_count` high with publishes present is a reconnecting device; (2) open the per-alert pcap and read the CONNACK reason codes and the CONNECT usernames, all cleartext [3]; (3) read the broker's log for the accounts tried and any success [1], `docs/wiki/alert-remediation.md:421-437`; (4) if an attack, block the source and ensure the broker requires authentication and does not allow anonymous connections [5]; if a stale-credential device, fix or remove it. Tuning: the two thresholds are independent, so raise `mqtt.brute_connects` on a segment of reconnecting devices while keeping `mqtt.brute_fails` low, which preserves the specific signal and drops the noisy one.
