## What the rule checks

Input: `s->http_log`, the HTTP observation ring of `MAX_HTTP_LOG` = 256 rows (`include/sloth.h:1145`, `:3511`), each an `http_log_entry_t` with `src`, `dst`, ports, `method`, `host`, a `path` of up to 127 bytes and the response-side fields (`include/sloth.h:1154-1189`). The parser copies the request URI into `path` (`src/http_log.c:478-480`); it runs on TCP payloads whose either port is 80, 8080 or 8000 (`src/capture/capture.c:795-796`). `http_log_record()` appends with no time expiry: when the ring is full the oldest row is overwritten and an eviction is tallied (`src/http_log.c:712-727`, the `full` branch at `:722-725`). `http_log_snapshot()` (`:731`) copies the ring into the state each poll (`src/poll.c:171`). A response is paired to its request by the reversed four-tuple and, when unambiguous, receives the request's `host` and `path` (`src/http_log.c:288-305`, the copy at `:300-301`); the response row's `src` is the server, because the response travels server to client (`:292-293`).

The matcher `attack_path_match()` (`src/alerts/rules_wired.c:264-283`) walks a 20-row static table (`:241-262`) and returns the first label whose needle is a case-insensitive (ASCII-folded) substring of the path: `../`, `..%2f`, `..%5c` (path traversal), `/etc/passwd`, `/etc/shadow`, `c:\windows`, `<script`, `javascript:` (XSS), `%00` (null byte), `union+select`, `union%20select`, `'+or+'1`, `'+or+1=1` (SQL injection), `${jndi:` (log4shell), `cmd.exe`, `/bin/sh`, `/bin/bash` (RCE), `wget+http`, `curl+http` (RCE download), `;nc+-` (RCE listener). The code comment says what the table is: high confidence, not exhaustive; encoded variants and novel payloads miss (`:233-237`).

Per tick `rule_attack_path()` (`:292-310`) walks every request row, skipping any row with `is_response` set (`:295`, #197), and for each match keys on `path:<src>:<label>` (`:300`), renders `"<src,20> -> <host,20> <path,30> [<label,14>]"` (`:301-306`) and fires CRIT with `match_ip` = the row's `src` and `match_port` fixed at 80 (`:307-308`). Three consequences follow from the code. First, the key is per (source, label), so one scanner sending traversal and SQLi probes mints two incidents, and ten traversal probes mint one. Second, the finding is attributed once, to the client that asked: before #197 (2026-11-12) the rule also matched paired responses, which carry the request's path with `src` = server, so the same probe fired a second key `path:<server>:<label>` with `match_ip` = server - the victim reported as its own attacker at CRIT, with the per-alert pcap and the device's `ALERT_TAGGED` bit pointed at it (field evidence in issue #197: every `.242` key had a `.245` mirror with identical first and last seen times). Third, `match_port` is 80 even for a flow on 8080 or 8000, and the per-alert pcap filter requires the port to match when it is non-zero (`src/alert_pcap.c:103-113`), so the pcap for a probe on 8080 holds nothing from that flow.

The engine increments `evaluations` (and the `count` alias) on every `fire()` under an open key (`src/alerts/engine.c:475-481`), resolves a key no rule re-asserted for `ALERT_RESOLVE_AFTER_S` = 300 s (`include/sloth.h:860`; `src/alerts/engine.c:927-935`) and opens a new incident, with `reopen_count` carried from the side table, when the key fires again (`:543-547`, `:594-598`). The `--db` `alerts` row folds every later incident on a key into its `reopens` column (`src/db_schema.c:534-545`). The rule runs right after `rule_attack_tool_ua` (`src/alerts/rules_table.c:96-97`). Tests: `tests/test_alerts.c:3418-3465` (traversal, SQLi, log4shell, raw `<script`, and the no-fire case), with the note at `:3448-3451` that the percent-encoded `<script>` is not caught.

## The mechanism

T1190 is initial access through something reachable from outside: "Adversaries may attempt to exploit a weakness in an Internet-facing host or system to initially access a network", and "Exploited applications are often websites/web servers" [3]. ATT&CK's procedure examples name the shapes on sloth's table: SQL injection and directory traversal (APT41, APT39), and VMware Horizon gateways "vulnerable to several Log4Shell vulnerabilities, including CVE-2021-44228" [3]. Path traversal "aims to access files and directories that are stored outside the web root folder" by "manipulating variables that reference files with 'dot-dot-slash (../)' sequences and its variations", where `..%2f` represents `../` and `..%5c` represents `..\`, the canonical target being `/etc/passwd` [5] - which is why three traversal spellings and two `/etc/` paths sit in the table. SQL injection "consists of insertion or 'injection' of a SQL query via the input data from the client" [6]. `${jndi:` is the Log4Shell trigger: CVE-2021-44228, CVSS v3.1 10.0 Critical, added to CISA's KEV on 2021-12-10 [7]. Scanning for these is its own technique, T1595.002: "Adversaries may scan victims for vulnerabilities that can be used during targeting" [4], and the repo's T1595 corpus document lists `ATTACK_PATH` under it for that reason [2].

The corpus states the limit precisely. The alert matches "request paths that exist only in exploit lists and scanner wordlists"; the 404 the server returns "is not the point: the *asking* is". But "neither alert observes a compromise. A request for an exploit path is a request"; "background scanning is the weather" for anything reachable, and "volume here is not a measure of risk; the target is"; and "HTTPS hides both" - the rule reads cleartext HTTP only [1]. The T1190 mapping is therefore a mapping of intent: what was asked for is an exploit, whether or not one landed.

## Evidence that proves it

What sloth records:

- `http` JSONL records for the request (`src`, `host`, `method`, `path`, `ja4h`; `docs/wiki/jsonl-schema.md:229-241`) and, when paired, for the response carrying the request's `host`/`path` plus `status` (`:243-248`), so the answer to the probe is on the stream even though the rule ignores it;
- `alert` / `alert.create` ... `alert.resolve` under `path:<src>:<label>`; `count` is evaluations, not requests (`docs/wiki/jsonl-schema.md:391`), and each return of the source after a resolve is a new `incident_id` (`:442-445`);
- the `--db` `alerts` row with `reopens`;
- a per-alert pcap if `--pcap-dir` is set (CRIT passes default `pcap.min_severity` 2, `src/tune.c:121`); filter `match_ip` = source and port 80 either side (`src/alert_pcap.c:103-113`), so the file holds the source's port-80 HTTP from the ring, including the request line that matched - and nothing from a flow on 8080/8000.

What makes it real: the target `host` runs what the path is for (a WordPress path on a WordPress host, a JNDI string at a Java service), the paired response `status` is not 404, the same source also fires `ATTACK_TOOL_UA` or `PORT_SCAN`, or the source is internal (a LAN host probing a LAN host is not background noise) (`docs/wiki/alert-remediation.md:65-67`). What makes it benign: the source is a public scanner hitting a host that does not run the software, every response is 404, and the path is one of the substring collisions below. What refutes it: the `path` field read in full shows the needle inside an ordinary URL. (A key under the server IP with the same first and last seen as a client's key is the pre-#197 response duplicate in older `--db` rows or JSONL, not a second actor.) Absence is not assurance: a probe over HTTPS, on a port other than 80/8080/8000, or in an encoded form not on the table produces nothing [1].

## Benign causes

- **Ordinary URLs containing a needle.** The match is a raw case-insensitive substring (`src/alerts/rules_wired.c:264-283`): a relative `../` in a badly-built link, `<script` in a search query about scripting, `%00` in an opaque token, `/bin/sh` or `cmd.exe` in a documentation or paste URL. OWASP notes web containers decode percent-encoding once [5], which is why the encoded traversal spellings are on the table, and also why a decoded ordinary string can land on a needle.
- **Authorised vulnerability scanning.** An operator's own scanner sends exactly these paths by design [4]; nothing in the request line says who runs the tool.
- **The paired response (fixed in #197).** A response matched to its request carries the request's `path` with `src` = server (`src/http_log.c:300-301`), and until 2026-11-12 a single probe opened a second incident keyed on the server with `match_ip` = server. The rule now skips response rows (`src/alerts/rules_wired.c:295`); history recorded before the fix still holds the duplicates.
- **Background internet scanning.** On a host reachable from the internet the probes never stop, and the corpus says to read the target, not the volume [1]. The host data below is what that looks like.

## Assessment

CRIT is the one thing to argue with. The rule's own comment calls it high confidence but not exhaustive (`src/alerts/rules_wired.c:233-237`), and that is true of what it matches; what it cannot do is tell a probe from an exploit, because the response is not consulted even though a paired response's `status` is in the same ring (`src/http_log.c:300-301`; `docs/wiki/jsonl-schema.md:243-248`). The corpus is explicit that the alert "does not observe a compromise" and that background scanning is continuous [1]. A CRIT that fires on weather trains the operator to ignore CRIT. Two refinements would make the level honest: open at WARN and escalate to CRIT when the paired response status is 200 or 500 rather than 404 (the engine already emits `alert.escalate` for a severity rise, `src/alerts/engine.c:36-45`); and skip rows with `is_response` set so the server-side duplicate key disappears - done in #197 (2026-11-12); the escalation is not. The T1190 mapping itself is right - it names what was attempted - and T1595 is the correct companion for the scanning half [2].

Prevalence: exploitation of public-facing applications is a standing initial-access technique [3], scanning for it is a technique of its own [4], and the table's `${jndi:` needle is a 10.0-scored KEV entry [7]. No fetched source quantifies a field rate and none is claimed; the corpus's qualitative claim is that anything reachable receives this traffic continuously [1].

Reference host: 3,961,645 fires on 14 keys, max CRIT, 570 reopens, first 2026-10-14, last 2026-11-03. Keys are per (source, label), so fourteen source/label pairs were ever seen; some of those are probably the server-side duplicates described above (removed by #197), which would halve the number of actors. The 283k evaluations per key bound the standing time at about 20 h at the 4 ticks/s floor; the CLEARTEXT_CRED arithmetic on the same host, where each key stood for the whole span, shows the loop averaged about 10 ticks/s, which puts the figure nearer 8 h per key in total. Spread across about 41 incidents per key that is minutes per incident: a matching request lands in the ring, is re-fired every tick until 256 newer HTTP rows evict it, the key resolves 300 s later, and the next probe from the same source reopens it. 570 reopens in 20 days is about 28 a day, the signature of recurring background scanning of a reachable host rather than 570 attacks. The alert page should show incidents, first/last seen and `reopens`, label the engine `count` as evaluations, and show the paired response status beside the path.

Sufficient to act on alone? No - it is a lead that names the source and the target. A responder should (1) read the full `path` and the `host`, and decide whether the target runs what the path is for (`docs/wiki/alert-remediation.md:572-576`); (2) read the paired `http` response `status` on the JSONL stream or the target's access log - a 200 to an exploit path is the finding, a 404 is a scan; (3) read the other alerts on the same source (`ATTACK_TOOL_UA`, `PORT_SCAN`); (4) if the target is exposed and unpatched, patch or take it off the exposed path, and block the source if it persists (`:578-586`). There is nothing to tune; the table is compile-time, and the right change is in the rule (escalate on response; response rows are skipped since #197), not in a threshold.
