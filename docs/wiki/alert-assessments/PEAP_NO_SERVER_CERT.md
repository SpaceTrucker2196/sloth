## What the rule checks

`rule_peap_no_server_cert()` (src/alerts/rules_enterprise.c:449-487) fires when a client here completed a TLS-in-EAP authentication without the AP ever presenting a server identity.

- **Input.** `s->rogue_radius[]` (MAX_ROGUE_RADIUS = 32, include/sloth.h:1781), per-BSSID 802.1X tracking. The relevant field is `nocert_sessions`, accumulated in `eap_track.c`.
- **How nocert_sessions is set** (src/eap_track.c:33-135). Per (BSSID, STA) session, between the first TLS-bearing EAP frame and the EAP-Success/Failure that resolves it, `eap_track` records whether the **AP** sent a TLS ServerHello (handshake type 2) and a Certificate (type 11), scanned by `tls_scan_handshake()` only on AP->STA frames (eap_track.c:120-131). On EAP-**Success** with `(!server_hello || !certificate)` it does `r->nocert_sessions++`, and `if (!ss->server_hello) r->nocert_no_hello++` (eap_track.c:101-108). On EAP-**Failure** nothing is recorded - "A Failure means the client refused - which is the supplicant behaving correctly" (eap_track.c:97-99). Direction matters: a Certificate travelling STA->AP is the client authenticating and does not count (eap_track.c:120-122).
- **Condition.** `if (r->nocert_sessions <= 0) continue;` (rules_enterprise.c:452), else fire.
- **Key.** `peapnocert:<bssid>` (rules_enterprise.c:463). The key is per BSSID but the detail names only `r->last_nocert_sta`, so two different clients failing against the same AP share one incident and the detail shows whichever failed last.
- **Detail.** `<sta> -> <bssid> EAP-Success with no <TLS ServerHello | Certificate observed> (N session(s))` plus `- YOUR network` / `- rostered client`. The ServerHello-vs-Certificate wording (rules_enterprise.c:466-474) encodes confidence: no ServerHello = no AP-sent ServerHello was *captured* between the first TLS-bearing EAP frame and EAP-Success (the strong form - but a frame the monitor radio missed, during a `--hop` dwell elsewhere or a capture drop, yields exactly this; the code cannot tell "never sent" from "not heard"); no Certificate = ServerHello seen but Certificate not, which "a large cert chain can also cross an EAP fragment boundary we do not reassemble". The choice is cumulative per BSSID, not per session: the detail says "TLS ServerHello" whenever `nocert_no_hello > 0`, i.e. if *any* recorded session on that BSSID lacked a ServerHello, even when later sessions were Certificate-only.
- **Severity.** CRIT when `ownership_is_my_bssid || ownership_is_known_device(sta)`, else WARN (rules_enterprise.c:483).
- **Count.** Plain `fire()`, no `match_ip` (802.1X/EAP, no IP yet), no evidence-ring citation. `nocert_sessions` is cumulative and the `rogue_radius` row is evicted only when the 32-row table is full and the row has the oldest `last_seen` (`STAB_OLDEST`, src/eap_track.c:18; no `stab_expire()` is ever called on this table), so once a bad session is seen the alert fires every poll until that eviction or process exit. There is no age-out, and `ALERT_RESOLVE_AFTER_S` never gets a chance to run because the rule re-asserts the key on every tick.

## The attack

T1557, Adversary-in-the-Middle: an adversary positions between two parties for sniffing, manipulation or replay [2]. The repo's enterprise-rogue page frames PEAP_NO_SERVER_CERT as the **client-side** half of the rogue-enterprise-AP problem, the complement of ROGUE_RADIUS (the AP-side half) [1].

WPA-Enterprise (802.1X) runs an EAP conversation between the client (supplicant) and a RADIUS server through the AP. In PEAP / EAP-TTLS / EAP-TLS, the server first proves its identity with a TLS handshake (ServerHello + Certificate) before the client sends inner credentials; the peer is expected to validate that certificate - RFC 5216 §5.3 says the EAP-TLS peer "SHOULD support validating the server certificate using RFC 3280 [RFC3280] compliant path validation" and that, once the session is up, peer and server "MUST validate that the identities represented in the certificate are appropriate and authorized"; PEAPv2 authenticates the server by certificate in normal operation and treats skipping the trust-anchor check as a provisioning mode that comes "at the cost of introducing man-in-the-middle vulnerabilities" [6a][6b]. If the client does not verify the server certificate, an attacker can stand up a rogue AP advertising the corporate SSID, skip proving who it is, and harvest the inner MSCHAPv2 challenge/response (offline-crackable) or, with a GTC downgrade, the plaintext password. eaphammer and hostapd-wpe automate exactly this - credential theft from WPA/WPA2-EAP networks, with eaphammer additionally doing an automatic GTC downgrade and hostapd-wpe impersonating PEAP/MSCHAPv2, the EAP-TTLS variants and EAP-FAST/MSCHAPv2 phase 0 [5a][5b].

CVE-2023-52160 is the specific flaw that makes the no-server-cert case a mass problem: "The implementation of PEAP in wpa_supplicant through 2.10 allows authentication bypass. For a successful attack, wpa_supplicant must be configured to not verify the network's TLS certificate during Phase 1 authentication, and an eap_peap_decrypt vulnerability can then be abused to skip Phase 2 authentication. The attack vector is sending an EAP-TLV Success packet instead of starting Phase 2" [3]. Vanhoef & Gollier's research put the affected population at ~2.3 billion Android users plus Linux and ChromeOS clients in the vulnerable configuration [4]. The upstream fix changed wpa_supplicant's default to require Phase 2 authentication, exposed via a new `phase2_auth` option [8].

The passive signal is an **absence**: in a sound exchange the AP's ServerHello and Certificate travel unencrypted inside EAP-Request frames, visible to a monitor radio; their absence before EAP-Success is the diagnostic [1][3]. This rule fires on the operator's own fleet doing the unsafe thing - it is silent until a device actually accepts an unverified server, which is why the enterprise-rogue page calls it "the more uncomfortable of the two" [1].

## Evidence that proves it

What sloth records:

- The alert detail: STA, BSSID, which half was missing (ServerHello vs Certificate), session count, ownership/roster tags.
- The `[z]` RADIUS view's `TLS?` column: `NONE` = a session completed with no server identity presented (fires this alert); `-` = no TLS-in-EAP session completed; a tick is never shown because "the absence of a finding is not proof the handshake was sound" (docs/views/rogue-radius.md:79-103, docs/wiki/enterprise-rogue.md "Export").
- JSONL: the alert persists in `alerts`; the `rogue_radius` table reports methods/identities observed (docs/views/rogue-radius.md:22 `eap_types_seen`). Note the enterprise-rogue page records that `nocert_sessions` is NOT a column in the persisted `rogue_radius` SQLite table (a schema-version cost).
- JSONL `eapol` records around the exchange (`msg_num`, `handshake_progress`, `assoc_evidence`) corroborate that an association formed.
- With `--collect-handshakes` + `--eapol-dir`, per-handshake pcaps capture the EAPOL/EAP frames (docs/wiki/pcap-export.md EAPOL section) - the route to confirming no ServerHello/Certificate by hand.

To call it real: the detail says **no TLS ServerHello** (the strong form - no AP ServerHello was captured; rule out capture gaps, e.g. a fixed-channel rather than `--hop` sensor, before reading it as "the AP never started TLS"), the BSSID is one the operator does not run, and ROGUE_RADIUS / EVIL_TWIN / KARMA_AP corroborate on the same BSSID (docs/wiki/enterprise-rogue.md "What to do when it fires"). The outer EAP identity, transmitted before any tunnel, is readable and tells you which account was exposed.

What refutes it (or weakens it): the detail says **no Certificate observed** (not "no ServerHello") - a ServerHello was seen, so the AP did start TLS, and a long certificate chain crossing an EAP fragment boundary sloth does not reassemble can produce this exact wording without any attack (eap_track.c / docs/wiki/enterprise-rogue.md "The honest limit: fragmentation"). On the operator's own BSSID the finding is still real but it is a *client misconfiguration* to fix, not an external rogue.

## Benign causes

- **A long server certificate chain that crosses an EAP-TLS fragment boundary** - sloth does not reassemble fragments, so the Certificate can be present on the wire but land past the first fragment; the "no Certificate observed" wording exists precisely to flag this (RFC 5216 §3.1 L/M/S fragmentation flags) [6a]. This is the main true false positive.
- **Server-unauthenticated provisioning modes** - PEAPv2/EAP-FAST anonymous provisioning deliberately runs without full server-cert validation (PEAPv2's provisioning mode: "the peer does not verify whether the certificate presented by the server chains to a provisioned trust anchor") [6b]; rare in ordinary enterprise use. Note this is a trust-anchor gap, not a missing Certificate message - the server still sends one, so this mode would not trip the rule's "no Certificate observed" branch on its own.
- Not a benign cause but worth stating: EAP-Failure never fires this (the client refused - the safe outcome), and non-TLS methods like EAP-MD5 are not tracked here (ROGUE_RADIUS covers them) - so the rule does not double-report.

## Assessment

**Severity.** WARN off-network, CRIT on `--my-bssid` or a `--known-macs` STA, is correct and well-reasoned: the CVE's actual population is the operator's own fleet, so "your device demonstrating it would fall for a rogue enterprise AP" is the CRIT case (rules_enterprise.c:483-487, docs/wiki/enterprise-rogue.md "Severity").

**Prevalence.** The vulnerable configuration is historically enormous - billions of Android devices plus Linux/ChromeOS shipped able to skip server-cert validation [3][4]. Whether a given alert means an active rogue is present depends on the BSSID: on a foreign BSSID it may be a live lure; on the operator's own BSSID it is a client-config exposure waiting to be exploited.

**Reference host noise verdict.** Quiet. 1,552,627 fires on 1 key, WARN. One key = one BSSID that recorded at least one no-server-cert session; because `nocert_sessions` is cumulative and sticky until the `rogue_radius` row evicts, the alert then fires every poll, so ~1.55M fires at ~4 Hz is ~108 hours of the counter standing non-zero, not 1.55M sessions. The number of *sessions* is in the detail's `(N session(s))`, not in the fire count. The JSONL stream is one `alert.create` plus throttled detail updates, so there is no stream firehose and no dedupe needed. If presentation surfaces the per-tick `count`, it should instead show `nocert_sessions` and the incident lifecycle. No threshold exists to tune (the trigger is simply `> 0`), which is correct - one accepted unverified server is a finding.

**Is the evidence sufficient to act on?** For "no ServerHello", yes on a fixed-channel sensor - no AP ServerHello was captured and the client accepted success anyway. On a hopping sensor confirm from the per-handshake pcap first, since a missed frame looks identical. For "no Certificate observed", treat it as probable but confirm against the fragmentation caveat, ideally from the per-handshake pcap.

**First step for a responder.** Identify the client from the STA address and the leaked outer identity, and check the BSSID: if it is not yours, you may be looking at a live rogue (corroborate with ROGUE_RADIUS/EVIL_TWIN on that BSSID) and the named account's credentials should be treated as exposed; if it is yours, the finding is the supplicant's configuration - set `ca_cert` and `domain_suffix_match`/`domain_match` and update wpa_supplicant past the CVE-2023-52160 fix.
