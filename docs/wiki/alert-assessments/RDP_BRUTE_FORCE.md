## What the rule checks

Input: `s->rdp_flows`, the RDP flow table of `MAX_RDP_FLOWS` = 64 rows keyed by **(client IP, server IP)** (`include/sloth.h:375-404`; `src/rdp_snoop.c:16-22`). `rdp_snoop_observe()` takes any TCP payload with 3389 on either side (`:103`; dispatched from `src/capture/capture.c:722-727`) and requires a TPKT envelope (version 0x03, reserved 0x00, length at least 11 and within the segment, `:105-108`) wrapping an X.224 TPDU whose code nibble is `0xE0` Connection Request with DST-REF `0x0000` (`:110-118`) - the Client X.224 Connection Request PDU that MS-RDPBCGR §2.2.1.1 defines as "sent from client to server during the Connection Initiation phase of the RDP Connection Sequence", a 4-byte `tpktHeader` and a 7-byte `x224Crq` followed by an optional cookie and an optional `rdpNegReq` [3]. Only the client-to-server direction can match, because a Connection Confirm has code `0xD0` and is rejected by the CR check (`:126-139`). From the user data it pulls the cookie - "Cookie: mstshash=IDENTIFIER" terminated by `0x0D0A` [3] - into `last_cookie` (`:53-78`, `:162-163`), and the `requestedProtocols` of the 8-byte RDP Negotiation Request (type 0x01, length 0x0008 [4]) OR-ed into `proto_mask` after masking to the low nibble (`:80-97`, `:164`). Each qualifying PDU increments `connect_req_count` (`:161`). One Connection Request begins each RDP connection; authentication (CredSSP, TLS) happens afterwards and is opaque, so the count includes connections that logged in successfully (`docs/wiki/rdp-snoop.md:20-22`, `:114-117`). The observer keeps no per-connection state, so a retransmitted CR segment counts again. RDP on a port other than 3389 is not observed (`:103`). The counter is a lifetime total for the row; nothing decays it.

Per tick the rule fires for any row whose `connect_req_count` is at or above `RDP_BRUTE_FORCE_THRESHOLD` = `tune_val(TUNE_RDP_BRUTE_FORCE)` (`src/alerts/rules_wired.c:1051`, `:1056`), default **10** (`src/tune.c:59`: `rdp.brute_force`, min 2, max 1000, unit "attempts"). Key: `rdp-brute:<client>-><server>` (`:1058-1060`). Detail: `"<client>-><server>: <n> RDP CRs (brute-force; user=<last_cookie, 20>)"` with `?` when no cookie was seen (`:1061-1065`). CRIT, `match_ip` = the client, `match_port` 3389 (`:1066-1068`; `docs/wiki/rdp-snoop.md:68-74`). The incident resolves 300 s after the last tick that re-asserted it (`include/sloth.h:860`). The 64-row table evicts the least-recently-seen pair when full (`STAB_OLDEST`, `src/rdp_snoop.c:21-22`; `src/stab.h:27`; tallied as `evict_rdp_flow`, `src/sensor_health.h:99`) and never expires rows by age; a process restart empties it (`:175-179`).

The rule's comment speaks of "ten or more X.224 Connection Requests ... inside the active window" and of tools that "open a fresh TCP connection per credential attempt" (`src/alerts/rules_wired.c:1039-1050`). The first half is right about the unit; there is no window.

## The mechanism

RDP is the Windows remote-desktop and remote-administration protocol on TCP/3389 (`docs/wiki/rdp-snoop.md:9-14`). MITRE T1110.001: "Adversaries with no prior knowledge of legitimate credentials within the system or environment may guess passwords", with "RDP / Terminal Services (3389/TCP)" in its list of targeted services, and the mitigation "Set account lockout policies after a certain number of failed login attempts to prevent passwords from being guessed" [2]; the parent technique's procedure list has Fox Kitten, which "has brute forced RDP credentials" [7]. The FBI's September 2018 PSA describes the operational picture: "Malicious cyber actors have developed methods of identifying and exploiting vulnerable RDP sessions over the Internet", "Attacks using the RDP protocol do not require user input, making intrusions difficult to detect", weak passwords "are vulnerable to brute-force attacks and dictionary attacks", and it lists "Allowing unrestricted access to the default RDP port (TCP 3389)" as a vulnerability, recommending "strong passwords and account lockout policies to defend against brute-force attacks" [5]. The tools: hydra lists RDP among its protocols [4]; Crowbar is a "brute forcing tool that can be used during penetration tests" supporting "RDP with NLA support", driven through FreeRDP or `xfreerdp` [6].

What the network sees of a guessing attempt is, as for SSH, connection cadence: every try is a fresh TCP connection that sends an X.224 Connection Request before the encrypted CredSSP exchange fails (`include/sloth.h:376-389`; `docs/wiki/rdp-snoop.md:16-22`). RDP adds two cleartext fields SSH lacks. The cookie carries the username the client is presenting, "Cookie: mstshash=IDENTIFIER" [3] - so the detail can say *which* account is being presented, and a cookie that cycles through names across CRs on one row is the password-spray shape (`docs/wiki/rdp-snoop.md:96-99`). The negotiation request says which security protocols the client offers: `PROTOCOL_RDP` 0x00000000 "Standard RDP Security", `PROTOCOL_SSL` 0x00000001 TLS, `PROTOCOL_HYBRID` 0x00000002 CredSSP, `PROTOCOL_RDSTLS` 0x00000004, `PROTOCOL_HYBRID_EX` 0x00000008 CredSSP with the Early User Authorization Result PDU [4] - sloth keeps the OR of the low nibble as `proto_mask` (`src/rdp_snoop.c:92-94`; the `RDP_PROTO_*` names at `include/sloth.h:391-394`). A client offering only standard RDP security, refusing NLA, is a shape the wiki flags as tool-like (`docs/wiki/rdp-snoop.md:100-102`). The corpus states the limits: the thresholds cannot separate a hostile automation from a broken one, the rule is a rate over a window, and an attempt that succeeds first time produces nothing [1].

## Evidence that proves it

What sloth records:

- `alert` / `alert.*` JSONL under `rdp-brute:<client>-><server>` with the count and the last cookie;
- `rdp_flow` state records keyed on `(src_ip, dst_ip)` (`docs/wiki/jsonl-schema.md:730`): `connect_req_count`, `last_cookie`, `proto_mask`, `first_seen`, `last_seen`; because `last_cookie` is overwritten on each CR, the *sequence* of `rdp_flow` records over time is what shows username rotation (`docs/wiki/rdp-snoop.md:96-99`);
- a per-alert pcap if `--pcap-dir` is set (CRIT passes the default `pcap.min_severity` 2, `src/tune.c:121`); the filter is `match_ip` = the client and port 3389 either side (`src/alert_pcap.c:104-114`), so the file holds that client's RDP connections from the ring: each TPKT/X.224 CR with its cookie and negotiation request, the server's Connection Confirm, and how quickly each connection ended.

What points to an attack: `connect_req_count` climbing by tens inside seconds of `first_seen`; cookies that cycle through `administrator`, `admin` and a list (`docs/wiki/rdp-snoop.md:107-110`); a `proto_mask` of 0x01 only; connections in the pcap that end right after the security negotiation with no session; an external or unknown client; and, decisively, the server's Security log showing repeated logon failures (and any success) from that address for those usernames [1], `docs/wiki/alert-remediation.md:383-400`. The FBI's note that these attacks need no user input means the target's user will not have noticed [5].

What refutes it: a count that grew by one or two a day across weeks; a stable cookie that is the user's own account; `proto_mask` containing 0x02 or 0x04 (a modern client doing NLA, `docs/wiki/rdp-snoop.md:86-87`); long sessions in the pcap; a server log with no failures.

## Benign causes

- **Daily reconnects.** The key is the lifetime number of connections between one client and one server (`src/rdp_snoop.c:161`; no `stab_expire`), so an administrator who opens a session to the same server each morning crosses 10 in two working weeks, provided the row survives, and on a segment with few RDP pairs it survives for the life of the process.
- **Sleep, wake and VPN drops.** The rule's own rationale allows "laptops behind NAT that re-connect a few times after sleep/wake" (`src/alerts/rules_wired.c:1047-1049`); each reconnect is a new CR, and the allowance is consumed permanently.
- **Successful sessions count.** The CR precedes authentication, so a login that succeeds counts as one CR exactly like one that fails (`docs/wiki/rdp-snoop.md:114-117`); the corpus's "stale credential" case [1] is one benign cause, but the larger one is credentials that work.
- **Shared jump hosts and NAT.** Several users behind one address are one row; their sessions sum, and their usernames cycle through `last_cookie` in a way that imitates a spray.
- **Scanners doing security negotiation.** A tool that probes which security protocols a server supports sends a CR per protocol tried (the negotiation request is per connection [4]); this is reconnaissance, not guessing, but it counts the same.
- **TCP retransmission.** A retransmitted CR segment is counted again (`src/rdp_snoop.c:99-167` keeps no per-connection state).

## Assessment

CRIT fits what the rule is named after, and RDP is a protocol whose exposed port draws exactly this problem often enough for the FBI to issue a PSA about it [5]. The rule also has better discriminating evidence to hand than its SSH sibling: the cookie names the account and `proto_mask` names the client's security offer, both cleartext [3], [4]. The caveat is the one all four brute-force rules in this family share: the count is a lifetime total with no window, it includes successful sessions, and the row never expires, so the rule converts a routine (admin, server) relationship into a standing CRIT over a few weeks. Two refinements worth considering: window `connect_req_count` as the comment already describes, and gate the severity on the evidence the snoop already collects - cycle to CRIT when `last_cookie` changes between CRs on one row or when `proto_mask` is 0x01 only, WARN otherwise. The wiki lists both the rate (`docs/wiki/rdp-snoop.md:120-123`) and the negotiation response (`:114-117`) as Tier 2 follow-ups.

Prevalence: a first-class sub-technique with RDP named among its targeted services [2], a named group brute-forcing it [7], a federal advisory about it [5] and commodity tools [4], [6]. No fetched source quantifies a field rate, so none is claimed.

Reference host: not seen (null) - consistent with no RDP server on the monitored segment. The behavioural note for an operator who deploys where there is one: each administrator workstation will eventually hold one standing incident per server it manages; record those pairs, and treat a new key - especially one whose cookie is not a known account or whose `proto_mask` is 0x01 only - as the finding.

Sufficient to act on alone? No - it names the pair and the last username, which is a strong lead but not proof. A responder should (1) read the `rdp_flow` record's `connect_req_count` against `first_seen`/`last_seen` to get a rate, and the stream of records for cookie rotation; (2) identify the client and open the per-alert pcap - short connections ending at negotiation are guessing, long ones are sessions; (3) read the server's Security log for failed logons and any success from that address [1], `docs/wiki/alert-remediation.md:383-400`; (4) if an attack, block the source, reset any account that logged in from it, and remove 3389 from anywhere it is reachable without need, which is the FBI's first mitigation [5]; if a stale credential, fix the client; if routine, record the pair. Tuning: raising `rdp.brute_force` delays the standing CRIT rather than preventing it; the fix is the window.
