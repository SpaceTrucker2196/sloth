## What the rule checks

Input: the per-BSSID Multi-Link table in `src/mle.c` (`sloth_mle_bss_t[]`, SLOTH_MLE_BSS_MAX=64, sloth.h:2279), fed by `mle_bss_observe_frame()` (mle.c:583) from `src/capture/probe.c:535` on Beacon (subtype 8) and Probe Response (subtype 5) frames. Run order: `src/alerts/rules_table.c:68` (0-based table index 41).

Detector (mle.c:583-615): the frame must be management (type 0), subtype 8 or 5, with a usable BSSID and a body of at least 12 bytes (Timestamp+BeaconInterval+Capability). `mle_frame_scan()` scans the IEs past those 12 bytes for Basic (`sc.basic`) and Reconfiguration (`sc.reconf`) Multi-Link elements. If the frame carries a Basic MLE, `e->basic_mle_seen` is set (mle.c:600). The finding fires only when `sc.reconf && !e->basic_mle_seen` (mle.c:610): a Reconfiguration MLE in a frame whose BSSID has never (in any frame sloth heard, including this one) carried a Basic MLE. It records `reconfig_no_mlo_total++`, the subtype, last-seen time, and the frame's evidence-ring event id (611-614). Only the Type subfield of the Reconfiguration MLE is read - the one field every MLE variant shares at a fixed position; a malformed Basic MLE still counts as the membership claim (its malformation is MLE_COMMON_INFO_LEN_BAD's finding, not this one's).

Rule (rules_mle.c:215-240): for each BSS row with `reconfig_no_mlo_total > 0`, build key `mle_reconfig_no_mlo:<bssid>` via the `akey_*` builder (224-226; empty key dropped). Detail (227-235): `BSSID <b> sent a Reconfiguration Multi-Link element in a <Beacon|Probe Response> without ever advertising a Basic Multi-Link element (<N> such frame(s) seen) - corroborates a forged AP MLD reconfiguration, does not confirm one - IEEE 802.11be-2024 9.4.2.322`. Fires `ALERT_SEV_WARN` via `fire_ev()` citing the one Reconfiguration frame from the evidence ring (236-239; zero ids when the frame carried no event id); `match_ip = NULL`.

## The attack

A Reconfiguration Multi-Link element announces that an AP MLD (a Wi-Fi 7 access point operating multiple links under one identity) is changing its set of affiliated APs - in a Beacon or Probe Response, that an affiliated AP is being removed, with an AP Removal Timer countdown [1][5]. This is grounded in three agreeing public implementations: hostapd defines the Multi-Link Control Type values (Basic 0, Reconfiguration 2) in `src/common/ieee802_11_defs.h` and its `hostapd_eid_eht_ml_beacon()` emits a Basic MLE and then the Reconfiguration MLE together (`hostapd_eid_eht_basic_ml_common()` followed by `hostapd_eid_eht_reconf_ml()`); Wireshark's dissector uses the same Type values; and Linux mac80211's `ieee80211_ml_reconfiguration()` (confirmed at net/mac80211/mlme.c:6200 in v6.12) reads the Reconfiguration MLE's per-STA profiles, takes each Link ID as a link the AP MLD is removing, reads the AP Removal Timer, and schedules the client's link teardown via `wiphy_delayed_work_queue()` - assuming immediate removal when the timer is absent (mlme.c:6239-6282) [1].

That makes the announcement a steering lever: a client acts on it, with no check other than that it is itself multi-link, so a forged Reconfiguration MLE pushes clients off a link without the deauthentication frame every deauth detector watches for. Only an AP affiliated with an AP MLD has such a change to announce, and such an AP states its membership with a Basic MLE in the same frame types. A BSSID that sends the announcement without ever making the membership claim is announcing a change to something it does not say it belongs to - the shape of a forgery. sloth tags it T1669 (Wi-Fi Networks); the assignment is the repo's (include/sloth_alerts.def), not a MITRE mapping of this specific forgery - T1669 as MITRE describes it is gaining access by connecting to a wireless network [7]. The rule does not catch a forgery sent from the cloned BSSID of a real AP MLD, which inherits that BSSID's Basic MLE history - named explicitly, not implied [1]. No specific public tool is documented as emitting this; hostapd only builds a Reconfiguration MLE under CONFIG_TESTING_OPTIONS, so legitimate ones on air come from vendor stacks that were not available to the research pass.

## Evidence that proves it

The detail carries the BSSID, the frame type it arrived in (Beacon or Probe Response), and the count of offending frames. The alert cites the one Reconfiguration frame by its evidence-ring event ID, so with `--collect-handshakes` the raw frame reaches disk (docs/wiki/pcap-export.md §4; the no-IP wireless rules cite frames because they have no flow to export on). JSONL carries `evidence_count`/`evidence_id_0` and the `technique` T1669.

What a reader should confirm in the cited frame: a Reconfiguration Multi-Link element (Type subfield 2) present, and no Basic Multi-Link element in that frame or in any prior Beacon/Probe Response from the same BSSID (the detector's whole condition). What refutes it: a Basic MLE anywhere in this BSSID's history - a conformant AP MLD removing a link sends the two together, so the finding should never arise for one (the detector counts the same-frame Basic MLE, so even the first frame heard from a conformant AP is quiet; `tests/test_mle_bss.c :: test_reconfig_alongside_basic_in_one_frame_not_flagged`). The finding "corroborates, does not confirm" - sloth cannot see whether any client tore down a link.

## Benign causes

- **A conformant AP MLD removing a link.** This is the thing the rule is built not to fire on: hostapd emits Basic-then-Reconfiguration in one frame, and the detector counts the in-frame Basic MLE, so a well-formed removal stays quiet even on the first frame (mle.c:600-614; test above).
- **A row evicted from the 64-entry table** before its Basic MLE was recorded, then a Reconfiguration seen - but the same-frame Basic MLE check still suppresses this, since a conformant frame carries both.
- **A truly first-frame-ever Reconfiguration with no in-frame Basic MLE from a legitimate non-hostapd stack** is the one residual benign case, and it would be a non-conformant legitimate implementation - unverifiable without a vendor capture.

## Assessment

WARN is correct: the detail is careful to say "corroborates ... does not confirm," because the passive receiver sees the frame, not the client's reaction. False-positive risk is low by construction - the same-frame Basic MLE gate is what keeps conformant Wi-Fi 7 APs quiet. On the reference host it is not seen, which fits both the null host data and the thin real-world population of Wi-Fi 7 AP MLDs today. Prevalence of the attack is effectively unmeasured: 802.11be was finalized in 2024-25 and MLO deployment is early, so this is forward-looking coverage of a new surface, grounded in the standard and three public stacks rather than in field reports. A responder should note the BSSID, check whether it is their own Wi-Fi 7 AP, and - if the transmitter is not theirs and on premises they control - locate and remove it, otherwise report it to whoever runs the site (docs/wiki/alert-remediation.md §MLE_RECONFIG_NO_MLO). The evidence is sufficient to investigate a rogue transmitter but not to assert a client was steered.
