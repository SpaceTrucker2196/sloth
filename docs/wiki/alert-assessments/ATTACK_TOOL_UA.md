## What the rule checks

*This section describes the rule as assessed, before #173. What #173 changed (the detail, and how often the rule fires) is in the **Since #173** paragraph at the end of Assessment; file:line references below are to the assessed tree except `rule_file`.*

Input is the HTTP log `s->http_log[]`, a 256-entry ring (`http_log.c`, MAX_HTTP_LOG 256) populated from cleartext HTTP parsing on the capture path; each entry carries `src`, `host`, `path`, and a 64-byte `user_agent` (truncated at parse, `http_log.c:476`). `rule_attack_tool_ua()` (`rules_wired.c:355-371`) walks every entry in the snapshot (newest first, `http_log.c:731-742`) and calls `attack_tool_ua_match()` (:333-353), a case-insensitive substring search of the UA against a fixed 18-row needle table (:309-331): `sqlmap, nmap, masscan, nuclei, nikto, gobuster, ffuf, hydra, wpscan, dirb, metasploit, ZAP, Burp, acunetix, nessus, openvas, skipfish, wfuzz`.

On a match it fires `ALERT_TYPE_ATTACK_TOOL_UA` at `ALERT_SEV_CRIT` (:368) with key `ua:<src>:<label>` (:362; the label is the table's display name, e.g. `OWASP ZAP`, `Burp Suite`, not the needle) - so the incident is per source-IP and tool label - detail `<src, 24> -> <host, 24> [<label, 16>]` (:363-367), and `match_ip = src`, `match_port = 80` (:369), so `--pcap-dir` carves the matching HTTP packets from that source. No confidence, no evidence IDs. A plain `fire()`.

The match is a self-report: the needle only fires when the tool left its default User-Agent. Confirmed defaults that this table catches (fetched from each project, 2026-10-27): sqlmap `sqlmap/<ver>#<type> (https://sqlmap.org)` [5]; Nmap NSE `Mozilla/5.0 (compatible; Nmap Scripting Engine; https://nmap.org/book/nse.html)` [6]; masscan `ivre-masscan/1.3 https://github.com/robertdavidgraham/` [7]; ffuf `Fuzz Faster U Fool v<ver>` [8]; hydra `Mozilla/4.0 (Hydra)` [9]; wpscan `WPScan v<ver> (https://wpscan.com/wordpress-security-scanner)` [10]; OpenVAS `Mozilla/5.0 [en] (X11, U; OpenVAS-VT <ver>)` [11]; nuclei uses a rotating UA list, so its default often will *not* contain the literal `nuclei` [12]; Metasploit's HTTP UA pool is browser strings with no `metasploit` literal, so that needle matches only explicitly-set UAs [13]. The table catches the tools that brand themselves and misses the ones that do not - by design (rule comment, :304-308).

Because the rule walks the whole ring each tick and keys on (src, tool) rather than on the request, every matching request from one source re-fires the same key - N matching entries in the ring are N `fire()` calls per tick on one key, each adding one to `evaluations` (`engine.c:478`; nothing in `fire()` collapses repeats inside a tick). A scanner that fills the 256-entry ring therefore moves its key by up to 256 per tick, ~1,024/s, until its requests age out; this is the source of the reference host's billion-scale count (see noise verdict).

## The attack

This is reconnaissance and exploitation traffic that names itself. ATT&CK T1595 (Active Scanning) covers probing a target over the network; T1190 (Exploit Public-Facing Application) covers the request for a known-vulnerable path or parameter - sloth maps the UA rule to both (`research/mitre/T1595.md`, `research/mitre/T1190.md` [1][14]). The tools in the table are the standard offensive web kit: sqlmap automates SQL injection, nikto/Acunetix/Nessus/OpenVAS are vulnerability scanners, gobuster/ffuf/dirb/wfuzz brute-force paths and parameters, hydra brute-forces auth, wpscan targets WordPress, Burp/ZAP are intercepting proxies, masscan is a mass port/HTTP scanner. When run with defaults, each stamps a recognisable User-Agent on every request.

What an attacker gains is whatever the tool is for - an injection point, a hidden path, a valid credential, a vulnerable version. What the *alert* observes is only that the request was made with a tool's default UA. ATT&CK's T1595 mitigation note is that the technique "cannot be easily mitigated with preventive controls since it is based on behaviors performed outside of the scope of enterprise defenses and controls" [4]; sloth's corpus is blunter: "Scanning is background radiation on the public internet ... A tool that changes its User-Agent produces nothing. ATTACK_TOOL_UA firing means someone did not bother. It not firing means nothing at all." [1][4][14].

## Evidence that proves it

sloth records the source IP, the target host, and the matched tool label in the detail, and carves the HTTP packets from that source (match_ip + port 80). The pcap is the evidence: it shows the literal User-Agent header and the request line, so a reader can confirm the UA really carried the tool string (not a coincidental substring) and see what paths/parameters the tool asked for.

To weight it, read what the target answered - the request is not a compromise, so pair it with the server's access/response log (`alert-remediation.md:548`). A tool's default UA plus a run of exploit-shaped requests (SQLi payloads, a path-brute wordlist, auth attempts) is a real scan; the UA alone is only "a tool knocked". What refutes a malicious reading: the source is the operator's own authorised scanner or CI security job (the remediation's first fix is "Block the source if it is not the operator's own testing"), or the UA was deliberately set to a tool string to make benign traffic look hostile (the self-report cuts both ways). HTTPS hides the UA entirely, so absence proves nothing.

## Benign causes

- **The operator's own vulnerability scanning / pentest / CI job** - the most common benign cause; a scheduled Nessus/OpenVAS/ZAP run against the operator's own hosts.
- **Security researchers and internet-wide scanners** (some mass scanners set identifying UAs) hitting an exposed host as background noise.
- **A deliberately spoofed UA** - anyone can set `User-Agent: sqlmap/1.0`, so the field can be used to frame a source or to test detection.
- A **coincidental substring** (e.g. a hostname or app containing `zap` or `dirb`) - possible but unlikely given the needle set.

## Assessment

Severity CRIT is too high for what the rule observes. The signal is a self-report that the repo's own documentation describes as trivially evaded and not evidence of compromise; a default-UA tool knocking is worth noticing but sits closer to PORT_SCAN's LOW/recon tier than to a confirmed attack. WARN, reserving CRIT for correlation with ATTACK_PATH or a confirmed response, would read more honestly. (This is an assessment of the rule, not a change made here.)

The reference host is the clearest noise case in this batch: 3.14e9 fires on 2 keys. That is two sources (two scanners), each re-counted once per matching ring entry per tick for as long as their requests sit in the HTTP ring - the count is "how many (poll, logged request) pairs matched", not "how many attacks", and with a full ring it climbs ~1,024/s. Dedupe is already per (src, tool) via the key; the remaining fix is presentational but needs one new number. `observations` is not it: with one target host the detail never changes and it stays near 1, and with several hosts the detail flips between ring entries within a tick, so it tracks `evaluations` (engine.c:487, 519, 534). The alert page should show a count of distinct matching ring entries per key plus `first_seen`/`last_seen`, and must never display `count`. A `pcap.key_cooldown_secs` already caps the carve to once per hour per key, so disk is protected; only the displayed count misleads.

A responder should identify the source and target, confirm it is not the operator's own testing, read the server's response to see whether anything was returned, and treat the UA as a lead that points at a target worth checking - "the target, not the volume, is the measure of risk" (`alert-remediation.md:548`). Block the source if external and unauthorised.

**Since #173.** The per-entry fire is gone: one fire per (src, tool) key per tick, and the detail summarises the key's ring entries as the target (or `N hosts`) and `N matching request(s) in the HTTP ring`, both through `count_bucket()`. The count of distinct matching ring entries this assessment asked for is that second figure. The severity question above is untouched. Test: `tests/test_alert_tick_rate.c`.
