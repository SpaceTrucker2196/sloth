## What the rule checks

Input: `s->snmp_flows`, the SNMP flow table of `MAX_SNMP_FLOWS` = 48 rows keyed by **(querier IP, agent IP)** with the direction normalised so that a response from port 161 or 162 is attributed back to the requester (`include/sloth.h:406-441`; `src/snmp_snoop.c:157-166`). `snmp_snoop_observe()` takes any UDP payload with 161 or 162 on either side, over IPv4 or IPv6 (`:95-96`; dispatched from `src/capture/capture.c:882-885`; both IP versions since #132, `docs/wiki/snmp-snoop.md:25-28`), and parses the BER envelope: outer SEQUENCE, version INTEGER, then for versions 0 and 1 (v1, v2c) the community OCTET STRING and the PDU tag, which must be `0xA0..0xA8` (`:98-155`) - the RFC 1157 `Message ::= SEQUENCE { version, community OCTET STRING, data }` shape, with the PDUs `GetRequest-PDU ::= [0]`, `GetNextRequest-PDU ::= [1]`, `GetResponse-PDU ::= [2]`, `SetRequest-PDU ::= [3]`, `Trap-PDU ::= [4]` [3]. The community is copied only if every byte is printable ASCII, otherwise dropped (`:141-148`). Version 3 messages record the version and nothing else - no community exists in the v3 envelope (`:122-130`). `record_community()` sets `last_community` and appends the string to the row's `communities[]` set if it is not already present and the set has fewer than `MAX_SNMP_COMMUNITIES` = 8 entries, incrementing `community_count` (`:79-89`). So `community_count` is the number of **distinct** strings seen on the pair, saturating at 8; it never decreases. The PDU type is tallied into `get_count`, `getnext_count`, `getbulk_count`, `set_count`, `response_count` and `trap_count` (`:182-192`).

Per tick the rule fires for any row whose `community_count` is at or above `SNMP_COMMUNITY_BRUTE_THRESHOLD` = `tune_val(TUNE_SNMP_COMMUNITY_BRUTE)` (`src/alerts/rules_wired.c:1085`, `:1090`), default **5** (`src/tune.c:60`: `snmp.community_brute`, min 2, max 1000, unit "communities tried"). Key: `snmp-brute` + `:<querier>-><agent>` (`:1092-1094`). Detail: `"<querier>-><agent>: <n> SNMP communities tried (last=<last_community, 16>)"` (`:1095-1099`). CRIT, `match_ip` = the querier, `match_port` 161 (`:1100-1102`; `docs/wiki/snmp-snoop.md:80-86`). The incident resolves 300 s after the last tick that re-asserted it (`include/sloth.h:860`). The 48-row table evicts the least-recently-seen pair when full (`STAB_OLDEST`, `src/snmp_snoop.c:21-22`; `src/stab.h:27`; tallied as `evict_snmp_flow`, `src/sensor_health.h:100`) and never expires rows by age; a process restart empties it (`:203-207`).

Two consequences of the cap. First, the detail's count tops out at 8 however many strings a sweep tried - a 200-word list shows as "8 SNMP communities tried". Second, the tune range (2..1000) exceeds the cap: a value of 9 or more can never be reached, so the rule goes silent without any error. A responder reading `community_count == 8` should assume "at least 8".

## The mechanism

SNMPv1 and v2c authenticate with a community name: "Each SNMP community is named by a string of octets, that is called the community name for said community", and the RFC allows that "Some SNMP implementations may wish to support only a trivial authentication service", which is what the community provides - a shared secret sent in cleartext in every message, received "at UDP port 161", with traps on "UDP port 162" [3]. Guessing it is T1110.001 Password Guessing, which lists "SNMP (161/UDP and 162/TCP/UDP)" among the services adversaries target with guessed credentials [2]. Because SNMP is connectionless, the guessing is fast and cheap: onesixtyone "takes advantage of the fact that SNMP is a connectionless protocol and sends all SNMP requests as fast as it can", pausing 10 ms between packets by default, and the README reports "3 seconds per class C" [4]; nmap's `snmp-brute` "Attempts to find an SNMP community string by brute force guessing", sending probes with each community from `nselib/data/snmpcommunities.lst` while a pcap socket "sniffs the network for an answer to the probes", and adds valid strings to its credentials database [5]; hydra attacks "SNMP v1+v2+v3" [6]. The guess succeeds when the agent answers (GetResponse), which is why the rule counts strings and the snoop tallies responses separately: a sweep that found nothing shows many communities and no responses; one that found the string shows a response and, if the actor proceeds, `set_count > 0` (`docs/wiki/snmp-snoop.md:109-112`; `include/sloth.h:419-422`).

Why distinct strings is the right unit: a legitimate collector has exactly one community per agent it polls (`src/alerts/rules_wired.c:1072-1084`; `docs/wiki/snmp-snoop.md:88-93`), so volume - thousands of GetNext in a walk - is normal while variety is not. The corpus's caveat about rate-over-window rules [1] applies less here because distinct strings do not accumulate through ordinary use, though the set is still never cleared.

## Evidence that proves it

What sloth records:

- `alert` / `alert.*` JSONL under the `snmp-brute`-prefixed key (`<querier>-><agent>`) with the distinct count and the last string tried;
- `snmp_flow` state records keyed on `(src_ip, dst_ip)` (`docs/wiki/jsonl-schema.md:731`): `version`, the six PDU counters, `community_count`, `last_community`, `first_seen`, `last_seen`; the `communities[]` set itself is in the row (`include/sloth.h:437`) but the schema row lists only the count and the last string, so the sequence of records over time is what shows which strings were tried;
- a per-alert pcap if `--pcap-dir` is set (CRIT passes the default `pcap.min_severity` 2, `src/tune.c:121`); the filter is `match_ip` = the querier and port 161 either side (`src/alert_pcap.c:104-114`), so the file holds that querier's SNMP from the ring: each request with its community string in cleartext, and any GetResponse that proves a string worked.

What points to a sweep: many distinct communities from one source to one agent with the well-known list order (`public`, `private`, `cisco`, `community`, `admin` is the wiki's example, `docs/wiki/snmp-snoop.md:88-93`); the strings arriving in a short burst near `first_seen` with no GetResponse in between (guessing, not polling); the same source hitting many agents with the same string set (a scan, `:113-115`); and, if the attack succeeded, a GetResponse followed by `set_count > 0` (a writable community being used, `:109-112`). The deciding evidence is the pcap: the community strings are in cleartext [3], so the file shows exactly which were tried and which the agent answered.

What refutes it: `community_count` of 1 (ordinary polling, however high the `get_count`); a source that is the operator's own monitoring host with a wrong configuration trying its old and new strings; strings that are all site tokens rather than list words. On the reference host there is nothing to refute - the type is null.

## Benign causes

- **The operator's own discovery or audit tooling.** A network-inventory run or a credentialed scan that tries a community list against each agent produces exactly this signature; it is a finding about who ran the scan, not a false positive.
- **Reconfigured collector.** A monitoring host migrated from one community to another, or misconfigured and corrected a few times, accumulates distinct strings against an agent; because the set is never cleared (`src/snmp_snoop.c:79-89`; no `stab_expire`), those stale strings stay counted for the life of the row.
- **Printers and embedded gear.** The wiki notes v2c is enabled by default on most embedded devices (`docs/wiki/snmp-snoop.md:13-15`); a management station that probes several default strings while onboarding a new device reaches 5 legitimately.
- **The cap hides scale, not existence.** `community_count` can never exceed 8 (`src/snmp_snoop.c:85`), so this rule under-reports a large sweep rather than over-reporting a small one - a conservative bias.

## Assessment

CRIT is appropriate, and this is the soundest of the four T1110.001 rules in this family, because its unit is right: distinct community strings, not connection volume. A legitimate collector sits at `community_count == 1` forever, so crossing 5 is a genuine signal rather than an artefact of accumulation. The weaknesses are two and both are bounded. The set is never cleared, so a collector reconfigured across several communities over months eventually qualifies - but that is itself worth surfacing, since stale community strings on the wire are an exposure. And the 8-entry cap means the rule cannot be tuned above 8: `snmp.community_brute` accepts up to 1000 but anything over 8 silences it, which is a latent foot-gun worth fixing (clamp the tune max to `MAX_SNMP_COMMUNITIES`, or raise the cap). The detail would also be more useful if it carried the response count, so a responder could tell a sweep that found a working string (GetResponse present) from one that did not.

Prevalence: a first-class sub-technique with SNMP named among its targeted services [2] and commodity tools whose whole purpose is this attack [4], [5], [6]. No fetched source quantifies a field rate, so none is claimed.

Reference host: not seen (null) - consistent with no SNMP community sweep during the window; monitoring polling, if any, would sit at `community_count == 1` and never fire. The behavioural note for an operator who deploys on a segment with SNMP agents: a single sweep leaves one standing incident per (source, agent) pair until the row is evicted, so a persistent `snmp-brute` key is the record of a past sweep as much as a present one, and `last_seen` says which.

Sufficient to act on alone? Close, for triage, because the pcap settles it. A responder should (1) open the per-alert pcap and read the community strings tried - cleartext [3] - and whether any GetResponse came back; (2) check whether the source is the operator's own monitoring or audit host [1], `docs/wiki/alert-remediation.md:402-419`; (3) if a working string was found (a GetResponse, then any SetRequest), treat the agent's community as compromised and rotate it; (4) if an outside source, block it; if the operator's own scan, record it. Tuning: lower `snmp.community_brute` to 2 or 3 on a segment that should see no community variety at all; never raise it above 8, where it stops firing.
