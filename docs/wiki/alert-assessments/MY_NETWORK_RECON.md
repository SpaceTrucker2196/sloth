## What the rule checks

Inert unless something is designated: `if (!ownership_any()) return;` (rules_wifi_mgmt.c:930) — it needs at least one `--my-ssid` or `--my-bssid` to run. It can only *fire* with a `--my-ssid`, because the trigger below matches probed SSID strings by exact `strcmp` against the designated SSID list (ownership.c:115-120); `--my-bssid` feeds only exoneration 1.

Inputs: the preferred-network-list table `s->pnl_clients[]` (MAX_PNL_CLIENTS = 128 rows, include/sloth.h:1847), built by `probe_pnl_observe()` from directed probe requests (src/probe_pnl.c). Each row has a client `mac`, `mac_random` flag, `first_seen`/`last_seen`, cumulative `probe_count`, and up to MAX_PNL_SSIDS_PER_CLI = 16 distinct SSIDs the client has probed for (deduplicated; when full, the oldest-inserted SSID is dropped FIFO, probe_pnl.c:147-163 — so a client that probes 16 later names pushes the designated SSID out and the alert stops re-asserting). Only directed probes create or update a row; wildcard probes are dropped (probe_pnl.c:108). Also read: `s->assocs[]` (who is associated to what), `s->seqnum_correlations[]` (randomized-MAC sibling pairs), and the ownership roster.

Condition (rules_wifi_mgmt.c:929-1008): for each PNL client, scan its probed SSIDs for any that `ownership_is_my_ssid()` matches; if none, skip. Then apply four exonerations, each of which skips the client:

1. `sta_is_associated_to_designated()` — the MAC is associated to a designated BSSID or SSID (rules_wifi_mgmt.c:877-886);
2. `correlated_sibling_is_associated()` — a seqnum-correlated sibling address is so associated (the randomized-probe / real-association case, rules_wifi_mgmt.c:894-905);
3. `ownership_is_own_device()` — the MAC is on the `--known-mac` roster, **or** it is one of the host's own interface addresses (#183). The self roster is filled from the `iface` records the PLATFORM phase polls every tick (`ownership_self_sync_ifaces()`, src/poll.c), so it covers every interface — the Ethernet port, the managed Wi-Fi card and the monitor radio's own address — with no flag and no new syscall. Entries are added and never removed: a poll that comes back short for one tick does not make the address stop being the host's;
4. `assoc_recorded_within_window()` — `sloth.db` holds an association for this MAC to a designated network whose `last_seen` is inside `recon.sustain_s` (#183, rules_wifi_mgmt.c:921-927 over `db_sta_designated_assoc_last_seen()`). Without `--db` this returns 0 and the rule behaves as it did before. The point is symmetry with the corroborator: `sustained` is measured over a 600 s window, so the association that answers it is allowed the same window instead of having to be live at the instant the rule runs. Only the client's own address is looked up, not its correlated siblings.

For survivors, compute two corroborators: `sustained` = span (last_seen - first_seen) >= recon.sustain_s (600 s) AND probe_count >= recon.sustain_probes (20); `multi` = named >= 2 designated SSIDs. Confidence (constants rules_wifi_mgmt.c:872-874, summed at :967-969): base 25, +30 if sustained, +25 if multi — so 25 bare, 55 sustained-only, 50 multi-only, 80 both.

Fire (rules_wifi_mgmt.c via fire_conf): if sustained OR multi, WARN at the computed confidence with a detail that says "possible reconnaissance" and names which corroborator; else LOW at 25 with a detail that says "probed for ... without associating ... uncorroborated, benign explanations include a returning device or an unobserved association" and deliberately omits the word reconnaissance.

Key (rules_wifi_mgmt.c:975): `myrecon:<mac>`. One incident per client MAC. The alert's title string is `MY_NET_RECON` (the `fire_conf` label), which is also how the docs/views/alerts.md:208 row names it; the enum is `ALERT_TYPE_MY_NETWORK_RECON`. Plain detail; no `match_ip` (L2), no evidence frames. Resolves 300 s after the PNL row stops matching or is evicted. The PNL table has no time-based ageing: a row leaves only when all MAX_PNL_CLIENTS (128) slots are full and it has the oldest `last_seen` (probe_pnl.c:119-126, counted as SH_EVICT_PNL_CLIENT), so on a quiet segment the LOW for a device that probed once and left stands until the table fills or the process ends.

Deliberate non-signals (code comments): a randomized MAC is explicitly NOT corroboration — it describes the handset population, not an adversary (rules_wifi_mgmt.c:860-862); and the *absence* of an observed association is NOT corroboration, because an incomplete capture is the benign case the rule exists to respect (rules_wifi_mgmt.c:957-960).

## The attack

A Wi-Fi client keeps a preferred-network list and, historically, actively probes for its saved SSIDs by name. Those directed probe requests are unauthenticated and broadcast in the clear (the SSID Confusion paper §2.1 [8]; in 802.11 terms a probe request is a Class 1 frame, sent before any authentication exists), so anyone in range can read which networks a device is looking for. MITRE frames reconnaissance that touches the target as T1595 Active Scanning [3]; research/mitre/T1595.md notes MY_NETWORK_RECON is sloth's own framing — "scanning aimed at the operator's own network" — rather than a protocol observable [1].

Two things make a device probing *the operator's* SSID interesting. First, an attacker preparing an evil twin needs to know which names nearby clients trust; a device probing the corporate SSID advertises that it trusts it. Second, KARMA and Known-Beacons attacks answer probe requests with a matching AP to lure the client in — wifiphisher's Known Beacons mode "broadcasts a dictionary of common ESSIDs that the around wireless stations have likely connected to," and its KARMA mode "masquerades as a public network searched for by nearby Wi-Fi clients" [7]. A device probing a designated SSID is both a target for that lure and, if it is not one of the operator's own devices, a possible reconnaissance platform cataloguing the operator's network.

But the same probe is overwhelmingly benign: it is how every returning phone rejoins. The rule's entire design is about separating the rare hostile case from the common benign one without the payload or intent it cannot see — hence LOW-by-default, three exonerations, and corroboration before the word "reconnaissance" appears. The passive-surveillance threat model it serves is real: Snoopy (SensePost, 2012) profiled people by the SSID history in their probe requests across distributed drones [11], and in 2013 "smart trash cans in the UK used Wi-Fi to track the movements of people" — the same mechanism in commercial hands (Vanhoef et al. [13] §1, citing Ars Technica [12]). Freudiger measured how often and how much real handsets probe [15]. Vanhoef et al. (AsiaCCS 2016) showed probe-request IE fingerprints plus sequence numbers track as much as 50% of devices for at least 20 minutes, and Martin et al. (PETS 2017) defeated randomization on ~96% of tested Android phones [13][14] — which is why this rule leans on seqnum correlation, not the MAC alone.

## Evidence that proves it

What sloth records: the detail line's client MAC, the first designated SSID it probed (cut to 32 bytes) and `probe_count`; the WARN detail adds the observation span in seconds and which corroborator fired (the LOW detail carries neither); plus a `confidence` value (25, 50, 55 or 80) in the JSONL `alert` record (jsonl.c:533-534 emits `confidence` whenever it is non-zero). No pcap (no match_ip), no cited frames. The browsable corroboration is the `[p] Probe`/PNL view (the client's full probed-SSID list, its presence classification, OS/PHY fingerprint) and `[j]` seqnum correlations. The JSONL `pnl_client` snapshot (change-only emission, schema "State snapshot record types") carries the per-client probe history over time.

To call it a real recon lead: look for the WARN case — a client that probed the designated SSID for 10+ minutes with 20+ probes (sustained) and never associated, or that named two or more of the operator's SSIDs (multi). Cross-check `[p]` for presence classification: a device classified `resident` or recurring that probes but never joins is more interesting than a `passing` one. Check whether the same canonical identity (via `[j]` seqnum correlation) recurs across visits (correlate with `RECURRING_TRANSIT`). A non-randomized MAC that persistently probes the operator's SSID without ever associating is the strongest passive case.

What refutes it (benign fingerprint): the client is actually associated to the operator's network under a per-SSID stable MAC while probing with a rotating one — the exact case exoneration 2 (correlated sibling) catches, but only if seqnum correlation linked the two addresses; if it did not, the LOW fires honestly on a device that was on the network the whole time. A former guest's phone that still remembers the SSID probes for it from the car park (named in the detail text and docs). A returning employee's device before it reassociates. An incomplete capture that simply never saw the association. All of these produce the LOW honestly, which is why the LOW does not say "reconnaissance".

## Benign causes

- **The sensor's own managed Wi-Fi card.** On any host that is associated to the designated network, this is the *first* device the rule finds, and it is the host running the detector. A managed card scans in the background while associated — wpa_supplicant / NetworkManager send directed probes for the SSID they are joined to, on other channels — and that cadence satisfies the sustained-probing corroborator (≥ 600 s span, ≥ 20 probes) on its own, so the finding arrives at WARN rather than LOW. On the reference host (2026-11-03) it was 330 WARN incidents on `24:41:8c:30:97:a1`, heard at −32 dBm / 1.5 m by the monitor radio sitting beside it, while the card was associated to that same SSID on another channel. Exonerated since #183 by the self roster (exoneration 3), with the stale-association case closed by exoneration 4. What the roster does **not** cover is the card's *randomized* scan addresses: those are locally administered MACs the `iface` records never name, so they are exonerated only when seqnum correlation links one to an address that is associated (exoneration 2) — eight such siblings appeared in 20 hours on the reference host.
- **Returning / former device.** A phone that once joined keeps the SSID in its PNL and probes for it; a former guest's device does this from outside (named in rules_wifi_mgmt.c detail and docs/wiki/alert-remediation.md "MY_NETWORK_RECON").
- **Roaming the operator's own APs.** A device moving between the operator's BSSIDs probes without a stable association at the moment of capture; exoneration 1 catches it when the association is seen.
- **Randomized-MAC probe/associate split.** Scan with a randomized address [13][14], join with the per-network private address that iOS 14+ and Android 10+ use by default [9][10]; exoneration 2 catches it only when seqnum correlation linked the pair.
- **Unobserved association.** Channel-hopping or a late start meant the sniffer never saw the join; deliberately NOT treated as evidence either way.

## Assessment

Severity rationale: this rule is the repo's exemplar of honest grading. LOW at 25% for the bare observation (a lead), WARN with explicit corroboration for the "possible reconnaissance" reading, the word "reconnaissance" withheld from the uncorroborated branch, three exonerations, and two deliberate non-signals (randomized MAC, absence of association) — all of this is correct and documented (docs/views/alerts.md:208, #94). Agree with the severity.

Real-world prevalence: probing for a known SSID is universal and benign; weaponized recon aimed at a specific operator is real but passively hard to prove, which is precisely why the rule refuses to over-claim. The surveillance threat model is well established (Snoopy [11]; the 2013 UK smart-bin tracking, via [13] §1 [12]) and the tracking-despite-randomization research is solid [13][14][15].

Reference-host noise verdict: 541,307,682 fires on 5,558 keys. Two inflation factors stack. First, per-tick counting: ~97k ticks per key ≈ at most 6.8 hours of a standing PNL row re-counted every tick (250 ms is the longest wait), so this is not 541M events. Second, and more important, 5,558 keys is itself inflated by MAC randomization — a single passing handset that rotates its probe address mints a new `myrecon:<mac>` key per address, and handsets commonly randomize their probe address [13][14]. The qualifier is that only *directed* probes naming the designated SSID create a row (wildcard probes are dropped, probe_pnl.c:108), so the inflation applies to devices that still send directed probes for that name. So the real device count is well below 5,558. A third factor sets the ~6.8 h: the PNL table has no time-based ageing (eviction only when 128 slots are full), so a passing phone's row and its LOW stand until 128 newer clients push it out — on a busy road that churn is what bounds the standing time, on a quiet one the row would stand for the life of the process. The rule already does the right structural things (excludes randomized MACs from corroboration, canonicalizes transit identities by seqnum), but the LOW keys are not coalesced by correlated identity before they become alerts. Recommendations: surface the distinct key count (merged by seqnum identity, below) and first_seen/last_seen, not `count` - and not `observations`, which for a regularly probing handset is close to `evaluations` because the cumulative `probe_count` (and, in the WARN form, the span in seconds) in the detail changes on every directed probe (rules_wifi_mgmt.c:982-1000, probe_pnl.c:136) and each change adds one per tick until the next 60 s update refreshes the stored `detail_sig` (engine.c:487, 534); alternatively bucket `probe_count` in the detail (AGENTS.md change-only emission rule); coalesce LOW `myrecon` keys by seqnum-correlated canonical identity so one randomizing handset is one lead; and consider suppressing the LOW entirely for `passing`-classified clients (a drive-by phone), reserving the alert for `resident`/recurring probers.

Is the evidence sufficient to act? For the LOW, no — it is explicitly a lead; a single sighting has no fix (docs/wiki/alert-remediation.md). For the WARN, it is enough to investigate: note the client and the designated SSID, check whether it is rostered (`--known-mac`), and correlate repeated sightings with `RECURRING_TRANSIT` as a pattern worth recording against the operator's context. Probing is ordinary client behavior, so there is no vendor fix; the operator's levers are rostering known devices (to silence benign returns) and treating a sustained, unrostered, non-randomized prober of their own SSID as worth physical attention.
