## What the rule checks

**Input.** `s->tls_log[]`, the 256-entry ring `src/tls_log.c :: tls_log_parse()` fills with the SNI (`tls_log_entry_t.host`), source and destination of every TLS ClientHello sloth overhears (MAX_TLS_LOG = 256, include/sloth.h:1092). The rule adds no capture surface - it is a lookup over state the TLS parser already produced [1].

**Condition (rules_wired.c:599-677).** Two passes. First, for each ring row with a non-empty, non-truncated `host`, `vendor_watchlist_match_domain()` (src/vendor_watchlist.c) tests a label-boundary suffix match against the embedded table; a `host_trunc` SNI is skipped, because a 63-byte prefix can end on a listed suffix while the real name continues elsewhere (rules_wired.c:605-609) [1]. Second, for each matched row, the detail's hostname is the **smallest** name this same local host used for this vendor across the ring (rules_wired.c:615-629) - so two names under one key do not flip the detail signature and emit an `alert.update` every 60 s.

**The watchlist (src/vendor_watchlist.c:27-67).** Four rows, three vendor strings (`axon` covers both `evidence.com` and `axon.com`). Each row is sourced to a vendor's own network-requirements or service document [2]:
- `evidence.com` → axon (evidence-cloud) - Axon's VR allowlist and Cloud FAQ name it [5].
- `axon.com` → axon (evidence-cloud) - the migration destination; also Axon's marketing site, a known structural FP [5].
- `flocksafety.com` → flock-safety (alpr-cloud) - the agency transparency-portal domain [8].
- `control.verkada.com` → verkada (camera-cloud) - every Verkada-operated FQDN in the page's per-region camera allowlists sits under it except the `vconductor.*.command.verkada.com` hosts (src/vendor_watchlist.c:55-66) [2][5]; the bare `verkada.com` is deliberately not used because it is also marketing [5].
Suffix semantics: `evidence.com` matches `ab4-upload.evidence.com` but not `notevidence.com` and not `evidence.com.attacker.example` (src/vendor_watchlist.c:69-81).

**Key.** `"surv-sni:<vendor>:<local-host>"` (rules_wired.c:656-657). On vendor + the operator's own host, deliberately **not** the SNI (a per-session upload hostname would make one dock a fresh alert per connection) and **not** the endpoint IP - which is remote-chosen and unbounded, and first shipped that way: 200 rows from one local host across 200 destination addresses filled the 128-slot engine (MAX_ALERTS = 128, include/sloth.h:823; the comment at rules_wired.c:633-655) and merged several local hosts into one alert. Keying on the local host bounds fan-out to the size of the operator's own segment, the axis a reader wants one row per [1][3].

**Detail.** `"<src> -> <smallest-host>: TLS to <vendor> <family> (device upload or portal use, not distinguishable)"` (rules_wired.c:663-666). `%.45s` on the source so an IPv6 literal is not cut; `%.40s` on the host.

**Severity.** WARN, unconditionally (rules_wired.c:674). Technique empty by design (`include/sloth_alerts.def:197`): T1041 / T1567.002 describe an attacker moving data *out*, while a body camera uploading to its own vendor is the system working as designed; on the named list in `tests/test_research_corpus.c :: test_uncitable_kinds_with_a_real_basis_are_still_cited` [1][3].

**pcap.** `match_ip = e->dst` (the remote endpoint), `match_port = 443` (rules_wired.c:674-675): the per-alert pcap is filtered to the conversation with the vendor, not the local host's other traffic. The engine sets `match_ip` only when the incident is created (engine.c:400-401, 579-580), so the filter is the destination of the first matching ring row at the first fire. Later rows for the same key that reach other vendor addresses (CDN rotation, a different upload host) are not in the export. Note the key names the local host and `match_ip` names the remote one - the two fields carry different ends of the same conversation on purpose (rules_wired.c:667-673) [1].

**Escalation / resolution.** None; WARN only. The "smallest host" detail is stable, so updates are rare. Resolves when the match ages out of the ring and the key is quiet for 300 s. The ring ages by newer ClientHellos, not by time, so on a quiet segment a single matching row can stay resident, and keep firing, for hours.

## The background (this is an exposure, not an attack)

Body-worn cameras and automated-licence-plate-recognition (ALPR) platforms are cloud products: a camera, its dock, or an analyst's workstation opens TLS to a vendor-operated evidence platform, and the ClientHello carries the server name (SNI) in cleartext [1]. The watchlist is restricted to domains the vendor's *own* operational documentation tells customers to allow through a firewall or DNS filter - the only kind of source checkable by someone who does not own the device [2]:

- **Axon** - the Cloud Customer FAQ states access "will begin transitioning from evidence.com to a new address under axon.com" and tells agencies with allowlists / DNS filtering / SSL inspection / proxies to permit the new `axon.com` addresses first; `status.evidence.com/status/network` is its own connectivity test [5]. Both domains are live service addresses, which is why both are listed.
- **Flock Safety** - publishes agency transparency portals at `transparency.flocksafety.com/<city-state>-pd` [8]. Flock's field cameras are solar-powered and cellular-uplinked according to the repo's corpus [1], which gives no primary URL for it, and the Flock page fetched here [8] says nothing about uplink - so this is repeated from [1], not independently verified in this pass; if true, a Flock camera's own traffic never crosses a monitored LAN; a `flocksafety.com` hit is a host on this network *using* the platform, not a camera on it [1].
- **Verkada** - the Camera Network Settings page lists per-region allowlists whose Verkada-operated camera FQDNs sit under `control.verkada.com` (api., relay., index., firmware., update., …; the page also lists `command.verkada.com` hosts and shared AWS endpoints, which the row deliberately excludes [2]), and states "DNS over HTTPS (DoH) is currently not supported" and that devices are incompatible with proxies / TLS inspection [5] - so both the DNS query and the ClientHello cross the wire unmodified, where sloth can read them.

The detector's claim is narrow: traffic on this segment went to that vendor. It cannot answer "is there a Flock on my street" (the camera is not on the LAN) and it cannot tell a docked camera uploading from an analyst's browser tab on the vendor portal [1]. ATT&CK maps nothing, deliberately: exfiltration techniques point the wrong way for a device uploading to its own vendor [1][6].

## Evidence that proves it

**What sloth records.** `alert` / `alert.create` with `title=SURV_CLOUD_SNI`, `sev=1`, no `technique` field, `key=surv-sni:<vendor>:<local-host>`, the detail above; `count` = evaluations (ticks), not sessions (jsonl-schema.md:297, 390). The `tls_log`-derived records around the alert hold the ClientHello SNI, JA3/JA4, source and destination; the `packet` record for the destination gives the 443 flow. A per-alert pcap (with the pcap flags above) holds the ClientHello to the vendor endpoint.

**What makes it real (a device, not a browser).** The local host also resolving the vendor domain over plaintext DNS (a `SURV_DNS` LOW alert for the same host+vendor corroborates - for Verkada this is guaranteed because the vendor does not support DoH [5]); the source host being a camera/dock by its `device` record (`device_class`, `camera_vendor`, `cam_signals`) rather than a general-purpose workstation [10]; a repeating upload cadence rather than interactive bursts; the SNI being an upload subdomain (`*-upload.evidence.com`) rather than the portal hostname. JA3/JA4 matching a known device TLS stack rather than a browser is the strongest single signal the TLS log carries.

**What refutes it (a browser / marketing).** An `axon.com` hit from a workstation whose other SNIs are ordinary web browsing, with no `SURV_DNS` and no camera `device` record, is a person reading a product page - the documented structural FP [1][5]. A `flocksafety.com` hit is by construction not a Flock camera (cellular uplink) [1]. A one-off hit that never repeats is a link preview or a prefetch.

## Benign causes

- **An analyst or officer using the vendor portal in a browser** - identical observation to a device upload; the detail says "not distinguishable" [1].
- **Reading `axon.com` as a marketing site** - a structural false positive the rule accepts rather than guessing at unpublished upload subdomains [1][5].
- **A legitimately deployed, operator-owned camera or dock uploading** - the system working as designed; reported so the operator *knows* the network carries the traffic, not because anything is wrong (the WARN rationale) [1].
- **A forwarding resolver's own lookups** (the `SURV_DNS` sibling's edge) - not this SNI rule, but relevant when triaging the pair [1].

## Assessment

**Severity.** WARN, never CRIT, is correct and well-argued in the code: most hits are the platform working as designed, and the finding exists so an operator knows their network carries surveillance-platform traffic [1]. I agree. Raising it would train operators to mute a type whose whole value is awareness.

**Prevalence.** High as *traffic*: Axon, Flock and Verkada are large municipal/enterprise deployments and the watchlist domains are the vendors' own service addresses [5][8]. As an *attack* it does not apply - there is no adversary in the observation.

**Reference host - the arithmetic.** 341,870 fires on 4 keys = ~85,000 evaluations per key. The count semantics make this tick x matching-row accumulation, not session volume: the key is `vendor x local-host`, the bounded axis the re-key was designed to produce (contrast the pre-#105 endpoint-IP key that filled the 128-slot engine from one host across 200 addresses [1][3]). So the reference host has four real incidents - at most four (vendor, local-host) pairs, i.e. at least two distinct local `src` strings (only three vendor strings exist, so one host can hold at most three keys; one dual-stack machine counts as two) talking to one-to-three of the watchlisted vendors - each re-counted every poll tick for the length of the run. **noisy, but in the count, not the incident set.** Because every matching ring row fires the key once per tick (engine.c:478-479; the per-row loop at rules_wired.c:611-676), 85,000 evaluations is an upper bound on presence, not a duration: with exactly one matching row it is ~85,000 ticks ≈ 5.9 h at the 250 ms default; with twenty of one host's sessions to the vendor sitting in the 256-entry ring at once it is ~4,250 ticks ≈ 18 min. Either way it is a steady flow or a kept-open portal, not 341,870 sessions. **Recommendation:** the "noise" is the tick-count standing in for volume. Surface the engine's `observations` (which only increment when the detail signature moves, engine.c:487-490) instead of `count/evaluations` in the TUI and record, and put session/first-seen in the detail; then one dock reads as "1 incident, N observations since T" rather than "341,870". No dedupe or threshold change is needed - the incident count (4) is already correct.

**Is the evidence sufficient to act on?** To act on "which of my hosts talks to which surveillance vendor", yes - that is exactly what the key answers. To act on "is this a device or a person", no, by design; pair it with `SURV_DNS`, the host's `device` record, and JA3/JA4 before concluding.

**Responder's first steps.** (1) Identify the local host from the key / `src` and its `device` record [10]. (2) Decide expected or not: a known camera/dock on a contract you run → expected, document and move on; an unknown host → find out what it is. (3) If unexpected and you must capture, set `pcap.min_severity=1` and `--pcap-dir` to get the ClientHello to the vendor endpoint [11]. (4) Remember the claim's limits: a `flocksafety.com` hit is platform *use* on your LAN, not a camera on your street [1].
