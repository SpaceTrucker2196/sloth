## What the rule checks

Input: `s->smb_sessions`, the SMB observation table of `MAX_SMB_SESSIONS` = 64 rows keyed by `(client_ip, server_ip, server_port)` (`include/sloth.h:539-549`). `smb_snoop_observe()` checks the first bytes of any TCP/445 or TCP/139 payload for the SMB magic: `\xFF S M B` = SMB1, `\xFE S M B` = SMB2/3, repeated after a 4-byte NetBIOS Session Service header for the port-139 / legacy framing case (`src/smb_snoop.c:34-45`). The server side is whichever endpoint is on 445 or 139 (`:52-68`). The recorded dialect is **sticky to SMB1**: once a flow is seen using v1, later v2 frames on it do not downgrade the record (`src/smb_snoop.c:86-91`; `docs/wiki/smb-snoop.md:56`), because a mid-flow downgrade to v1 is the pattern worth keeping. SMB2 and SMB3 are merged, as distinguishing them needs the negotiate response and the rule does not need it (`include/sloth.h:535-538`).

Per tick the rule walks the table and, for each row whose `dialect` is exactly `"SMB1"` (`src/alerts/rules_wired.c:895-896`), keys on `smb1:<client>><server>:<port>` (`:898-900`) and renders the detail with client, server, port, the session `count`, and the deprecation note (`:901-907`). It fires CRIT with `match_ip` = the server (the side to patch/harden) and `match_port` = the server port (`:908-909`; `docs/wiki/smb-snoop.md:70-75`). One alert per (client, server, port) tuple, so new endpoint pairs mint new incidents. The incident resolves 300 s after the last tick that re-asserted the key (`include/sloth.h:860`); the 64-row table evicts least-recently-seen (`evict_smb_session`, `src/sensor_health.h:97`).

Because the rule re-fires every tick a SMB1 row is present, and the engine increments `count = evaluations` on each (`src/alerts/engine.c:478-479`), count measures how long the session stayed in the table, not how many SMB operations occurred.

## The mechanism

SMB is the Windows file-share, named-pipe and printer protocol, on TCP/445 and TCP/139. SMBv1 is the original dialect; Microsoft publicly deprecated it in 2014 and, since Windows 10 version 1709 and Windows Server version 1709, no longer installs it by default (and auto-removes an unused client after 15 days) [6]. The rule's comment, the detail string and `docs/wiki/smb-snoop.md:20` all say "deprecated since 2017" (`src/alerts/rules_wired.c:887-888`, `:903-905`); 2017 is the MS17-010 and default-removal year, 2014 is the deprecation per Microsoft's own page [6]. The reason it is a CRIT and not a note: MS17-010 (March 2017) fixed a set of SMBv1 remote code execution flaws, the best known being CVE-2017-0144, exploitable by an unauthenticated attacker sending a crafted packet to an SMBv1 server [3], [4]. That exploit, EternalBlue, was the propagation mechanism of WannaCry and NotPetya [5], and MITRE lists SMB/EternalBlue/MS17-010 explicitly under T1210 Exploitation of Remote Services, used by WannaCry, Bad Rabbit, NotPetya, Emotet, TrickBot and several named groups [2]. The repo maps the rule to T1210 deliberately: sloth observes the exposed surface (the protocol version in the unencrypted negotiate exchange), not an exploit in flight, so it reports the reachable vulnerability class rather than lateral movement [1]. A patched host still fires, correctly, because the patch fixed the CVE but did not remove the protocol, and SMBv1 has other reasons to be gone (no pre-auth integrity, no modern encryption) [1], [6]. CISA's WannaCry advisory and MS17-010 both recommend disabling SMBv1 where the patch cannot be applied, while cautioning that disabling it may break access to legacy shares [3], [5].

## Evidence that proves it

What sloth records:

- `alert` / `alert.*` JSONL under `smb1:<client>><server>:<port>`, detail naming the endpoints, the session `count`, and the deprecation guidance;
- `smb_session` state records (`docs/wiki/jsonl-schema.md:723`): `client_ip`, `server_ip`, `server_port` (445 or 139), `dialect` (sticky to SMB1), `first_seen`, `last_seen`, `count` - these pin exactly which pair spoke v1 and for how long;
- a per-alert pcap if `--pcap-dir` is set (CRIT passes default `pcap.min_severity` 2); the filter is `match_ip` = server and the server port either side (`src/alert_pcap.c:102-111`), so the file holds that SMB flow from the ring, including the negotiate exchange with the `\xFF S M B` magic that is the proof of dialect.

What makes it real and actionable: the server side is a host that should not be serving v1 (a Windows file server, a domain member), especially if a flow first negotiated v2 and then shows v1 (the sticky dialect catches a forced downgrade, `docs/wiki/smb-snoop.md:56`, `:77-79`); or many clients talking v1 to one server. What tells you it is benign-but-still-worth-fixing: the server is a NAS, a printer or an embedded appliance (common, a legacy device needing firmware or replacement [6], `docs/wiki/smb-snoop.md:29-32`). Absence is not assurance - sloth reports only the flows it saw; a v1 session on a VLAN the sensor is not on produces nothing [1].

## Benign causes

- **Legacy device doing its job.** The overwhelming majority: an old NAS, scanner or printer that only speaks SMBv1 [1], [6]. This is a true finding (the surface is exposed) but not an attack in progress; reading the alert as an active intrusion would be wrong nearly every time [1].
- **A fully patched host with SMBv1 still enabled.** Not vulnerable to CVE-2017-0144 but still reported, correctly, because the protocol remains deprecated [1], [3].
- **Not a false-positive source, but note:** older Linux/Samba endpoints requiring v1 are flagged by Microsoft's own client event 32002/32000 as well [6], so the sensor's finding will agree with the Windows client logs.

## Assessment

CRIT is defensible and the repo's reasoning is sound: the finding is the exposed, deprecated, historically-wormable surface, and T1210 is the honest mapping because sloth sees the surface, not its exploitation [1], [2]. The one caveat for an operator is that CRIT here means "a vulnerability class is reachable", not "an attack is underway" - the detail string already says the endpoint should be patched or v1 disabled (`src/alerts/rules_wired.c:903-906`), and the alert page should keep that framing so a responder does not misread a legacy printer as an intrusion.

Prevalence: EternalBlue is among the most consequential network vulnerabilities of the last decade [1], [5], and while SMBv1 is now off by default on modern Windows [6], it persists on legacy NAS, printers, embedded gear and after configuration drift [6], `docs/wiki/smb-snoop.md:29-32`. So true positives are uncommon but real and almost never spurious - false-positive risk low.

Reference host: 64,349,933 fires on 4 keys, max CRIT. Keys are per (client, server, port), so four SMB1 endpoint pairs were ever observed - quiet by findings. The ~16M evaluations per key reflect the sticky-dialect row sitting in the 64-slot table being re-fired at least 4 times a second (at most ≈46 days of residency each, less if the loop woke faster), not 16M SMB operations. Recommendation: the alert page should present the `smb_session` `count` and `first_seen`/`last_seen`, label the engine `count` as evaluations, and the rule could re-fire a given key at most once per cooldown rather than every tick, the way `pcap.key_cooldown_secs` already deduplicates pcap export (`src/tune.c:122`).

Sufficient to act on alone? Yes for triage. The detail names the server to fix. A responder should (1) identify client and server and whether the server should be serving v1 (`docs/wiki/alert-remediation.md:281-301`); (2) check MS17-010 status - a patched host still fires, so the protocol is the problem, not just the CVE; (3) disable SMBv1 on both ends, replace or isolate the legacy device that needs it, and apply MS17-010 to any unpatched Windows host [2], [3], [5], [6].
