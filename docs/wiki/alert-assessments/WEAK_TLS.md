## What the rule checks

Input: `s->tls_log`, the TLS observation ring of `MAX_TLS_LOG` = 256 rows (`include/sloth.h:1123`, `:3505`), each a `tls_log_entry_t` with `src`, `dst`, `host` (the SNI, empty if absent), `tls_ver[8]`, `ja3`, `ja4` and `host_trunc` (`include/sloth.h:1125-1142`). It is fed by `try_sni()`, which `decode_tcp` calls on every TCP payload with no port gate (`src/capture/capture.c:794`): the parser itself gates on a TLS handshake record (`0x16`), major version 3, and handshake type ClientHello (`0x01`) (`src/tls_log.c:124-133`). The version recorded is the **highest the client offered**: `legacy_version` is read from the ClientHello body (`:160-162`) and is the default (`:219`); if a `supported_versions` extension (`0x002b`) is present the walk takes the highest value that is not a GREASE value (`:286-300`); with no extension the legacy field stands (`:328-329`). `ver_string()` maps `0x0304`..`0x0301` to `"TLS 1.3"`..`"TLS 1.0"` and everything else, including `0x0300`, to the bare `"TLS"` (`:24-32`), written to `tls_ver` at `:351`. `tls_log_record()` appends with no time expiry and overwrites the oldest row when full (`:430-441`); `tls_log_snapshot()` (`:444`) copies the ring into the state each poll (`src/poll.c:172`).

Per tick `rule_weak_tls()` (`src/alerts/rules_wired.c:215-231`) walks every row and skips those whose `tls_ver` is not weak (`:218`), where `tls_ver_is_weak()` (`:173-179`) is a string compare against `"SSL 2.0"`, `"SSL 3.0"`, `"TLS 1.0"`, `"TLS 1.1"`. Key: `weak_tls:<src>:<ver>` (`:221-222`), so one client offering both 1.0 and 1.1 surfaces twice, as the comment intends (`:166-172`). Detail: `"<src,20> -> <host or dst,24> offered <ver> (deprecated)"` (`:223-227`). WARN, `match_ip` = the client, `match_port` fixed at 443 (`:228-229`). The rule runs after `rule_attack_path` (`src/alerts/rules_table.c:98`). The engine increments `evaluations` (the `count` alias) on each `fire()` under an open key (`src/alerts/engine.c:475-481`), resolves after 300 s without one (`include/sloth.h:860`; `src/alerts/engine.c:927-935`), and opens a new incident with `reopen_count` carried over when the key fires again (`:543-547`, `:594-598`); the `--db` row folds later incidents into `reopens` (`src/db_schema.c:534-545`). Tests: `tests/test_alerts.c:3265-3297`; the SSLv3 case at `:3275-3281` passes because the helper at `:3261` writes the version string into `tls_ver` by hand, so it proves the rule's string compare, not that the parser can produce `"SSL 3.0"`.

Three things the code says that the comment and one corpus sentence do not. The `"SSL 2.0"` and `"SSL 3.0"` branches of `tls_ver_is_weak()` are unreachable: `ver_string()` never produces them, so an SSLv3-only client (legacy_version `0x0300`) records `"TLS"` and does not fire, and an SSLv2-format hello is not a `0x16` record at all. No cipher suite is examined - the rule reads `tls_ver` only (`:218`), as `docs/views/alerts.md:141` and `docs/wiki/alert-remediation.md:593-595` say correctly, whereas `research/rfc/8996.md:50-52` says "Sloth reads both, and the cipher-suite half is where a TLS 1.2 connection can still be worth reporting"; that sentence describes a check that does not exist. And `match_port` is 443 although the parser accepts a ClientHello on any port, so the per-alert pcap filter, which requires a port match when the port is non-zero (`src/alert_pcap.c:103-113`), would drop a weak handshake on 8443, 993 or 465 - moot at the default `pcap.min_severity` of 2 (`src/tune.c:121`), which a WARN does not reach.

## The mechanism

RFC 8996 "formally deprecates Transport Layer Security (TLS) versions 1.0 (RFC 2246) and 1.1 (RFC 4346)" because they "require the implementation of older cipher suites that are no longer desirable for cryptographic reasons", lack AEAD ciphers "which were not supported prior to TLS 1.2", and because "The integrity of the handshake depends on SHA-1 hash" and "The authentication of the peers depends on SHA-1 signatures" [2]. Its requirements are unconditional: "TLS 1.0 MUST NOT be used. Negotiation of TLS 1.0 from any version of TLS MUST NOT be permitted" (section 4) and the same for 1.1 (section 5), with "clients MUST NOT send a ClientHello with ClientHello.client_version set to {03,01}" and "{03,02}" [2]. RFC 7568 did the same for SSLv3 earlier: "SSLv3 MUST NOT be used" and "clients MUST NOT send a ClientHello with ClientHello.client_version set to {03,00}" [5].

Where the offered version lives is why sloth can read it passively. In TLS 1.3 "the client indicates its version preferences in the 'supported_versions' extension" and "the legacy_version field MUST be set to 0x0303" (RFC 8446 section 4.1.2); the extension "contains a list of supported versions in preference order, with the most preferred version first", and when it is absent a server "MUST negotiate TLS 1.2 or prior as specified in RFC 5246" (section 4.2.1) [3]. The ClientHello is in the clear by necessity, so the highest version a client is prepared to speak is visible to any listener; that is the field `tls_log.c` extracts. RFC 8701 is why the walk filters GREASE: a client "MAY select one or more GREASE version values and advertise them in the 'supported_versions' extension", drawn from `0x0A0A`, `0x1A1A` ... `0xFAFA`, and "Servers MUST correctly ignore unknown values" [4]; without the filter a leading `0x?A?A` would read as a version above 1.3 (`src/tls_log.c:296-299`).

The ATT&CK mapping is T1600, Weaken Encryption: "Adversaries may compromise a network device's encryption capability in order to bypass encryption" [6]. The corpus chose it deliberately over an interception technique "because what sloth observes is the *weakened state*, not an adversary exploiting it. The weakness is real whether or not anyone is on the path" [1]. It also sets the boundary: "A deprecated version is not a broken one. Attacks on TLS 1.0 in practice need conditions - a position on the path, many sessions, a cooperative client - that a passive alert cannot assume. This is a posture finding, and its answer is a migration plan" [1].

## Evidence that proves it

What sloth records:

- `tls` JSONL records per ClientHello: `src`, `dst`, `host` (SNI), `ver`, `ja3`, `ja4` (`docs/wiki/jsonl-schema.md:201-214`), so the stream carries every weak offer with the server name it was aimed at and a fingerprint of the stack that made it;
- `alert` / `alert.*` under `weak_tls:<src>:<ver>`; `count` is evaluations (`docs/wiki/jsonl-schema.md:391`), and each return after a resolve is a new `incident_id` (`:442-445`);
- the `--db` `alerts` row with `reopens`;
- no per-alert pcap at the default `pcap.min_severity` 2 (`src/tune.c:121`); at 1 the filter is client IP and port 443 either side (`src/alert_pcap.c:103-113`).

What makes it real and actionable: the client is a host on your segment, the `host` field names the services it reaches with that offer, and the JA3/JA4 fingerprint identifies the library (`docs/wiki/ja3-fingerprinting.md`); a client that offers 1.0 to everything has an old stack, a client that offers 1.0 to one host only has a per-destination fallback. What makes it benign-but-still-a-finding: the client is an embedded controller that cannot be updated [1]. What refutes it as a finding: the source is a deliberate TLS audit of your own server, or a test client. Absence is not assurance: sloth does not parse the ServerHello (`research/rfc/8996.md:24-27`), so a server that *accepts* 1.0 from a client that offered 1.3 produces nothing, and a weak session the sensor's segment does not carry produces nothing.

## Benign causes

- **Embedded devices.** "Building-management controllers, medical devices and industrial gear routinely speak TLS 1.0 and cannot be updated. The finding stands; the remediation is segmentation rather than an upgrade" [1].
- **An old library or OS.** RFC 8996 counts the spread of versions itself as a risk: "Support for four TLS protocol versions increases the likelihood of misconfiguration" [2]. A stack that never gained 1.2 offers nothing above 1.1 on every connection, and the SNI list in the `tls` records shows that pattern.
- **A TLS audit tool.** A scanner that offers each version in turn to see what a server accepts produces one weak ClientHello per version, from the operator's own host; the rule reads only `tls_ver` (`src/alerts/rules_wired.c:218`) and cannot see intent.
- **Not a false positive, but a gap:** a client with no `supported_versions` extension and `legacy_version` `0x0303` is recorded as 1.2 even if it would have accepted a downgrade; the rule under-reports there rather than over-reporting.

## Assessment

WARN is right and the mapping is right. The finding is a client-side exposure that RFC 8996 forbids outright [2], observed in the one message a passive sensor is guaranteed to see in the clear [3], and the corpus is careful that a passive alert cannot assume the conditions a practical attack on 1.0 needs [1]. CRIT would page on every building-management controller. The three code facts above are worth fixing in the documentation rather than the rule: the comment's SSLv2/SSLv3 claim (`src/alerts/rules_wired.c:166-172`) and the corpus's cipher-suite sentence (`research/rfc/8996.md:50-52`) both describe checks the rule does not make, and an operator who believes either will read silence wrongly. If SSLv3 detection is wanted, `ver_string()` needs a `0x0300` case (`src/tls_log.c:24-32`); today that hello records as `"TLS"`.

Prevalence: the deprecation is unconditional and standards-track [2], [5]; the trigger population the corpus names is embedded and industrial gear [1]. No fetched source quantifies how often a 1.0-or-1.1-only client appears on a segment, so no rate is claimed.

Reference host: 39,750,702 fires on 6 keys, max WARN, 198 reopens, first 2026-10-14, last 2026-11-03. Keys are per (client, version), so at most six clients, fewer if one offered both 1.0 and 1.1. The 6.6M evaluations per key bound the standing time at about 19 days at the 4 ticks/s floor, nearly the whole span; the CLEARTEXT_CRED arithmetic on the same host shows the loop averaged about 10 ticks/s, which puts it nearer 7.7 days, and a client whose repeated weak ClientHellos held several of the 256 rows at once accrued several evaluations per tick, so the true standing time is shorter still. The 33 reopens per key are the ring at work: on a segment with enough TLS to turn the 256-row ring over, a client's weak rows are evicted within minutes to hours, the key resolves 300 s after the last one leaves, and its next connection reopens it. Six clients, two hundred incidents, one posture each. The alert page should present per-client first/last seen, the set of `host` values it offered weak versions to, and `reopens`, and label the engine `count` as evaluations. A rule-side cooldown would not help: at 300 s or more it would leave the key un-asserted past `ALERT_RESOLVE_AFTER_S` (`include/sloth.h:860`) and turn one finding into a resolve/reopen stream, the point SMB1_USE's review made.

Sufficient to act on alone? Yes, for the posture it names. A responder should (1) identify the client from the alert's address and the services from the `host` fields in its `tls` records (`docs/wiki/alert-remediation.md:591-600`); (2) find the software on it that offers nothing newer than 1.1, using the JA3/JA4 fingerprint to name the stack; (3) update or replace that stack so it offers 1.2 or later, or segment the device if it cannot be updated (`:602-612`); (4) confirm the servers refuse anything below 1.2, knowing that does not fix the client - a client that can offer nothing newer then simply fails (`:609-612`). Nothing to tune.
