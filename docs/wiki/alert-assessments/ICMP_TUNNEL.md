## What the rule checks

Inputs: the ICMP log ring `s->icmp_log[]` (MAX_ICMP_LOG = 256 records, include/sloth.h:1066), each record carrying `src`, `dst`, `type`, `payload_len` (bytes past the 8-byte ICMP echo header, icmp_log.c:97), `is_v6` and `ts`. The payload length is metadata: `len - 8` where `len` is the ICMP message length bounded by the IP length field (capture.c:895-897, icmp_log.c:97) — the rule never reads the payload bytes (rules_wired.c:465-467). The ring holds 256 records in total, so under heavy ICMP the effective look-back is however long 256 records span, which can be shorter than the nominal 60 s window.

Condition (rules_wired.c:472-533): walk the ring, keep only Echo Requests (v4 type 8, v6 type 128, rules_wired.c:484-487 — the request side carries outbound tunnel data; replies mirror it), drop any with `payload_len < ICMP_TUNNEL_MIN_PAYLOAD` (64) or older than `ICMP_TUNNEL_WINDOW_S` (60 s). Bucket survivors by (src, dst) into a fixed 16-bucket array, tracking count and min/max payload length. After the walk, fire for every bucket whose count reaches `ICMP_TUNNEL_THRESHOLD` (8). Gating on both size and volume is deliberate (rules_wired.c:464-466): a single large diagnostic ping does not trip it, and interactive ping's fixed small payload (56 B Linux, 32 B Windows) is below the size floor.

Key (rules_wired.c:514-515): `icmp-tunnel:<src,39 cut>-><dst,39 cut>`. One incident per directed (src,dst) pair.

Detail (rules_wired.c:524-528): `<src>-><dst>: <n> oversized echo reqs (payload <min>-<max> B; ICMP covert channel)`. Carries both addresses, the count and the payload size range; does not carry a rate, entropy, or payload contents.

Severity WARN (rules_wired.c:530-531). `match_ip = dst`, `match_port = 0` (portless — ICMP has no port; dst is the tunnel endpoint), so when `--pcap-dir` is set and the alert meets the export policy (`pcap.min_severity` default 2 = CRIT only, src/tune.c:121, applied in engine.c:865, so a WARN does NOT export unless the operator sets it to 1 or 0), the matching packets in the `s->packets[]` ring are dumped once, when the incident opens (engine.c:860-896, `pcap_dumped`). Two limits matter for this rule: the ring is MAX_PACKETS = 256 packets of *all* traffic (include/sloth.h:27), and each stored packet keeps at most its first 64 bytes (`raw[64]`, PCAP_SNAPLEN_WIRED_RING, src/pcap_format.h:63; alert_pcap.c:204-205). Behind Ethernet + IPv4 + the 8-byte echo header that leaves ~22 bytes of Echo payload per packet, and almost none for IPv6. `match_port = 0` means `packet_matches` (alert_pcap.c:104-114) takes every packet to or from dst, not only ICMP. No evidence-ring frames (plain `fire()`). Resolves 300 s after the last tick that re-asserted the key.

Only 16 (src,dst) pairs are tracked per tick (bucket array full -> excess pairs skipped, rules_wired.c:496), a deliberate bound.

## The attack

ICMP Echo Request/Reply (RFC 792 type 8/0 for IPv4 [9], RFC 4443 §4.1/4.2 type 128/129 for IPv6 [10]) carries a Data field that exists only to be echoed back; both RFCs place no length limit and no content constraint on it [9][10]. That field is the covert channel. Because ICMP is almost always permitted outbound, carries an arbitrary payload, and is rarely logged, it is MITRE's canonical Non-Application Layer Protocol C2 (T1095) [3].

The technique is old and well-tooled. Project Loki (daemon9/route and alhambra, Phrack 49, 1996) first demonstrated encapsulating arbitrary data inside ICMP_ECHO/ICMP_ECHOREPLY payloads to slip past firewalls [7]. ptunnel (Daniel Stødle) reliably tunnels TCP over ping, the client sending data in Echo Requests and the proxy replying in Echo Replies, with a custom header (magic, state, seq, ack, length) layered in the payload — measured at ~150 kb/s down, ~50 kb/s up [5]. icmptunnel (Dhaval Kapil) "transparently tunnels your IP traffic through ICMP echo and reply packets" via a virtual interface [6].

Real actors use it. Unit 42 documents GALLIUM's PingPull RAT: its ICMP variant issues Echo Request packets to the C2, which answers with Echo Reply, each carrying an 8-byte value, a sequence number, a "PROJECT"-prefixed identifier, length fields, and base64-encoded AES-encrypted command data — explicitly exploiting that "few organizations implement inspection of ICMP traffic" [8]. MITRE's T1095 procedure examples include Anchor, COATHANGER and Regin using ICMP for C2 [3][4].

The passive tell sloth keys on is size plus volume: interactive ping sends a fixed small payload about once a second, while a tunnel fills toward the MTU at a higher rate. research/mitre/T1095.md describes the detector as watching "the **payload**, not the rate", with "payload size and entropy" as the signal and rate "deliberately not the trigger". That is not the rule that ships: the code reads only `payload_len`, computes no entropy, and *does* gate on volume (>= 8 oversized requests from one pair inside the window). The note's closing caveat still holds for the deployed rule — a patient adversary who keeps the payload small accepts lower throughput and stays under the 64-byte floor [1] — but the note should be read as design intent, not as a description of the code.

## Evidence that proves it

What sloth records: the detail line's src, dst and payload-size range, plus — uniquely among the six types in this batch — a pcap when `--pcap-dir` is enabled and the export policy permits it. That pcap is a one-shot snapshot of the 256-packet ring at incident open, truncated to 64 bytes per frame (see above), not a recording of the flow (match_ip = dst; note the default pcap.min_severity = 2 means a WARN does not export unless the operator sets pcap.min_severity to 1 (WARN and up) or 0 (any), docs/wiki/cli-reference.md). The JSONL `icmp` records around the alert carry per-packet `src`/`dst`/`ty`/`plen`/`v6` (jsonl.c, schema "icmp"), so a consumer can reconstruct the burst's size distribution and timing. `sensor_health` moves `SH_EVICT_ICMP_LOG` if the 256-record ring overflows, which also tells you the ICMP rate is high.

To call it real: look for sustained oversized Echo Requests between one internal host and one external endpoint, payloads clustered near the MTU rather than at 56/32 B, over a long duration (an interactive tunnel is slow and steady — minutes to hours). If `--pcap-dir` exported a snapshot, the first ~22 bytes of each IPv4 Echo payload are there to compare: a tunnel's data varies packet to packet (shell output, encrypted/compressed bytes; ptunnel's own header sits at the front of the payload [5]); a diagnostic ping's payload is a fixed pattern or incrementing bytes, identical every packet. For the full payload, capture the pair separately (tcpdump on the sensor) — sloth's ring does not keep it. A matching outbound-only direction (requests one way, replies mirroring) and an external dst that is not a known monitoring target strengthen it.

What refutes it (benign fingerprint): payloads that are a fixed repeating pattern or a simple timestamp, identical across packets (ordinary ping -s); a dst that is a known PMTU-test or monitoring target; a steady single size exactly at a round diagnostic value (e.g. 1472 for MTU probing). research/mitre/T1095.md: large ICMP payloads have legitimate uses (PMTU discovery, ping -s, vendor keepalives), and entropy — which this rule does not compute — is the discriminator that survives those [1].

## Benign causes

- **ping -s / deliberate large diagnostics.** Named in research/mitre/T1095.md and docs/wiki/alert-remediation.md [1]; a human or monitoring job sending large pings sustains the pattern.
- **Path-MTU discovery.** Large Echo Requests with DF set probing for the MTU produce clustered large payloads from one pair.
- **Vendor keepalives.** Some appliances keepalive over large ICMP; fixed-size, fixed-pattern, periodic — the opposite of a filled tunnel.

## Assessment

Severity rationale: WARN is correct. Metadata-only evidence (size + rate, no payload) is a strong lead but cannot prove a covert channel, and the research note names entropy as the discriminator that survives the benign causes — a discriminator the shipped rule does not compute [1]. Escalating to CRIT would over-claim; leaving it at WARN is the honest design. Note that at WARN the default export policy writes no pcap at all, and when it does the snapshot is 64 bytes per frame, so the analyst's payload check usually needs a separate capture.

Real-world prevalence: a genuine and actively-used class — Loki to ptunnel to PingPull [5][6][7][8] — but less common than HTTP(S)/DNS C2 because its throughput is low and a defender who inspects ICMP catches it. Worth acting on when corroborated.

Reference-host noise verdict: 5,659,835 fires on 14 keys. The rule counts per tick while a (src,dst) bucket stays >= 8 oversized Echo Requests in the sliding 60 s window, so this is ~404k ticks ≈ 28 hours of standing condition per pair, not 5.6M distinct packets — 14 host pairs that each sustained oversized Echo traffic for long stretches. Fourteen pairs is small enough to investigate individually, but the counter inflates each into a multi-million "flood". The core ambiguity the numbers expose: an interactive tunnel and a long-running MTU/keepalive loop both produce exactly this standing pattern, and the rule cannot separate them without payload entropy. Recommendations: surface `observations` not `count`; add a packets-per-minute rate and a size-variance flag to the detail; and, where policy permits payload reading, a coarse entropy estimate would move this from "lead" to "finding".

Is the evidence sufficient to act? As a lead, yes; for attribution, look at the payloads - sloth's exported snapshot (if `pcap.min_severity` was lowered) shows only the first ~22 payload bytes per packet, so a separate capture of the pair is usually needed. A responder should first identify the two hosts and the payload sizes, confirm it is not a known diagnostic (ping -s, MTU testing, a monitoring job), check how long the exchange has run, and if it is not explained, isolate the internal host and examine it for a tunnel client (docs/wiki/alert-remediation.md "ICMP_TUNNEL"). This is a covert channel, not a bug — there is no vendor fix; the control is egress ICMP inspection/filtering.
