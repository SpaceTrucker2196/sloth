## What the rule checks

Input: `s->ldap_events`, the LDAP aggregate table of `MAX_LDAP_EVENTS` = 64 rows keyed by **client IP** - whichever endpoint of a TCP/389 or TCP/3268 flow is not on the LDAP port (`include/sloth.h:477-498`; `src/ldap_snoop.c:100-108`). `ldap_snoop_observe()` walks the BER envelope of each TCP payload the capture thread hands it (`src/capture/capture.c:704-709`): outer SEQUENCE, messageID INTEGER, then the protocolOp tag byte (`src/ldap_snoop.c:47-69`). It recognises three tags, `0x60` BindRequest, `0x63` SearchRequest and `0x73` SearchResultReference (`:25-27`), which are the `[APPLICATION 0]`, `[APPLICATION 3]` and `[APPLICATION 19]` constructed tags RFC 4511 assigns to those operations [3]. A SearchRequest increments `search_count`; a BindRequest increments `bind_count` and, if its `name` LDAPDN is the empty string, `bind_anon_count`; a reference increments `search_ref_count` (`:125-139`). Only the first message in a segment is parsed - `peek_op` is called once per payload, not in a loop (`:110-112`) - so several LDAP messages packed into one TCP segment count once, and a request split across segments is missed. The counters are lifetime totals for the row; nothing decays them. TLS variants on 636 and 3269 are not observed (`src/capture/capture.c:701-703`; `docs/wiki/ldap-snoop.md:18-19`).

Per tick the rule fires for any row whose `search_count` is at or above `LDAP_SEARCH_FLOOD_THRESHOLD` = `tune_val(TUNE_LDAP_SEARCH_FLOOD)` (`src/alerts/rules_wired.c:949`, `:954`), default **50** (`src/tune.c:56`: `ldap.search_flood`, min 2, max 10000, unit "searches"). Key: `ldap-flood:<src_ip>` (`:956-957`). Detail: `"<src>: <n> LDAP SearchRequest messages (AD enumeration indicator; bind=<b>, anon_bind=<a>, referrals=<r>)"` (`:958-963`). CRIT, `match_ip` = the client, `match_port` 389 even when the flow was on 3268 (`:964-968`; `docs/wiki/ldap-snoop.md:64-70`). The incident resolves 300 s after the last tick that re-asserted it (`include/sloth.h:860`). The 64-row table evicts the least-recently-seen client when full (`STAB_OLDEST`, `src/ldap_snoop.c:19-20`; `src/stab.h:27`; tallied as `evict_ldap_event`, `src/sensor_health.h:95`) and never expires rows by age - none of the six observers in this family calls `stab_expire()`.

Note what gates: `search_count` alone. `bind_count`, `bind_anon_count` and `search_ref_count` are reported in the detail but do not affect the decision, and the rule does not look at the search filter, base or attribute list (`docs/wiki/ldap-snoop.md:103-109` lists per-attribute inspection as out of scope).

## The mechanism

LDAP is the directory protocol Active Directory speaks; domain controllers listen on the IANA-assigned port 389 [3] and on 3268 for the Global Catalog (`docs/wiki/ldap-snoop.md:9-11`). MITRE T1087.002 is "Adversaries may attempt to get a listing of domain accounts", to "determine which domain accounts exist to aid in follow-on behavior such as targeting specific accounts which possess particular privileges"; the page names `ldapsearch`, `net user /domain`, PowerShell AD cmdlets, and lists BloodHound ("can collect information about domain users, including identification of domain admin accounts"), AdFind, Cobalt Strike, CrackMapExec and IcedID ("can query LDAP ... to identify additional users") among the software that does it, with APT29, Volt Typhoon, Scattered Spider, Wizard Spider and many others among the groups [2]. The collector that defines the shape is SharpHound, which "uses native Windows API functions and LDAP namespace functions to collect data from domain controllers": group memberships, trusts, abusable rights on AD objects, GPO links, OU structure, sites, and properties from computer, group and user objects [4]. ldapdomaindump is the Python equivalent - "Active Directory information dumper via LDAP" that "will try to dump every single attribute it can read" and accepts an empty username for anonymous authentication [5].

The repo corpus explains why the rule is a rate rule and not a content rule: each query an enumeration tool sends is individually ordinary - asking for all users is what a directory is for - and what distinguishes collection from use is that collection asks for everything, from one place, in a short time [1]. It is mapped to T1087.002 rather than to brute force because nothing here is an authentication failure; the adversary is already authenticated, usually as an ordinary user, and that is why the enumeration succeeds [1]. The limits the corpus states are the limits of this rule: LDAPS content is invisible, so an adversary using LDAPS produces nothing here, and volume is not intent [1].

## Evidence that proves it

What sloth records:

- `alert` / `alert.*` JSONL under `ldap-flood:<src>` with the four counters in the detail;
- `ldap_event` state records keyed on `src_ip` (`docs/wiki/jsonl-schema.md:727`): `bind_count`, `bind_anon_count`, `search_count`, `search_ref_count`, `first_seen`, `last_seen`;
- a per-alert pcap if `--pcap-dir` is set (CRIT passes the default `pcap.min_severity` 2, `src/tune.c:121`); the filter is `match_ip` = the client and port 389 either side (`src/alert_pcap.c:104-114`), so the file holds that client's cleartext LDAP from the ring - including the SearchRequest filters and attribute lists the rule itself does not read.

What makes it enumeration: a **burst** - `search_count` climbing by hundreds inside seconds of `first_seen` (`docs/wiki/ldap-snoop.md:72-77` puts SharpHound and ldapdomaindump at 200-2000 searches in their first seconds; that figure is the wiki's, not a fetched source's), from a workstation rather than a server; a non-zero `bind_anon_count` alongside it (anonymous bind is ldapdomaindump's no-credential mode [5]); `search_count` high with `bind_count` low, which the wiki reads as a replayed ticket querying without re-binding (`docs/wiki/ldap-snoop.md:98-99`); and, in the pcap, SearchRequests whose filters enumerate `objectClass=user`, group membership or `servicePrincipalName` across the whole base. The deciding evidence is off the wire: the directory's own logs say which account ran the searches, and whether that account is a known bulk reader [1], `docs/wiki/alert-remediation.md:325-343`.

What refutes it: `search_count` that grew slowly over days from a server address (the sensor's lifetime counter does not distinguish 50 searches in one second from 50 in a week); a source that is on the operator's list of identity-sync, monitoring, backup, address-book or scanner hosts [1]; a pcap that shows ordinary per-logon lookups repeated across many sessions rather than one sweep.

## Benign causes

- **Legitimate bulk readers.** Identity-sync connectors, monitoring agents, backup software, address-book clients and vulnerability scanners all pull the directory in bulk on a schedule, and the corpus says every one of them will trigger this rule [1]. On an AD segment these are the dominant source of firings.
- **Lifetime counter.** `search_count` is never reset or windowed (`src/ldap_snoop.c:133-135`; no `stab_expire`), so a workstation doing 10-20 searches per logon (`docs/wiki/ldap-snoop.md:72-74`) reaches 50 after three to five logons while its row survives in the 64-slot table. On a quiet segment with few LDAP clients, rows survive for the life of the process.
- **Global Catalog and multi-DC traffic folding.** The key is the client IP only, so one client's searches against several DCs (and against 3268) sum into one row - correct for enumeration, but it also means a client legitimately talking to three DCs reaches the threshold three times faster.
- **Undercounting is also possible.** Several messages in one segment count once (`src/ldap_snoop.c:110-112`), so a tool that pipelines requests can run below the threshold; absence of the alert is not evidence of absence of enumeration, and LDAPS is invisible entirely [1].

## Assessment

CRIT is right for the thing the rule is named after: bulk collection from one host is the first step of almost every AD intrusion, and the tools that do it are the most-cited in the technique's procedure list [1], [2]. The caveat is structural. The rule's comment calls the window "the active aggregation window" (`src/alerts/rules_wired.c:941-948`) but no window exists: the counter is a lifetime total per row, and the row leaves only by LRU eviction. So the rule cannot separate 50 searches in one second (SharpHound) from 50 across a week (a workstation that logged on five times), and on an AD segment the second case is far more common. Two refinements worth considering: a time window on `search_count` (a count over the last N seconds, as the comment already describes), and the Tier 2 filter/attribute inspection the wiki lists (`docs/wiki/ldap-snoop.md:103-109`), which would let the detail say "enumerating servicePrincipalName" rather than "many searches".

Prevalence: a first-class ATT&CK sub-technique with a long procedure list of software and groups, BloodHound and AdFind foremost [2]; SharpHound reads the whole graph from the DC over LDAP by design [4], and ldapdomaindump dumps every readable attribute by default [5]. No fetched source quantifies a field rate, so none is claimed.

Reference host: not seen (null) - consistent with no cleartext LDAP on the monitored segment (no domain controller; the sibling `KERB_PREAUTH_BURST` is null for the same reason). The behavioural note for an operator who deploys on an AD segment: because `search_count` never decays, each known bulk reader will cross the threshold once and then stand as a CRIT until evicted; expect one standing incident per such source, record the sources, and treat a *new* key - a workstation, not a server - as the finding.

Sufficient to act on alone? No - it is a lead that names the host to look at. A responder should (1) identify the source and the account doing the searching, and check it against the known bulk readers [1], `docs/wiki/alert-remediation.md:325-343`; (2) read the `ldap_event` record's `first_seen`/`last_seen` against `search_count` to tell a burst from a slow accumulation; (3) open the per-alert pcap and read the SearchRequest filters - enumeration asks for all users, groups, computers and trusts, a logon asks for one user's memberships; (4) if the reader is not a known bulk reader, disable the account and investigate the host [1]. Tuning: raise `ldap.search_flood` only after the known bulk readers are recorded, not to silence them; the ceiling of 10000 is there for a segment with a heavy sync job.
