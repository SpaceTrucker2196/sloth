## What the rule checks

Inputs. The module-global RRM pair table `g_rrm[]` in src/action_snoop.c, read under its mutex through `rrm_busiest_pair()` and `rrm_find()` (the rule does not read the `s->rrm_pairs[]` snapshot), filled by `rrm_frame()` (src/action_snoop.c:621+) from Radio Measurement action frames (category 5 - src/action_snoop.h:27,45). A Measurement **Request** (action 0) carrying a Measurement Request element (tag 38) whose measurement type is Beacon (5) is a Beacon Request; the parser reads the Beacon Request body per §9.4.2.20.7 - OpClass, Channel, then optional subelements - and treats subelement 0 (the SSID subelement) as the signal: present and non-empty means **targeted** (`targeted_reqs++`, `last_ssid` recorded), absent means a wildcard and only bumps `broadcast_reqs` (action_snoop.c:661-709). A Measurement **Report** (action 1, tag 39) bumps `reports_seen` for the pair. The pair is keyed on (BSSID asking, STA being asked); a request travels AP->STA (sta = addr1/da), a report the other way, both folded into the same pair (action_snoop.c:634-636). A PMF-protected action frame is ciphertext and never parsed, so on a protected BSS these records describe only the unprotected minority (jsonl-schema contract note, #124).

Condition. `rule_rrm_survey_abuse()` asks `rrm_busiest_pair(now, 300, 6, ...)` (rules_wifi_mgmt.c:490-494; src/action_snoop.c:719-734) for the pair with the largest `targeted_reqs` among pairs whose `last_seen` is inside the trailing 300 s and whose `targeted_reqs` is >= 6. Note what is and is not windowed: the 300 s applies to the pair's last activity only; `targeted_reqs` is a cumulative counter on the (BSSID, STA) slot, reset only when the slot is evicted (LRU once `SLOTH_RRM_MAX_PAIRS` = 64 is full, action_snoop.c:594-612). Six targeted requests spread over an hour therefore qualify if the sixth - or any later request or report on the pair - arrived within the last five minutes; "6 in 5 min" (docs/views/alerts.md) is the intent, not the arithmetic, and the detail's `%d req/%ds` prints the cumulative count against the window label. Only that one pair is examined per tick: if the busiest qualifying pair fails both discriminators below, the rule returns, and a smaller pair that would pass them is not looked at until it overtakes the busiest one (ties go to the earlier table slot, `<= best`). It then applies two discriminators, not rate:

- **fishing** - the asker has been heard beaconing *something* (`asker_beacons`) but never the SSID it is asking about (`asks_own_ssid` false), checked against the beacon inventory entries for that same BSSID - its current `ssid` and its own `ssid_history[]` (rules_wifi_mgmt.c:507-521). Despite the code comment's "multi-VAP" wording, a sibling VAP's *different* BSSID on the same radio is never consulted, so an AP asking clients about an SSID its sibling BSSID advertises reads as fishing. Only the pair's most recent targeted SSID (`last_ssid`) is tested. A legitimate AP asks clients about SSIDs it itself advertises; asking about one it never beaconed is the recon tell. With `--hop` the AP inventory is a sample, so "never heard this BSSID beacon" is deliberately *not* treated as fishing (it would fire on every AP the sweep missed).
- **outsider_on_my_net** - the surveyed SSID is a `--my-ssid` network but the asking BSSID is not `--my-bssid` (rules_wifi_mgmt.c:525-527): an outsider enumerating the operator's own network through the operator's own clients.

The rule returns without firing unless `fishing || outsider_on_my_net` (rules_wifi_mgmt.c:529). Requests with no SSID subelement (wildcard, ordinary steering) never count toward the threshold. Key is `rrm:<bssid>-><sta>` (rules_wifi_mgmt.c:539). Severity is CRIT when `outsider_on_my_net || twin` (the asker is a known evil-twin candidate, `btm_candidate_is_twin`), else WARN (rules_wifi_mgmt.c:549-550). The detail names asker, client, the SSID asked for, the req/window count, reports-seen, evil-twin status, and the fishing / my-network suffixes (rules_wifi_mgmt.c:540-547). No evidence IDs, no match_ip, no pcap.

## The attack

802.11k Radio Resource Measurement lets an AP ask an associated client to go measure something and report back. A **Beacon Request** asks the client to scan a channel (or all channels) and return a Beacon Report listing the BSSIDs it heard, their signal strength and capabilities (IEEE 802.11-2020 §11.10, §9.6.7) [3]. It is a genuine roaming optimization: the client surveys the air so the AP can make a better steering decision; Apple documents 802.11k support across its current devices [4], and hostapd implements the AP side (`rrm_beacon_report` in hostapd.conf, `hostapd_cli req_beacon` to send one) [5].

The abuse - MITRE T1595.002, Active Scanning: Vulnerability Scanning [1] - is that the AP's request is unauthenticated on a non-PMF link, and the recon is performed *by a station that trusts its AP*. An attacker impersonating (or being) an AP sends targeted Beacon Requests and harvests the Beacon Reports: the adversary's own radio never transmits a probe, yet it learns the exact RF neighbourhood as seen from the victim's antenna - which is precisely the input a convincing evil twin needs (it tells the attacker which BSSIDs, channels and signal levels to imitate). Asking about a specific SSID the attacker does not itself run is the behavioural tell: a legitimate AP has no reason to make its clients survey for a network it does not operate. The strongest case is an outsider surveying the operator's own SSID through the operator's own clients.

Tooling: this is a crafted-action-frame technique (hostapd `req_beacon`, custom 802.11k tooling, research scripts), not a commodity flooder - mdk4 ships no RRM mode [6].

## Evidence that proves it

What sloth records. The alert detail carries asker BSSID, client STA, the requested SSID (`last_ssid`), the targeted-request count over the 5-minute window, `reports_seen`, whether the asker is an evil-twin candidate, and the fishing / my-network context. The `rrm_beacon_request` JSONL record (keyed `bssid`+`sta_mac`) keeps `targeted_reqs` and `broadcast_reqs` as **separate** fields - only the first is the signal - plus `reports_seen` separately again (a reply is evidence a survey succeeded, not that one was attempted), `last_ssid`, `last_channel` and `measurement_mode` (0 passive, 1 active, 2 table). No pcap is written.

What makes it real. A single asking BSSID that has directed six or more targeted Beacon Requests at one client and is still active, naming an SSID that BSSID has never been heard to beacon, with Beacon Reports coming back (`reports_seen > 0`) - that is recon being performed and succeeding. The CRIT case - the surveyed SSID is the operator's own, the asker is not the operator's BSSID - is unambiguous: someone outside the network is enumerating it through its clients. An asker that is itself a live evil-twin episode half ties the recon directly to an impersonation in progress.

What refutes it. A controller-managed deployment legitimately asks its clients to survey, and if sloth has only seen part of the controller's VAP/SSID layout, an asker beaconing "Corp-Guest" while requesting surveys for "Corp-Secure" (both the same controller's) reads as fishing. The fingerprint of the benign case: the asking BSSID and the requested SSID belong to the same physical deployment (same vendor OUI, co-located, overlapping client set), and the requests are broadly distributed across clients rather than hammering one. `measurement_mode` and the channel pattern matching ordinary roaming behaviour also point benign.

## Benign causes

- **Enterprise roaming controllers.** Cisco, Aruba, Mist and similar push 802.11k Beacon Requests as part of assisted roaming; a multi-SSID controller whose full VAP map sloth has not observed can satisfy the "beacons one SSID, surveys for another" fishing test entirely legitimately. This is the documented benign trigger (docs/views/alerts.md).
- **Client-side roaming support.** Apple documents 802.11k on iPhone 5s and later, iPad, Apple Vision Pro and Apple-silicon Macs (not Intel Macs), using the Neighbor Report to prioritise roaming scans [4]; a network tuned for those clients runs 802.11k, and its Beacon Requests are legitimate traffic.
- **Sibling VAPs and hidden SSIDs.** The fishing test only compares against the asking BSSID's own beaconed SSIDs, so a radio asking about an SSID served by its sibling BSSID, or an AP with a hidden (empty-SSID) beacon whose name sloth has not yet learned from a probe response (`beacon_reveal_hidden_ssid()`, src/beacon_snoop.c:1451), asking about its own network both satisfy "beacons something, never that SSID".
- **Partial observation under --hop.** A hopping sensor samples the AP inventory, so "we never heard this asker beacon that SSID" is weaker; the rule already refuses to treat a never-heard BSSID as fishing for this reason, but a BSSID heard beaconing only one of its several SSIDs can still mislead.

## Assessment

Severity rationale. The design is sound: the rule refuses to fire on rate (which would indict every roaming controller) and turns instead on the semantic discriminator - asking about an SSID the asker never advertised - with CRIT reserved for the two cases that are specifically adversarial (an outsider surveying the operator's own network, or a known evil twin doing the asking). That is a defensible WARN/CRIT split.

Real-world prevalence. 802.11k is widely deployed and the Beacon Request is a normal frame [4][5]; weaponizing it for recon is a recognized technique (T1595.002) but is low-volume, targeted, and absent from commodity flood toolkits [6]. There is little public telemetry on how often it is abused in practice, so treat a finding as rare and worth a closer look rather than routine.

Reference-host noise. 85,215 fires on **1 key** at max_sev CRIT. Because `count` is per-tick and the key is one (BSSID, STA) pair, this is a single incident that stayed open and kept re-qualifying for roughly 5.9 hours at 4 ticks/s - one persistent surveyor against one client, not 85,215 frames and not a flood of alerts. Cadence caveat: the tick arithmetic assumes the default 250 ms poll with an idle keyboard. `poll_tick()` runs once per main-loop iteration (`poll_data()` at src/main.c:1628 calls it at :205) and the wait before it is cut short by any keypress or by `event_wake_signal()` on a new or escalated alert (src/alerts/engine.c:526, 608), so real ticks/s is >= 4 and every duration derived here is an upper bound; `--refresh-ms` changes the base. The per-pair key dedupes correctly and no additional throttle is warranted. The arithmetic to show a responder: 85,215 fires / 1 key = one continuous finding; read `targeted_reqs` in the detail for the actual frame volume.

Is the evidence enough to act on? For the CRIT (outsider surveying a `--my-ssid` network, or a twin asker), yes - that is targeted reconnaissance of a declared-own network. For a bare WARN fishing finding with no ownership context, corroborate against the `rrm_beacon_request` stream and the beacon inventory: confirm the asker and the requested SSID are not two VAPs of one managed deployment before escalating. First response: note the asker and the client; determine whether the asker is the operator's AP and ever beaconed the SSID it asked about; if it is not the operator's, remove it (docs/wiki/alert-remediation.md). Do not join or probe the asker.
