## What the rule checks

Input: the DNS log ring `s->dns_log[]` (`dns_log_entry_t`, filled by `src/dns_log.c` from the capture path, which hands any UDP packet with port 53 at either end to the DNS parser - src/capture/capture.c:822). No new capture surface - the qname is already in state. Run order: `src/alerts/rules_table.c:55` (0-based table index 28), immediately after `rule_surv_cloud_sni`.

Per entry (rules_wired.c:714-775):

1. Skip responses, empty qnames, and truncated qnames: `e->is_resp || !e->qname[0] || e->qname_trunc` (725). Responses are skipped because their source is the resolver, which would fold every client behind it into one alert. `qname_trunc` (stored name cut at 63 bytes or at a NUL octet) is skipped because a prefix can end on a listed suffix while the real name continues under another domain - `<43 x a>.control.verkada.com.evil.example` stores as a Verkada host, and any web page can make a browser resolve such a name.
2. `vendor_watchlist_match_domain(e->qname, &vend, &fam)` (726; vendor_watchlist.c:83) - a label-boundary suffix match (`domain_suffix_match`, vendor_watchlist.c:73, the same shape as the matcher in src/threat_intel.c:46) against `kEndpoints[]` (vendor_watchlist.c:31-66): `evidence.com` (axon), `axon.com` (axon), `flocksafety.com` (flock-safety), `control.verkada.com` (verkada). Each entry matches itself and any subdomain.

For a matched query the rule picks the smallest qname this host asked for that vendor across the ring (738-745), so two names under one key do not flip the detail signature and cost an `alert.update` every `ALERT_UPDATE_MIN_S`. Key via the typed `akey_*` builder: `surv-dns:<vendor>:<local-host>` (752-757), not the qname (a vendor hands out per-region/per-session names, so one device would otherwise be many alerts). Detail (759-763): `<src> looked up <qname>: <vendor> <family> (DNS lookup only; device or portal use not distinguishable)`. Fires `ALERT_SEV_LOW` with `match_ip = e->src`, `match_port = 53` (767-768) - the asking host and 53, so the per-alert pcap worth having is that host's DNS traffic.

## The attack

This is not an attack; the technique is empty on purpose. The rule reports an exposure: a host on the monitored segment is resolving the service domain of a cloud surveillance vendor. Before a device opens TLS to a vendor's cloud it resolves the name, and sloth already logs the DNS queries it overhears [1]. The companion rule SURV_CLOUD_SNI reads the same watchlist from the TLS ClientHello; SURV_DNS exists for the cases where no parseable ClientHello follows - a QUIC upload, a ClientHello using Encrypted Client Hello, or a TLS path the capture does not see. For Verkada the vendor states its devices "do not support" DNS over HTTPS and resolve over UDP port 53, so a Verkada device's lookups are plaintext by design [6][7].

The repo (#105) rejected T1071.004 (Application Layer Protocol: DNS), which describes command-and-control carried inside DNS - a claim about the payload of the lookup that a vendor-name match cannot make. A body camera uploading to its own vendor's evidence cloud, or an analyst with the vendor portal open in a browser tab, is the system working as designed, not an adversary step. The watchlist is deliberately short and every row is sourced to a vendor's own network-requirements or firewall allow-list document (the #145 bar: one row per document) [5]: Axon's Cloud Customer FAQ names the evidence.com->axon.com migration and tells agencies with allowlists/DNS filtering/proxies to permit axon.com [5, Axon FAQ]; Verkada's Camera Network Settings lists the per-region camera FQDNs (api., relay., index., firmware., update., time. and the `*.vnetcap` family) under control.verkada.com, beside coarse `*.verkada.com`, `*.amazonaws.com` and `time.cloudflare.com` rules that the watchlist deliberately does not copy; the page's `vconductor.*.command.verkada.com` hosts are not under control.verkada.com and are not matched either [6]; Flock's transparency portals live under flocksafety.com [5]. Ring and ~20 other vendors were checked and failed the bar (no published domain) and are pinned absent by `test_unsourced_domains_are_absent` [1].

## Evidence that proves it

The detail carries the asking host, the (smallest) queried name, the vendor and family, and the explicit limit `DNS lookup only; device or portal use not distinguishable`. Because `match_ip`/`match_port` are set to the host and 53, a critical-severity export path exists - but this rule is LOW, so a per-alert pcap is written only if `pcap.min_severity` is lowered from its CRIT default (docs/wiki/cli-reference.md; the pcap, when written, is that host's DNS traffic). JSONL emits `src`/`53` and no `technique` field (dropped because `alert_technique()` is empty; docs/wiki/jsonl-schema.md). When SURV_CLOUD_SNI also fires for the same host and vendor, the two corroborate each other; neither confirms a device.

What a reader should confirm: the asking host is a device, not a browser or a forwarding resolver (if it is a Pi-hole or router dnsmasq, the real asker is a client behind it - find that client). What refutes it as meaningful: a prefetching browser, a link preview, or a filtering resolver that resolved the name without any device connecting; and for `axon.com` specifically, a plain web visit to Axon's marketing site, which shares the domain. The repo is explicit that neither rule can tell a device from a browser (research doc §"What the detector does not establish").

## Benign causes

- **Browser / prefetch / link preview.** The dominant false positive and the reason for LOW: a name resolved with nothing connecting [1][5].
- **Marketing-site visit on a shared domain.** `axon.com` is Axon's marketing site as well as its evidence-platform migration target, so a product-page visit fires it [5].
- **Filtering resolver.** A DNS filter resolving the name to decide whether to block it.
- **Forwarding resolver on the segment** appears as its own asking host, with a row that merges every client behind it - not suppressed, because guessing which local hosts are resolvers would hide a real asker.

## Assessment

LOW is correct and deliberately one tier under SURV_CLOUD_SNI: a lookup is weaker than a session. The match itself is precise (vendor-published domains, label-boundary suffix, truncated names skipped), so false positives come from the signal's weakness, not from sloppy matching. On the reference host the type is not seen (null data). The arithmetic to expect if it fires: count rises per tick while a query stays in the 256-entry ring (count-bounded, not time-bounded), keyed per (vendor, host), so a single host that resolved a vendor domain once is one row with a climbing count until DNS traffic pushes that query out. Neither column counts queries: `count` is ticks, and `observations` moves only when the detail changes - which, because the detail pins the smallest qname, is rarely. A responder should note the local host and the vendor domain, check whether the asker is a device or a resolver, and treat it as expected if the host is known to use that platform; otherwise identify the device or application (docs/wiki/alert-remediation.md §SURV_DNS). All of SURV_CLOUD_SNI's limits apply unchanged: it cannot tell a device from a browser, and for Flock specifically the camera uplinks over cellular, so a hit means a host on this network uses the platform, not that a camera is on the segment.
