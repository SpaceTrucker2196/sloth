## What the rule checks

Input is `s->mdns_services[0..mdns_count]` — DNS-SD service rows that sloth observed passively (no query is sent; the comment stresses "sloth sends no query"). For each row (src/alerts/rules_camera.c:36-41):

- `e->instance[0]` must be non-empty (a named instance).
- `cam_mdns_service(e->service, &label, &specific)` must match — the predicate in `src/camera_vendor.c:636-650` compares the service's first label (up to the first dot) case-insensitively against a small embedded table (src/camera_vendor.c:622-634): `_axis-video` (IANA "Axis Video Cameras", camera_specific 1), `_cctv` (IANA "IP and Closed-Circuit Television for Securitiy applications", camera_specific 1), `_rtsp` (IANA port 554 "Real Time Streaming Protocol", camera_specific 0 — a protocol, not a device class).

Key: `akey_begin("cammdns")` + `akey_remote(e->instance, 40)` → `cammdns:<first 40 chars of the instance, non-key-safe bytes as '_'>:<FNV-64 of the whole stored instance>` (lines 43-47; src/alert_key.c:92-104). `e->instance` is the full Service Instance Name as read from the PTR rdata (e.g. `Name._axis-video._tcp.local`, include/sloth.h:171), stored in 64 bytes, so the service type is part of the identity and two service types under one instance label are two keys; two names identical in their first 63 bytes share a row (src/mdns_snoop.c:29-37). The DNS-SD instance name is the identity (RFC 6763 §4.1 "Instance . Service . Domain") and survives a DHCP lease change, so the IP is carried in the detail and the pcap match but is not the key [3]. WARN, confidence 0. Detail (lines 58-65): the instance, the service type, the human label, where (`at <ip>:<port>` / `at <ip>` / "(address not yet seen)"), the host if known, and for `_rtsp` the clause "; RTSP corroborates, not a device class". `fire(...)` passes `e->ip` as match_ip and `e->port` as match_port (lines 66-68), so with `--pcap-dir` a per-alert pcap of that host's packets is written.

Technique deliberately empty: the camera's own announcement read from unsolicited traffic, so T1046 (Network Service Discovery) would claim an enumeration sloth never performed. Pinned alongside CAM_WS_DISCOVERY and CAM_SETUP_SSID by `tests/test_research_corpus.c :: test_uncitable_kinds_with_a_real_basis_are_still_cited`.

## The attack

There is no attack — the finding is an *exposure/identity* signal. DNS-SD (RFC 6763) lets a device advertise a service by an IANA-registered Service Name (RFC 6335: 1-15 chars, letters/digits/hyphens, registered in the Service Name and Transport Protocol Port Number Registry) [3][7]. A Service Instance Name is "Instance . Service . Domain" [3]. Cameras advertise so that apps and NVRs can find them zero-config. The IANA registry lists `axis-video` as "Axis Video Cameras" and `cctv` as "IP and Closed-Circuit Television for Securitiy applications" — these name the device class itself — and `rtsp` (554) as the "Real Time Streaming Protocol," a streaming protocol that cameras commonly advertise but which media servers also use [4].

Why it matters to an operator: a camera on the monitored network is a surveillance and attack-surface concern. IP cameras and DVRs were the backbone of the Mirai botnet (peak ~600,000 infected devices; "Mirai primarily targeted IP cameras, DVRs, and consumer routers"), typically via default credentials [5][6], and camera web stacks carry their own critical bugs (e.g. Hikvision CVE-2021-36260, a command injection in the web server of "some Hikvision product", CVSS 3.1 9.8 [8]). sloth surfaces the device's *presence* and *identity claim*; it does not probe or exploit, and the detail says a match "corroborates, does not confirm" the device class.

## Evidence that proves it

The detail (above) names the DNS-SD instance, the service type and label, the IP and SRV port, and the host. With `--pcap-dir`, `alert_pcap` writes every packet in the ring whose src or dst matches the instance IP (and port, if non-zero) at fire time (src/alert_pcap.c:105-113) — for an mDNS advertiser that captures the multicast DNS responses carrying the PTR/SRV/TXT records, and any contemporaneous traffic to/from the camera's IP. The JSONL `alert.*` records carry `key`, `detail`, `sev`, `match_ip`/`match_port`, and `pcap_path` once a file is written (src/jsonl.c:616-617); no `technique` field (empty, dropped). The `sensor_health` counter `evict_mdns_service` moves if the mDNS table is full and a new instance is refused.

To call it a real camera service: in the pcap/mDNS log, a PTR record for `_axis-video._tcp` or `_cctv._tcp` (device-class names) with an SRV record resolving to the host, ideally with a TXT record and a vendor-consistent hostname. For `_rtsp._tcp` alone, treat it as corroboration only — pair it with the device's other signals (an RTSP SERVER banner, a camera-vendor OUI) before calling the host a camera. What refutes "camera": an `_rtsp._tcp` instance that resolves to a known media server (Plex, a NAS), or an instance name that clearly belongs to a non-camera appliance.

## Benign causes

Not false positives (the device really is advertising the service), but non-camera triggers of the *camera* reading: `_rtsp._tcp` from a media server, NAS, or streaming appliance (the single most likely mislabel, which is why its row is camera_specific 0 and the detail says so). `_axis-video` and `_cctv` are device-class names in the IANA registry, so a match there is a strong camera signal with little benign noise. The other dimension of "benign" is authorised cameras: a correctly-inventoried doorbell or security camera trips this on first sighting exactly as an unknown one does — the rule makes no ownership distinction, so the operator reconciles it against their inventory.

## Assessment

WARN is the right altitude: a privacy/exposure finding about the device's own announcement, not an adversary action — hence the empty ATT&CK technique, correctly. Prevalence of the underlying thing (LAN/IP cameras) is high and the security stakes are real (Mirai, camera-stack CVEs) [5][6], so surfacing a camera's presence has operational value even though the finding itself is benign. On the reference host it did not fire (host data null) and is structurally quiet: one row per advertised camera service instance, and cameras are few. No dedupe or threshold tuning is warranted. The evidence (the device's self-advertisement, plus a pcap of its mDNS records and traffic) is sufficient to identify and locate the device but not to assert compromise. A responder reconciles the instance against the operator's inventory; an unexpected camera should be located, its firmware and credentials checked (default-credential and CVE exposure), and removed or segmented if it does not belong [remediation: docs/wiki/alert-remediation.md].
