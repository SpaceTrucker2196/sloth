## What the rule checks

Input is the per-(BSSID, STA) WPS registration-session table built by `src/wps_track.c` from the EAP-WSC opcode stream (`wps_track_observe()`, capture thread, parse-only). The rule snapshots the table under one lock (`wps_track_snapshot`, src/alerts/rules_enterprise.c:281) and reads the silence floor from the tune registry (`tune_val(TUNE_WPS_PIXIE_SILENCE_S)`, line 283).

For each session it calls `wps_track_m3_abandon(&sess[i], now, &m3, &quiet)` (src/wps_track.c:199-217). That helper returns 1 for the Pixie-Dust shape — an attempt (one M1 to the next M1) that reached **M1 and M3 and never M4..M8 or Done**. It checks the current open attempt first (`attempt_m3_ts` set, `attempt_bits` has the M1+M3 bits and none of the past-M3 bits or the Done bit, src/wps_track.c:202-210), with silence = `now - last_seen`; otherwise it reports the newest *closed* abandoned attempt (`abandon_m3_ts`, whose silence was frozen when a re-arming M1 closed it, lines 211-215). The rule then requires `quiet >= silence` (default 60 s) before firing (src/alerts/rules_enterprise.c:289). WARN, confidence 0.

Key: `akey_begin("wpspixie")` + `akey_mac(bssid)` + `akey_mac(sta)` → `wpspixie:<bssid>:<sta>` (lines 297-301), so the dedup unit is the exact pair. Detail string fields (lines 306-310): the STA, the BSSID, the configured silence threshold (not the live silence — a ticking number in the detail would alter the change signature every second and emit an `alert.update` every `ALERT_UPDATE_MIN_S`, so the floor is printed instead), the Bongard-2014 attribution, the words "corroborates, does not confirm", and " - YOUR network" when `ownership_is_my_bssid()` matches.

## The attack

Wi-Fi Protected Setup (WPS) lets a device join a protected Wi-Fi network by proving knowledge of an 8-digit PIN instead of the passphrase [2][7]. In the WPS "external registrar" exchange the enrollee — usually the AP itself [3] — commits to the two halves of the PIN inside message **M3**, as two hashes [3]:

    E-Hash1 = HMAC_AuthKey(E-S1 || PSK1 || PKE || PKR)
    E-Hash2 = HMAC_AuthKey(E-S2 || PSK2 || PKE || PKR)

E-S1 and E-S2 are two 128-bit secret nonces [3]. In a sound implementation they are unpredictable, so the hashes reveal nothing. Bongard's 2014 finding is that many implementations generate E-S1/E-S2 from a weak PRNG seeded with no real entropy — a 32-bit linear congruential generator producing them "right after N1" (the enrollee nonce, sent in the clear in M1), a 32-bit LFSR whose "state [is] trivial to recover from the nonce", or code where "E-S1 = E-S2 = 0x0" [3]. Given the nonce from M1 and the two hashes from M3, the attacker recovers E-S1/E-S2 offline and brute-forces the PIN halves offline, with no further radio traffic and no lockout risk [3][4]. The tool is `pixiewps`, which recovers the PIN "in a matter of seconds or minutes ... if vulnerable" [4], driven by `reaver -K` (or `-Z`), which feeds it PKE, PKR, E-Hash1, E-Hash2, E-Nonce and the AuthKey and "will then try to attack Ralink, Broadcom and Realtek detected chipset" [5]. Bongard's own step list is: "Do the WPS protocol up to message M3 / Get the Nonce from M1 / Bruteforce the state of the PRNG / Compute E-S1 and E-S2 / Bruteforce PSK1 / PSK2 ... / Do the full WPS protocol to get the credentials" [3]. This rule watches for the first on-air step: M3 taken, then nothing. MITRE classifies the offline recovery of credential material as T1110.002 Password Cracking [6].

## Evidence that proves it

Detail fields (above) name the STA and BSSID of the abandoned run, the silence threshold crossed, and whether it is the operator's own BSSID. No per-alert pcap is written: `fire(...)` is called with `match_ip = NULL`, `match_port = 0` (src/alerts/rules_enterprise.c:311-312), because the evidence is L2 EAP-WSC, not an IP flow, and `alert_pcap` keys on IP (src/alert_pcap.c:105). The substrate is instead the `src/wps_track.c` session: its `ev[]` opcode timeline (WPS_EVT_RING = 16, src/wps_track.h:46-50) and `msg_bits`/`attempt_bits` are readable in the `[b]` beacon detail screen via `wps_track_for_bssid()`. The JSONL `alert`/`alert.*` records carry `key`, `detail`, `sev`, `technique` T1110.002, and the `observations`/`evaluations` split (src/jsonl.c:574-575): a Pixie probe should show observations ~1 (the shape does not change) against evaluations climbing with silence.

To call it real, the reader wants, from the session timeline: an M1 and an M3 from the station to the AP, then no M4 and no Done, then silence past 60 s — and ideally a *re-armed* run (a later M1) that also stops at M3, which the lone-event benign path rarely does. What refutes it: an M4 or a Done anywhere in that attempt (then it is not the shape at all; the tracker clears it, `test_m4_in_the_attempt_is_not_the_shape`, `test_done_after_m3_is_not_abandoned`), or evidence the receiver simply left — the same AP heard continuing a normal exchange on another channel, or the gap coinciding with a --hop dwell elsewhere.

## Benign causes

A channel-hopping or weak-signal receiver that heard M1 and M3 of a *legitimate* enrolment and then moved away sees exactly this shape; the repo corpus states this is the benign trigger and the reason the rule is WARN not CRIT [1]; Bongard's slides do not discuss the receiver side. A genuine enrolment that the user abandoned mid-way (walked off, device timed out after M3) also qualifies. The discriminator is repetition and context: Pixie tooling against a failing target NACKs and re-arms, leaving several M3-abandoned attempts; one isolated M3 gap on an AP the operator was knowingly enrolling to is almost certainly benign. Note the rule deliberately does **not** fire on a NACK after M3 by itself (the tool sends one, and so does a failed legitimate run) — only on the silence.

## Assessment

Severity WARN is correctly calibrated to what a passive sensor can know: the on-air shape corroborates Bongard's step 1, but the PRNG weakness that makes the attack succeed "cannot be read off the brand" [1] (the corpus's gloss on Bongard's "Many of the implementations are the reference code for the chipset / Only the GUI is reskinned" [3]), so the rule reports a sequence, never a compromise (the repo's #145 ruling 2 standard). Real-world exposure is broad — WPS was on by default across major vendors [7] and the weak generators are shared chipset reference code [3] — but no figure for the currently-vulnerable fraction was found, so the honest statement is "widely shipped, per-model unknown." On the reference host the rule did not fire (host data null) and is structurally quiet: at most one fire per WPS session, and WPS sessions are rare. No dedupe or threshold tuning is warranted; `--tune wps.pixie_silence_s` exists only to separate "left" from "slow" and its floor of 1 is deliberate (src/tune.c:228-234). The evidence (an L2 shape, no PRNG visibility) is enough to warrant investigation, not to conclude breach. A responder should first confirm whether the BSSID is their own AP and whether a legitimate enrolment was underway; if neither, treat it as reconnaissance against WPS and disable WPS PIN on the operator's AP — the only fix the source can name, since the vulnerability is per-firmware [3][6].
