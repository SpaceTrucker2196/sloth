## What the rule checks

For every data frame, `observe_locked()` (src/fragattack.c:470) reads the CCMP packet number (`dot11_frame_ccmp_pn`, 499) and the A-MSDU Present bit (`dot11_frame_amsdu`, 500). When both are readable it calls `mpdu_note()` (504), which keys a table on `(transmitter TA, PN)` within a 10 s window (`mpdu_key_t`, 424; `FRAG_MPDU_WINDOW_S`, src/fragattack.h). `stab_expire()` first drops rows older than the window (443) so a PN that recurs only after a legitimate rekey (PNs restart at 0 after a PTK rotation) is not compared.

The verdict (436-468): if a record already exists for `(TA, PN)` and its stored A-MSDU bit differs from the current frame's, it returns 1 (a replay with the bit flipped) and does **not** overwrite the stored bit (so repeated replays each count — comment 450-453); if the bit matches, it is a plain retransmission and returns 0. On a 1 return, `observe_locked()` does `b->amsdu_flip++` and updates `last_sa/last_da/last_hit` (505-508). This runs before every other gate and needs no witnessed key install — the readable 48-bit CCMP PN is itself proof the frame is encrypted (comment 495-498).

`rule_fragattack()` fires `ALERT_TYPE_FRAG_AMSDU` at CRIT when `b->amsdu_flip > 0` (648-662). Key: `fragamsdu:<BSSID>` (649). Detail: `"%u protected MPDU%s on %.17s replayed with the A-MSDU bit flipped - last %.17s -> %.17s (CVE-2020-24588)"` (650-654). No escalation; resolution only on row eviction (STAB_OLDEST by `last_seen`).

This is **not** the detector #75 proposed. The subframe DA/length/LLC that CVE-2020-24588 manipulates sit inside the ciphertext, which sloth does not decrypt (MISSION §2); only the A-MSDU Present bit is in the plaintext MAC header. The shippable signal is the replay, identified by the PN, because a PN is never legitimately reused under one key per CCMP replay protection (802.11-2020 §12.5.3.4.4) [1][2]. Keying on the 48-bit PN rather than the 12-bit sequence number avoids the wrap-every-4096-frames problem a seqnum detector would have (src/fragattack.h).

## The attack

Frame aggregation (A-MSDU, mandatory to receive in 802.11n) packs several subframes into one MPDU; a receiver parses the payload as subframes when the A-MSDU Present bit is set in the QoS Control field. That bit "is not authenticated" in WPA, WPA2 or WPA3 unless SPP A-MSDU is negotiated, and "none of the devices we tested support this feature, meaning in practice the A-MSDU flag is never authenticated" [3, §3.2]. CVE-2020-24588 is the resulting design flaw: an adversary in a multi-channel MitM position flips the bit on an otherwise valid encrypted frame, so the receiver reparses the same ciphertext as aggregated subframes with attacker-influenced contents — the paper uses it to run a port scan and to point the victim at a malicious DNS server [3, §3.1-3.3]. The injected packet is smuggled in the subframe length / IP ID arithmetic of a frame the attacker induced the victim to send [3, §3.2].

Because sloth cannot see inside the ciphertext, it detects the replay that carries the flip, not the subframe parse. The paper describes the mechanism as retransmitting a frame the victim already sent with the bit changed [3, §3.2], and that retransmission reuses the original frame's PN — the anomaly sloth keys on.

CVSS: Intel rates CVE-2020-24588 at 5.3, Cisco at 5.7 [10][11]. Tooling: the `fragattacks` tool's `amsdu-inject` and `amsdu-inject-bad` cases [6]; the attack needs patched drivers and a MitM position to run in practice [3]. No mainstream framework is documented as shipping it.

## Evidence that proves it

What sloth records: `alert`/`alert.create` JSONL with key `fragamsdu:<BSSID>` and the detail (carrying `last SA -> DA`). No pcap (`match_ip = NULL`) and no evidence ring. The `[c]` view shows the per-BSS `amsdu_flip` counter, SA->DA, age and gate count; `frag_mpdu_count()` exposes how many `(TA,PN)` records are held (src/fragattack.c:624). `sensor_health` carries `frag_mpdu` eviction counts.

To call it real: within 10 s on the named BSSID, the same transmitter (Address 2) emits two frames carrying the same 48-bit CCMP PN, one with the QoS Control A-MSDU Present bit set and one clear. Because CCMP never reuses a PN under one key, two frames with the same PN *to the same receiver* already violate the protocol before the flipped bit is considered — the rule does not check the receiver, so confirm Address 1 matches too. The confirming external-capture signal is two MPDUs, identical TA and PN, differing only in the A-MSDU bit, not separated by a rekey (which would restart PNs). The paper's own injection leaves the second subframe's addresses invalid (the first subframe is dropped, the attacker's packet is the second) [3, §3.2] — but those are inside the ciphertext and not visible here.

What would refute it (benign fingerprint): a single underlying frame delivered twice by the capture path (e.g. two radios/interfaces hearing it, or a monitor retry) where one copy's A-MSDU flag was mis-decoded — this would show identical PN and timing to the microsecond and no corresponding injected traffic. A genuine rekey between the two frames would also reset the PN, so a "match" spanning a rekey is a stale-window artefact (the 10 s window is meant to prevent this). A third refuter the rule cannot see: the two frames have different receivers (Address 1), i.e. two clients' independent PN counters coincided. The single reference-host key (below) — one replay, AP-to-client, on a BSSID with five associated stations — is most plausibly one of these, not an attack.

## Benign causes

- **Cross-client PN collision.** The AP keeps one pairwise key, and so one PN counter starting at 0, per client [13]; `mpdu_note` keys on (TA, PN) without the receiver, so AP->client-A PN n (A-MSDU) and AP->client-B PN n (not A-MSDU) inside 10 s look like a flip. Fingerprint: TA = the BSSID (downlink), the two frames' Address 1 differ, several clients associated recently. This is a code-level gap, not a protocol event, and is the best fit for the reference-host hit.
- **Capture double-delivery / flag mis-decode.** Another candidate for the reference-host hit: one transmitted frame observed twice with inconsistent A-MSDU-bit decoding, on a specific adapter/driver or a multi-interface capture. Fingerprint: the two "frames" are sub-millisecond apart, the counter advanced exactly once (so `count` grew by ticks, not by new replays), and no injected/anomalous IP traffic accompanies it. Stated from the capture model, not independently sourced.
- **A rekey inside a stale window** pairing a pre-rekey and post-rekey frame that happen to share a PN. The 10 s window is sized to exclude this (src/fragattack.h), so it should be rare; fingerprint is a visible PTK rotation (new-ANonce M3) between the two frames.
- There is **no legitimate transmitter behaviour** that reuses a CCMP PN under one key; CCMP replay protection forbids it [1][2]. So a true PN reuse *under one key* (same TA and same RA, no rekey) with a differing aggregation bit has no benign protocol reading — only the attack or a capture artefact. Same TA alone is not one key.

## Assessment

Severity: CRIT is correct *for what the rule means to detect* — a protocol invariant (unique PN per key) violated with the specific bit-flip CVE-2020-24588 abuses. As implemented the key omits the receiver, so on a multi-client AP the rule can fire on two different keys' PNs coinciding; until RA is added to the key, treat a single downlink hit as unconfirmed. The per-station key-install gate is not even needed here because the PN proves encryption.

Prevalence: a design flaw affecting essentially all WPA/WPA2/WPA3 (and WEP) devices that receive A-MSDUs, which is nearly all of them [3, §1, §3.2]; disclosed 2021-05-11 and patched across vendors [7][10][11]; no in-the-wild use reported [4][8]. As with the rest of FragAttacks the attack needs a MitM position in radio range, so sightings should be rare and significant.

Noise on the reference host: **noisy** — host:{keys:1, fires:245735, max_sev:2}. Read against the count semantics: one key = one BSSID ever matched, and 245,735 fires is the engine re-evaluating one standing condition every poll — 6,059 s of it at ~40.6 evaluations/s (first_seen 2026-10-16 22:55:29 to last_seen 2026-10-17 00:36:28 UTC in ~/sloth-snap.db), not 245,735 distinct replays and not ~2.8 days. The leading integer in that incident's detail is the real replay count, and it is 1. This is the clearest example in the batch of the family's shared defect: `rule_fragattack` tests `> 0` on a monotonic counter, so a single event (here most likely a cross-client PN collision: one AP-to-client hit on a BSSID with five associated stations) produces a quarter-million fires in under two hours. The incident did end while the process kept running, consistent with the 64-slot BSS row being evicted. Recommendations: (0) add the receiver address to `mpdu_key_t`, so two clients' PN counters cannot collide; (1) fire only when `amsdu_flip` advances since the last evaluation (store it per BSS in the rule); (2) resolve on `last_hit` age rather than only on row eviction; (3) add a `--tune frag.amsdu_window_s` knob over FRAG_MPDU_WINDOW_S so a deployment seeing benign double-delivery can tighten it; (4) consider requiring two distinct `(TA,PN)` replays before firing, to drop single-artefact hits.

Sufficient to act on? The alert is strong evidence a PN was reused with a flipped aggregation bit, but with no pcap and no evidence ring a responder cannot distinguish the attack from a capture artefact from the alert alone — and the reference-host data suggests the artefact is the common case. First step: open the `[c]` view for the replay count and SA->DA, then capture that channel externally and confirm two genuinely separate on-air MPDUs with the same PN and no intervening rekey before treating it as an injection.
