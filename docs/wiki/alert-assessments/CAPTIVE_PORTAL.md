## What the rule checks

Inputs. The captive-portal event ring `s->cp_events[]` (`CP_MAX_EVENTS` = 64, include/sloth.h:2128, 3522), filled by `cp_record()` / `cp_record_ex()` (src/captive_portal.c:364-406) from three independent detectors in the capture path:

- **HTTP body** (`cp_check_response`, captive_portal.c:106-135, called from capture.c:600): a **complete** HTTP response on a known connectivity-check sentinel URL whose status or body differs from the vendor's published answer returns `CP_KIND_HIJACK`. It fires **only on a complete body** (`resp->body_complete`) - sloth does not reassemble TCP (#71), so a prefix that differs is a segment boundary, not an interception; a chunked response is never complete, so a rogue that chunks evades this check (but not the DNS/TLS ones). The sentinel table (`SENTINELS[]`) covers Apple `captive.apple.com/hotspot-detect.html` (69-byte body with trailing LF), Microsoft connecttest and NCSI on their IPv4/IPv6 hosts, Firefox `success.txt` and `canonical.html` and the `firefox-portal-detection.com` pair, and Google/Android `generate_204` on four hosts including `clients3.google.com` (captive_portal.c:23-66).
- **DNS** (`cp_check_dns`, captive_portal.c, called from capture.c:833): a sentinel host resolving into RFC1918/CGNAT/link-local space returns `CP_KIND_DNS_SPOOF`; resolving to a public address outside the range that host is known to use returns `CP_KIND_DNS_UNEXPECTED` (the deliberately soft signal - CDN ranges change).
- **TLS** (`cp_check_tls`, called from capture.c:676): a TLS ClientHello for a sentinel host going to a private address returns `CP_KIND_TLS_MITM`.
- **Kit pages** (`CP_KIND_KIT`, recorded at capture.c:615; :605 is the hijack record): the first HTTP response segment matches two-or-more features of a named evil-twin kit's default portal page (wifiphisher, Pineapple Evil Portal/PortalAuth, airgeddon, fluxion); form contents and page bytes are never stored, only the kit/scenario label and the responder address.

Condition and grading (#169). `rule_captive_portal()` (rules_twin.c:514-569) walks recent events (ts within 600 s). A kit event goes to `cp_fire_kit()` (rules_twin.c:495-512), key `portalkit:<kit id>:<server ip>` (the numeric kit id via `akey_u`, not the name), **always CRIT**, `match_ip` = the serving address. A probe event computes context (`cp_context`, rules_twin.c:392-430): the client IP is ARP-joined to a MAC, that MAC's most recent row in the association table names its BSS, and that BSS is tested for `--my-bssid`/`--my-ssid` (`own_net`) and for a live evil-twin finding (`on_twin`); failing an ARP+association match, if either the client or the responder is an ARP neighbour on one of the sensor's own Wi-Fi station interfaces, the sensor's currently associated AP(s) are tested instead. The third escalator is a kit page served to the same client in the last 600 s (`cp_kit_for`, rules_twin.c:433-443). Key is `portal:<host, 40 kept>:<kind>` with the host taken off the wire and the kind as a number (rules_twin.c:532-538). Severity: for `DNS_UNEXPECTED`, WARN if escalated else LOW; for everything else, CRIT if escalated else LOW (rules_twin.c:562-567). `match_ip` = the responder's server. The detail names the intercepted host, the client, the kind label, the evidence, and the "why" - "on your own network", "AP ... is a known evil twin", "client was served fluxion", or "legitimate captive portals do this too".

## The attack

Every modern OS runs a connectivity check: on joining a network it fetches a fixed vendor URL and expects a byte-exact answer (Apple a 69-byte "Success" page, Windows NCSI "Microsoft Connect Test" at `www.msftconnecttest.com/connecttest.txt`, Android/Chrome an empty HTTP 204 at `generate_204`, Firefox `success.txt`/`canonical.html`) [4][5][6]. The probe is deliberately unauthenticated and deliberately plaintext - it has to work before the user has any credentials - and that is exactly what makes it the cleanest interception target on the network: answer it wrongly and the victim's OS pops a browser at whatever page you serve. Microsoft's own KB documents the mechanism and the intended result: on a network that needs sign-in, "The default browser (for example, Internet Explorer or Edge) opens, and shows a web page such as a sign-in page for the network or the MSN portal page" [4].

The malicious version is MITRE T1557 (Adversary-in-the-Middle) [1][2]: a rogue AP, hostile resolver, or wired MITM intercepts the probe and answers with its own page to drive the victim's browser to attacker-controlled content - the opening move of credential harvesting. When the rogue is an evil twin that then serves a credential-capture page, it is specifically T1557.004 (Evil Twin): "Upon logging into the malicious Wi-Fi access point, a user may be directed to a fake login page or captive portal webpage to capture the victim's credentials," a technique MITRE attributes to APT28 using Wi-Fi Pineapple tooling [3]. The kit detectors catch exactly that step: wifiphisher, Pineapple Evil Portal/PortalAuth, airgeddon and fluxion all automate standing up a fake portal and answering the probe (fluxion's lighttpd 307-redirects every host a phone touches to its captive page) [7].

The hard part is not deciding the answer is wrong (it is published and fixed) but deciding a wrong answer is an *attack* - which it usually is not, because a hotel, airport or guest-Wi-Fi portal answers the probe the same way, by design. That is why #169 grades it: wrong answer alone is LOW, and only context (own network, evil twin, kit page) makes it CRIT.

## Evidence that proves it

What sloth records. The alert detail carries the intercepted sentinel host, the client, the kind (body hijack / DNS spoof / DNS unexpected / TLS MITM / kit page), the evidence string (what was seen instead, or the kit/scenario label), and the context "why". The `captive_portal_event` JSONL record (keyed `host`+`ts`) carries `host`, `src`, `kind`, `kind_label`, `evidence`, and since #169 `server`/`server_port` (the responder) and `kit` (the named kit, "" for none). Because the alert passes the responder as `match_ip`, with `--pcap-dir` set the rule writes a per-alert pcap of that flow - the HTTP exchange that carried the wrong answer or the kit page (src/alert_pcap.c, gated on `pcap.min_severity`).

What makes it real. For a probe finding to be an attack rather than a hotel, the context has to escalate it: the client is on a network the operator declared their own (which should have no portal), or the client's BSS is a live evil-twin episode, or that same client was served a named kit's page in the last 10 minutes. A kit finding is self-proving - no innocent network serves wifiphisher's firmware-upgrade page or fluxion's redirect; two-or-more fingerprint features in the first response segment is the kit. In the pcap, a responder serving a non-sentinel body on the sentinel's host+path, or a kit's title/form-action/redirect, is the artifact.

What refutes it. The dominant benign fingerprint: the intercepting responder is a legitimate captive portal (hotel/airport/guest Wi-Fi), the network is not the operator's, no evil twin is present, and no kit page was served - which is exactly the LOW case whose detail ends "legitimate captive portals do this too." A local DNS filter answering for the sentinel produces a DNS finding benignly. A `DNS_UNEXPECTED` on a large operator whose CDN range shifted is weak by construction and sits a grade lower. Only a complete-body mismatch is trusted at all; a truncated differing body is suppressed.

## Benign causes

- **Legitimate captive portals.** Hotels, airports, cafes and guest Wi-Fi answer the connectivity probe wrongly on purpose - that is how they trigger the sign-in browser. This is the overwhelming cause of a bare finding and the reason the base grade is LOW [4].
- **Local DNS filters / split-horizon resolvers.** A network that filters or rewrites DNS answers the sentinel query locally, producing a `DNS_SPOOF`/`DNS_UNEXPECTED` benignly.
- **CDN range drift.** Large operators (Apple, Google, Microsoft) change their address space; a sentinel resolving outside sloth's coarse known-range list is `DNS_UNEXPECTED`, graded softest for exactly this reason.
- **Kits run on purpose.** A lab, a training, or an authorised assessment running wifiphisher/fluxion produces a genuine kit finding; it is CRIT anyway, because the operator should know a credential-harvest portal is in range either way (research/tools/captive-portal-kits.md).

Telling them apart is what the grading does: the LOW/CRIT line is drawn exactly at "is this the operator's own network, a known evil twin, or a named kit?"

## Assessment

Severity rationale. The #169 grading is the right model and a good example of severity following evidence: the detection ("the answer is wrong") is near-certain, but the *meaning* ("this is an attack") depends on context, so the base grade is LOW and escalation is tied to the operator's own-network declaration, a live evil-twin finding, or a kit fingerprint. Kit pages always-CRIT is correct - there is no innocent reading of a tool's phishing page on the air. DNS_UNEXPECTED one grade lower throughout correctly reflects that CDN drift is a real false-positive source.

Real-world prevalence. The interception *mechanism* is ubiquitous because connectivity probes are universal and legitimate portals intercept them constantly [4][5][6]; evil-twin kits that harvest credentials via a fake portal are widely available and the technique is attributed to real actors [3][7]. But a genuine *malicious* interception on a given operator's own network is the rare, high-value case - which is exactly what the CRIT tier isolates.

Reference-host noise. 372,750 fires on **3 keys**, max_sev CRIT. As with the other wireless rules, the per-tick count inflates the picture: ~124,000 fires/key is **3 findings**, not 372,750. It is not 3 single events: the rule fires once per in-window ring event per tick, and probe events are appended per interception rather than merged, so a key's count is ticks x the number of live events sharing it, and ~8.6 h per key at >= 4 ticks/s is an upper bound that holds only if each key had one live event at a time. The host-keyed (or kit+server-keyed) dedupe collapses those events into one incident, as intended. Cadence caveat: the tick arithmetic assumes the default 250 ms poll with an idle keyboard. `poll_tick()` runs once per main-loop iteration (`poll_data()` at src/main.c:1628 calls it at :205) and the wait before it is cut short by any keypress or by `event_wake_signal()` on a new or escalated alert (src/alerts/engine.c:526, 608), so real ticks/s is >= 4 and every duration derived here is an upper bound; `--refresh-ms` changes the base. max_sev CRIT means at least one of the 3 escalated via own-network, evil-twin, or kit context (the per-type maximum does not say all three did) - so each key's detail "why" suffix is where a responder starts. Two grading wrinkles follow from the per-event loop: several events on one key are fire()d in the same tick, the last one processed (the oldest in window) sets the incident's severity and detail because fire() overwrites `sev`, so an escalated interception can be shown at LOW whenever an older unescalated event on the same host+kind is still live; and the alternation counts as observations. Recommendation: surface `observations` instead of `evaluations`/`count` on the alert page so the 372,750 collapses toward 3, and fold same-key events to one fire() per tick at the highest severity; no threshold change is warranted.

Is the evidence enough to act on? For a CRIT, yes - a wrong probe answer on the operator's own network, from a live evil twin, or a named kit page, is actionable, and the per-alert pcap (with `--pcap-dir`) captures the responder's flow for confirmation. For a LOW, it is informational - almost always a legitimate portal. First response: note the intercepted host and the client; check whether the AP is a known evil twin and whether the network legitimately has a portal; disconnect the client and check what it entered on the portal page; if the rogue AP is not the operator's and is on premises they control, locate and remove it, else report it - do not join or probe it (docs/wiki/alert-remediation.md).
