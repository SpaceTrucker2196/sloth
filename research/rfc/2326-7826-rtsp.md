# RFC 2326 / RFC 7826 — RTSP DESCRIBE answered with no challenge

What `ALERT_TYPE_CAM_RTSP_UNAUTH` (#106 slice B) detects from. Both RFCs
were retrieved as plain text from rfc-editor.org on 2026-10-20; the
quotations below are from those copies.

## The exchange, read off the RFCs

**DESCRIBE returns the stream description.** RFC 7826 §13.2: "The
DESCRIBE method is used to retrieve the description of a presentation
or media object from a server. [...] The server MUST respond with a
description of the requested resource and return the description in the
message body of the response, if the DESCRIBE method request can be
successfully fulfilled." RFC 2326 §10.2 defines the same method for
RTSP/1.0. The 200 to a DESCRIBE is therefore the media initialisation a
client needs before SETUP and PLAY — the §13.2 example is an SDP body.

**401 is how RTSP asks for a credential.** RFC 7826 §17.4.2: "The
request requires user authentication using the HTTP authentication
mechanism [RFC7235]. [...] The response is to include a WWW-Authenticate
header (Section 18.58) field containing a challenge applicable to the
requested resource. The agent can repeat the request with a suitable
Authorization header field." §19.1 imports the HTTP framework whole:
"RTSP uses the corresponding RTSP error codes (401 and 407) and headers
(WWW-Authenticate, Authorization, Proxy-Authenticate,
Proxy-Authorization)".

**Responses are paired by CSeq, per connection.** RFC 7826 §18.20:
"The CSeq general-header field specifies the sequence number (integer)
for an RTSP request/response pair. This field MUST be present in all
requests and responses. [...] Each requester and responder is
identified by its socket address (IP address and port number), i.e.,
per direction of a TCP connection. [...] The RTSP response MUST have the
same sequence number as was present in the corresponding request. [...]
the agent MUST use the sequence number in the response to pair it with
the corresponding request." RFC 2326 §12.17 says the same for 1.0. An
RTSP response carries no URI, so this is the only way a passive
observer can know which path an answer was for.

**Ports.** RFC 2326 §3.2: "If the port is empty or not given, port 554
is assumed." RFC 7826 §10.2: "In addition to the registered default
ports, i.e., 554 (rtsp) and 322 (rtsps), there is an alternative port
8554 registered." 322 is RTSP over TLS and is opaque to sloth.

**Message shape.** Request-Line `Method SP Request-URI SP RTSP-Version
CRLF` (RFC 2326 §6.1, RFC 7826 §7.1); Status-Line `RTSP-Version SP
Status-Code SP Reason-Phrase CRLF` (2326 §7.1, 7826 §8.1). RFC 7826 §5:
"Lines MUST be terminated by a CRLF"; RFC 2326 §4 adds that "receivers
should be prepared to also interpret CR and LF by themselves as line
terminators" — sloth accepts a lone LF and not a lone CR. Interleaved
media on the same connection is framed with `$` (RFC 7826 §14) and is
not a message.

## What `src/rtsp_snoop.c` reads from this

A DESCRIBE seen on TCP 554/8554 is remembered against (client, client
port, server, server port, CSeq), with its path and one bit: whether it
carried an `Authorization` or `Proxy-Authorization` header. The value of
that header is never read. When the response with the same CSeq comes
back on the same connection:

- **401** marks the connection challenged and counts a challenge on the
  (server, port, path) row, keeping only the scheme token (`Digest`,
  `Basic`).
- **200** counts *anonymous* when the request carried no authorization
  header and the connection had no 401 before it; otherwise
  *authenticated*.
- any other code retires the request and says nothing either way.

A Request-URI with userinfo (`rtsp://user:pass@host/`) or a
credential-shaped parameter (`user=`, `password=`, ...) is not tracked
at all: it is neither anonymous nor safe to store.

## The finding, and what it does not say

`ALERT_TYPE_CAM_RTSP_UNAUTH` fires once per server IP with at least one
anonymous row, WARN, with the distinct-path count in the detail. What
the wire shows is that **a stream description was handed to a client
that presented no credential and was not challenged for one** — the
RFC's own authentication step did not happen on that exchange.

It corroborates anonymous stream access and does not confirm it:

- a server may leave DESCRIBE open and challenge SETUP or PLAY instead;
  that slice does not follow the session past DESCRIBE;
- a server may admit by source address, which leaves no trace in RTSP;
- RTSP is spoken by NVRs, encoders, VMS relays and media servers as
  well as cameras, so the detail says "RTSP server".

`alert_technique()` returns `""`. T1078.001 (Valid Accounts: Default
Accounts) is the technique #106 lists for the default-credential path,
and it does not fit here: there was no account to use. T1046 / T1595
describe an adversary enumerating, which sloth did not do and cannot
attribute to whoever sent the DESCRIBE — often the operator's own VMS.
This is an exposure of the server, the same position as
`ALERT_TYPE_CAM_WS_DISCOVERY` (`research/papers/ws-discovery-onvif.md`).

## What is deliberately not done

- **No credential comparison.** The issue's `data/camera_default_creds.csv`
  match was dropped by the #145 owner ruling: the `src/cleartext_creds.h`
  guardrail — the password is never stored or compared — stands.
- **No report of Basic over cleartext.** RFC 7826 §19.1 says "Any RTSP
  message containing an Authorization header using the Basic
  authentication scheme MUST be using a TLS connection". sloth sees
  that header's presence on 554 and does not raise it: deciding the
  scheme means reading the header value, and the existing
  `CLEARTEXT_CRED` rule is where cleartext credentials are reported.
- **Nothing is sent.** No DESCRIBE, OPTIONS or connection originates
  from sloth.
