# IEEE 802.11be-2024 §9.4.2.322 — what one BSS's Beacons and Probe Responses must agree on

Clause-annotated summary. The standard text is paywalled and was **not
read** for this slice, the same position the #129 Presence Bitmap fix
took; every layout fact below is taken from three public
implementations that agree with each other, and each is named so it can
be checked. Our own description, not an excerpt.

Clause numbering: hostapd labels the Multi-Link element **IEEE Std
802.11be-2024 §9.4.2.322** (`src/common/ieee802_11_defs.h`). The
earlier sloth documents (`802.11be-9.4.2.312-mld-identity.md`,
`research/cve/2026-58374.md`) cite §9.4.2.312, the number in the
drafts the first slices were written against. Same element.

  0`, `_PROBE_REQ 1`, `_RECONF 2`, `_TDLS 3`, `_PRIOR_ACCESS 4` (Table
  9-417f); Basic Presence Bitmap `BASIC_MULTI_LINK_CTRL_PRES_LINK_ID
  0x0010`, `_BSS_PARAM_CH_COUNT 0x0020`, `_MSD_INFO 0x0040`,
  `_EML_CAPA 0x0080`, `_MLD_CAPA 0x0100`, `_AP_MLD_ID 0x0200` (Figure
  9-1074o), as bits of the 16-bit Multi-Link Control word.
- **hostapd**, `src/ap/ieee802_11_eht.c`:
  `hostapd_eid_eht_basic_ml_common()` writes Common Info Length, the
  own MLD MAC Address, the own Link ID, BSS Parameters Change Count,
  EML Capabilities and MLD Capabilities in every Basic MLE it builds,
  and an AP MLD ID only when its caller asks (`include_mld_id`).
  `hostapd_eid_eht_ml_beacon()` emits that Basic MLE and then
  `hostapd_eid_eht_reconf_ml()`: a Reconfiguration MLE (Type 2, empty
  Presence Bitmap, Common Info Length 1) with one Per-STA Profile per
  affiliated AP being removed, carrying its Link ID and an AP Removal
  Timer (`EHT_PER_STA_RECONF_CTRL_AP_REMOVAL_TIMER 0x0040`).
- **hostapd**, `src/ap/beacon.c`: `hostapd_probe_resp_fill_elems()`,
  answering a multi-link probe, emits the requested AP MLD's Basic MLE
  with `include_mld_id = true` and Per-STA Profiles, and then this
  BSS's own Basic MLE without one. The Beacon tail emits only the own
  Basic MLE.
- **Wireshark**, `epan/dissectors/packet-ieee80211.c`: the same Type
  values (`BASIC_MULTI_LINK 0` … `PRIORITY_ACCESS_MULTI_LINK 4`), the
  same bitmap masks ("Link ID Info Present" 0x0010, "AP MLD ID Present"
  0x0200), and a Basic Common Info dissected as Length, MLD MAC
  (unconditional), then Link ID Info when present.
- **Linux mac80211**, `net/mac80211/mlme.c`:
  `ieee80211_ml_reconfiguration()`, called from the Beacon receive path,
  reads the Reconfiguration MLE's Per-STA Profiles, takes each Link ID
  as a link the AP MLD is removing, and schedules the client to tear
  that link down when the AP Removal Timer runs out — immediately when
  the timer is absent.

## MLE_RECONFIG_NO_MLO

**The invariant.** A Reconfiguration MLE in a Beacon or Probe Response
announces a change to an AP MLD's set of affiliated APs. Only an AP that
is affiliated with an AP MLD has such a set, and that AP states its
membership with a Basic MLE in the same frame types — hostapd emits the
two together, Basic first. A BSSID that sends the announcement and has
never, in any Beacon or Probe Response sloth heard, made the membership
claim is announcing a change to something it does not say it belongs
to.

**Why it matters.** The announcement is acted on. mac80211 schedules a
client's link teardown from it, with no other check than that the
client is itself multi-link. A forged one is a way to push clients off
a link without a deauthentication frame, which is the frame every
deauth detector, sloth's included, is watching for.

**What sloth checks.** `src/mle.c :: mle_bss_observe_frame()` keeps a row
per BSSID that has sent any Multi-Link element. It reads only the
**Type** subfield of a Reconfiguration MLE — the one field every variant
shares at a fixed position — because its Common Info and Presence
Bitmap are variant-specific. The Basic MLE in the same frame counts:
hostapd's removal-window Beacon (Basic, then Reconfiguration) does not
fire even on the first frame heard, which is
`tests/test_mle_bss.c :: test_reconfig_alongside_basic_in_one_frame_not_flagged`.
A malformed Basic MLE still counts as the claim; its malformation is
`MLE_COMMON_INFO_LEN_BAD`'s finding, not this one's.

**What it does not catch, named rather than implied.** An attacker who
clones the BSSID of a real AP MLD and sends a Reconfiguration MLE from
it inherits that BSSID's Basic MLE history, so this rule stays quiet —
the rule as ruled is about BSSIDs that never claimed MLO. A crude forgery
of that kind would still lack a Basic MLE in its own frame; flagging that
same-frame absence on a known AP MLD is a different, stricter rule and is
not built here. hostapd builds its Reconfiguration MLE only under
`CONFIG_TESTING_OPTIONS`, so the legitimate ones on the air come from
vendor stacks, which were not available to check.

WARN, T1669 (Wi-Fi Networks). Corroborates a forged announcement; does
not confirm that any client acted on it.

## MLE_PR_BEACON_DIFF

**The invariant.** A Beacon and a Probe Response from one BSSID are the
same BSS describing its own AP MLD membership. In both, the BSS's own
Basic MLE carries the **MLD MAC Address** (unconditional in the Basic
variant) and, in what hostapd builds, the BSS's own **Link ID**. Neither
can differ between the two frames while the AP MLD is unchanged. Two
answers for one BSSID is the shape of a second transmitter answering
probes under that BSSID with another MLD identity.

**Only fields both frames must carry are compared, and that is the
rule's shape, not a simplification.** The issue proposed comparing the
link set. That would fire on every Wi-Fi 7 AP that answers a multi-link
probe: a Beacon carries no Per-STA Profiles, and a multi-link Probe
Response carries Complete ones for the other affiliated APs. Also not
compared:

- **A Basic MLE that carries an AP MLD ID.** hostapd puts the requested
  AP MLD's element first in a multi-link Probe Response, with an AP MLD
  ID and that MLD's MAC. It describes an AP MLD of a multiple-BSSID set,
  not necessarily this BSS's own, so the identity is the first Basic MLE
  *without* one. `test_conformant_ml_probe_response_does_not_fire` is
  that frame.
- **BSS Parameters Change Count**, which moves on every critical update.
- **EML and MLD Capabilities**: carried by both in hostapd, but not
  needed for the identity question, and their bit layout is where the
  #104 slice-2 note found draft-revision churn.
- **Link ID when either frame lacks Link ID Info.** Compared only when
  both set Presence Bitmap bit 4.

**Window.** A Probe Response is compared with the newest Beacon of the
same BSSID no older than **30 s** (`MLE_PR_BEACON_WIN_SECS`). That is the
window the issue proposed, not a cited value. It is a freshness bound,
not a threshold: it limits how long an AP MLD that was legitimately
reconfigured can be held to its old identity, and one mismatch inside it
is the finding. The newest Beacon is the baseline, so a reconfigured AP
MLD is compared against what it says now.

**What it does not catch.** Only the Probe Response is checked against
the Beacon, not the reverse, and two disagreeing Beacons for one BSSID
are not this rule's question. A forger who copies the real MLD MAC and
Link ID is not visible here, by construction.

Two evasions follow directly from the false-positive guards above, and
are cheaper than copying the identity:

- **Every Basic MLE carries an AP MLD ID.** The guard that keeps a
  conformant multi-link Probe Response quiet skips any Basic MLE with
  AP MLD ID Present, so a forged Probe Response that sets it on its only
  Basic MLE, or that simply sends no Basic MLE without one, offers no
  identity and is never compared. The guard is right — hostapd's
  legitimate ML Probe Response is exactly an AP-MLD-ID Basic MLE followed
  by the BSS's own (`src/ap/beacon.c`, the ML probe path) — so
  the gap is the price of the guard, not a bug in it. A stricter rule
  would flag a Probe Response from a BSSID already known as an AP MLD
  that carries no Basic MLE *without* an AP MLD ID. Not built here.
- **Link ID Info left out.** Link ID is compared only when both frames
  set Link ID Info Present, so a forger who clears that bit in the Probe
  Response turns the Link ID comparison off and is checked on MLD MAC
  alone.

WARN, T1669 (Wi-Fi Networks). The detail names both sides and does not
say which is genuine: sloth hears two frames, not which radio sent which.
