# IEEE 802.11be §9.4.2.312 — the link_id-to-address binding is the identity claim

Clause-annotated summary. The standard text is copyrighted; this is our
own description of the invariant sloth checks, not an excerpt.

## What the element asserts

A Multi-Link element's Per-STA Profile subelement names one affiliated
link of a Multi-Link Device (MLD) with two things: a 4-bit **Link ID**
(0-14, see `research/cve/2026-58374.md` for why 15 is illegal) and,
when the MAC Address Present bit is set, that link's own hardware
address. Together they say: *"link N of this MLD is this radio."* That
binding does not change for the life of the association — an MLD's
per-link radios are fixed hardware, not addresses rotated for privacy
the way a pre-association probe request is.

`src/mle.c`'s `mle_observe()` already merges link sets across frames
on this basis (#67, #104 slices 1-3): a device advertising a different
*subset* of its links on a different band is normal and is accumulated,
never replaced. That merge logic depends on the binding being stable —
it is explicitly why replacing rather than merging was rejected as
"worse than not having it."

## Why a conflicting binding is not another subset

If a later frame reports the **same** (MLD MAC, link_id) pair with a
**different** address, it is not a new fact about the same device's
link set — the protocol's own identity claim for that link_id has
changed. Two readings are available and both are the operator's
business: either a rogue device has cloned the MLD MAC to impersonate
an established Multi-Link identity, or two unrelated devices have
collided on both the MLD MAC and a link_id by chance. Neither is
benign, and nothing in the standard's definition of a conformant MLD
produces this shape — a real MLD's link_id-to-address map is fixed for
the association, so observing it change is itself the finding.

## What `ALERT_TYPE_MLD_MAC_COLLISION` does and does not say

It does not identify which of the two devices is genuine, and it does
not confirm an attack succeeded — sloth is a passive receiver sharing
the channel, not a party to either device's association. It reports
that two different addresses have claimed one (MLD MAC, link_id)
identity, which upstream software and an operator can resolve with the
corroborating context sloth already has (roster membership, RSSI,
timing) that this rule does not need to decide the question itself.

Mapped to MITRE ATT&CK T1669 (Wi-Fi Networks, Initial Access), the same
technique as the sibling CVE-2026-58374-class MLE rules: a crafted or
cloned management-frame identity is the access vector regardless of
which specific field carries it.

## The per-link RSNE, and why absence is not weakness

The same clause lets each Per-STA Profile carry its own **complete
profile** of the reported link: the elements that link advertises,
including its RSNE. That is what makes a per-link security posture a
thing sloth can read at all — the MLD is describing each radio's
ciphers and management-frame-protection stance in one element.

Two properties matter for `ALERT_TYPE_MLE_CROSS_LINK_CIPHER_DOWNGRADE`.

**One posture, several radios.** The links of one MLD are the same
logical network reached over different bands. Nothing in the clause
forbids configuring them differently, and no conformance rule is broken
by doing so — but a client that can reach the MLD on any of its links
will take the one offered to it, so a link advertised with
management-frame protection *not required*, or with a weaker pairwise
cipher than its siblings, is the lane an adversary-in-the-middle wants
used. The finding is a posture mismatch being advertised, not an
exploit having succeeded, which is why the rule is WARN.

**Inheritance means a missing element is not a missing feature.** To
keep a Beacon carrying several complete profiles from bloating past the
frame, 802.11be defines an inheritance model: an element the reporting
AP already carries is *omitted* from a Per-STA Profile and inherited
from the reporting AP's own body. A Per-STA Profile with no RSNE has
therefore said "the same RSNE as the AP", not "no encryption". Reading
absence as weakness would fire on the ordinary, efficient case — the
reason `src/mle.c` compares only links that carry an **explicit** RSNE,
and the reason `tests/test_mle.c ::
test_link_without_an_rsne_inherits_and_is_not_flagged` exists.

A link may also suppress inheritance explicitly, with the
Non-Inheritance element. sloth does not decode that element, so a link
that refuses the AP's RSNE without supplying its own reads to sloth as
an ordinary inheriting link — a false negative, named here rather than
implied.

## Where the STA Profile begins

The posture read needs the element list inside the STA Profile field,
and reaching it needs two offsets the clause fixes:

- The **STA Info Length** subfield counts itself, so the STA Profile
  field begins at `STA Control(2) + STA Info Length value` from the
  start of the Per-STA Profile body. That is the same declared-length
  skip the Common Info Length field provides, and it is proof against a
  later amendment adding an optional STA Info subfield.
- In a Beacon or Probe Response the STA Profile begins with a 2-octet
  **Capability Information** field before the element list. Linux's own
  `cfg80211_parse_ml_elem_sta_data()` reads exactly that, and it is the
  only frame type whose fixed prefix sloth asserts.

sloth also hands association-request MLEs to the same parser, and those
carry a different fixed prefix. Rather than branch on a frame type the
parser is not told, `sta_profile_rsn()` requires the element chain to
**tile the remainder exactly**: a wrong prefix then yields no finding
instead of a wrong one. Profiles fragmented across Fragment
subelements are not reassembled and fail the same check — also a false
negative rather than a false positive.
