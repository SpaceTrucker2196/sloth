# IEEE 802.11-2020 §9.6.14 — BSS Transition Management

Clause-annotated summary. The standard text is copyrighted; this is our
own description of the frame format sloth parses, not an excerpt.

## Request Mode bitfield (Figure 9-924)

| Bit | Field |
|---|---|
| B0 | Preferred Candidate List Included |
| B1 | Abridged |
| **B2** | **Disassociation Imminent** |
| B3 | BSS Termination Included |
| B4 | ESS Disassociation Imminent |

**B2 is the bit that matters** and it is the one most easily got wrong:
issue #59 originally described Disassociation Imminent as "bit 3", which
read literally is `0x08` — BSS Termination Included, a different field.
sloth implements B2 (`0x04`) per the figure, with both constants pinned
by test.

## Field order in the Request body

Category, Action, Dialog Token, Request Mode, Disassociation Timer (2),
Validity Interval, then optionally:

1. BSS Termination Duration (12 bytes) — present iff B3
2. Session Information URL (1 + n) — present iff B4
3. Neighbor Report elements (tag 52) — the candidate list

The optional fields appear in that fixed order. Skipping the wrong
number of bytes still yields a "successful" parse with the wrong
candidate BSSIDs, which is why each combination is tested separately.

## Why this is abusable

A Request with B2 set tells a client it is about to be dropped. Clients
honour it — that is the point of the mechanism. It moves a station with
no deauthentication frame at all, which is why `ALERT_TYPE_DEAUTH_FLOOD`
never sees this attack, and it carries no RSSI proximity constraint, so
the attacker need not out-signal the legitimate AP.
