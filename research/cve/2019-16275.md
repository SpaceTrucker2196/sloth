# CVE-2019-16275 — unauthenticated management frames on an MFP BSS

hostapd before 2.10 did not consistently validate the source of certain
management frames on a BSS advertising management-frame protection. An
adversary could inject frames that the AP acted on despite MFP being in
force, defeating exactly the protection the BSS advertised.

The general shape matters more than the specific hostapd bug: on a BSS
where MFP is **required**, an individually addressed robust Action frame
with the Protected bit clear should never be accepted. A stack that
processes one is vulnerable, and a frame that arrives that way is either
a non-conforming implementation or an injection.

## Why sloth cites this

`ALERT_TYPE_MFP_UNPROTECTED` fires on the on-air artefact of that shape:
a robust Action frame, individually addressed, Protected bit clear, on a
BSS whose own beacon advertises MFP required.

Sloth cannot tell a non-conforming stack from an injected frame — both
put the same bytes on the air — and does not claim to. What the alert
says is that the frame arrived and the BSS said it should not have.

`ALERT_TYPE_SA_QUERY_FLOOD` cites the same advisory from the other
direction. SA Query (802.11w §11.13) is the mechanism MFP uses to refuse
a spoofed disassociation, so a storm of them is a network *successfully*
defending itself against the attack class this CVE is about — visible
evidence of an attempt that the AP's own logs may be the only other
record of.

## What it does not say

It does not license reading the Protected bit on a group-addressed
management frame. Those are protected by BIP, which appends a Management
MIC element rather than setting that bit, so a broadcast Action frame
with Protected clear is ordinary.

Nor does it make MFP *capable* a finding. Capable-but-not-required is
the common WPA2 posture and an unprotected action frame there is legal —
it is a downgrade lane, which is `ALERT_TYPE_WPA_DOWNGRADE`'s subject,
not this one.
