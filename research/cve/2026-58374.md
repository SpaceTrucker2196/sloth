# CVE-2026-58374 — hostapd `links[]` out-of-bounds write on MLO association

A missing bounds check in `hostapd_process_ml_assoc_req()`
(`src/ap/ieee802_11_eht.c`), reachable by an unauthenticated station
within radio range sending a crafted Wi-Fi 7 (IEEE 802.11be) Multi-Link
Operation association request. The received Per-STA Profile `link_id`
field is four bits wide (0-15), but hostapd's own `links[]` array has
valid storage only for 0-14. A frame claiming `link_id = 15` writes out
of bounds, before the 4-way handshake and with no credential needed.
CVSS v3 base score 7.1 (ADJACENT_NETWORK / low complexity / high
availability impact). Fixed in hostapd 2.12; the broader w1.fi 2026-1
advisory covers eight related multi-link parsing gaps across AP and STA
mode (association, reassociation, probe/beacon, reconfiguration, scan
result).

## Why sloth cites this

`ALERT_TYPE_MLE_INVALID_LINK_ID` does not detect the crash — sloth has
no AP process to crash and never will (MISSION §2). It detects the
**frame shape that causes it**: a Per-STA Profile subelement whose
`link_id` is 15, or one repeated inside a single Multi-Link Element.
Neither has a benign explanation. IEEE 802.11be reserves 0-14 for real
links; a conformant MLD never emits 15 and never names one link twice
in the same element. Seeing either is the attacker's own crafted frame,
observed on the wire before it ever reaches a vulnerable AP — passive
detection of exactly the input class the advisory describes.

Mapped to T1669 (Wi-Fi Networks, Initial Access): an unauthenticated,
management-frame-driven association is the access vector, independent
of whether the target AP happens to be patched.

## What it does not say

**It does not confirm the target crashed.** sloth is a passive receiver
sharing the channel, not the AP under attack; it cannot see hostapd's
process state. The alert means "this frame was sent," not "this AP went
down."

**A patched hostapd is still worth alerting on.** 2.12 fixes the
out-of-bounds write; it does not make `link_id = 15` a legal value. The
frame is malformed either way, and an operator with an unpatched AP on
the segment needs to know regardless of which firmware the sender was
probing for.

## `ALERT_TYPE_MLE_COMMON_INFO_LEN_BAD` (#104 slice 2)

The same w1.fi 2026-1 advisory names "eight related multi-link parsing
gaps" across association, reassociation, probe/beacon, reconfiguration
and scan-result handling — the `link_id` overflow above is only the one
with its own CVE number. A second gap in the same family is a parser
that trusts the Multi-Link element's **Common Info Length** field
without checking it against either the field's own structural floor or
the element's actual bounds, then uses that trusted value to compute
where the next field starts. That is the same "attacker-controlled
length drives a pointer" shape as the `link_id` write, one field over.

`mle_parse()` rejects a Common Info Length under 7 (it must cover
itself plus the mandatory 6-byte MLD MAC Address) or one that would
place Link Info beyond the element's own length — either shape is
exactly the value a crafted frame would carry to push a trusting parser
past the buffer it allocated. Flagging it is passive detection of the
input class, identical in spirit to `MLE_INVALID_LINK_ID`: sloth does
not decode every optional Common Info subfield (EML Capabilities, MLD
Capabilities, and related fields moved between presence-bitmap bit
positions across 802.11be draft revisions — asserting a bit position
sloth cannot verify against the sender's actual draft version would
risk flagging legitimate hardware), only the two bounds any conformant
sender must satisfy regardless of draft revision.

Same T1669 mapping as the sibling rule: the access vector is an
unauthenticated, management-frame-driven exchange, not a specific
optional field.

## `ALERT_TYPE_MLE_SUBELEM_OVERRUN` (#104 slice 3)

**What the advisory actually names, stated precisely.** The eight
mitigation commits w1.fi 2026-1 lists (re-read from the advisory text on
2026-10-08, source URL above, HTTP 200) are six link-ID validation fixes
and two Common Info length fixes — the two gaps slices 1 and 2 already
cover. No listed commit is a subelement-chain bounds fix. The basis for
this third rule is the advisory's own two other statements:

- its impact class is *"process termination due to buffer read overflow
  checks and memory corruption"*, reached by *"sending invalid
  Management frames without needing authentication or user action"*; and
- *"code review of similar areas showed other potential areas that did
  not have complete validation of the received messages … more thorough
  validation has been added to minimize risk for unknown issues or
  issues enabled by future extensions of the functionality in this
  area."*

A Link Info subelement chain whose declared lengths reach past the
enclosing Multi-Link element is precisely a buffer **read** overflow in
that family, and it is the one gap in the issue's eight-rule design for
which the overrun has already *happened* in the frame rather than merely
being set up by a hostile length. That difference is why this rule is
**CRIT** where its two siblings are WARN.

**The structural rule.** `mle_len` as sloth receives it is the element's
own declared length — `src/beacon_snoop.c` hands `mle_parse()` the IE
length byte, not a slice of a larger buffer — and IEEE 802.11 subelements
are ID(1) + Length(1) + body with no padding defined between them. The
chain therefore has to tile Link Info exactly. `mle_parse()` flags two
shapes of failure to do so:

1. a subelement whose `ID + Length + body` reaches past the element end
   (the summed-lengths-exceed-container case the issue describes); and
2. a trailing fragment too short to hold a subelement header, where the
   byte that remains can only be the start of a subelement whose
   mandatory 2-byte header is already one byte past the boundary.

Both record how far the chain overshot. The walk stops at the first
finding: there is no safe offset to continue from, and whatever was
decoded before it (the MLD MAC, any affiliated link address from a
subelement that did tile) is kept as evidence rather than discarded.

## What this section does not claim

**hostapd's own loop is not this strict about shape 2.** The upstream
per-STA-profile walks stop when fewer than two bytes remain rather than
treating the tail as an error, so a 1-byte tail is tolerated there. Sloth
reports it anyway, for the same reason it reports a patched AP's
`link_id = 15`: a conformant sender cannot emit it, so it is evidence
about the sender regardless of whether any particular receiver survives
it. An operator reading this CRIT should take it as "the subelement chain
in this frame does not fit the element it arrived in," not as "a specific
named CVE was exercised."

**The evidence ring (#92) is not wired to this rule.** It is the first
natural consumer — the issue asks for the raw frame bytes to be kept —
but `src/evidence_ring.h` is a store with no alert-side recording path
yet, and building one is #92's own exporter slice.
