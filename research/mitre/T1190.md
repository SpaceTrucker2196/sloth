# T1190 — Exploit Public-Facing Application

Initial access through a service reachable from outside: a web
application, an API, an admin panel. It is consistently among the most
common initial-access vectors, because the attack surface is by
definition exposed.

## Why sloth cites this

Two HTTP alerts, both reading the request line and headers that TLS has
not yet hidden — or that were never protected.

**`ATTACK_PATH`** matches request paths that exist only in exploit
lists and scanner wordlists. Nobody navigates to
`/wp-admin/setup-config.php` on a host that runs no WordPress, or to a
vendor-specific shell path by accident. The 404 the server returns is
not the point: the *asking* is.

**`ATTACK_TOOL_UA`** matches a scanner that named itself in the
User-Agent. High confidence, trivially evaded — a fair summary of its
value is that it catches the unskilled and the unbothered, which is
still a large share of what actually knocks on an exposed service.

## What it does not say

**Neither alert observes a compromise.** A request for an exploit path
is a request. Whether the application was vulnerable, and whether it
answered usefully, is not visible in the request line — and sloth does
not reassemble response bodies to find out.

**Background scanning is the weather.** Anything reachable from the
public internet receives this traffic continuously from bots that have
never heard of the operator. Volume here is not a measure of risk; the
target is.

**A tool that changes its User-Agent produces nothing.** `ATTACK_TOOL_UA`
firing means someone did not bother. It not firing means nothing at all.

**HTTPS hides both.** These read cleartext HTTP. On a network where the
exposed service is properly TLS-terminated elsewhere, the alerts are
silent regardless of what is being attempted.
